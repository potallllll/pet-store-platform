# 03E 客户端「商品浏览 + 购买需求」模块

> 状态：已确认子模块
> 所属阶段：03 客户端微信小程序
> 版本：V1.0

## 1. 设计定位

V1.0 商品模块定位为“轻商城 / 购买需求提交”，不做完整电商。

客户端支持浏览、搜索、选择规格、加入购物车并提交购买需求，但不支持：

- 在线支付
- 快递配送
- 收货地址
- 运费
- 物流状态

正式成交仍由门店线下收款并由有权限店员确认。

## 2. 客户端入口

首页推荐商品展示当前门店 3～6 个推荐商品，并提供“查看更多”进入商品列表。

商品列表支持：

- 商品搜索
- 商户自定义分类
- 商品图片
- 商品名称
- 售价 / 参考售价
- 客户可见库存状态

客户侧库存默认只展示：

- 有货
- 库存紧张
- 暂时无货

不默认展示精确库存数量。

## 3. 商品与 SKU

V1.0 商品结构必须支持 SKU / 规格。

同一商品可存在不同口味、容量、包装等规格，每个 SKU 可拥有独立售价与库存。

若商品只有一个可售规格，客户端自动选中，减少客户操作。

## 4. 商品详情页

商品详情页至少支持：

- 商品图片
- 商品名称
- 售价
- 库存状态
- 规格选择
- 数量选择
- 商品介绍
- 加入购物车
- 直接提交购买需求

客户端按钮统一使用“提交购买需求”等准确表述，不使用会让客户误认为已经线上成交的“立即付款”。

## 5. 购物车

V1.0 保留购物车能力。

客户可将多个商品 / SKU 合并后一次提交购买需求，形成一笔商品需求单，避免多个商品产生多笔重复订单。

提交时客户只需确认商品、规格、数量和可选备注；手机号、当前商户等已有信息自动带出，不要求重复填写。

## 6. 提交购买需求

客户提交购买需求后：

- 状态进入“门店确认中”。
- 不立即确认成交。
- 不立即扣减正式库存。
- 不产生正式营业额。
- 不标记为已支付。

门店需对商品、数量和金额进行确认。

## 7. 店员一屏确认

店员端处理商品需求时，正常场景应能在列表卡片 / 单一处理页面完成：

- 查看客户
- 查看商品及数量
- 查看库存状态
- 确认
- 修改数量
- 取消

正常库存充足时应支持一键确认，不要求频繁进入多层详情页面。

## 8. 店员修改商品需求

门店可在确认收款前修改商品数量和最终应收金额。

若仅修改数量，例如客户申请 3 件但门店仅剩 2 件：

- 店员可直接改为 2 件。
- 客户端自动显示原需求与门店确认后的当前内容。
- V1.0 不要求客户额外点击“同意”；客户最终线下付款视为成交确认。

若门店需要将客户选择的商品替换为完全不同商品，V1.0 不允许静默替换。门店应取消 / 移除原商品并联系客户重新确认；V1.0 不建设复杂的线上替代商品确认链路。

## 9. 库存预占

门店确认商品需求后，系统自动进行库存预占。

规则：

- 门店确认前：不占库存。
- 门店确认后：对应 SKU 数量进入预占库存。
- 正式收款完成：预占库存转为正式出库。
- 订单取消 / 超时：释放预占库存重新成为可售库存。

库存预占由系统自动完成，不增加店员额外操作。

## 10. 待付款保留时间

V1.0 支持商户配置商品订单确认后的保留时间。

可选值至少包括：

- 2 小时
- 6 小时
- 12 小时
- 24 小时
- 48 小时
- 不自动取消

V1.0 默认值确定为 24 小时。

超过保留时间仍未确认收款：

订单自动取消
→ 释放预占库存
→ 已锁定但未核销的优惠券恢复可用

系统需记录自动取消原因和时间。

## 11. 优惠券自动匹配

门店确认商品后，系统根据已确认商品、金额和适用范围自动识别客户可使用的优惠券。

若存在多张可用券，默认推荐对客户最优惠的一张。

优惠券选择阶段仅锁定，完成收款后正式核销；订单取消或超时后恢复可用。

V1.0 每单最多使用一张优惠券。

## 12. 人工调价

确认收款前允许有权限店员进行人工调价。

系统必须分别保存：

- 商品明细原价
- 系统原始应收
- 优惠券优惠金额
- 人工调价金额
- 最终应收
- 调价原因
- 操作人
- 操作时间
- 可选备注

不得只保存最终金额。

## 13. 线下收款与正式成交

客户到店 / 线下付款后，由有权限店员选择支付方式并确认已收款。

支持：

- 会员余额
- 微信
- 支付宝
- 现金
- 其他已配置支付方式
- 组合支付

确认已收款后系统自动：

- 将预占库存转为正式出库
- 生成正式销售 / 支付记录
- 计入营业额
- 核销优惠券（如有）
- 更新客户端订单状态为已完成

## 14. 商品订单来源

客户端提交购买需求与店员线下直接商品销售，应最终进入统一的商品订单模型。

仅通过 `source_channel` 等字段区分来源，例如：

- mini_program
- wechat
- meituan
- douyin
- phone
- walk_in
- other

库存、营业额、客户消费记录和后续统计均使用同一套正式订单数据。

## 15. 商品录入的减操作原则

后续老板 / 店员端商品维护应支持最简建档：

- 商品名称
- 分类
- 图片
- 售价
- 库存

即可先完成上架。

规格、条码、成本价、品牌、推荐状态、详细介绍等作为可选扩展字段，避免小型门店录入大量商品时操作过重。

## 16. V1.0 核心流程

商品浏览 / 搜索
→ 选择 SKU 与数量
→ 加入购物车或直接提交
→ 客户提交购买需求
→ 门店一键确认 / 必要时改单
→ 系统自动预占库存
→ 自动匹配优惠券
→ 待线下付款
→ 默认 24 小时保留
→ 店员确认实际收款
→ 正式扣库存并计入营业额

整个流程遵循“前端简单、后台自动化、关键财务与库存操作可审计”的原则。

## 17. 寄养加餐 / 投喂零食

V1.0 在宠物处于有效“寄养中”状态时，支持客户从寄养详情发起一次轻量的零食购买与投喂请求。

客户端按钮文案统一为：

> 投喂零食

内部业务场景可命名为：`boarding_feed` / “寄养加餐”。

### 17.1 展示前提

仅在同时满足以下条件时展示可提交的“投喂零食”入口：

- 当前宠物存在有效寄养记录且状态为“寄养中”。
- 当前宠物寄养资料允许“寄养期间额外投喂零食”。
- 当前门店存在被标记为允许寄养投喂的可售商品 / SKU。

若宠物寄养资料明确为“不允许额外投喂零食”，客户端不得绕过该设置提交投喂请求。

### 17.2 可投喂零食列表

点击“投喂零食”后，展示当前门店可用于寄养加餐的商品。

商品 / SKU 需要支持“允许寄养投喂”业务标记，例如 `boarding_feed_enabled`；只有该标记有效的商品才进入列表。

列表继续复用普通商品库存规则：

- 有货
- 库存紧张
- 暂时无货

暂时无货不得提交；默认不因为寄养加餐场景额外暴露精确库存数量。

商品可选维护食材 / 口味 / 过敏原等结构化投喂标签。若商品标签与宠物已明确记录的过敏、禁食 / 忌口信息发生可确定冲突，应阻止提交并提示选择其他商品；如果数据不足以自动判断，则必须展示宠物饮食注意事项供客户与店员确认，不得使用 AI 猜测或伪造安全结论。

### 17.3 客户提交路径

寄养加餐不要求客户进入普通购物车，默认走低步骤路径：

寄养详情
→ 点击“投喂零食”
→ 选择可投喂零食 / SKU
→ 确认宠物、商品、数量与当前参考金额
→ 提交投喂请求
→ 客户端提示“已通知店员”

提交后形成统一商品购买需求，不建立独立“投喂订单”模型。

该购买需求至少关联：

- 当前 `merchant_id / store_id`
- 当前 `customer_id`
- 当前 `pet_id`
- 当前 `boarding_id`
- 所选商品 / SKU 与数量
- `source_channel = mini_program`
- 独立业务场景字段 `business_scenario = boarding_feed`

`source_channel` 只表示来源渠道，不用 `boarding_feed` 替代现有渠道值；寄养加餐通过独立业务场景字段区分。

### 17.4 店员处理

客户提交后，店员端必须形成明确待处理事项，例如“某宠物有新的投喂请求”，而不是只生成一条容易被忽略的普通消息。

店员处理继续复用普通商品购买需求能力，可：

- 查看宠物与当前寄养信息
- 查看商品 / SKU 与数量
- 查看宠物过敏、禁食 / 忌口和其他饮食注意事项
- 确认商品
- 必要时修改数量
- 必要时修改最终应收金额
- 取消请求
- 按统一收银规则确认实际付款
- 实际完成投喂后确认“已投喂”

不能因为这是寄养场景就绕过库存、调价、支付、审计和商品订单规则。

### 17.5 库存、付款与营业额

寄养加餐仍按普通商品购物处理：

- 客户提交时不正式扣库存。
- 店员确认后按现有商品规则预占库存。
- 实际付款确认后转正式出库。
- 付款、会员余额、优惠券、组合支付等继续遵循统一订单 / 钱包规则。
- 客户端不新增线上付款能力。
- 正式成交只计入商品销售收入，不重复计入寄养收入。

### 17.6 寄养动态联动

店员实际完成投喂并确认后，系统自动向当前 `boarding_id + pet_id` 的寄养时间轴增加一条投喂动态，例如：

> 15:32 加餐 · 鸡肉冻干 ×1 · 已完成投喂

该寄养动态与商品订单关联，但不复制生成第二笔营业额或第二套商品数据。

### 17.7 防重复误触

同一宠物已有一笔尚未处理完成的寄养加餐请求时，客户端应明显展示“投喂请求处理中”等状态，避免用户连续误触生成多笔重复请求。

客户仍可进入查看当前请求内容和处理状态；上一笔处理完成 / 取消后，再恢复正常“投喂零食”入口。

## 18. 需求变更记录

### 2026-09-01：新增寄养加餐 / 投喂零食场景

【需求变更】

- 原规则：客户端商品购买需求仅从推荐商品、商品列表、详情和购物车等普通商品路径发起；寄养详情没有直接购买零食并请求店员投喂的能力。
- 新规则：宠物处于寄养中且主人允许额外零食时，寄养详情增加“投喂零食”入口；客户选择门店允许寄养投喂且有库存的商品后提交，系统提示已通知店员，并生成统一商品购买需求，通过 `business_scenario = boarding_feed` 关联 `boarding_id / pet_id`。店员按普通商品购物、库存和收银规则处理，实际投喂完成后自动写入寄养动态。
- 财务边界：寄养加餐成交只计入商品销售，不重复计入寄养收入；不建立第二套投喂订单、库存或支付模型。
- 影响范围：客户端寄养详情、宠物寄养资料、商品 / SKU、商品购买需求、店员待办、库存、订单 / 收银、钱包、寄养时间轴、消息通知、统计、API 与数据库设计。
