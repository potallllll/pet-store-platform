## 1. 设计定位

V1.0 商品模块定位为“轻商城 / 购买需求提交”，不做完整电商。

客户端支持浏览、搜索、选择规格、加入购物车并提交购买需求，但不支持：

- 在线支付
- 快递配送
- 收货地址
- 运费
- 物流状态

正式成交由门店线下实际收款，或按03d§10.1明确确认零元免单后成立；免单不是虚假付款，仍按同一商品／SKU、库存和审计规则执行。

## 2. 客户端入口

首页推荐商品展示当前门店 3～6 个推荐商品，并提供“查看更多”进入商品列表。

商品列表支持：

- 商品搜索
- 商户自定义分类
- 商品图片
- 商品名称
- 售价 / 参考售价
- 客户可见库存状态

客户侧库存默认只展示：

- 有货
- 库存紧张
- 暂时无货

不默认展示精确库存数量。

## 3. 商品与 SKU

V1.0 商品结构必须支持 SKU / 规格。

同一商品可存在不同口味、容量、包装等规格，每个 SKU 可拥有独立售价与库存。

若商品只有一个可售规格，客户端自动选中，减少客户操作。

## 4. 商品详情页

商品详情页至少支持：

- 商品图片
- 商品名称
- 售价
- 库存状态
- 规格选择
- 数量选择
- 商品介绍
- 加入购物车
- 直接提交购买需求

客户端按钮统一使用“提交购买需求”等准确表述，不使用会让客户误认为已经线上成交的“立即付款”。

## 5. 购物车

V1.0 保留购物车能力。

客户可将多个商品 / SKU 合并后一次提交购买需求，形成一笔商品需求单，避免多个商品产生多笔重复订单。

提交时客户只需确认商品、规格、数量和可选备注；手机号、当前商户等已有信息自动带出，不要求重复填写。

## 6. 提交购买需求

客户提交购买需求后：

- 状态进入“门店确认中”。
- 不立即确认成交。
- 不立即扣减正式库存。
- 不产生正式营业额。
- 不标记为已支付。

门店需对商品、数量和金额进行确认。

## 7. 店员一屏确认

店员端处理商品需求时，正常场景应能在列表卡片 / 单一处理页面完成：

- 查看客户
- 查看商品及数量
- 查看库存状态
- 确认
- 修改数量
- 取消

正常库存充足时应支持一键确认，不要求频繁进入多层详情页面。

## 8. 店员修改商品需求

门店可在结算完成（实际收款或明确确认免单）前修改商品数量和最终应收金额，结算后不能直接改写。

若仅修改数量，例如客户申请 3 件但门店仅剩 2 件：

- 店员可直接改为 2 件。
- 客户端自动显示原需求与门店确认后的当前内容。
- V1.0 不要求客户额外点击“同意”；正金额以客户线下付款及门店确认实收成交，零元按第13节明确确认免单成交。

若门店需要将客户选择的商品替换为完全不同商品，V1.0 不允许静默替换。门店应取消 / 移除原商品并联系客户重新确认；V1.0 不建设复杂的线上替代商品确认链路。

## 9. 库存预占

门店确认商品需求后，系统自动进行库存预占。

规则：

- 门店确认前：不占库存。
- 门店确认后：对应 SKU 数量进入预占库存。
- 正式结算完成（实际收款或明确确认免单）：预占库存转为正式出库，免单金额／收入为0但不能省略出库。
- 尚未结算的订单取消／超时：释放预占库存重新成为可售库存；已结算不能由未付款超时任务返库。

库存预占由系统自动完成，不增加店员额外操作。

## 10. 待付款保留时间

V1.0 支持商户配置商品订单确认后的保留时间。

可选值至少包括：

- 2 小时
- 6 小时
- 12 小时
- 24 小时
- 48 小时
- 不自动取消

V1.0 默认值确定为 24 小时。

超过保留时间仍未完成结算（含输入0但尚未确认免单）：

订单自动取消
→ 释放预占库存
→ 已锁定但未核销的优惠券解除锁定；锁定时有效的券按03c§11补回实际锁定时长后恢复可用

系统需记录自动取消原因和时间。

## 11. 优惠券自动匹配

门店确认商品后，系统根据已确认商品、金额和适用范围自动识别客户可使用的优惠券。

若存在多张可用券，默认推荐对客户最优惠的一张。

优惠券选择阶段仅锁定，实际收款或明确免单完成消费结算后按03c§11正式核销一次；订单取消或超时后解除锁定。锁定开始时有效的券在锁定期间暂停有效期倒计时，释放时继续原剩余有效时长；锁定前已过期的券不得复活。免单成功不能再按未付款超时解锁已核销券或返还已出库库存。

V1.0 每单最多使用一张优惠券。

## 12. 人工调价

结算前本店老板及有效员工可整单输入最终应收总额调价，不设业务金额／比例上限，不需老板逐单审批；负数／非法金额不允许，调前／调后确认及原因必填，快捷原因和“其他”补充文字按03d§10.1执行。参考价、SKU售价及原始明细不被覆盖，不新增逐项分摊算法。

系统必须分别保存：

- 商品明细原价
- 系统原始应收
- 优惠券优惠金额
- 人工调价金额
- 最终应收
- 调价原因
- 操作人
- 操作时间
- 可选备注

不得只保存最终金额。

## 13. 线下收款与正式成交

有正金额时，客户线下付款后由本店有效老板／员工选择真实支付方式并确认已收款；最终应收为0则必须另行明确“确认免单”，无真实支付记录、不扣余额，规则以03d§10.1为准。

支持：

- 会员余额
- 微信
- 支付宝
- 现金
- 其他已配置支付方式
- 组合支付

按03d§1.1／11～12、04§4.4，全部消费同次最多两种支付方式（余额本金／赠送算一种）、合计等于应收。财务是线下交易记账，不接外部收银／支付接口；确认记账仍自动联动销售、流水、余额、库存和券。允许晚录入不取消本模块预占／未结算超时，也不能让未记账商品提前展示成交或跳过加餐结算前提。

商品退款本店老板／有效员工均可登记，无需老板审批；按原付款渠道／原账户退款，不改原实付。退款本身不回库，实际收回且可再销售才按原SKU登记退货并自动一次入库，不需老板逐单审批；只退钱／不退货／不可再销售不恢复库存，不混积分奖励库存。优惠券按03c§11，不新增另一套退款政策；部分退款分配等未决规则不据此放行。

实际收款或明确确认免单结算成功后，系统幂等执行：

- 将预占库存转为正式出库
- 生成正式销售记录；有实际收款才生成支付／组合支付记录，免单保留waived结算及审计，不虚构付款
- 按真实金额计入营业额，免单收入为0
- 核销优惠券（如有）
- 普通商品订单更新客户端状态为已完成；寄养加餐仅更新付款结果，仍需按第 17 节完成实际投喂，不得将已收款等同于已投喂

仅输入0元不触发上述成交动作；免单确认与取消／超时／收款并发须校验同一金额版本及状态，不重复出库或核销，成功后金额锁定。商品缺货、SKU不可售或越店对象不能因免单放行。

## 14. 商品订单来源

客户端提交购买需求与店员线下直接商品销售，应最终进入统一的商品订单模型。

仅通过 `source_channel` 等字段区分来源，例如：

- mini_program
- wechat
- meituan
- douyin
- phone
- walk_in
- other

库存、营业额、客户消费记录和后续统计均使用同一套正式订单数据。

## 15. 商品录入的减操作原则

04§3.0.8“服务项目管理”的商品大类只选择／关联本店已有商品／SKU，不在该入口创建商品或复制为服务项目。商品主资料、SKU售价、介绍及库存以本模块为唯一来源；原商品字段和维护边界不被三类服务表单的30字／300字等规则覆盖。

后续老板 / 店员端商品维护应支持最简建档：

- 商品名称
- 分类
- 图片
- 售价
- 库存

即可先完成上架。

规格、条码、成本价、品牌、推荐状态、详细介绍等作为可选扩展字段，避免小型门店录入大量商品时操作过重。

## 16. V1.0 核心流程

以下是正金额实际收款路径；最终应收为0时改走第13节“明确确认免单”，同样一次正式出库、收入为0，不创建实际支付，也不因流程图省略而取消免单能力。

商品浏览 / 搜索
→ 选择 SKU 与数量
→ 加入购物车或直接提交
→ 客户提交购买需求
→ 门店一键确认 / 必要时改单
→ 系统自动预占库存
→ 自动匹配优惠券
→ 待线下付款
→ 默认 24 小时保留
→ 店员确认实际收款
→ 正式扣库存并计入营业额

整个流程遵循“前端简单、后台自动化、关键财务与库存操作可审计”的原则。

## 17. 寄养加餐 / 投喂零食

V1.0 在宠物处于有效“寄养中”状态时，支持客户从寄养详情发起一次轻量的零食购买与投喂请求。

客户端按钮文案统一为：

> 投喂零食

内部业务场景可命名为：`boarding_feed` / “寄养加餐”。

### 17.1 展示前提

仅在同时满足以下条件时展示可提交的“投喂零食”入口：

- 当前宠物存在有效寄养记录且状态为“寄养中”。
- 当前宠物寄养资料允许“寄养期间额外投喂零食”。
- 许可取当前boarding_id的本次有效资料及最新必要限制；本次授权待核实、拒绝或资料矛盾时，不以长期档案旧允许值放行，先核实，不用AI猜测。临时修改只影响本次的规则见03b§4.3／04§5.1。
- 当前门店存在被标记为允许寄养投喂的可售商品 / SKU。

若宠物寄养资料明确为“不允许额外投喂零食”，客户端不得绕过该设置提交投喂请求。

### 17.2 可投喂零食列表

点击“投喂零食”后，展示当前门店可用于寄养加餐的商品。

商品 / SKU 需要支持“允许寄养投喂”业务标记，例如 `boarding_feed_enabled`；只有该标记有效的商品才进入列表。

列表继续复用普通商品库存规则：

- 有货
- 库存紧张
- 暂时无货

暂时无货不得提交；默认不因为寄养加餐场景额外暴露精确库存数量。

商品可选维护食材 / 口味 / 过敏原等结构化投喂标签。若商品标签与宠物已明确记录的过敏、禁食 / 忌口信息发生可确定冲突，应阻止提交并提示选择其他商品；如果数据不足以自动判断，则必须展示宠物饮食注意事项供客户与店员确认，不得使用 AI 猜测或伪造安全结论。

### 17.3 客户提交路径

寄养加餐不要求客户进入普通购物车，默认走低步骤路径：

寄养详情
→ 点击“投喂零食”
→ 选择可投喂零食 / SKU
→ 确认宠物、商品、数量与当前参考金额
→ 提交投喂请求
→ 客户端提示“已通知店员”

提交后形成统一商品购买需求，不建立独立“投喂订单”模型。

该购买需求至少关联：

- 当前 `merchant_id / store_id`
- 当前 `customer_id`
- 当前 `pet_id`
- 当前 `boarding_id`
- 所选商品 / SKU 与数量
- `source_channel = mini_program`
- 独立业务场景字段 `business_scenario = boarding_feed`

`source_channel` 只表示来源渠道，不用 `boarding_feed` 替代现有渠道值；寄养加餐通过独立业务场景字段区分。

### 17.4 店员处理

客户提交后，店员端必须形成明确待处理事项，例如“某宠物有新的投喂请求”，而不是只生成一条容易被忽略的普通消息。

店员处理继续复用普通商品购买需求能力，可：

- 查看宠物与当前寄养信息
- 查看商品 / SKU 与数量
- 查看宠物过敏、禁食 / 忌口和其他饮食注意事项
- 确认商品
- 必要时修改数量
- 必要时修改最终应收金额
- 取消请求
- 按统一收银规则确认实际付款，或最终应收0时明确确认免单
- 实际完成投喂后确认“已投喂”

不能因为这是寄养场景就绕过库存、调价、支付、审计和商品订单规则。

收款确认和实际投喂确认是两个独立动作。执行投喂前，门店应重新确认宠物仍在本次有效寄养中、主人仍允许额外投喂，以及最新过敏 / 禁食 / 忌口信息；条件失效时停止执行并按第 17.8 节处理。收款成功不得自动关闭投喂待办。

04§5.1统一照护表单的普通“喂食”只记录真实日常照护，不替代本商品单的实际投喂确认、不扣库存／余额、不产生销售或重复动态。同一次商品加餐从原单确认并生成唯一关联事件，不能再从普通喂食入口重复登记；日常照护选择时间／选填照片也不能用来绕过当前寄养授权、原单结算或执行校验。

### 17.4.1 同一订单上的付款与执行状态

寄养加餐不建立第二套订单。统一商品订单分别保留付款结果与投喂执行状态，客户端聚合展示按 `03d-customer-orders.md` 第 4.3 节执行。

| 执行状态 | 进入条件 | 可继续的动作 |
|---|---|---|
| 待处理 | 客户购买需求已提交 | 门店确认商品 / 数量 / 金额，或取消 |
| 待投喂 | 门店已确认购买需求 | 按统一规则实际收款或确认免单完成结算；符合全部执行条件后才实际投喂并确认 |
| 已投喂 | 实际投喂已完成且确认成功 | 查看投喂与交易记录；错误记录按审计规则纠正 |
| 异常待处理 | 提前离店、授权撤回或其他原因导致无法继续，处理尚未结束 | 门店处理取消及必要财务事项，记录结果 |
| 已取消 | 已停止执行，且取消及必要后续事项已处理完毕 | 查看取消原因与交易记录 |

- “待投喂”结合结算信息展示：未结算且正金额显示“待线下付款”，未结算零元显示“待门店确认免单”；实际收款或免单成功后显示“投喂请求处理中 · 待投喂”，免单另标“已免单，实付0元”。
- 已收款但尚未实际投喂，不得显示已投喂 / 整体已完成，也不得重新开放同宠物的投喂提交入口。
- 已免单同样不代表已投喂，不自动完成动态、服务或重新开放提交；不能把无实际付款的免单标成现金／微信已收款。
- 确认已投喂时必须保存实际投喂时间、执行人员和本次订单关联；不能通过只修改客户端状态完成投喂。
- 付款、退款与投喂执行各自保留真实记录，任何一项变化不得无痕覆盖另一项。

### 17.5 库存、付款与营业额

寄养加餐仍按普通商品购物处理：

- 客户提交时不正式扣库存。
- 店员确认后按现有商品规则预占库存。
- 实际付款或明确确认免单完成结算后转正式出库；免单收入为0，不跳过SKU和库存约束。
- 付款、会员余额、优惠券、组合支付等继续遵循统一订单 / 钱包规则。
- 客户端不新增线上付款能力。
- 正式成交只计入商品销售收入，不重复计入寄养收入。

实际投喂只推进执行状态和寄养动态，不重复扣库存、核销优惠券、扣余额或确认第二次收入。已收款后仍待投喂的请求，不适用“未收款超时自动取消”；执行异常按第 17.8 节处理。

已免单仍待投喂的请求同样不适用未结算超时取消；免单不扣会员余额，出库／核销仍只发生一次，不因后续投喂重试补扣库存或收入。

### 17.6 寄养动态联动

店员实际完成投喂并确认成功后，系统自动向该订单绑定的 `boarding_id + pet_id` 的寄养时间轴增加一条投喂动态，例如：

> 15:32 加餐 · 鸡肉冻干 ×1 · 已完成投喂

该寄养动态与商品订单及同一次投喂确认稳定关联，以实际投喂时间进入时间轴，不以付款时间或重试时间冒充实际发生时间。同一次投喂确认只产生一条动态；重复点击、重试和消息补偿均不得重复写入。执行状态和时间轴写入需可恢复：写入失败时继续补偿同一事件，不得再次投喂来修复系统记录。

已收款、预占库存、取消请求或退款本身都不得生成“已完成投喂”动态，也不得复制生成第二笔营业额或第二套商品数据。

### 17.7 防重复误触

同一商户下同一宠物已有一笔待处理、待投喂或异常待处理的寄养加餐请求时，客户端应明显展示“投喂请求处理中”或“投喂异常待处理”，并可进入该请求；服务端必须校验只存在一笔有效未处理完毕请求，不能仅依赖按钮置灰。

客户可查看当前商品、付款和投喂状态。只有上一笔实际投喂确认成功，或取消及必要后续处理完成进入“已取消”后，才解除这笔请求的提交限制；恢复“投喂零食”入口时还须重新满足第 17.1 节的有效寄养、主人允许和可售商品条件。单纯收款成功、刷新页面、切换门店或重复提交都不得解除限制。

### 17.8 取消、提前离店与无法投喂

寄养是否在住按04§5.2已确认的实际离店事实判定，不按是否收款／挂单判断。结算流程确认本批应收后，该批已离店，未付款也不得继续新建／执行加餐；原未投喂商品按本节停止并处理，不能因寄养欠款保留投喂入口或自动标已喂，不能自动退款／回库。后续补收寄养费不恢复原寄养或加餐资格。

- 尚未结算且未实际投喂（含未确认免单的零元单）：按统一规则取消、释放预占库存和未核销券，记录原因；不写虚假投喂动态。
- 已收款或已免单但未实际投喂：因提前离店、主人授权变化等无法继续时停止投喂并保留异常待处理，不直接抹去交易、改成未付款或自动退款。免单无实际收款，不生成可退现金／余额；后续取消、撤销及库存／券处理继续按相应规则审计。
- 门店需记录取消原因和后续处理结果；消费退款／真实退货由本店老板或有效员工按03d§12办理，无需老板审批；钱包／券按03c，其他撤销／冲正规则不由本模块自行补齐。金额、方式和库存结果保留真实记录，不另定一套退款政策。
- 必要后续事项处理完成后才将执行状态收口为“已取消”，保留原收款、退款及取消记录；寄养已结束或主人不允许时，不恢复投喂入口。
- 已经实际投喂的请求不能通过取消或退款改为“未投喂”。退款只记录财务变化；投喂记录发生错误时按审计规则留痕纠正，不删除或伪造真实发生的事件。

### 17.9 必须覆盖的验收情形

- 收款成功但未投喂：订单与寄养详情仍显示处理中，投喂待办保留，不能提交第二笔。
- 免单成功但未投喂：显示已免单／实付0元及待投喂，不生成虚假支付或动态；一次出库，免单重试、投喂重试不二次扣库存，已免单不能被未付款超时取消。
- 实际投喂确认成功：对应时间轴仅出现一条动态，财务与库存不二次记账；满足入口条件时才可继续提交。
- 确认成功响应丢失后重试 / 重复点击：读取同一执行结果，只保留一条动态。
- 付款后提前离店、撤回允许或无法投喂：停止执行并进入异常处理，保留真实付款；不自动无条件退款，不产生已投喂动态。
- 取消及后续处理完毕：保留原因与财务结果；已结束寄养不重新显示可提交入口。
