# 03E 客户端「商品浏览 + 购买需求」模块

> 状态：已确认子模块；部分替换及结算细节待确认
> 所属阶段：03 客户端微信小程序
> 版本：V1.0

## 1. 设计定位

V1.0 商品模块定位为“轻商城 / 购买需求提交”，不做完整电商。客户端支持浏览、搜索、选择规格、加入购物车并提交购买需求，但不支持在线支付、快递配送、收货地址、运费和物流状态。正式成交仍由门店线下收款并由有权限店员确认。

## 2. 客户端入口

首页推荐商品展示当前门店3～6个推荐商品，并提供“查看更多”进入商品列表。商品列表支持搜索、商户自定义分类、图片、名称、售价/参考售价及客户可见库存状态。库存默认只显示“有货 / 库存紧张 / 暂时无货”，不默认展示精确数量。

## 3. 商品与 SKU

V1.0必须支持SKU/规格。同一商品可有不同口味、容量、包装，每个SKU独立售价与库存。只有一个可售规格时自动选中。

## 4. 商品详情页

至少支持商品图片、名称、售价、库存状态、规格、数量、介绍、加入购物车及直接提交购买需求。按钮不使用误导线上成交的“立即付款”。

## 5. 购物车

多个商品/SKU可合并为一笔购买需求。提交时确认商品、规格、数量及可选备注；手机号、当前商户等已有信息自动带出，不重复填写。

## 6. 提交购买需求

提交后进入“门店确认中”，不立即成交、不扣正式库存、不产生营业额、不标记已支付。门店需确认商品、数量和金额。提交及响应丢失恢复遵循03i§13.1，不能因重试重复创建需求。

## 7. 店员一屏确认

正常场景应在列表卡片/单一处理页查看客户、商品数量、库存状态，并完成确认、修改数量、取消。库存充足时一键确认，避免多层跳转。

## 8. 店员修改商品需求

门店可在确认收款前修改商品数量和最终应收金额。仅修改数量时，例如申请3件但仅剩2件，店员可改为2件，客户端展示原需求与确认后的内容；V1不要求客户额外线上点击同意，最终线下付款作为成交确认。

**不同商品不得静默替换。** 门店应取消/移除原商品并联系客户重新确认，不建设复杂线上替代商品确认链路。不同SKU、规格、口味的替换及线下确认记录边界由`DEC-PRODUCT-01`收口；未确认前不得自行扩大免确认范围。已付款后的变更不得无痕覆盖原交易。

系统保留原始需求、正式明细、修改前后数量与金额、操作人、时间及必要原因。涉及明细变化时，服务端须按当前有效库存和优惠券资格重新校验；已预占库存的调整必须保持占用与正式明细一致。唯一计算次序、重算、退款分摊由`DEC-SETTLE-01`在阶段06收口，不在此另定算法。

## 9. 库存预占

门店确认前不占库存；确认后对应SKU数量进入预占；正式收款确认后预占转正式出库；订单取消/超时释放预占。库存预占自动执行，不增加店员步骤。

确认及调整必须由服务端校验实际可售量，不得超卖；同一业务确认和重试不得重复预占、释放或出库。具体跨模块事务/补偿边界在阶段06及11唯一结算契约中确定，不能因库存服务失败仍宣称收银全部成功。

## 10. 待付款保留时间

商户可配置商品订单确认后的保留时间：2、6、12、24、48小时或不自动取消。默认24小时。

超过保留时间仍未确认收款时，服务端确认符合超时关闭条件后自动取消，释放预占库存，并按03c§11释放未核销的优惠券；释放后仍需重新校验券资格，不能无条件变回可用。记录自动取消原因和时间。已确认收款、支付结果不确定或正在处理的交易不得仅凭前端定时器直接释放资产；其一致性与恢复按阶段06处理。

## 11. 优惠券自动匹配

门店确认商品后，系统根据已确认商品、金额和适用范围自动识别可用券，默认推荐对客户最优惠的一张，店员可更换。每单最多一张。

选择阶段仅锁定，普通待付款期间保持锁定，确认收款后正式核销。只有订单取消、超时关闭或明确解除占用等正式事件才按03c§11释放，不能因“尚未付款”就恢复可用。释放后的有效期与使用条件重新校验；锁定中显示“使用中”，不计入立即可用数量。券占用、核销、恢复的权威规则只由03c负责，剩余边界见`DEC-COUPON-01`。

## 12. 人工调价

确认收款前允许有权限店员人工调价。系统分别保存商品明细原价、系统原始应收、自动优惠、优惠券优惠、人工调价、最终应收、调价原因、操作人、操作时间及可选备注，不能只保存最终金额。

允许店员调整最终总价的既有业务要求不变。券门槛、自动优惠、人工调价的计算顺序和明细变化后的重算以`DEC-SETTLE-01`为待决；不能把本文件的展示顺序当作已确认财务算法。

## 13. 线下收款与正式成交

客户线下付款后，由有权限店员选择实际支付方式并确认已收款。支持会员余额、微信、支付宝、现金、其他已配置方式及组合支付。

确认收款后系统自动将预占库存转正式出库、生成正式销售/支付记录、计入营业额、核销优惠券（如有）。普通商品订单完成；寄养加餐只更新付款结果，仍须按第17节实际投喂。

一次确认不得重复扣余额、核销券、出库或计入收入。跨订单、钱包、券和库存的事务一致性、未知结果恢复及冲正按阶段06统一结算契约执行；辅助通知、广告、AI或统计失败不得造成核心交易重复或错误成功。

## 14. 商品订单来源

客户端购买需求与店员线下销售进入统一商品订单模型。`source_channel`至少支持mini_program、wechat、meituan、douyin、phone、walk_in、other。库存、营业额、消费记录和统计使用同一正式订单数据。

## 15. 商品录入的减操作原则

老板/店员可只输入名称、分类、图片、售价、库存完成最简建档。规格、条码、成本价、品牌、推荐状态、详细介绍为可选扩展，避免小店重复录入。

## 16. V1.0 核心流程

浏览/搜索 → 选择SKU及数量 → 购物车或直接提交 → 门店一键确认/必要时改单 → 自动预占库存 → 匹配优惠券 → 待线下付款（默认24小时保留） → 店员确认实际收款 → 正式出库并计入收入。

前端简单，后台自动化，关键财务与库存动作可审计。未确认的金额算法不得由实现者自行选择。

## 17. 寄养加餐 / 投喂零食

V1.0在宠物有效寄养中支持轻量零食购买与投喂请求。客户端按钮为“投喂零食”，内部业务场景为`boarding_feed`/寄养加餐。

### 17.1 展示前提

同时满足有效寄养中、主人允许额外零食、当前门店存在允许寄养投喂的可售SKU。明确不允许时不得绕过设置提交。

### 17.2 可投喂零食列表

只展示`boarding_feed_enabled`有效的SKU，库存状态复用普通商品；无货不可提交，不默认暴露精确数量。可维护食材/口味/过敏原结构化标签。与宠物明确过敏、禁食或忌口冲突时阻止提交；信息不足时展示饮食注意事项供客户与店员确认，不用AI猜测安全结论。

### 17.3 客户提交路径

寄养详情 → 投喂零食 → 选择SKU → 确认宠物、商品、数量与参考金额 → 提交 → 已通知店员。不要求进入普通购物车。

复用统一商品购买需求，不建第二套投喂订单。至少关联merchant_id/store_id、customer_id、pet_id、boarding_id、商品/SKU/数量、`source_channel=mini_program`、`business_scenario=boarding_feed`。渠道和业务场景是独立字段。

### 17.4 店员处理

生成明确待办。店员可查看宠物/寄养、商品、饮食注意事项，确认、修改数量/金额、取消、按统一收银确认付款，实际执行后确认已投喂。不得绕过库存、调价、支付及审计。

收款与实际投喂是独立动作。投喂前重新校验有效寄养、主人当前允许及最新饮食禁忌；失效时停止执行，按17.8处理。收款成功不能自动关闭投喂待办。

### 17.4.1 同一订单上的付款与执行状态

统一商品订单分别保留付款结果和投喂执行状态；客户端聚合按03d§4.3。

| 执行状态 | 进入条件 | 可继续动作 |
|---|---|---|
| 待处理 | 请求已提交 | 门店确认明细或取消 |
| 待投喂 | 门店已确认 | 统一收银；已收款且符合条件后实际投喂并确认 |
| 已投喂 | 实际执行完成且确认成功 | 查看执行和交易记录，错误按审计纠正 |
| 异常待处理 | 提前离店、授权撤回或其他无法执行，处理未完 | 处理取消及必要财务事项 |
| 已取消 | 停止执行且必要后续处理完成 | 查看取消原因与交易记录 |

待投喂须结合付款显示：未收款为“投喂请求处理中 · 待线下付款”，已收款为“投喂请求处理中 · 待投喂”。已收款未投喂不得显示整体完成、不得开放第二笔。确认执行须保存实际投喂时间、执行人员及订单关联；付款、退款和执行各自保留真实记录。

### 17.5 库存、付款与营业额

提交不扣正式库存，确认后预占，收款后正式出库；钱包、券、组合支付沿用统一规则。正式成交只计商品收入，不重复计寄养。实际投喂只推进执行及时间轴，不再次出库、核销、扣余额或确认收入。已收款未投喂不适用未付款超时自动取消，异常按17.8。

### 17.6 寄养动态联动

实际投喂确认后，向绑定的boarding_id+pet_id时间轴写一条关联同一订单和执行确认的动态，例如“15:32 加餐 · 鸡肉冻干 ×1 · 已完成投喂”。按实际投喂时间排序，不以付款/重试时间冒充。重复点击、重试、消息补偿只对应一条动态；写入失败时补偿同一事件，不得再次投喂来修复记录。收款、预占、取消或退款本身不生成“已投喂”动态，也不重复收入。

### 17.7 防重复误触

同商户同宠物已有待处理、待投喂或异常待处理的有效请求时显示处理中/异常并可进入该请求；服务端保证同一时刻只有一笔有效未处理完毕请求。实际投喂确认成功，或取消及必要后续处理完成后才解除限制；解除后仍重新校验17.1。收款成功、刷新、切店或重复提交不得解除限制。

### 17.8 取消、提前离店与无法投喂

- 未收款未投喂：有权限店员取消，按统一商品规则释放预占与未核销券，保留原因，不写已投喂动态。
- 已收款未投喂：提前离店、主人撤回允许或其他无法执行时停止投喂并保留异常待办，不抹去交易、不改未付款、不自动退余额或无条件退款。
- 门店按权限、审批及统一退款/撤销/冲正规则处理财务，记录原因与结果。具体金额/退回方式由阶段06决定，不另定退款政策。
- 必要后续处理完成后收口已取消，保留收款、退款及取消记录。寄养已结束或主人不允许时不恢复入口。
- 已实际投喂不得通过取消/退款改为未投喂；错误记录留痕纠正，不伪造发生事实。

### 17.9 必须覆盖的验收情形

- 已收款未投喂仍处理中、有待办、不能提交第二笔。
- 实际执行成功只写一次动态，不二次记账；符合条件才恢复入口。
- 执行确认响应丢失重试返回同一结果。
- 付款后提前离店、撤回允许或无法投喂时进入异常，不自动无条件退款，不生成执行完成动态。
- 取消及后续处理完成保留原因和财务结果，已结束寄养不恢复入口。

验收编号统一引用03i§14.1，不在本文件另建独立编号语义。

## 18. 需求变更记录

本节为历史追溯，已被替代的内容不作为当前实施依据。

### 2026-09-01：新增寄养加餐

原规则：商品仅从普通商品路径发起。新规则：有效寄养且主人允许时，寄养详情可发起统一商品购买需求，关联boarding_id/pet_id，店员按统一库存/收银处理，实际投喂回写时间轴。财务只计商品一次，不建第二套订单。影响客户端、寄养、商品、店员、库存、订单、钱包、消息、统计、API与数据库。

### 2026-09-08：收款与执行状态收口

原规则：收款即完成与实际投喂之间缺少明确映射。新规则：同一订单分别记录付款和执行，已收款未投喂保留处理中，实际执行只写一次动态，异常及取消保留财务与执行事实。影响订单、收银、寄养、库存、API和验收。

### 2026-09-08：商品变更、券占用与结算口径澄清

原规则：商品改单范围及待付款券释放存在跨文档歧义。新规则：数量/金额调整与不同商品替换分开；不同商品不得静默替换，细节待DEC-PRODUCT-01；普通待付款保持券锁定，释放与核销归03c；金额计算、重算及退款分摊由DEC-SETTLE-01待确认。影响商品、钱包、库存、收银、审计、API和阶段06，不擅自确认新算法。
