# 需求—实现—测试追踪记录

> 状态：交付治理模板；不新增业务规则，不代表任何测试已通过。

## 使用范围

客户端验收ID唯一语义由03i§14.1维护。业务验收条件仍由对应模块负责。本文件仅规定每次交付如何记录实现与证据；正式阶段12可在此基础上扩展其他端的追踪矩阵，不新增第二套客户端验收定义。

每次PR或独立交付建立一份实际执行记录，不能将模板默认值视为测试结果。可使用CI输出、测试报告、截图、日志或经过授权的演示记录作为证据；敏感信息必须脱敏。未执行和被待决政策阻塞的测试不得标记通过。

## 记录字段

| 字段 | 填写要求 |
|---|---|
| Requirement ID | 03i或对应端唯一验收ID；组合场景拆出具体子项 |
| Authority | 权威业务章节和适用UI章节 |
| Decision dependencies | DEC ID、状态及是否已落实 |
| Delivery scope | 原型 / 服务端 / 端到端 / 第三方真实接入 |
| Implementation | 页面、API、业务模块、提交或PR |
| Test case | 测试ID、输入、前置条件、预期结果 |
| Execution | 环境、实际执行命令/步骤、时间、执行人或工具 |
| Actual result | 真实观察结果及必要的业务记录核对 |
| Evidence | 可复现的日志、测试报告、截图或CI链接 |
| Status | 未执行 / 阻塞 / 通过 / 失败 / 不适用 |
| Follow-up | 缺陷、阻塞决策、修复提交及复验结果 |

## 交付门槛

原型演示只能证明标注范围内的UI交互；模拟广告完成、AI结果、付款、库存或积分不等于真实后端验收。正式业务至少验证适用的成功、失败、重复提交、并发、未知结果恢复、权限及租户隔离。财务与库存不得仅检查页面显示，应核对服务端实际记录、唯一业务键、资产变化和重复事件处理。

组合场景不能只记录“总通过”，需将每个子项和结果单独关联。对尚待产品确认的算法、期限、权限或第三方能力，以阻塞状态记录并指向DEC，不自行填写默认值。最终验收结果须由实际执行证据支持。
