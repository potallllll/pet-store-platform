## 1. 设计原则

- 第一次建档尽量少填，降低客户录入门槛。
- 后续预约、洗护、美容、寄养尽量自动带出宠物资料，减少重复输入。
- 客户和店员均可在权限范围内维护宠物基础资料。
- 客户可见资料与门店内部备注必须分离。
- 历史体重、服务记录、服务照片等数据自动沉淀，不要求额外重复录入。

## 2. 宠物列表

入口：我的 → 我的宠物。

列表展示包含：宠物头像、名称、类型 / 品种、性别、年龄、当前体重，并提供“查看档案”和“添加宠物”。

## 3. 首次添加宠物

首次添加仅要求最少必要信息：

- 宠物名称：必填
- 宠物类型（猫 / 狗 / 其他）：必填
- 宠物头像：选填
- 品种：选填
- 性别：选填
- 出生日期：选填
- 当前体重：选填

其他信息进入“完善宠物档案”，不得强迫客户一次填写大量资料。

## 4. 宠物档案结构

宠物档案分为：

1. 基本资料
2. 护理档案
3. 寄养资料
4. 服务记录
5. 服务相册
6. 宠物行为与服务安全档案

### 4.1 基本资料

包含：头像、名称、类型、品种、性别、出生日期、系统自动计算年龄、当前体重、是否绝育等。

年龄应根据出生日期自动计算，不要求用户每年更新。

### 4.2 护理档案

用于洗护 / 美容过程中自动提示，包含可选标签和备注，例如：

- 性格：温顺、胆小、活泼、敏感、其他
- 怕水
- 怕吹风
- 怕剪指甲
- 容易应激
- 不喜欢陌生人
- 其他护理注意事项

店员创建或开始洗护 / 美容服务时，应自动展示相关注意事项，避免重复询问或录入。

### 4.3 寄养资料

用于寄养预约和入住时自动带出，包括：

- 喂食习惯
- 每日餐数
- 自带粮 / 门店粮
- 遛狗习惯
- 性格
- 过敏情况
- 禁食 / 忌口信息
- 长期用药
- 特殊照护
- 寄养期间是否允许额外投喂零食
- 其他寄养备注

后续寄养预约时默认展示已有资料，让客户选择“信息无误”或“本次修改”，不要求每次重新填写。

“寄养期间是否允许额外投喂零食”用于控制客户端寄养中的“投喂零食 / 寄养加餐”能力：

- 允许：宠物处于有效寄养中时，可在寄养详情进入门店可投喂零食列表。
- 不允许：客户端不得提供可提交的投喂入口，避免绕过主人寄养偏好。
- 过敏、禁食 / 忌口和其他饮食注意事项必须在投喂确认与店员处理场景中可见，不得仅保存在宠物档案而不向实际处理人员提示。
- 自动饮食风险判断只能基于已明确记录的宠物资料与商品结构化标签，不使用 AI 猜测宠物是否适合某种零食。
- 商品缺少足够结构化标签、无法安全自动匹配时，应优先展示宠物饮食注意事项供客户和店员确认，不得伪造“已安全校验”。

具体投喂商品、购买需求、库存和收银规则见 `03e-customer-products.md`。

### 4.4 宠物行为与服务安全档案

原“宠物交友设置”已移除。

每只宠物可维护与实际服务有关的行为 / 安全信息。跨店共享方向不使用“凶、难搞、性格差”等主观定性，而优先使用可操作的标准化标签，例如：

- 怕生 / 对陌生人紧张；
- 抗拒吹风；
- 抗拒剪指甲；
- 护食；
- 对犬 / 猫敏感；
- 有挣脱倾向；
- 曾发生咬人 / 抓伤；
- 需要双人操作；
- 喜欢的安抚方式；
- 禁忌操作 / 触碰区域。

信息来源需要区分主人自报、店员观察、真实服务事件和多次服务重复观察，并保留最近更新时间。

本店自由文本备注仍然只属于当前 Merchant。只有经过平台审核、结构化且确有服务安全必要的信息，才可以进入未来跨门店安全档案候选。

具体哪些门店可查看、主人如何授权 / 关闭、严重安全事件保留多久与何时重新评估，仍受 `DEC-PETSAFETY-01` 阻塞，详细见 `03h-customer-risk-feedback.md`。 

## 5. 客户与店员共同维护

已确认：客户和店员都可以维护宠物基础资料。

但系统必须区分：

### 客户可见 / 可维护资料

如名称、出生日期、性别、是否绝育、喂食习惯、客户填写的护理注意事项等。

### 门店内部备注

必须支持门店内部备注，默认客户不可见，例如：

- 洗澡时挣扎明显
- 剪指甲需两人配合
- 有咬人历史
- 某类操作需特别注意

门店内部备注必须归属于当前商户，不得跨商户共享。

### 跨店行为安全共享边界

“客户和店员共同维护基础资料”不等于某一家门店可以把自由文本评价直接传播给其他门店。

门店内部备注继续按 Merchant 隔离。进入跨店共享候选的宠物行为信息必须使用结构化服务安全语义，并经过平台审核；跨店可见范围和主人授权仍按 `03h-customer-risk-feedback.md` 的待决规则执行。

## 6. 体重历史

已确认保存体重历史，而不是只覆盖一个当前体重值。

每次新增体重记录至少保存：

- 宠物 ID
- 体重
- 测量 / 记录时间
- 数据来源（客户、店员、服务记录等）
- 记录人（如适用）

客户端宠物主页只展示当前最新体重；历史体重可在二级页面查看，并为未来体重趋势分析预留能力。

## 7. 服务记录

宠物档案下应按宠物维度展示历史洗护、美容、寄养等服务记录。

“我的订单”和“宠物服务记录”属于同一底层业务数据的不同查询入口：

- 我的订单：按订单维度查看
- 宠物档案：按宠物维度查看

不得复制生成两套互相独立的数据。

## 8. 服务相册

已确认自动生成宠物服务相册。

店员在洗护 / 美容服务报告中上传的前后照片，应自动归档到对应宠物服务相册，不增加店员额外上传步骤。

同一次服务支持 N 组“服务前 + 服务后”对比照片。服务相册应保留照片与所属服务、所属对比组、前 / 后类型和排序关系，不能只把所有照片作为无关系的平铺图片保存。

客户端服务结果页根据完整对比组动态生成 N 组拖动对比；服务相册则可按日期 / 服务记录浏览对应的洗护前、洗护后或美容前后照片。

如果某个对比组缺前图或缺后图，仍可保留已有照片，但不得在客户端伪造成完整前后对比。

## 9. 宠物移除与历史数据

已有订单、报告、寄养记录、照片等历史数据的宠物不得通过普通用户操作进行物理删除。

客户端使用“移除宠物 / 归档宠物”语义；历史业务数据继续保留，并支持在合理权限下恢复。

宠物被移除 / 归档后不得继续作为新的跨店服务安全共享对象；既有服务事件与审计历史仍按数据保留规则保存。

真正的数据删除应由后续账号注销、隐私与数据保留规则统一处理。

## 10. 店员搜索

店员端客户 / 宠物搜索必须支持至少：

- 客户姓名 / 昵称
- 手机号
- 宠物名称

社区门店员工常以宠物名称识别客户，因此宠物名称必须作为核心搜索字段。

## 11. 跨商户宠物档案

宠物基础档案属于平台用户 / 客户可授权复用的基础资料。

客户进入其他商户时，可主动选择复用已有宠物基础档案，减少重复建档。

新商户只能访问客户明确授权的基础资料，不得看到其他商户的：

- 历史订单
- 消费记录
- 会员资产
- 服务报告
- 商户内部备注
- 员工评价
- 其他经营数据

跨商户宠物行为与服务安全信息不因在 A 商户记录就自动向 B 商户公开；共享前提、可见范围和主人授权由 `03h-customer-risk-feedback.md` 与 `DEC-PETSAFETY-01` 统一收口。
