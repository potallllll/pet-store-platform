## 1. 客户端定位

客户端不提供充值入口，也不允许客户发起充值申请或自行完成余额支付。

“我的”页面直接展示当前商户下的会员资产摘要，客户无需先进入钱包页面即可看到：

- 当前可用余额
- 当前可使用优惠券数量
- 当前本金余额
- 当前赠送余额

其中“当前可用余额”作为主信息，以大号金额展示；优惠券数量、本金余额、赠送余额作为同一资产卡片中的辅助信息展示。

“我的钱包”用于查看和使用当前商户下的其他会员资产与明细，包括：

- 余额明细
- 优惠券
- 邀请码兑换

“我的钱包”页面不重复展示大号当前可用余额卡片，避免与“我的”页面重复占用空间。

V1.0 包含独立的 Platform User 级平台积分体系，入口位于“我的”页面的积分入口 / 积分摘要，具体规则见 `03k-customer-loyalty-points.md`。商户钱包不承载平台积分，不将积分放入会员资金资产卡、余额或余额流水；积分不可直接作为现金余额扣款。

不同商户之间的会员余额、优惠券及相关会员权益严格隔离。

## 2. 充值由门店侧发起

会员充值完全由门店侧处理。

基本流程：

店员选择客户
→ 填写本次实际充值本金
→ 按需填写赠送余额、选择赠送优惠券及数量
→ 有赠送时填写备注，无赠送时备注选填
→ 客户线下付款
→ 店员选择实际支付方式
→ 店员确认已收款
→ 系统生成充值流水
→ 增加会员余额
→ 按本次确认内容增加赠送余额 / 发放所选优惠券，保留充值关联

客户无需先在小程序进行任何充值操作。

财务按03d§1.1只记录线下真实交易，可即时或工作结束后录入，不接第三方收款／退款接口；记账确认后仍自动更新余额、赠送权益及流水，不要求手动再改数字。未录入前客户端只显示当前已记账数据，不假装余额已更新。原充值成功后按§4.2锁定；需要退还时只从原充值记录发起§4.3充值退款，不提供修改余额、充值更正或无关联撤销。

## 3. 单次充值金额与备注

不设充值套餐，不提供套餐新增、修改、启停、恢复或选择入口。门店在每次办理充值时，按实际线下交易填写本次金额：

- 充值本金：本次真实收到、用于增加本金余额的金额，沿F-WAL-020。
- 赠送余额：选填，未赠送时为0，沿F-WAL-021，与本金分别保存。
- 赠送优惠券及数量：选填，从本商户已有优惠券模板选择，沿F-WAL-023，不在充值表单创建或修改模板。
- 本次余额到账总额：沿F-WAL-022，由系统按本金＋赠送余额计算；优惠券不折成现金加入余额或实收。
- 备注：沿F-WAL-017；赠送余额大于0或选择了赠券时必须填写非空说明，仅赠券也需要备注；没有任何赠送时选填。条件由服务端校验，不接受只填空白，也不自动编造赠送原因。

例：实收本金300元、赠送30元，余额到账330元，充值实收仍为300元；只充值300元并赠送洗护券1张，余额到账300元，也须填写赠送备注。每次金额／所选券／备注只对应本次充值，不形成下次自动套用的套餐或规则。

原F-WAL-018／019／024～027套餐专属字段退役为D，永久注册号保留供历史追溯，不再作为本次充值输入或自动规则。F-WAL-020～023保留原金额及赠券逻辑字段名，改为本次实际充值内容；不新建第二套同义金额／备注字段。已有历史充值及已发权益不因套餐取消被删除、重算或撤销。

V1.0 不引入复杂营销条件引擎。

## 4. 充值时选择赠送权益

门店办理充值时可选择赠送余额、优惠券，两者均可不选，也可同时选择；有任一赠送时按§3填写必填备注。优惠券来源仍记“充值赠送”，并关联本次充值，不改记成独立人工赠券、邀请码或平台积分兑换。

门店确认真实充值记账成功后，系统按本次已确认内容增加本金／赠送余额并发放所选优惠券、生成对应记录；不另要求店员手工改余额或再逐张发券。服务端校验当前商户／顾客、实际操作者、金额、所选本商户券及数量、赠送条件和备注；失败不假报到账，同次成功请求重试不再次入余额或发券。客户端仍无充值／确认收款／选择赠送入口，只按原权限查看真实资产及明细。

此处确认单次充值及随单赠送；充值成功后原记录按§4.2锁定。确需退还时从原充值详情发起§4.3充值退款，原流水不覆盖；初始充值不得伪造未收到的钱。

### 4.1 门店充值记录查询

门店在顾客详情查看该顾客的充值记录，也可从“业务 → 订单与收银 → 充值记录”查看本店原充值记录；沿当前顾客／钱包记录的原读取权限，不新增跨商户／他人员工业绩或原始审计权限。列表固定日期、顾客、实收金额、赠送余额、赠送优惠券、经办人六列，实收只取本次本金，赠送和含赠送到账额不作为实收。

支持本店顾客手机号和日期组合查询，默认今天，可选昨天、本月、自定义日期，业务时区及详细日期边界按04§3.0.12。两入口引用原充值业务及流水，不复制消费订单／收入。

点击详情可查看本次本金、赠送余额、赠券、备注及原真实余额变化；原成功记录及流水锁定，不提供充值更正、撤销或修改余额。需要退还时从原充值详情发起§4.3充值退款。列表日期、筛选和排序统一使用原充值单据F-CORE-013 created_at；昨天收款、今天补录的单据按今天生成时间排序，真实充值收入仍归昨天的实际收款日期。

### 4.2 已记账充值锁定

充值成功记账后，原充值实收、赠送金额、赠券、实际发生时间和经办人锁定，不再提供“充值更正／撤销”或直接覆盖原值。录错且确实需要退回资金时，统一走§4.3充值退款；不以改余额、删流水或超管直接覆盖代替退款。系统保留原充值和后续退款的完整关联与自动审计。

## 5. 本金与赠送余额

后台必须区分：

- 充值本金余额
- 赠送余额
- 客户端显示的总可用余额

“我的”页面资产卡同时展示总可用余额、本金余额、赠送余额和当前可使用优惠券数量，方便客户直接理解资产构成，不要求进入二级页面才能查看。

总可用余额仍是主金额；本金余额和赠送余额属于辅助资产信息，不改变后台必须分别记账、分别形成流水和后续按规则扣减 / 退款的要求。

消费扣款顺序已确认：先扣本金，本金不足的余额支付部分再扣赠送余额；两类分别形成真实变动，不允许负余额。某次余额消费100元、消费前本金80／赠送50时，扣本金80及赠送20，余本金0／赠送30；原扣款构成必须随原交易保留，退款不得用当前余额或之后的充值赠送规则倒算。

消费退款全部原路退回：原余额付款退回原商户／原顾客钱包，本金部分退本金、赠送部分退赠送，不把赠送转本金或退现金；原微信／支付宝／现金等付款仍退原渠道，外部账户须线下由经办人核实是原付款账户。系统只记账，不接外部退款接口。

原消费余额100元含本金80／赠送20，全额退款须恢复本金80／赠送20；本次各渠道及本金／赠送退款不得超过各自已付／已扣未退金额，累计不得超过各自原实付／实际扣款。组合付款全额退款分别退各原渠道剩余可退金额，不将外部付款改退钱包或将余额提现。

2. **上限及合计**：本次各原渠道退款金额合计必须等于本次退款总额，金额按原Money精度且不为负、整次实际退款总额须大于0。每渠道本次上限＝原真实已付金额－该渠道此前已确认退款；整单本次上限＝原实际已收款－此前已确认退款总额，累计均不能超原款。原付款／已退关联或金额未知时不能猜分配、假填0或提交成功；草稿不消耗可退金额。
3. **钱包内部先本金**：仅对本次填写的“会员余额”原路退款额，系统先恢复本单原扣且尚未退回的本金，不足部分再恢复原扣且尚未退回的赠送金额。本次退本金＝本次钱包退款额与原本金扣款剩余可退额的较小值；本次退赠送＝本次钱包退款额－本次退本金。每项均不得超其原扣未退，不能手动换成另一组成、将赠送转本金／现金，或用顾客当前钱包余额、之后充值及赠送规则倒算。
4. **多次退款与例子**：原付款为钱包60（本金40＋赠送20）和微信40。第一次退款30、填钱包20＋原微信10时，恢复本金20、赠送0；第二次填钱包退款30时，原本金剩余可退20，故恢复本金20＋赠送10。此后钱包仅余赠送10、原微信仅余30可退，不重置原本金额度；全退剩余款时各自恢复原剩余组成。先本金是本轮明确确认的退款规则，不是仅从消费先扣本金推导。
5. **确认真实记账**：原微信／支付宝／现金等仍线下按原账户实际退回后登记，不声称系统已打款；钱包分项在确认退款时系统实际入原钱包并关联原消费／退款流水。确认时重验当前原单、渠道及分项剩余可退、F-PAY-013请求版本与原资格，退款结果与钱包分项／流水一致成功，失败不部分生效。重复确认返回原结果、不重复加余额；不同退款请求并发不能超退，过期草稿须重新核对，不因改归属／换经办重置额度。
6. **原业务边界**：消费退款原因必填、原实付及历史交易不覆盖；已确认退款沿真实退款日期和原订单业绩归属作减项，最终业绩为实际实收减已确认退款的净消费。部分退款不自动重开服务、离店或回库，真实退货仍按原规则。充值退还必须走§4.3充值退款，不得修改余额或混用消费退款。

字段沿F-PAY-001／002原付款、007／010／011／013～017原退款及原F-WAL-011／012分项变化，原订单与商户／顾客隔离保持；不新建第二账本、渠道金额副本或“先退本金”同义资产字段。

## 6. 余额支付

客户不能在客户端自行发起余额扣款。

门店结算记账时，由本店老板／有效店员选择会员余额作为支付方式，并由系统完成余额校验和实际扣减、生成流水；不是外部扣款通道，也不能只登记支付方式而不扣余额。与线下其他方式组合仍按03d§11最多两种、一次完整确认，系统余额不足不能记成负数。

余额不足时支持组合支付，由系统自动计算剩余应收金额，避免店员手工计算。

例如：订单应收 200 元，会员余额 80 元，可自动形成：会员余额 80 元 + 微信 / 支付宝 / 现金等 120 元。

## 7. 余额流水与审计

任何余额变化都必须形成不可删除的独立流水，不允许直接覆盖余额数字。

流水类型至少包括 / 预留：

- 充值
- 赠送
- 消费
- 退款
- 人工增加
- 人工扣减
- 冲正
- 历史初始化

每条关键流水至少记录：

- 客户
- 商户
- 操作时间
- 变动前余额
- 变动金额
- 变动后余额
- 本金 / 赠送部分变化
- 关联订单或充值单
- 支付方式（如适用）
- 操作员工
- 原因 / 备注

原充值记错不得直接更正、撤销或覆盖；确需退还时按§4.3从原充值记录发起充值退款，保留原充值与退款关联。

## 8. 优惠券类型

V1.0 只保留三类优惠券：

1. 满减券：例如满 100 减 20。
2. 无门槛 / 指定范围金额券：例如洗护抵扣 20 元。
3. 折扣券：例如美容 9 折，可配置最高优惠金额。

老板创建优惠券时至少配置：

- 优惠券名称
- 优惠券类型
- 优惠金额 / 折扣比例
- 使用门槛（如适用）
- 最高优惠金额（折扣券适用）
- 适用范围
- 有效期
- 启用 / 停用
- 备注（可选）

适用范围 V1.0 支持：

- 全部消费
- 洗护
- 美容
- 护理
- 寄养
- 商品

### 8.1 模板管理、启停与已发券

“老板管理 → 优惠券管理”只由本店老板新增／修改本商户模板，普通员工仅可按§9.2选择已有券赠送，不能维护模板或从直接API绕过。模板表单仍沿本节已确认的三类券及字段，不增加复杂营销引擎。

## 9. 优惠券发放方式

V1.0 支持以下四种来源：

### 9.1 充值时选择赠券

门店在本次充值表单选择已有优惠券及数量、填写赠送备注；充值成功后系统按本次选择发放一次，不依赖充值套餐。规则见§3～4。

### 9.2 老板／有效员工单独赠券

顾客详情 → 会员资产 → 赠送优惠券，本店老板及有效员工都可操作、不限原经办人、无需老板审批，也不要求同时充值。选择本商户已有且当前启用的模板及本次数量后确认；数量须为正整数，赠送原因选填。模板不能由店员在赠券表单修改或新建。

本次数量用F-CPN-021 coupon_grant_quantity，不借商品数量、充值赠券或邀请码绑定字段冒充本次独立赠送；原因沿F-AUD-009，人员及时间沿原审计，优惠券备注F-CPN-018仍为原可选字段，不被改成全局必填。每张实际券有原F-CPN-002稳定实例，来源F-CPN-014记“人工赠送”，关联当前本店顾客；不伪造一笔充值／付款／积分兑换来发券。

服务端同时校验本店／顾客／有效身份、当前模板及启用、数量与原因；失败不报发放成功，同次成功请求重试不重复发券，顾客只按原权限查看已成功发放的券与可用券数量。员工可获取完成发放所需的模板内容，不因此获得老板模板管理、原始系统审计或跨商户资产权限。

### 9.2.1 顾客赠券数量直接修改／删除

本店老板和有效员工可在“顾客详情 → 会员资产 → 优惠券”直接减少当前赠券数量或点击“删除赠券”，不要求原发放人、不设老板审批或独立误发申请／作废工单，也不强制先作废再重新赠送。删错／发错由门店手工调整；本次删除／数量变更原因选填，系统自动记录真实经办、服务端时间和前后实例／数量。

操作明确到当前本商户／顾客的实际coupon_instance_id，不按平台User汇总或跨店删券；减少至0即移除本次对应可操作赠券，不能仅改一个“总券数”留下仍可核销的原券。删除数量从本次移除的具体实例派生，不借coupon_grant_quantity当剩余持券数或新增随意可写的总券数字段。增加券仍用原赠券动作，不通过改数量绕过启用模板及发放条件。

删除只作用于未使用且未锁定的持有赠券；删除和结算核销都校验当前服务端状态，不能借删除撤销已核销事实。已使用券不提供删除或重复核销。失败不部分改资产，重复成功请求不再减少数量，不能删错其他顾客或相同名称下不同实际实例。

界面“删除”将持有实例沿F-CPN-013记removed，退出可用券列表，可用数量F-WAL-005按剩余真实可用实例重新计算；原模板、原发放来源、赠送事实及本次操作历史保留，不物理抹账。模板仍不提供删除，顾客持券可删除与模板无删除是两个对象。删赠券不自动撤销原充值／兑换、不改本金或赠送余额、不退积分／生成收退款，也不自动补发新券；顾客按原资产权限查看最新结果，内部审计权限不扩大。具体规则见04§3.0.16。

## 10. 优惠券／活动券的结算选择与自动校验

1. 店员在订单结算页选择该顾客当前可用的优惠券或活动券；不再从顾客详情独立点击“已核销”，也不要求先手工改价模拟券优惠。
2. 服务端必须校验门店、顾客、券状态、有效期、适用业务、最低消费、折扣上限、订单版本及是否已被其他订单使用；前端展示不能代替校验。
3. 校验通过后由系统按券快照计算优惠并更新最终应收。店员仍可在结算前按调价权限修改最终应收，但不得重复叠加同一券优惠。
4. 只有结算成功才把券标记已使用并关联原订单；结算失败、取消提交、旧版本或并发冲突均不得消耗券。相同请求重试返回原结果，不重复核销。
5. 免单仍须填写免单原因并明确确认；选券把应收降到0不自动等于免单成功。
6. 本期结算后的取消、全额退款和部分退款均不自动退券；历史合法退券记录只读保留。
## 11. 券实例状态、删除与历史

1. 未在结算中使用的可用券，老板或有效员工仍可从顾客详情删除；删除原因选填。已结算核销券不能日常撤销、删除或再次使用。
2. 券实例保存真实来源、发放快照、有效期、使用订单、核销时间和核销操作人；系统自动记录所有状态修改的操作者、时间及前后值。
3. 券模板停用只阻止以后发放，不影响已经发出的合法实例按原快照参与结算。
4. 券状态必须由服务端事务更新；跨店、过期、已用、已删除、并发使用或顾客不匹配均拒绝，失败不半核销。
5. 取消／退款不退券；确需平台纠正历史异常时仅由平台按受控数据修复处理，不向门店提供“误点撤销核销”。
## 12. 客户端优惠券展示

“我的优惠券”仅需区分：

- 可使用
- 历史券：已使用 / 已过期 / 已删除（removed）

每张券至少显示：

- 券名称
- 优惠内容
- 适用范围
- 有效期
- 使用门槛（如有）

客户端不提供复杂领券中心。

“我的”页资产卡中的“优惠券 X 张”表示当前商户下客户当前可使用的优惠券数量，用于快速资产摘要；详细券内容仍进入“我的优惠券”查看。

## 13. 权限原则

商户老板默认拥有全部会员相关权限。

有效在职店员统一使用02§4规定的本店店员业务权限，不设置逐员工权限开关。会员业务涉及：

- 查看余额
- 使用余额收款
- 执行充值
- 人工调整余额
- 冲正充值
- 查看优惠券
- 手动赠送优惠券

统一业务资格不等于可以直接改余额或抹除流水；充值成功后锁定，退还走§4.3充值退款且退款原因必填。独立赠券与删除未使用券允许老板／有效员工办理，原因选填、无审批；所有成功修改自动记录实际操作人、服务端时间和改前改后。优惠券模板配置仍归老板管理。

门店消费订单结算最多两种支付方式，会员余额本金／赠送内部拆分算一种；消费先扣本金、再扣赠送，原扣款构成留痕。消费退款本店老板／有效员工均可登记、无需老板审批；全部款项按原付款渠道／原账户退回，不能主动改退余额或现金。原余额部分在确认退款时由系统实际退回原钱包、按原本金／赠送归属形成独立流水；原微信／支付宝／现金等在线下按原路实际退回后登记。保存草稿不代表已退，重试不重复增余额，按03d§1.1／12；部分退款按§5.1由原渠道分别填金额、钱包原剩余本金先退后赠送。该消费规则不开放充值退款、任意余额调整或积分补偿，不以界面失败假回滚或免单造付款。

## 14. 减少操作原则

钱包 / 会员资产模块必须优先减少门店和客户操作：

- “我的”页用一张资产摘要卡直接展示当前可用余额、本金余额、赠送余额和可使用优惠券数量。
- 客户点击整张资产卡可进入余额明细，不额外增加必须点击的小按钮。
- “我的钱包”不重复展示当前余额大卡，主要承载余额明细、优惠券和邀请码兑换。
- 老板维护优惠券模板，不配置充值套餐。
- 门店充值时填写本次本金，按需填写赠送余额／选择已有优惠券；有任一赠送时备注必填。
- 充值成功后按本次确认内容发放赠送权益，同次请求不重复到账或发券。
- 全部优惠券与活动券在结算时选择，由服务端自动校验、计算优惠并在结算成功后核销、绑定原单；未成功不得核销。
- 组合支付由系统自动计算剩余应收。
- 邀请码由客户自行输入；优惠券兑换成功自动发券，不增加发券操作。直接兑换服务／商品活动的范围已定，后续履约操作另按§9.3待确认规则收口。
- 客户端不承担充值和余额支付。

资产摘要卡的背景颜色、渐变、高光、字体、圆角、阴影和具体视觉风格不在本阶段冻结，统一留到阶段 10 UI / Design System 确定；参考图仅用于确认信息布局，不作为正式品牌色要求。
