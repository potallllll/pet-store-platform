# 03C 客户端「我的钱包」模块

> 状态：已确认子模块
> 所属阶段：03 客户端微信小程序
> 版本：V1.0

## 1. 客户端定位

客户端不提供充值入口，也不允许客户发起充值申请或自行完成余额支付。

“我的”页面直接展示当前商户下的会员资产摘要，客户无需先进入钱包页面即可看到：

- 当前可用余额
- 当前可使用优惠券数量
- 当前本金余额
- 当前赠送余额

其中“当前可用余额”作为主信息，以大号金额展示；优惠券数量、本金余额、赠送余额作为同一资产卡片中的辅助信息展示。

“我的钱包”用于查看和使用当前商户下的其他会员资产与明细，包括：

- 余额明细
- 优惠券
- 邀请码兑换

“我的钱包”页面不重复展示大号当前可用余额卡片，避免与“我的”页面重复占用空间。

V1.0 包含独立的 Platform User 级平台积分体系，入口位于“我的”页面的积分入口 / 积分摘要，具体规则见 `03k-customer-loyalty-points.md`。商户钱包不承载平台积分，不将积分放入会员资金资产卡、余额或余额流水；积分不可直接作为现金余额扣款。

不同商户之间的会员余额、优惠券及相关会员权益严格隔离。

## 2. 充值由门店侧发起

会员充值完全由门店侧处理。

基本流程：

店员选择客户
→ 选择老板预先配置的充值套餐
→ 客户线下付款
→ 店员选择实际支付方式
→ 店员确认已收款
→ 系统生成充值流水
→ 增加会员余额
→ 自动发放套餐中配置的赠送余额 / 优惠券

客户无需先在小程序进行任何充值操作。

## 3. 老板配置充值套餐

商户老板可自行维护充值套餐，例如：

- 实收 300 元，赠送 30 元，到账 330 元
- 实收 500 元，赠送 60 元，并赠送洗护优惠券 1 张
- 实收 1000 元，赠送 150 元，并赠送指定优惠券

每个套餐支持：

- 套餐名称
- 实际收款金额
- 赠送余额
- 实际到账总额
- 赠送优惠券及数量
- 启用 / 停用
- 生效时间 / 失效时间（可选）
- 备注

V1.0 不引入复杂营销条件引擎。

## 4. 充值赠送权益

充值套餐可配置：

- 赠送余额
- 赠送优惠券

充值成功后系统自动发放套餐中已配置的赠送权益，店员不需要再次手动增加赠送余额或逐张发券。

## 5. 本金与赠送余额

后台必须区分：

- 充值本金余额
- 赠送余额
- 客户端显示的总可用余额

“我的”页面资产卡同时展示总可用余额、本金余额、赠送余额和当前可使用优惠券数量，方便客户直接理解资产构成，不要求进入二级页面才能查看。

总可用余额仍是主金额；本金余额和赠送余额属于辅助资产信息，不改变后台必须分别记账、分别形成流水和后续按规则扣减 / 退款的要求。

具体扣款顺序、退款时本金与赠送余额如何处理，在核心业务规则阶段最终确认。

## 6. 余额支付

客户不能在客户端自行发起余额扣款。

门店收银时，由有权限的店员选择会员余额作为支付方式，并由系统完成余额校验和扣减。

余额不足时支持组合支付，由系统自动计算剩余应收金额，避免店员手工计算。

例如：订单应收 200 元，会员余额 80 元，可自动形成：会员余额 80 元 + 微信 / 支付宝 / 现金等 120 元。

## 7. 余额流水与审计

任何余额变化都必须形成不可删除的独立流水，不允许直接覆盖余额数字。

流水类型至少包括 / 预留：

- 充值
- 赠送
- 消费
- 退款
- 人工增加
- 人工扣减
- 冲正
- 历史初始化

每条关键流水至少记录：

- 客户
- 商户
- 操作时间
- 变动前余额
- 变动金额
- 变动后余额
- 本金 / 赠送部分变化
- 关联订单或充值单
- 支付方式（如适用）
- 操作员工
- 原因 / 备注

错误操作通过冲正处理，不删除或直接修改历史流水。

## 8. 优惠券类型

V1.0 只保留三类优惠券：

1. 满减券：例如满 100 减 20。
2. 无门槛 / 指定范围金额券：例如洗护抵扣 20 元。
3. 折扣券：例如美容 9 折，可配置最高优惠金额。

老板创建优惠券时至少配置：

- 优惠券名称
- 优惠券类型
- 优惠金额 / 折扣比例
- 使用门槛（如适用）
- 最高优惠金额（折扣券适用）
- 适用范围
- 有效期
- 启用 / 停用
- 备注（可选）

适用范围 V1.0 支持：

- 全部消费
- 洗护
- 美容
- 寄养
- 商品

V1.0 不要求老板维护复杂多层营销条件。

## 9. 优惠券发放方式

V1.0 支持以下四种来源：

### 9.1 充值套餐自动赠送

老板在充值套餐中预先绑定优惠券。充值完成后系统自动发放，不增加店员操作。

### 9.2 老板 / 有权限员工手动赠送

老板可选择客户并直接赠送已配置的优惠券。

普通店员是否允许赠券由权限体系控制；默认不开放随意赠券权限。

### 9.3 邀请码兑换

V1.0 不做“系统活动自动赠送优惠券”，改为邀请码兑换。

老板可创建邀请码并绑定一张或多张已配置优惠券。邀请码至少支持：

- 邀请码内容（系统生成或老板指定）
- 绑定优惠券及数量
- 启用 / 停用
- 生效时间 / 失效时间
- 总兑换次数上限（可选）
- 单个客户兑换次数上限；默认同一邀请码同一客户仅可兑换一次
- 已兑换次数
- 创建人
- 创建时间
- 备注（可选）

客户端在“我的钱包”中提供轻量入口：

邀请码兑换
→ 输入邀请码
→ 后端校验当前商户、邀请码状态、有效期、次数限制和客户领取资格
→ 校验成功后自动发放绑定优惠券
→ 显示兑换结果

邀请码 V1.0 仅用于兑换优惠券，不直接增加会员余额，避免绕过充值和余额审计流程。

邀请码必须属于当前商户，不允许跨商户兑换。

### 9.4 平台积分兑换

客户按 `03k-customer-loyalty-points.md` 的积分商城规则兑换线下消费优惠券，向兑换时确定的 Merchant Customer 发放正式商户优惠券。

- 积分域扣减平台积分并保存兑换记录；钱包 / 优惠券域负责发券和后续核销，两个账本保持分离。
- 优惠券记录保留“平台积分兑换”来源、积分兑换记录关联和适用商户；不得因后续切换门店改变该券归属。
- 扣积分与发券必须支持幂等和补偿，避免已扣积分未发券或同一兑换重复发券。
- 兑换后的正式优惠券继续遵循本模块的适用范围、有效期、单券使用、核销与退款规则；使用该券的消费订单退款不直接等同于取消原积分兑换，不自动返还兑换积分。

## 10. 收银时优惠券使用

收银时系统自动识别该客户当前订单可使用的优惠券。

如果存在多张可用券，系统自动计算并默认推荐对客户最优惠的一张，店员无需人工逐张寻找。

店员可按需要更换其他可用优惠券。

V1.0 每个订单最多使用一张优惠券，不做多张优惠券叠加。

优惠券与人工调价可同时存在，但后台必须分别保存：

- 原始金额
- 优惠券优惠金额
- 人工调价金额
- 最终应收金额

不得只保存最终成交金额。优惠券门槛、自动优惠与人工调价的唯一计算顺序及改单后的重算口径属于 `DEC-SETTLE-01`，在阶段06确认前不得由实现者自行选择算法。

## 11. 优惠券核销与退款

优惠券在店员选择时仅锁定，不立即核销。

正常流程：

选择优惠券
→ 临时锁定
→ 普通待付款期间保持锁定
→ 确认订单收款
→ 正式核销

普通待付款、尚未完成线下付款不构成释放条件。订单取消、超时关闭，或有权限人员明确终止收银并解除该订单占用时，才释放尚未核销的锁定券。解除占用不得仅凭页面关闭、网络超时或前端自行判断付款失败触发。

释放后重新校验优惠券有效期、适用范围及使用条件；只有仍满足条件时才恢复为可立即使用。已过期或不再符合条件的券不得因释放而重新获得使用资格。明确终止收银的操作、锁定期间过期以及支付结果不确定时的最终处理细节见 `DEC-COUPON-01`，不得擅自补默认策略。

同一优惠券不能被两笔未完成订单同时形成有效占用；选择、释放和核销需由服务端并发校验及幂等处理。已正式核销的优惠券不能通过普通释放动作直接变回未核销状态，退款恢复须按正式冲正规则留痕。

V1.0 退款规则采用简单方案：

- 整单取消 / 全额退款：若优惠券仍在有效期，则恢复优惠券。
- 部分退款：不恢复优惠券。

更复杂退款边界在核心业务规则阶段统一复核，不得把待决的退款分摊、过期恢复例外自动视为已确认。

## 12. 客户端优惠券展示

“我的优惠券”至少区分：

- 可使用
- 使用中（已锁定、未核销）
- 已使用 / 已过期

“使用中”券应显示关联订单及可返回的订单详情入口，不混入可立即使用券数量；页面不允许通过普通点击自行解除服务端占用。取消、超时或其他正式释放结果成立后再更新可用状态。

每张券至少显示：

- 券名称
- 优惠内容
- 适用范围
- 有效期
- 使用门槛（如有）

客户端不提供复杂领券中心。

“我的”页资产卡中的“优惠券 X 张”表示当前商户下客户当前可立即使用的优惠券数量，用于快速资产摘要；已锁定的“使用中”券不计入该数字。详细券内容仍进入“我的优惠券”查看。

## 13. 权限原则

商户老板默认拥有全部会员相关权限。

普通店员的权限后续通过细粒度权限开关控制，例如：

- 查看余额
- 使用余额收款
- 执行充值
- 人工调整余额
- 冲正充值
- 查看优惠券
- 手动赠送优惠券

默认普通店员不拥有“人工调整余额”“冲正充值”“随意赠券”等高风险权限。

## 14. 减少操作原则

钱包 / 会员资产模块必须优先减少门店和客户操作：

- “我的”页用一张资产摘要卡直接展示当前可用余额、本金余额、赠送余额和可使用优惠券数量。
- 客户点击整张资产卡可进入余额明细，不额外增加必须点击的小按钮。
- “我的钱包”不重复展示当前余额大卡，主要承载余额明细、优惠券和邀请码兑换。
- 老板提前配置充值套餐和优惠券模板。
- 店员充值时直接选择套餐，不重复输入赠送金额和赠送券。
- 充值成功后自动发放赠送权益。
- 收银时系统自动匹配并推荐最优惠的可用券。
- 组合支付由系统自动计算剩余应收。
- 邀请码兑换由客户自行输入，兑换成功后系统自动发券，不增加店员操作。
- 客户端不承担充值和余额支付。

资产摘要卡的背景颜色、渐变、高光、字体、圆角、阴影和具体视觉风格不在本阶段冻结，统一留到阶段 10 UI / Design System 确定；参考图仅用于确认信息布局，不作为正式品牌色要求。

### 2026-08-31

【历史变更，仅供追溯】

- 原规则：入口名称为“我的会员”，当前可用余额主要在“我的会员”页面展示。
- 新规则：入口名称改为“我的钱包”；当前可用余额直接展示在“我的”页面；“我的钱包”不重复展示余额大卡，主要承载余额明细、优惠券和邀请码兑换。
- 影响范围：客户端信息架构 / UI；不改变余额数据库模型、充值流程、支付规则、财务流水或商户隔离规则。

### 2026-09-01：“我的”资产卡展示资产构成

【历史变更，仅供追溯】

- 原规则：“我的”页面主要直接展示总可用余额，本金 / 赠送构成通常不在首页直接展示。
- 新规则：“我的”页面使用资产摘要卡，同时展示当前可用余额、当前可使用优惠券数量、本金余额和赠送余额；总可用余额为主金额，其他三项为辅助信息。整张卡可进入余额明细。
- 视觉边界：参考图只确认信息层级和版式方向，不冻结背景颜色、渐变、高光、字体、圆角或阴影，具体视觉在阶段 10 确定。

### 2026-09-08：同步平台积分与兑换优惠券来源

【历史变更，仅供追溯】

- 原规则：钱包保留“不设计积分”的旧总结，优惠券来源仅列充值赠送、人工赠送和邀请码兑换。
- 新规则：同步 `03k` 已确认的平台积分体系，明确积分不进入商户资金卡和钱包账本；优惠券来源补充平台积分兑换，保留兑换关联、适用商户及幂等补偿边界。
- 影响范围：钱包资产展示、优惠券来源与发放、积分商城兑换、退款边界、API 和验收；不改变会员充值和余额支付权限。

### 2026-09-08：澄清优惠券占用与待付款

- 原规则：第11节“订单取消或未完成收款时释放”可被误读为普通待付款就应释放，与03e确认后预占、取消或超时释放的规则不一致。
- 新规则：正常待付款保持锁定，取消、超时或明确解除占用才释放；释放后重新校验资格，使用中不计入可用数量。并发占用、核销及退款留痕要求继续有效，剩余操作细节登记 `DEC-COUPON-01`，计算顺序登记 `DEC-SETTLE-01`。
- 影响范围：钱包、优惠券、收银、商品订单、余额与退款规则、API、数据库、并发和验收；不在本次决定新的退款分摊或过期恢复例外。
