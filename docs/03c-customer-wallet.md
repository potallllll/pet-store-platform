## 1. 客户端定位

客户端不提供充值入口，也不允许客户发起充值申请或自行完成余额支付。

“我的”页面直接展示当前商户下的会员资产摘要，客户无需先进入钱包页面即可看到：

- 当前可用余额
- 当前可使用优惠券数量
- 当前本金余额
- 当前赠送余额

其中“当前可用余额”作为主信息，以大号金额展示；优惠券数量、本金余额、赠送余额作为同一资产卡片中的辅助信息展示。

“我的钱包”用于查看和使用当前商户下的其他会员资产与明细，包括：

- 余额明细
- 优惠券
- 邀请码兑换

“我的钱包”页面不重复展示大号当前可用余额卡片，避免与“我的”页面重复占用空间。

V1.0 包含独立的 Platform User 级平台积分体系，入口位于“我的”页面的积分入口 / 积分摘要，具体规则见 `03k-customer-loyalty-points.md`。商户钱包不承载平台积分，不将积分放入会员资金资产卡、余额或余额流水；积分不可直接作为现金余额扣款。

不同商户之间的会员余额、优惠券及相关会员权益严格隔离。

## 2. 充值由门店侧发起

会员充值完全由门店侧处理。

基本流程：

店员选择客户
→ 填写本次实际充值本金
→ 按需填写赠送余额、选择赠送优惠券及数量
→ 有赠送时填写备注，无赠送时备注选填
→ 客户线下付款
→ 店员选择实际支付方式
→ 店员确认已收款
→ 系统生成充值流水
→ 增加会员余额
→ 按本次确认内容增加赠送余额 / 发放所选优惠券，保留充值关联

客户无需先在小程序进行任何充值操作。

财务按03d§1.1只记录线下真实交易，可即时或工作结束后录入，不接第三方收款／退款接口；记账确认后仍自动更新余额、赠送权益及流水，不要求手动再改数字。未录入前客户端只显示当前已记账数据，不假装余额已更新。原充值记录更正／有条件撤销按§4.2已确认；当前余额修改及充值余额退还按§4.3统一处理，平台异常具体细节仍待确认，不因消费退款无需审批而自动开放。

## 3. 单次充值金额与备注

不设充值套餐，不提供套餐新增、修改、启停、恢复或选择入口。门店在每次办理充值时，按实际线下交易填写本次金额：

- 充值本金：本次真实收到、用于增加本金余额的金额，沿F-WAL-020。
- 赠送余额：选填，未赠送时为0，沿F-WAL-021，与本金分别保存。
- 赠送优惠券及数量：选填，从本商户已有优惠券模板选择，沿F-WAL-023，不在充值表单创建或修改模板。
- 本次余额到账总额：沿F-WAL-022，由系统按本金＋赠送余额计算；优惠券不折成现金加入余额或实收。
- 备注：沿F-WAL-017；赠送余额大于0或选择了赠券时必须填写非空说明，仅赠券也需要备注；没有任何赠送时选填。条件由服务端校验，不接受只填空白，也不自动编造赠送原因。

例：实收本金300元、赠送30元，余额到账330元，充值实收仍为300元；只充值300元并赠送洗护券1张，余额到账300元，也须填写赠送备注。每次金额／所选券／备注只对应本次充值，不形成下次自动套用的套餐或规则。

原F-WAL-018／019／024～027套餐专属字段退役为D，永久注册号保留供历史追溯，不再作为本次充值输入或自动规则。F-WAL-020～023保留原金额及赠券逻辑字段名，改为本次实际充值内容；不新建第二套同义金额／备注字段。已有历史充值及已发权益不因套餐取消被删除、重算或撤销。

V1.0 不引入复杂营销条件引擎。

## 4. 充值时选择赠送权益

门店办理充值时可选择赠送余额、优惠券，两者均可不选，也可同时选择；有任一赠送时按§3填写必填备注。优惠券来源仍记“充值赠送”，并关联本次充值，不改记成独立人工赠券、邀请码或平台积分兑换。

门店确认真实充值记账成功后，系统按本次已确认内容增加本金／赠送余额并发放所选优惠券、生成对应记录；不另要求店员手工改余额或再逐张发券。服务端校验当前商户／顾客、实际操作者、金额、所选本商户券及数量、赠送条件和备注；失败不假报到账，同次成功请求重试不再次入余额或发券。客户端仍无充值／确认收款／选择赠送入口，只按原权限查看真实资产及明细。

此处确认单次充值及随单赠送，原充值更正／撤销按§4.2已确认规则执行；初始充值不伪造未收到的钱；当前余额修改及余额退还另按§4.3统一处理，原流水不无痕覆盖，平台异常及剩余交易技术契约仍待决。

### 4.1 门店充值记录查询

门店在顾客详情查看该顾客的充值记录，也可从“业务 → 订单与收银 → 充值记录”查看本店原充值记录；沿当前顾客／钱包记录的原读取权限，不新增跨商户／他人员工业绩或原始审计权限。列表固定日期、顾客、实收金额、赠送余额、赠送优惠券、经办人六列，实收只取本次本金，赠送和含赠送到账额不作为实收。

支持本店顾客手机号和日期组合查询，默认今天，可选昨天、本月、自定义日期，业务时区及详细日期边界按04§3.0.12。两入口引用原充值业务及流水，不复制消费订单／收入。

点击详情可查看本次本金、赠送余额、赠券、备注及原真实余额变化；原成功记录及流水不覆盖或删除，本店老板／有效员工可从原详情按§4.2更正当前有效本金、赠送金额、赠券，原因必填、保留前后记录和差额流水；有条件撤销及超管异常按该节执行，当前余额修改／退还按§4.3，平台异常等其余范围仍待决，不借普通查询直接改余额或重发权益；客户端仍无充值入口。用户已明确列表订单日期为充值单据生成日期：日期展示、日期筛选沿原充值记录的F-CORE-013 created_at，并按完整生成时间从新到旧。昨天收款、今天补录生成单据时，记录按今天单据日期显示／查询／排序；真实收款日期及录入时间分别保留，充值收入仍按昨天的实际收款日期统计，不能以今天生成的充值单列表合计冒充今天实收。完整规则见04§3.0.12，剩余真实交易时间技术映射仍待收口。

### 4.2 充值更正、撤销及超管异常处理

本店老板／有效员工可在原充值详情“更正充值”，修改本次本金、赠送余额及赠券／数量，原因必填、无需审批；不强制先整笔撤销再重录。原充值、原本金／赠送流水及历次内容保留，当前列表／详情显示更正后的有效内容；前后金额／券、修改人、原因和时间沿原审计留存，不覆盖原经办／单据日期。充值更正处理原单记错；修改当前余额及退还余额按§4.3统一操作，不通过改余额反向改写原真实收款事实。

系统按新旧有效金额差额分别调整本金和赠送余额、形成关联原充值的真实流水；不是再增加一遍新总额。赠券按差异新增／撤回，未变券不重复发放，原备注保留、更正原因单独记录。例：原300赠30改500赠50，只增加本金200／赠送20，实际充值实收更正为500且仍归原真实收款日；赠送与券不作实收。

整笔误录可用“撤销记账”，原因必填，按当前有效本金／赠送／需撤回的赠券扣回并形成反向关联记录，不删除历史、不当真实退款，原充值不再计实收。需要扣回的本金或赠送余额不足、或需撤回赠券已使用时，门店提示“无法撤销，请联系平台超级管理员处理”，老板与员工均不能绕过；不扣成负数、不跨本金赠送补扣、不改已有消费或伪造券未使用。失败不部分改资产，同次成功重试不重复记账或发撤券。

仅Platform Super Admin在平台管理侧可更正此类异常数据，原因／前后值／经办／时间同样留痕；具体后台界面、余额不足和已用券的异常数据联动等留阶段05／06／08确认。原充值列表仍按原单据生成日期查询排序，资产调整时间按真实操作另存，不伪造之前余额已到账；实际充值收入按更正后真实金额与原实际收款日期统计。详细权限／并发／字段边界见04§3.0.13；顾客退还余额统一按下节修改余额，线下退钱门店处理，无独立充值退款流程。

### 4.3 修改余额：统一处理充值余额退还

门店不另设充值退款流程，直接在“顾客详情 → 会员资产 → 修改余额”调整当前资产。本店老板和有效员工均可操作，无需老板审批：预填当前本金余额／赠送余额，只修改需要变更的项、填写必填原因，点击“确认修改”。目标分项金额沿原Money规则、不得为负，总可用余额由系统计算；原因去空白后必须有内容，不另要求选择原充值、填写退款申请或办理渠道步骤。

系统分别计算目标本金／赠送与当前值的差额，自动更新余额并形成不可删除的调整流水，保留修改前后值、原因、真实经办及服务端时间。例：本金100赠送20改本金40赠送10，只记本金-60／赠送-10，总余额120变50，不再扣第二笔退款。原历史流水保留，当前数据变化后旧表单须重新核对，同次成功请求重试不重复增扣，保存失败不假报成功或部分改资产。

线下退钱由门店自行处理；本动作只记录账面余额修改，不自动证明已线下退款，也不生成新充值实收、消费退款或另一个充值退款记录。原充值本金实收和实际收款日期、原消费／收退款及业绩不因修改余额被重写；原充值记错须按§4.2更正，不把真实充值发生过的事实当误录删除。既有消费退款原路和先本金后赠送规则保持。

原充值更正／撤销因需要扣回余额不足或需要撤券已用而失败的，仍只能由Platform Super Admin处理；修改余额不把该原单标成已撤销、不撤回已用券或改已完成消费。赠券沿原充值及更正规则，本表单不追加自动扣赠比例或赠券处置步骤。顾客按原资产／流水权限看真实结果、无修改入口；字段、租户、并发和权限边界详见04§3.0.14。

## 5. 本金与赠送余额

后台必须区分：

- 充值本金余额
- 赠送余额
- 客户端显示的总可用余额

“我的”页面资产卡同时展示总可用余额、本金余额、赠送余额和当前可使用优惠券数量，方便客户直接理解资产构成，不要求进入二级页面才能查看。

总可用余额仍是主金额；本金余额和赠送余额属于辅助资产信息，不改变后台必须分别记账、分别形成流水和后续按规则扣减 / 退款的要求。

消费扣款顺序已确认：先扣本金，本金不足的余额支付部分再扣赠送余额；两类分别形成真实变动，不允许负余额。某次余额消费100元、消费前本金80／赠送50时，扣本金80及赠送20，余本金0／赠送30；原扣款构成必须随原交易保留，退款不得用当前余额或之后的充值赠送规则倒算。

消费退款全部原路退回：原余额付款退回原商户／原顾客钱包，本金部分退本金、赠送部分退赠送，不把赠送转本金或退现金；原微信／支付宝／现金等付款仍退原渠道，外部账户须线下由经办人核实是原付款账户。系统只记账，不接外部退款接口。

原消费余额100元含本金80／赠送20，全额退款须恢复本金80／赠送20；本次各渠道及本金／赠送退款不得超过各自已付／已扣未退金额，累计不得超过各自原实付／实际扣款。组合付款全额退款分别退各原渠道剩余可退金额，不将外部付款改退钱包或将余额提现。

尚未确认的是部分退款的分配算法：组合付款部分退款先退哪个原渠道、是否按比例，以及同次扣过本金和赠送时部分退款如何在两者间分配。先扣本金仅是消费顺序，不自动推出“退款先退本金／赠送”或反向扣款顺序。以上按DEC-STAFF-05待决，不得自设默认、手工任意改渠道或把整份文件视作已解阻；已确认的消费扣款顺序和全额原路退回不再列待决。

## 6. 余额支付

客户不能在客户端自行发起余额扣款。

门店结算记账时，由本店老板／有效店员选择会员余额作为支付方式，并由系统完成余额校验和实际扣减、生成流水；不是外部扣款通道，也不能只登记支付方式而不扣余额。与线下其他方式组合仍按03d§11最多两种、一次完整确认，系统余额不足不能记成负数。

余额不足时支持组合支付，由系统自动计算剩余应收金额，避免店员手工计算。

例如：订单应收 200 元，会员余额 80 元，可自动形成：会员余额 80 元 + 微信 / 支付宝 / 现金等 120 元。

## 7. 余额流水与审计

任何余额变化都必须形成不可删除的独立流水，不允许直接覆盖余额数字。

流水类型至少包括 / 预留：

- 充值
- 赠送
- 消费
- 退款
- 人工增加
- 人工扣减
- 冲正
- 历史初始化

每条关键流水至少记录：

- 客户
- 商户
- 操作时间
- 变动前余额
- 变动金额
- 变动后余额
- 本金 / 赠送部分变化
- 关联订单或充值单
- 支付方式（如适用）
- 操作员工
- 原因 / 备注

原充值记错按§4.2更正／有条件撤销处理，界面可改当前有效金额和赠券、原因必填，系统追加差额／反向流水及前后记录，不删除或直接覆盖历史流水。

## 8. 优惠券类型

V1.0 只保留三类优惠券：

1. 满减券：例如满 100 减 20。
2. 无门槛 / 指定范围金额券：例如洗护抵扣 20 元。
3. 折扣券：例如美容 9 折，可配置最高优惠金额。

老板创建优惠券时至少配置：

- 优惠券名称
- 优惠券类型
- 优惠金额 / 折扣比例
- 使用门槛（如适用）
- 最高优惠金额（折扣券适用）
- 适用范围
- 有效期
- 启用 / 停用
- 备注（可选）

适用范围 V1.0 支持：

- 全部消费
- 洗护
- 美容
- 护理
- 寄养
- 商品

V1.0 不要求老板维护复杂多层营销条件。新增“护理”可作为明确适用范围，不因此扩大旧洗护／美容限定券；护理仍只供门店开单，不增加顾客预约入口。

### 8.1 模板管理、启停与已发券

“老板管理 → 优惠券管理”只由本店老板新增／修改本商户模板，普通员工仅可按§9.2选择已有券赠送，不能维护模板或从直接API绕过。模板表单仍沿本节已确认的三类券及字段，不增加复杂营销引擎。

新建模板成功后默认启用；老板可停用／恢复，恢复沿原coupon_template_id及历史，不提供删除模板操作。停用后不得新发券，包括单独赠券、充值赠券及依赖本模板的其他已有发券来源；服务端发放前校验当前启用状态及本商户条件，旧页面／链接不能继续发放。

已经发出的coupon_instance_id继续按发放时的优惠条件／范围／有效期使用；模板停用不将旧实例标失效、已用或已过期。模板改名、优惠、范围或期限只影响以后发出的券，原实例沿发放快照，不读取后来模板覆盖旧优惠。已有券的有效期锁定暂停／解除后补回时长、核销与退款仍按§11执行，不因本次确认被取消；恢复模板不复活原已用／过期实例或重发旧券。

模板维护保留前后内容、老板／服务端时间；发券记录保留本次真实模板、顾客、券实例和来源。模板变化与发放并发时须核对当前合法状态／内容，不用旧页面发出不一致快照；剩余版本与跨渠道技术映射按字段注册表先收口。顾客持有赠券的直接减量／删除按§9.2.1已确认；已发券其他内容更改及超管异常等未列细则仍待确认。

## 9. 优惠券发放方式

V1.0 支持以下四种来源：

### 9.1 充值时选择赠券

门店在本次充值表单选择已有优惠券及数量、填写赠送备注；充值成功后系统按本次选择发放一次，不依赖充值套餐。规则见§3～4。

### 9.2 老板／有效员工单独赠券

顾客详情 → 会员资产 → 赠送优惠券，本店老板及有效员工都可操作、不限原经办人、无需老板审批，也不要求同时充值。选择本商户已有且当前启用的模板及本次数量，填写本次赠送原因后确认；数量须为正整数，原因去空白后非空必填。模板不能由店员在赠券表单修改或新建。

本次数量用F-CPN-021 coupon_grant_quantity，不借商品数量、充值赠券或邀请码绑定字段冒充本次独立赠送；原因沿F-AUD-009，人员及时间沿原审计，优惠券备注F-CPN-018仍为原可选字段，不被改成全局必填。每张实际券有原F-CPN-002稳定实例，来源F-CPN-014记“人工赠送”，关联当前本店顾客；不伪造一笔充值／付款／积分兑换来发券。

服务端同时校验本店／顾客／有效身份、当前模板及启用、数量与原因；失败不报发放成功，同次成功请求重试不重复发券，顾客只按原权限查看已成功发放的券与可用券数量。员工可获取完成发放所需的模板内容，不因此获得老板模板管理、原始系统审计或跨商户资产权限。

### 9.2.1 顾客赠券数量直接修改／删除

本店老板和有效员工可在“顾客详情 → 会员资产 → 优惠券”直接减少当前赠券数量或点击“删除赠券”，不要求原发放人、不设老板审批或独立误发申请／作废工单，也不强制先作废再重新赠送。删错／发错由门店手工调整；本次赠券数量变更沿已确认的变更原因要求填写原因，并记录真实经办、时间和前后实例／数量，不能用原赠送说明自动代本次原因。

操作明确到当前本商户／顾客的实际coupon_instance_id，不按平台User汇总或跨店删券；减少至0即移除本次对应可操作赠券，不能仅改一个“总券数”留下仍可核销的原券。删除数量从本次移除的具体实例派生，不借coupon_grant_quantity当剩余持券数或新增随意可写的总券数字段。增加券仍用原赠券动作，不通过改数量绕过启用模板及发放条件。

手工删除作用于未使用、未被原订单占用的持有赠券：原订单锁定／核销规则不被删除绕过，已使用券仍按之前的超管异常边界处理，不撤销既有消费。服务端提交时校验当前身份／本店顾客／具体券状态，不能让旧页面删除刚被锁定或使用的券；失败不部分改资产，重复成功请求不再减少数量，不能删错其他顾客或相同名称下不同实际实例。

界面“删除”将持有实例沿F-CPN-013记removed，退出可用券列表，可用数量F-WAL-005按剩余真实可用实例重新计算；原模板、原发放来源、赠送事实及本次操作历史保留，不物理抹账。模板仍不提供删除，顾客持券可删除与模板无删除是两个对象。删赠券不自动撤销原充值／兑换、不改本金或赠送余额、不退积分／生成收退款，也不自动补发新券；顾客按原资产权限查看最新结果，内部审计权限不扩大。具体规则见04§3.0.16。

V1.0 不做系统活动自动赠送优惠券，沿邀请码兑换。

老板只需创建邀请码并选择兑换内容；不提供启停、恢复、换码、调整活动或修改已创建码的管理流程，不要求维护多种可配置次数或有效期。兑换范围已明确包括本店优惠券，以及直接兑换本店服务活动／商品活动；服务和商品活动无需强制转成优惠券后才能兑换。优惠券仍沿已有绑定券及数量，不直接增加会员余额。服务／商品活动兑换成功先生成待使用活动权益，到店后由本店老板或有效员工使用，并关联原服务单／商品单；兑换不是实际服务完成或商品交付。单码是否可混合多种内容、兑换后使用期限及使用过程的库存、结算、撤销和数据契约等仍待确认，不能把范围确认当作整套活动流程已经确定。

**一条码总共一次**：每个邀请码在所属本店的全部顾客之间合计只能成功兑换一次，不是每位顾客各一次，也不是每张绑定券各一次。一次成功兑换按创建时确定的内容取得相应兑换结果，仍只消耗该码的一次资格；优惠券分支原可绑定多张券，活动分支及跨类型组合的具体数量规则待确认，不同顾客并发仅允许一笔成功，不产生第二份权益。

**固定3天**：从服务端成功创建邀请码时开始连续72小时，创建即生效，不按三个自然日或顾客首次输入起算。沿F-INV-011创建时间、005生效时间和006失效时间，005等于011，006等于011加72小时；服务端当前时间严格早于006且尚未成功兑换才可兑换，恰好到期拒绝。次数和期限不可由老板或前端自行改写，已兑换与到期均不能通过恢复／修改活动重新获得资格。该72小时只规定邀请码兑换窗口，不规定兑换后权益的使用期限；优惠券沿原发放快照及有效期，服务／商品活动的使用期限另行确认。

优惠券分支的创建内容沿F-INV-002邀请码内容（系统生成或老板指定）、003绑定优惠券及数量、010创建人、011服务端创建时间和012选填备注；服务／商品活动引用及兑换结果的数据契约须在规则确认后先注册，不把003改成活动引用或将商品SKU复制成服务项目；007总上限固定为1，009成功次数只可0或1。不再使用004启停、008单顾客可配上限；永久号与历史字段保留为D，禁新写。创建后保留原码、内容及历史，不设编辑／删除操作；已创建码的状态由成功兑换事实和到期时间判断，不借用优惠券模板的启停状态代替邀请码状态。

客户端“我的钱包 → 邀请码兑换”：
输入邀请码 → 服务端核对所属本店、当前本店Customer、未兑换及未到期和原领取资格 → 成功后按所选类型取得兑换结果并消耗唯一一次资格 → 当前页显示结果。普通输入、查看、越店或资格失败不消耗次数。

老板生成或指定的邀请码仅限其本店使用，不允许跨门店、跨商户兑换。邀请码归属生成它的Merchant／Store，沿F-CORE-002 merchant_id、003 store_id和004 customer_id，不以创建者身份冒充门店归属；优惠券及直接兑换的服务／商品活动均只限本店，不因活动扩容变成跨店权益。其他门店输入或接口篡改拒绝，不发券、不计次。

兑换成功必须将唯一一次消耗与实际兑换结果作为一次一致的业务结果保存：失败不消耗资格或留下部分权益；同一已成功请求沿原F-CORE-010恢复原成功结果，不再发券或重复生成活动结果，也不能误报首次成功失败；其他请求在成功后提示已兑换。并发、重试与到期判断均以服务端实际受理结果为准，不能先在客户端判断可用再越过期限提交。

**服务／商品活动领取与使用**：已确认先领取待使用活动权益，到店由本店老板／有效员工使用，并关联原服务单／商品单，不在输入邀请码时直接生成待处理订单。实际服务仍走原检查及服务状态，商品仍与原SKU／库存关联；不能因领到活动权益写成服务已开始／完成、商品已交付或已经收款。权益使用与库存预占／出库、应收及结算、业绩记账、取消／中止／退货后权益处理的具体时点和规则仍待确认，不自行把活动统一视为零元免单；不得复建独立商品库存或服务主资料。取得服务权益不等于新增客户端护理预约，护理原预约限制保持。

店员查看复制、独立兑换记录查询与具体入口位置尚未确认；不由“只创建邀请码”扩展这些菜单或普通员工创建权限。通知仍按03f原兑换成功规则：当前页结果和站内记录，不额外微信通知；不得把一次兑换误成付款、充值或已完成服务。

### 9.4 平台积分兑换

客户按 `03k-customer-loyalty-points.md` 的积分商城规则兑换线下消费优惠券，向兑换时确定的 Merchant Customer 发放正式商户优惠券。

- 积分域扣减平台积分并保存兑换记录；钱包 / 优惠券域负责发券和后续核销，两个账本保持分离。
- 优惠券记录保留“平台积分兑换”来源、积分兑换记录关联和适用商户；不得因后续切换门店改变该券归属。
- 扣积分与发券必须支持幂等和补偿，避免已扣积分未发券或同一兑换重复发券。
- 兑换后的正式优惠券继续遵循本模块的适用范围、有效期、单券使用、核销与退款规则；使用该券的消费订单退款不直接等同于取消原积分兑换，不自动返还兑换积分。

## 10. 收银时优惠券使用

收银时系统自动识别该客户当前订单可使用的优惠券。

如果存在多张可用券，系统自动计算并默认推荐对客户最优惠的一张，店员无需人工逐张寻找。

店员可按需要更换其他可用优惠券。

V1.0 每个订单最多使用一张优惠券，不做多张优惠券叠加。

优惠券与人工调价可同时存在，但后台必须分别保存：

- 原始金额
- 优惠券优惠金额
- 人工调价金额
- 最终应收金额

不得只保存最终成交金额。

## 11. 优惠券核销与退款

优惠券在店员选择时仅锁定，不立即核销。

流程：

选择优惠券
→ 临时锁定
→ 确认订单结算（实际收款或03d§10.1明确确认零元免单）
→ 正式核销

订单取消或未完成结算时，尚未核销的锁定券解除锁定。若优惠券在锁定开始时有效，则有效期在锁定期间暂停计算，解除锁定后继续原剩余有效时长：

`remaining_validity = valid_until_before_lock - coupon_locked_at`

`new_valid_until = coupon_unlocked_at + remaining_validity`

该规则等价于仅补回实际锁定时长，不额外赠送可使用时长。锁定前已过期的券不得被锁定或复活；重复锁定每次只暂停当次锁定期间的倒计时，不因重试或重复释放再次延期。锁定、解除、延期前后截止时间及关联订单必须留痕。

V1.0 退款规则采用简单方案：

- 整单取消 / 全额退款：若优惠券仍在有效期，则恢复优惠券。收款后已核销再发生退款，不属于上述“锁定期暂停”场景，不自动把退款等待时间计入延期。
- 部分退款：不恢复优惠券。

更复杂退款边界在核心业务规则阶段统一复核。

零元免单成功属于消费结算而非实际收款，已选优惠券按原适用及单券规则核销一次，不因没有支付记录被未付款任务解锁／延期；仅输入0或优惠后为0、尚未确认免单时仍未结算。免单不产生会员余额扣款或充值赠送；未实际收取的金额不能据此退款。限定洗护／美容的券不因新增护理类别自动扩大适用范围。

## 13. 权限原则

商户老板默认拥有全部会员相关权限。

有效在职店员统一使用02§4规定的本店店员业务权限，不设置逐员工权限开关。会员业务涉及：

- 查看余额
- 使用余额收款
- 执行充值
- 人工调整余额
- 冲正充值
- 查看优惠券
- 手动赠送优惠券

统一业务资格不等于可以直接改余额、抹除流水或任意赠券；原充值更正／撤销按§4.2已确认、原因必填，无需老板审批，失败需超管处理的边界按该节；当前余额修改及充值余额退还按§4.3已确认，原因必填、无需审批；独立赠券按§9.2已确认，老板／有效员工可办、原因必填无审批；顾客持有赠券直接减量／删除按§9.2.1已确认；平台异常细节及其他未列范围仍按对应待决项收口。充值套餐已取消；优惠券模板配置仍归老板管理，充值时选择已有券按§3～4办理；未确认的动作不能借统一权限提前开放。

门店消费订单结算最多两种支付方式，会员余额本金／赠送内部拆分算一种；消费先扣本金、再扣赠送，原扣款构成留痕。消费退款本店老板／有效员工均可登记、无需老板审批；全部款项按原付款渠道／原账户退回，不能主动改退余额或现金。原余额部分在确认退款时由系统实际退回原钱包、按原本金／赠送归属形成独立流水；原微信／支付宝／现金等在线下按原路实际退回后登记。保存草稿不代表已退，重试不重复增余额，按03d§1.1／12；部分退款分配按§5待决。该消费规则不开放充值退款、任意余额调整或积分补偿，不以界面失败假回滚或免单造付款。

## 14. 减少操作原则

钱包 / 会员资产模块必须优先减少门店和客户操作：

- “我的”页用一张资产摘要卡直接展示当前可用余额、本金余额、赠送余额和可使用优惠券数量。
- 客户点击整张资产卡可进入余额明细，不额外增加必须点击的小按钮。
- “我的钱包”不重复展示当前余额大卡，主要承载余额明细、优惠券和邀请码兑换。
- 老板维护优惠券模板，不配置充值套餐。
- 门店充值时填写本次本金，按需填写赠送余额／选择已有优惠券；有任一赠送时备注必填。
- 充值成功后按本次确认内容发放赠送权益，同次请求不重复到账或发券。
