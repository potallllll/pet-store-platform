## 1. 文件作用与开工边界

本文件约束 DeepSeek 或其他实现者如何读取需求、开发、提交证据和接受复核，不新增业务规则，也不表示 V1.0 已冻结。正式业务只读 `AGENTS.md`、`docs/README.md`、`docs/REQUIREMENTS-STATUS.md`、对应模块和 `FIELD-REGISTRY.md`；`docs/history/`、聊天、旧原型和旧提示词均不得作为现行规则。

正式代码开发仍受两项执行决策阻塞：

| ID | 状态 | 必须由用户确定的内容 |
|---|---|---|
| DEC-EXEC-01 | pending | 本次开发批次、排除项、目标仓库／分支，以及是否允许冻结前限定范围开发 |
| DEC-EXEC-02 | pending | 小程序技术栈、后端／数据库、AppID与环境、接口契约负责人和部署目标 |

在两项未关闭前，默认只做 G0：读取、冲突审计、需求追踪、技术盘点和测试计划；不得假称真实接口、微信能力、支付、权限或部署已完成。

## 2. 强制读取顺序

1. 根 `AGENTS.md`、`docs/README.md`、`docs/REQUIREMENTS-STATUS.md`。
2. `00-project-workflow.md`、`01-project-positioning.md`、`02-roles-and-accounts.md`。
3. 按 `docs/README.md` 的完整或单模块矩阵读取业务文档；完整双端任务必须读取 `03` 全部现行子模块、`04`、`10a`～`10c`。
4. 涉及字段、API、DTO、事件、缓存、数据库或跨端映射时必须读取 `FIELD-REGISTRY.md`。
5. 记录实际读取的完整 Git commit SHA、文件路径和章节；每次交付／复验前重新比较基线。

任何两个正式来源冲突时停止受影响分支并报告，不自行选择。字段注册表只统一字段，不得覆盖业务权限和状态迁移。

## 3. 全局执行原则

- 所有门店业务操作均不设置老板审批或二次审批。
- 只有消费退款、充值退款和免单原因必填；其他原因一律选填。
- 每次成功修改由服务端自动记录操作者、服务端时间、修改前值、修改后值和稳定请求标识。
- 财务是线下真实交易的系统账本，不接外部收银／退款通道；预约与服务状态仍须及时操作。
- 服务端是金额、余额、券、积分、库存、权限、限频、状态迁移和审计的最终判断者；前端隐藏按钮不能代替鉴权。
- 原型可演示页面和状态，但不得用 Mock 成功、静态假数据或 H5 可点击冒充正式功能验收。

## 4. 当前业务防错清单

### 4.1 结算、余额、优惠券与积分

1. 结算成功后锁定最终应收、实收、付款拆分和收款时间。少收从原单新增真实补收；多收或不应收从原单发起消费退款。不得提供“更正收款”或直接覆盖原金额。
2. 取消“修改余额”。已入账充值需要退还时，只能从原充值记录发起部分或全额充值退款，原因必填、无需审批；不得把充值退款做成无关联余额增减。
3. 结算时选择优惠券／活动券，服务端校验门店、顾客、适用项目、有效期、状态和并发占用，计算优惠；只有结算成功后才自动核销并关联原单。不得保留顾客详情手动核销或手动改价替代券计算。
4. V1 积分商城只兑换实物，不兑换优惠券、服务活动或商品活动。
5. 免单必须把最终应收改为0并点击“确认免单”，免单原因必填；0元输入本身不等于结算成功，不生成虚假付款。
6. 消费退款按原付款渠道／原账户退回；钱包退款先退该原单尚未退回的本金组成，再退赠送组成。退款只扣减原订单归属人的业绩一次。

### 4.2 服务、寄养与上门喂养

1. 快速开单完成必填资料与风险提醒后直接开始服务；普通预约到店后仍由员工手动点击开始。
2. 补图和修改普通说明不发送任何通知；除此之外的服务结果错误不得覆盖原事实，必须重新开单。取消或中止后再次服务也必须重新开单。
3. 寄养客户端状态只使用：寄养中／待结算／已完成／已取消。
4. 寄养照护时间轴及客户端动作类型只使用店员端录入的四种值：喂食／遛狗／清扫笼子／其他。每条可选填一句话和照片；代喂药、送医、代接、异常处理等均按店员实际选择的类型展示，选择“其他”时客户端显示“其他”及原说明；照片／视频是附件，不是独立事件类型，寄养加餐仍在时间轴外作为普通商品展示。
5. 寄养继续按北京时间凌晨3点计算过夜晚数；结算时单独核对入住和真实离店时间，真实离店后停止计费。收款或明确免单完成后为已完成。
6. 上门喂养到结束日期自动变“已结束”。附近无正常服务门店时提示“附近暂无服务门店”并结束；定位失败时允许顾客手动选区。
7. 当前负责门店停用时，未完成需求转给按原绑定门店位置计算的最近有效门店，保留原接单人和历史；新店重新确认后可以查看双方完整联系方式。03j§8是上门喂养业务状态唯一来源；10b仅展示映射状态，不得新增“进行中／已完成”等状态，“已结束”不代表实际服务完成。

### 4.3 身份、门店与客户资料

1. 一个已认证手机号只对应一个平台账号；手机号相同识别为同一顾客账号。同店顾客资料冲突时提示人工处理，不自动合并两个既有业务对象。
2. 同一平台账号同一时刻只能属于一家有效经营门店：已经是某店老板或员工时，不能同时成为其他门店老板或员工。
3. V1不提供跨店Customer档案、宠物服务报告／护理历史或商户私有业务数据导入；唯一例外是顾客明确授权后按01§5与03g§12一次性复制选定的宠物基础档案。不得持续同步、转移Customer关系、复制订单／余额／优惠券／内部备注或自动合并；手机号相同不构成授权。
4. 员工可以查看本店顾客完整手机号；营业执照只有本店老板和平台管理员可看。
5. 门店日常经营和老板设置都在店员小程序；网页后台只供平台使用。
6. 历史消费订单缺少业绩归属时默认归本店老板；每单只归属一人，业绩按实际收款减已确认退款计算。

### 4.4 消费争议、食品问题和顾客风险

1. 消费争议、投诉和顾客风险均不提供自助申诉入口、状态或消息；统一提示“如有异议，请联系客服处理”。
2. 顾客风险包含顾客相关和宠物相关事件；宠物相关必须关联具体宠物，可按统一规则跨店查看，不恢复独立“宠物行为与服务安全”菜单。
3. 跨店顾客风险只按已认证手机号匹配；必须经过客服审核、双方门店授权、顾客分项同意、真实业务触发、每查看门店对同顾客每自然月最多3次及逐次审计。顾客端不得显示风险记录存在、数量、状态、摘要、证据或来源。
4. 第三方证据只分高／中／低三档，由审核员人工判断，不做数值权重或自动定责。
5. 未入驻门店被投诉时标记“未入驻”；门店入驻后可以补回应。事实裁决由持有`complaint_review.decide`权限的Platform Super Admin执行，解决确认由持有`complaint_review.resolve`权限的Platform Super Admin执行；不新增客服／审核员系统角色。
6. 同一用户可对同一食品批次再次投诉，但必须提供新证据；集中反馈再次触发时重新计算提示有效期。
7. 食品问题由平台直接联系厂家；门店只收到知悉通知，不参与前置核实、厂家沟通或回信维护。平台录入并审核通过厂家回应即算回应，不设回应期限。
8. 食品问题热度只显示低／中／高三档。建议只给平台看，门店不回应。
9. 投诉公开脱敏内容自首次公开起保留1年；原始视频保留3个月，原始图片及必要的投诉关联身份信息保留1年。账号注销不触发提前删除，也不延长或重置期限；到期下架、删除／匿名化及例外保全按03h§12.1执行。跨店顾客风险仍按03h§10.1独立的12个月展示、3年受限留存规则，不与投诉资料期限混用。
10. 第三方佐证审核／脱敏由持有`evidence.review`权限的Platform Super Admin执行；跨店顾客风险审核由持有`customer_risk.review`权限的Platform Super Admin执行。

### 4.5 页面、广告、通知与积分实物

1. 客户端首页顶部禁止品牌／生活方式 Banner，只保留唯一门店栏；商品区标题为“本店推荐”；消费争议先使用简版卡片。
2. 删除“宠物好友邀请”消息类型。整个小程序通知等级只保留普通通知和重要通知。
3. 启动广告资源总等待最多2秒；自定义图片展示最多3秒并始终可以立即跳过。超时、失败或无填充恢复原目标。
4. 积分实物领取门店停用时自动取消原兑换、退回积分并发送重要通知，不让顾客改选门店。
5. 积分实物出现问题由平台在原兑换单处理，门店没有处理入口。正常已发货记录超过30天未登记领取时仍按03k既定规则默认已领取，不能与门店停用取消混用。

## 5. 状态、权限与并发验收

每个写操作至少覆盖：有权成功、越店／无权拒绝、失效身份、重复请求、并发竞争、旧版本提交、服务端失败不产生半状态、审计完整。待办归门店，谁处理记谁；不做领取、转交或个人锁定。

涉及金额、券、积分、库存、身份换绑、跨店风险、审核和状态终结的实现必须提供服务端测试，不接受仅前端按钮或截图证据。

## 6. 原型与前端安全

- 禁止直接使用 `innerHTML =` 写入动态内容。仓库原型的统一 HTML 写入助手必须清理危险标签、事件属性和 `javascript:` URL；动态文本必须转义。
- 禁止浏览器原生 `alert()`、`confirm()`、`prompt()`；使用应用内可访问弹层。
- 表单使用 `novalidate`，字段错误可见并关联；文本域不可拖拽；按钮防重复提交。
- 交互元素使用语义按钮／链接，提供可见焦点；窄屏、键盘、减少动态效果和中文长文本必须可用。

## 7. 交付证据包

每个批次必须提交：

1. 需求 commit SHA、实际读取文件与章节。
2. 需求条目到页面、API、数据对象、权限、状态、测试的追踪矩阵；客户端沿用03i唯一C-ID。
3. 改动文件清单和未实现／阻塞清单。
4. 格式化、静态检查、单元／集成／端到端、构建命令及原始结果。
5. 真机或真实浏览器证据，覆盖成功、失败、加载、空态、权限、重复提交、窄屏和键盘。
6. 服务端对租户隔离、金额、券、积分、库存、身份和审计的证据。

`passed` 只能用于实际执行通过的用例；`blocked`、`not_run`、`failed` 不得改写为通过。需求审计、H5静态检查和截图均不能代替正式小程序、后端或微信能力验收。
