## 1. 适用范围与授权边界

本文件规定 DeepSeek 或其他实现者如何读需求、提交代码和接受审查，**不新增业务规则，不表示 V1.0 已冻结，也不代替阶段14的最终开发总提示词**。当前阶段唯一读取 [REQUIREMENTS-STATUS.md](../REQUIREMENTS-STATUS.md)。

用户授权本次建立执行标准和启动店员需求分析；这不等于已经选定技术栈、开通生产服务或确认全部店员业务。默认只执行 G0 开工准备。原型授权不能作为正式上线授权。

原型、接口契约准备和真实开发必须分别标明；H5 可点击不等于微信小程序可运行，Mock 回执不等于真实后端。不得直接把既有 H5 的样例字段、固定日期、广告演示、同图前后对比或 sessionStorage 账本搬入生产。

### 执行准备决策（不是业务决策）

| ID | 当前状态 | 需要用户确认的结果 | 阻塞范围 |
|---|---|---|---|
| DEC-EXEC-01 | pending | 先做客户端的具体批次、排除项、代码仓库/分支；是否明确允许冻结前的限定范围开发 | G1及后续代码实现；不阻塞G0或店员需求分析 |
| DEC-EXEC-02 | pending | 小程序技术栈、后端/数据库方案、AppID与环境、接口契约负责人、部署目标 | 对应工程初始化与真实接入；没有凭证不能假称联调完成 |

上述决策唯一在本节维护。业务待决项从阶段状态和正式子模块实时读取，不在此复制另一份完整清单。

## 2. 责任与监督机制

| 主体 | 责任 | 不得越权 |
|---|---|---|
| 用户 / 产品负责人 | 确认需求、范围、业务取舍、费用和最终发布 | 不把“看起来没问题”代替验收证据 |
| DeepSeek / 实现者 | 逐条实现、提供完整源码与可复现测试、报告缺陷、整改 | 不自行批准业务变更，不自签最终通过 |
| 产品监工（本任务助手） | 需求追踪、代码/测试/交互复核、风险判定、整改清单与复验 | 未检查的代码不得宣称已验收；不能保证绝对无缺陷 |

监督按提交批次开展：实现者提交证据包 → 用户提供代码分支/PR和材料 → 监工审查 → 返回阻断项 → 实现者整改 → 同一问题复验关闭。仅有 DeepSeek 的“已完成”说明不能通过。

当前没有建立对 DeepSeek 会话或私有开发环境的自动连接，也没有后台持续监控任务。没有代码访问权限时只能审查已提供材料，并标明证据限制；后续自动监控需另行明确仓库、分支和触发方式。不得暗示监工已经检查尚未生成的代码。

## 3. 开工读取与基线锁定

1. 读取根 [AGENTS.md](../../AGENTS.md)、[阅读指南](../README.md)、[阶段状态](../REQUIREMENTS-STATUS.md)、00/01/02。
2. 完整客户端任务使用阅读指南§3.1全量清单；单模块按§3.2且补齐依赖。正式实现也使用这套读取矩阵，不因“不是H5”跳过文档。
3. 逐文件检查 `status`、`status_scope` 或 `confirmed_scope/pending_scope`、`development_readiness`、`blocked_by`。字段缺失或冲突先报告。
4. 记录实际读取的完整 Git commit SHA、文件路径和章节；不能只记录“main最新”。每轮开工、交付、复验前比较需求与代码基线差异。
5. 需求发生变化，列出受影响页面/API/数据库/权限/测试，不静默套用旧方案。已有代码和未提交改动先识别、保留。
6. `docs/history/` 不参与当前规则推导；讨论稿只供提问，不作为实现依据。

## 4. 需求追踪与防遗漏

客户端验收 ID 的唯一语义来源为 [03i §14.1](../03i-customer-screen-blueprint.md#141-唯一验收-id-索引)。交付记录见 [customer-delivery-tracker.md](customer-delivery-tracker.md)，它只追踪证据，不重新定义 ID 含义。

实现者必须把本批次正式文档各条要求映射到：原文章节 → 页面 → API → 数据对象/唯一归属 → 操作者权限 → 状态迁移 → 测试用例 → 实际证据。03i的ID索引不是完整业务规则替代品；详细模块中没有独立ID的要求也必须映射章节并拆测试子项。旧 C-SOCIAL-* 已随宠物交友退役，不得把新投诉业务复用到旧ID；当前以 C-RISK / C-COMPLAINT / C-FOOD-RISK 为准。

不能改旧ID含义、复制表格后删难项或把多个子场景一次写成通过。`blocked`、`not_run` 和 `failed` 不能记成 `passed`；阻塞场景保持在分母中，另报“本批次通过/总基线未完成”，不声称全量完成。

## 5. 必须拦截的错误实现

本表是复核索引；业务细节和允许例外只读来源。未来源规则变更时同步复核，不能把此处摘要当第二份业务权威。

| 风险检查 | 必须证明的事实 | 权威来源 |
|---|---|---|
| 租户与本人范围 | 修改请求中的merchant/store/customer/pet/order ID仍不能跨租户或访问他人；列表/详情/导出/媒体/后台任务同样校验 | 01、02、03g |
| 唯一归属 | User与Customer分离；staff.merchant_id与staff_store_assignment.store_id分离；各业务对象明确唯一所有者及仅关联字段 | 01、02、各子模块 |
| 客户资金越权 | 客户不能确认付款、充值或改余额；金额、积分、库存、优惠券、权限均由服务端决定 | 01、03c、03d、03e、03k |
| 账务与库存重复 | 重试/重复点击/回调不二次扣款、扣分、出库、核销或记收入；失败可审计恢复 | 03c、03e、03k、03m |
| 预约偷偷定规则 | 预约不是订单；不能把03a§11的推荐容量模型当已确认；依赖该模型的接口保持阻塞 | 03a、REQUIREMENTS-STATUS |
| 投喂重复业务 | 复用商品请求，区分source_channel与business_scenario；收款不是实际投喂，实际确认只写一次动态 | 03e§17、03d§4.3 |
| 服务结果造假 | N组真实素材、缺图真实提示；普通结果先可看，AI资格和任务独立；时间轴按发生时间 | 03、03i、03m |
| 投诉/风险与喂养隐私 | 投诉未核验不得伪装成立；7天逾期不自动定责；3条独立投诉是集中反馈硬门槛；跨店顾客主观人格标签禁止共享；喂养首个有效接单原子锁定，publisher_store_id不随切店改变 | 03h、03j |
| 积分与履约 | 服务端自然周约束、漏签规则、独立奖励库存；取消与自提期限不补默认值 | 03k |
| 总仓权限扩大 | 只有同时持有reward_fulfillment.manage的Platform Super Admin可执行总仓发货；Merchant Owner/Staff不得取得该权限，也不借此解锁取消/退积分 | 02§2、03k§8 |
| 顾问资格绕过 | owner_type=store、owner_id=store_id；门店资格与Platform User额度分别校验，切店/直接API/广告入口不能绕过 | 03l、03m |
| 广告混用 | 激励、底部曝光、启动广告分别配置；可信验证/权益幂等；失败恢复原业务目标；测试与生产隔离 | 03m、03o、03p、10c |
| 历史或离职记录被破坏 | 不删除交易/余额历史；停用员工使会话失效但保留历史操作者；纠错留痕 | 01、02、03c、03d |
| 视觉遮挡和误触 | 页面地图、导航、字号、对比、拖动替代、短屏首操作、安全区、草稿恢复按规范逐项实测 | 03i、10a、10b、10c |

## 6. 分阶段放行标准

每个关卡报告 `gate_result: passed | failed | blocked | not_reviewed`。实现者只能填写自测结果；监工结论和用户放行记录分别保留。没有记录默认未放行。

| 关卡 | 实现者交付 | 通过条件 | 不能通过的典型情况 |
|---|---|---|---|
| G0 读取与拆解 | SHA/阅读清单、冲突/待决清单、全量覆盖表、批次方案、架构选项与理由 | 无遗漏误读；DEC-EXEC-01/02被明确处理；用户确认本批范围和技术方案 | 未读取仓库就写页面；以H5为规格；擅自选付费服务 |
| G1 契约与基础 | 已批准方案、API/数据所有权/权限/状态契约、测试环境、迁移与安全设计 | 契约与批准范围一致；凭证不进代码；基础构建可复现 | “前端做好再补后端权限”；新权限默认全开 |
| G2 纵向小批次 | 一个有闭环的客户功能及必要后端、单元/集成测试、可运行小程序 | 成功/失败/无权限/重复/恢复均有结果；未依赖未决规则 | 只有页面、假接口、截图或TODO |
| G3 跨端与高风险 | 门店操作到客户端的真实联动、并发/幂等/账务/故障恢复证据 | 联动依赖已确认；数据库与API结果一致；风险用例逐项通过 | 店员端未确认却硬写状态；UI成功但账本失败 |
| G4 微信真机与完整回归 | 开发者工具编译、iOS/Android微信真机记录、广告/身份真实测试、全部适用ID | 对批准交付范围无漏测；Mock不可进入生产；明确尚未闭合全项目范围 | 浏览器H5通过即称小程序验收通过 |
| G5 发布评审 | 精确发布SHA/包、配置清单、备份/回滚/告警/隐私配置、风险清单 | 全部发布阻断关闭；监工完成复验；用户明确批准该版本发布 | 自动发布、把未验证风险隐藏成“后续优化” |

上述是关卡依赖顺序，不是擅自确定开发排期。G0提出批次后由用户确定；每批先复验其依赖，不要求把尚未确认的其他端硬做出来。限定范围通过不代表全平台通过。

## 7. 工程执行底线

- 技术栈与目录布局先提案再获准；选微信原生、跨端框架或云开发均需说明真实小程序支持、后端隔离、部署和维护代价。不把DeepSeek模型当运行框架。
- 开发分支隔离；非本批变更不提交；不覆盖用户代码，不强推，不静默合并或上线。业务需求改动必须先获用户确认并更新正式文档/历史。
- API契约明确身份、资源归属、输入校验、可操作状态、错误码、幂等键、重试/查询路径、审计事件。错误码和实现算法须技术设计确认，不能假称已有API。
- 服务端对资金/库存/积分等做一致性保护；具体事务、队列或补偿选型进入技术方案，不用前端按钮防重代替。
- 未知提交结果先查原请求，不能盲目重发；旧请求和切店过期响应不能覆盖当前数据；状态冲突返回当前有效结果。
- 安全输入、上传类型/大小与访问控制、媒体签名、日志脱敏、依赖与密钥检查纳入测试。生产个人数据不得放进AI提示词、公开仓库或测试夹具。
- 无真实凭证时可做明确标识且隔离的测试替身，但对应真机/真实接入仍为blocked；用户提供凭证走安全环境配置，不贴进聊天/提交记录。
- 禁止删测试、降低断言、注释功能来换绿灯。失败记录、根因、修改范围及回归结果必须保留。

## 8. 每批证据包（固定普通 Markdown 字段）

在实现代码仓库的 `delivery/<batch_id>/report.md` 提交下列字段；这是约定输出路径，不表示本需求仓库已经存在交付物。

```text
batch_id: <稳定批次编号>
execution_mode: preparation | prototype | production_implementation
requirements_repo: <URL>
requirements_sha: <完整SHA>
code_repo: <URL或明确的本地交付路径>
code_branch: <实际分支>
code_sha: <完整SHA；未有代码写not_created>
approved_scope_ref: <用户批准记录位置；缺失写missing>
gate: G0 | G1 | G2 | G3 | G4 | G5
self_test_result: passed | failed | blocked | not_run
review_result: not_reviewed
release_approval: not_requested
implemented_refs: [<正式章节及C-ID>]
blocked_by: [<实际决策ID；无阻塞用[]>]
mock_dependencies: [<仍为模拟的接入；无则[]>]
known_issues: [<问题ID；无则[]>]
```

随后附：变更文件表、需求到代码与测试映射、执行命令/退出码/运行时间/环境与实际输出、真机型号/微信与基础库版本、截图或视频、脱敏API与账本结果、迁移与回滚说明。写“测试通过”但没有命令/结果，视为 `not_run`。

测试结果严格绑定code_sha；整改后新SHA要重跑受影响测试。用户确认后才能记录相应授权引用，不允许自造批准记录。

### 缺陷与复验记录

```text
issue_id: <唯一问题编号>
severity: P0 | P1 | P2
status: open | in_progress | awaiting_review | closed
source_ref: <需求章节/测试ID>
reproduction: <账号角色、门店、数据前置、动作>
expected: <引用规则>
actual: <实际观察>
evidence: <脱敏证据位置>
fix_sha: <整改SHA或not_fixed>
retest_result: not_run | passed | failed | blocked
reviewer: <实际审查人或not_assigned>
```

P0：越权、数据泄露、账务/权益损坏、破坏历史；立即阻止有关操作与发布并评估影响。P1：核心流程错误、已确认需求遗漏、恢复失败；相关批次不得通过。P2：非阻断体验/文案问题，必须列明，是否允许带缺陷发布由用户决定。任何严重度都不能未经复验自行关闭。

## 9. 验收的最低证据范围

代码检查、构建、单元、API集成、数据库一致性、小程序端到端、真机交互、权限负向、并发与故障恢复分开报告。只做其中一层不能声称其他层已通过。

高风险测试至少覆盖：两个商户/多个用户越权、员工停用后旧会话、篡改金额/对象ID、同一请求并发/重放、最后一份库存、广告重复及伪造回调、收款后未投喂、投喂补偿不二次执行、积分扣除部分失败、跨店权益校验、通知失败不回滚主业务。涉及尚未确认的取消/过期/容量子场景只登记阻塞，不编造期望值。

客户端视觉与交互按10a/10b/10c的支持矩阵验收，包括320/375/430宽度、100/150/200%字号、长内容、虚拟键盘、安全区、慢网、空/无结果/失败、后台恢复、可访问名称与非拖动替代。若正式源范围更新，以新批准基线为准。

## 10. 停止与升级条件

以下任一成立，停止受影响动作并报告，不必阻塞无依赖的准备工作：已确认文档冲突；状态范围不明；未决决定权限/金额/时限；接口/技术栈未批准；缺账号或真机条件；发现越权/账务错误；代码基线改变；需要新付费服务、生产迁移、不可恢复删除、权限扩张或发布。

报告必须包含：阻塞事实、来源、影响范围、可安全继续部分、建议选项与代价、需要用户作出的最小决定。不得把阻塞包装成完成。
