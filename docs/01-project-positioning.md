# 01 项目定位

> 状态：已确认
> 版本：V1.0

## 1. 产品定位

本项目是一套面向社区型、小型宠物店的免费多商户 SaaS 经营管理平台。

核心目标：

- 降低小型宠物店使用数字化系统的成本。
- 提高员工操作透明度与经营审计能力。
- 改善寄养流程管理。
- 提升客户复购。
- 提升洗护 / 美容报告的专业度与服务透明度。
- 降低商户从其他宠物店管理系统迁移历史数据的成本。

系统由以下部分组成：

1. 客户端微信小程序
2. 店长 / 员工端微信小程序
3. Web 管理后台
4. 统一后端 API
5. 统一数据库
6. 多商户数据隔离体系

V1.0 不以宠物医疗业务为核心，但架构应避免阻碍未来扩展。

## 2. 商业模式

软件计划免费提供给其他宠物店使用，因此从 V1.0 起按多租户 SaaS 架构设计。

平台方拥有跨商户管理能力；普通商户不得访问其他商户数据。

## 3. 商户与门店模型

正式采用简化模型：

Platform
→ Merchant / Tenant（商户）
→ Store（门店）

V1.0 强制规则：

- 一个 Merchant 只对应一家 Store。
- 一个商户老板只管理自己这一家门店。
- 不支持一个老板拥有多家门店。
- 不支持一个员工同时属于多家门店。
- 平台超级管理员可以查看全部商户、全部门店及平台级数据。
- 商户老板只能查看和管理自己门店的数据。
- 不同商户之间严格数据隔离。

平台整体仍然是“多门店系统”，因为平台可以同时承载大量彼此独立的宠物店，但单个商户内部不设计连锁多店结构。

## 4. 平台用户与商户客户身份

系统必须区分：

- 平台用户 User：用于微信登录、手机号等平台级身份识别。
- 商户客户 Customer：用户与某个 Merchant 建立的经营关系。

同一个平台 User 可以同时成为多个不同商户的 Customer，但每个商户只能查看自己与该客户之间的业务数据。

不同商户之间不得共享或查看以下信息：

- 订单
- 消费金额
- 会员余额
- 优惠券
- 商户内部备注
- 员工评价
- 经营分析标签

## 5. 宠物档案

宠物基础身份与客户关联，但商户业务记录相互隔离。

支持客户主动授权将宠物基础档案迁移 / 同步给新的商户，可包含：

- 宠物名称
- 头像
- 类型
- 品种
- 性别
- 出生日期 / 年龄
- 体重
- 是否绝育
- 性格
- 基础健康提示
- 过敏等由客户维护的基础资料

默认不得跨商户迁移：

- 历史消费记录
- 会员余额
- 优惠券
- 商户内部备注
- 员工评价
- 经营分析标签

## 6. 客户端微信小程序定位

客户端核心定位：

“服务过程透明 + 客户资料与资产查询 + 业务意向提交”。

客户端不承担真实线上支付，也不提供会员充值入口。

主要方向：

- 查看洗护状态
- 查看美容状态
- 查看寄养状态
- 查看洗护 / 美容服务报告
- 查看寄养过程记录
- 查看宠物档案
- 查看消费记录
- 查看会员余额
- 查看优惠券
- 邀请码兑换优惠券
- 浏览商品
- 提交商品购买需求
- 查看业务 / 订单处理状态
- 接收门店服务通知
- 在线预约洗护、美容、寄养等服务

客户端可以发起预约和商品购买需求等业务请求，但不能自行把任何交易标记为“已支付 / 已收款”，也不能直接增加或扣减会员余额。

## 7. 商品业务原则

V1.0 采用门店自提 / 到店购买，不做快递电商。

基本流程：

客户选择商品
→ 提交购买需求
→ 店员端收到待处理记录
→ 店员确认商品、数量和应收金额
→ 店员可在结算前进行人工调价
→ 顾客线下完成付款
→ 有权限店员确认已收款及支付方式
→ 形成正式交易记录
→ 扣减库存
→ 计入营业额
→ 客户端显示成交结果

### 人工修改总价

店员侧必须支持在“确认已收款”之前修改订单最终应收总价。

系统不得直接覆盖原始计算金额，必须同时保留：

- 商品 / 服务明细原价
- 系统自动计算原始应收金额
- 优惠券 / 会员等自动优惠金额
- 人工调价金额
- 最终应收金额
- 调价原因
- 调价操作人
- 调价时间
- 可选备注

人工调价必须进入订单变更记录和操作日志，不得无痕修改。

确认已收款后订单金额锁定；如发生错误，必须通过撤销、冲正、退款或补收流程纠正，禁止直接修改已结算历史金额。

具体调价权限、幅度上限和审批规则在后续权限体系与核心业务规则阶段确定。

## 8. 会员充值原则

客户端不提供充值入口，也不允许客户发起充值申请。

会员充值完全由门店侧发起：

店员选择客户
→ 选择商户老板预先配置的充值套餐
→ 客户线下付款
→ 有权限店员选择实际支付方式并确认已收款
→ 系统生成充值流水
→ 增加会员余额
→ 自动发放套餐中配置的赠送余额 / 优惠券
→ 客户端显示最新余额与相关记录

充值套餐、赠送余额、赠送优惠券等具体规则以已确认会员子模块为准。

## 9. 会员余额人工调整

禁止直接覆盖余额数字。

任何人工调整必须以独立余额流水方式记录，至少包含：

- 调整前余额
- 调整金额
- 调整后余额
- 调整原因
- 操作人
- 操作时间
- 关联客户
- 可选备注 / 凭证

历史余额流水原则上不得删除或覆盖。错误操作通过反向冲正处理。

## 10. 店员端定位

店员端是实际经营操作中心，当前核心方向包括：

- 销售额统计
- 接单 / 订单处理
- 客户管理
- 宠物管理
- 洗护管理
- 美容管理
- 寄养管理
- 收银确认
- 人工调价
- 商品销售
- 库存管理
- 员工业绩
- 员工提成
- 会员管理
- 会员余额调整
- 优惠券
- 财务对账
- 操作日志
- 服务状态更新
- 洗护 / 美容专业报告填写
- 客户通知
- 预约处理
- 退款 / 撤销 / 冲正
- 订单改单
- 必要时的客户欠款 / 挂账能力
- 日结 / 交接班

商户老板默认拥有店员端的全部权限。

## 11. Web 管理后台定位

Web 后台按照登录身份展示不同范围的数据。

平台超级管理员可：

- 查看全部商户
- 查看全部门店
- 管理商户账号和状态
- 查看平台级运营数据
- 管理平台配置
- 处理异常商户 / 数据问题
- 查看关键审计日志
- 管理平台资源与使用限制

商户老板可：

- 管理自己门店
- 查看和管理本门店的订单、客户、宠物、员工、库存、会员、财务和统计数据
- 导入历史订单
- 管理店员权限

普通商户不得访问其他商户数据。

## 12. 历史订单导入

系统支持从其他宠物店管理平台导入历史订单。

最低必需字段：

- 历史订单号
- 消费时间
- 客户手机号
- 消费金额

可选字段可包括客户姓名 / 昵称、宠物名称、服务项目、商品信息、原支付方式、来源系统名称、备注等。

每次导入必须建立导入批次，并记录导入人、导入时间、来源平台、原文件名、成功条数、失败条数、重复条数和错误原因。

历史导入订单与本系统原生订单必须明确区分。

历史订单默认可以参与：

- 客户累计消费
- 消费频次
- 最近消费时间
- 复购分析
- 客户价值分析

历史订单默认不得直接影响：

- 当前库存
- 今日 / 当期营业额
- 当前现金流
- 员工提成
- 当前会员余额
- 当期财务对账

会员余额等资产迁移必须通过独立初始化 / 迁移流程完成。

## 13. 洗护 / 美容专业化方向

洗护 / 美容不能只使用“待服务 / 服务中 / 已完成”三个简单状态。

需要支持更细的服务过程，例如：

已接宠
→ 服务前检查
→ 基础护理
→ 洗澡
→ 吹干
→ 梳理
→ 修剪 / 美容
→ 服务后检查
→ 服务完成
→ 等待接宠
→ 已接走

服务过程应支持服务前后照片、皮肤、耳道、牙齿、指甲、毛发 / 打结、异常情况、员工备注、服务员工和服务时长等记录，并最终形成客户可查看的结构化服务报告。

## 14. 寄养方向

寄养模块作为独立核心业务设计，需覆盖入住、离店、位置管理、喂食、饮水、排便、遛宠、特殊照护、图片 / 视频、异常事件、客户通知、延住、提前离店、费用调整和交接记录等场景。

## 15. 其他已确认方向

V1.0 需求设计必须考虑：

- 在线预约但不在线支付
- 微信业务通知
- 退款、撤销、冲正
- 服务中途改单 / 加项
- 客户欠款 / 挂账场景
- 员工权限分级
- 日结 / 交接班
- 异常操作审计
- 商户数据导出
- 商户停用 / 注销的数据处理
- 图片压缩和资源管理
- 防刷 / 滥用限制
- 免费 SaaS 的单商户资源配额或合理使用策略

## 16. 产品核心差异化

本项目不定位为单纯的宠物店收银软件。

核心定位为：

> 面向社区宠物店的免费 SaaS 经营系统，以服务过程透明、宠物服务报告、会员经营、寄养管理、数据迁移和经营审计为核心。
