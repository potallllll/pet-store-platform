# 01 项目定位

> 状态：讨论中
> 版本：V1.0 Draft
> 本文记录当前讨论结论与待确认事项，不代表需求冻结。

## 1. 产品定位

本项目是一套面向社区型、小型宠物店的免费多商户 SaaS 经营管理平台，核心目标是降低小型宠物店使用数字化经营系统的门槛，并提高门店经营透明度、寄养管理能力、客户复购能力和洗护/美容服务专业度。

系统由以下部分组成：

1. 客户端微信小程序
2. 店长 / 员工端微信小程序
3. Web 管理后台
4. 统一后端 API
5. 统一数据库与多租户权限体系

## 2. 目标商家

主要服务：

- 社区型宠物店
- 小型单店宠物店
- 同一老板经营的多门店宠物店
- 小型连锁宠物门店

V1.0 暂不将宠物医院等医疗业务作为核心场景，但技术架构不应阻碍未来扩展。

## 3. 平台商业模式

产品计划作为免费软件提供给其他宠物店使用。

因此系统必须从第一版即按照多商户 SaaS 模型建设，而不能按“仅自家门店使用”的单租户系统实现。

平台方拥有跨商户管理能力；普通商户不得访问其他商户数据。

## 4. 建议的数据隔离模型

建议使用“商户 Tenant / Merchant”为最高业务隔离边界，而不是直接以单个 Store 为最高边界。

结构建议：

平台 Platform
→ 商户 Merchant / Tenant
→ 门店 Store
→ 店长 / 员工 / 客户业务关系

规则建议：

- 平台超级管理员可查看所有商户和全部门店数据。
- 商户老板只能查看自己 Merchant 下的数据。
- 一个 Merchant 可以拥有一个或多个 Store。
- 店长 / 员工只可访问被授权的 Store。
- 不同 Merchant 之间严格数据隔离。
- 同一 Merchant 下是否允许跨门店客户、会员、余额、积分、优惠券共享，后续作为业务规则单独确认。

注：用户原始描述为“不同门店之间数据完全隔离”，但该规则与“多门店老板统一查看自己数据”存在潜在冲突，因此当前暂按待确认处理。

## 5. 客户端微信小程序定位

客户端主要用于“服务过程透明 + 客户信息查询 + 业务意向提交”，不承担在线支付。

当前功能方向：

- 查看洗护状态
- 查看美容状态
- 查看寄养状态
- 查看洗护 / 美容服务报告
- 查看寄养过程记录
- 查看宠物档案
- 查看历史消费记录
- 查看会员余额、积分、优惠券等资产
- 商品浏览与购买意向提交
- 会员充值申请 / 充值意向提交
- 查看订单 / 消费状态
- 接收门店服务通知

### 支付原则

客户端 V1.0 不直接进行微信支付、余额支付或其他真实资金扣款。

对于“购买商品”“会员充值”等涉及金额的操作，建议采用：

客户提交请求
→ 门店端收到待处理记录
→ 线下完成付款
→ 店长 / 有权限员工选择支付方式并确认“已收款”
→ 系统形成正式交易记录
→ 客户端显示结果

任何客户端提交的“已付款”状态都不能直接作为财务入账依据。

## 6. 店长 / 员工端定位

店端是实际经营操作中心。

当前核心功能方向：

- 销售额统计
- 接单 / 订单处理
- 客户管理
- 宠物管理
- 洗护管理
- 美容管理
- 寄养管理
- 收银确认
- 商品销售
- 库存管理
- 员工业绩
- 员工提成
- 会员管理
- 会员余额调整
- 优惠券
- 积分
- 财务对账
- 操作日志
- 服务状态更新
- 洗护 / 美容专业报告填写
- 客户通知

## 7. Web 管理后台定位

Web 后台根据账号和权限呈现不同管理范围。

### 平台方

平台管理员可：

- 查看全部商户
- 查看全部门店
- 管理商户账号
- 管理系统配置
- 查看平台级运营数据
- 处理异常商户 / 数据问题
- 查看关键操作审计日志

### 商户老板

商户老板可登录 Web 后台查看和管理自己授权范围内的数据，包括经营、订单、客户、宠物、员工、库存、会员、财务、统计等。

普通商户不得访问其他商户数据。

## 8. 历史数据迁移

系统需要支持从其他宠物店管理平台导入历史订单，降低商户切换系统的成本。

最低历史字段：

- 历史订单号
- 消费时间
- 客户手机号
- 消费金额

建议同时支持可选字段：

- 客户姓名 / 昵称
- 宠物名称
- 服务项目
- 商品信息
- 原支付方式
- 原门店
- 原系统名称
- 备注

历史数据必须通过“导入批次”管理，并记录：

- 导入人
- 导入时间
- 来源平台
- 原文件名
- 成功条数
- 失败条数
- 重复条数
- 错误原因

默认建议：历史订单导入只用于客户历史、消费统计和复购分析，不自动影响当前会员余额、库存、积分、员工提成和当期财务；如未来需要迁移这些资产，应使用独立迁移流程。

## 9. 核心问题

本项目重点解决：

1. 市面宠物店 SaaS 软件收费，社区小店使用成本较高。
2. 员工操作过程不透明，关键经营数据缺少审计能力。
3. 寄养流程和过程记录混乱。
4. 客户复购率低，缺少持续运营工具。
5. 洗护 / 美容报告简单，专业感不足。
6. 老系统迁移困难，商户存在历史数据绑定问题。

## 10. 财务与会员能力

V1.0 需要涉及：

- 会员储值
- 会员余额手动调整
- 优惠券
- 积分
- 员工提成
- 财务对账

建议所有“余额调整”采用不可删除流水账模型：

余额变化 = 一条独立交易流水，而不是直接修改余额数字。

每次人工调整至少记录：

- 调整前余额
- 调整金额
- 调整后余额
- 调整原因
- 操作人
- 操作门店
- 操作时间
- 关联客户
- 可选审批 / 备注 / 凭证

历史余额流水原则上不得删除或覆盖，只能通过反向冲正方式纠错。

## 11. 免费 SaaS 必须额外考虑的系统能力

由于软件将免费开放给外部门店使用，V1.0 架构必须考虑：

- 商户注册 / 开通 / 停用
- 数据租户隔离
- 商户与门店生命周期
- 用户隐私与手机号保护
- 数据导出
- 账号注销 / 商户停用后的数据处理
- 操作审计
- 数据备份
- 文件存储配额
- 防滥用与接口限流
- 系统异常监控
- 导入文件安全校验

具体实现规则将在后续技术架构和权限阶段确认。

## 12. 当前发现的逻辑冲突 / 待确认项

### A. 客户端购买商品但不能支付

建议解释为“客户提交购买请求，店端确认线下收款后完成订单”，而不是客户端直接完成电商支付。

### B. 客户端充值会员但不能支付

建议解释为“客户提交充值申请 / 店员发起充值，线下付款后由有权限人员确认充值到账”。不能由客户点击按钮直接增加会员余额。

### C. 不同门店完全隔离 vs 多门店老板管理

需要明确隔离边界。建议严格隔离不同 Merchant；同一 Merchant 下的多门店由老板统一管理，但客户、余额、积分等是否跨店共享需要另外确认。

### D. 老板可以手动调整会员余额 vs 员工操作透明

如果允许直接覆盖余额，会破坏财务审计。建议禁止直接改余额字段，所有调整必须生成不可删除流水，并保留原因和操作人。

### E. 历史订单导入 vs 当前财务真实性

历史导入记录不能默认进入当前库存、当前现金流、员工提成、积分或会员余额，否则容易造成账目污染。建议历史迁移与实时业务账严格区分。
