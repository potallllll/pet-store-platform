## 1. 产品定位

本项目是一套面向社区型、小型宠物店的免费多商户 SaaS 经营管理平台。

日常经营以老板加少量店员的社区小店为设计重点，典型“老板＋一名店员”不构成员工人数上限。优先少配置、人工快速处理；洗护／美容预约采用期望时间申请及门店人工确认，不使用固定预约间隔或时段硬名额，详见03a与04§3.0.7。

财务定位是线下真实交易的账本，不接入收银系统或第三方收款／退款接口；老板／有效员工可即时或工作结束后记账，系统自动更新会员余额、资金流水和适用库存，详见03d§1.1。预约确认、接宠检查和服务状态仍在营业时及时操作；“可晚记财务”不是整个系统只作事后补录，也不能绕过商品成交记账与库存规则；加餐商品按普通销售，真实照护另记且不要求先收款。

核心目标：

- 降低小型宠物店使用数字化系统的成本。
- 提高员工操作透明度与经营审计能力。
- 改善寄养流程管理。
- 提升客户复购。
- 提升洗护 / 美容报告的专业度与服务透明度。
- 降低商户从其他宠物店管理系统迁移历史数据的成本。

系统由以下部分组成：

1. 客户端微信小程序
2. 店员端微信小程序（商户老板也可使用，并默认拥有全部店员权限）
3. Web 管理后台
4. 统一后端 API
5. 统一数据库
6. 多商户数据隔离体系

V1.0 不以宠物医疗业务为核心，但架构应避免阻碍未来扩展。

## 2. 商业模式

基础经营软件免费提供给宠物店，并提供可选Store级付费权益，例如已确认的养宠顾问；因此按多租户SaaS和独立权益边界设计。商品入库／AI拍照入库当前按普通功能，不校验会员；AI拍照入库的平台门店会员验证后置，价格套餐额度和购买续费后期确认，不作为本阶段入库前置，也不影响顾问原付费规则。

平台方拥有跨商户管理能力；普通商户不直接访问其他商户私有数据。03g§5.5允许顾客本人明确授权，将限定档案与顾客可见服务护理历史导入当前门店，资金／内部备注仍隔离。

## 3. 商户与门店模型

正式采用简化模型：

Platform
→ Merchant / Tenant（商户）
→ Store（门店）

V1.0 强制规则：

- 一个 Merchant 只对应一家 Store。
- 一个商户老板只管理自己这一家门店。
- 不支持一个老板拥有多家门店。
- 不支持一个员工同时属于多家门店。
- 平台超级管理员可以查看全部商户、全部门店及平台级数据。
- 商户老板只能查看和管理自己门店的数据。
- 不同商户之间严格数据隔离。

平台整体仍然是“多门店系统”，因为平台可以同时承载大量彼此独立的宠物店，但单个商户内部不设计连锁多店结构。

## 4. 平台用户与商户客户身份

系统必须区分：

- 平台用户 User：用于微信登录、手机号等平台级身份识别。
- 商户客户 Customer：某个 Merchant 为真实顾客建立的客户业务记录／关系；可由门店在线下先建，在安全绑定前可以没有关联的Platform User。

一个Platform User可以在多个Merchant下分别关联经安全确认的Customer记录；同一Customer至多绑定一个当前有效Platform User。Customer不等于登录账号，未绑定User的线下Customer仍可承载该门店的宠物、服务、充值和消费记录。每个商户只能查看自身Customer关系下的私有业务数据；顾客本人确认的一键档案／服务护理历史导入按03g§5.5，客观风险共享另按03h独立规则，不合并资金及订单金额。一个已认证手机号只对应一个平台登录账号，店员身份只是该账号的有效经营关系，不因切店／角色重复注册同号账号。

不同商户之间不得共享或查看以下信息：

- 订单
- 消费金额
- 会员余额
- 优惠券
- 商户内部备注
- 员工评价
- 经营分析标签

## 5. 宠物档案

宠物基础身份与客户关联，但商户业务记录相互隔离。

支持客户主动授权将宠物基础档案迁移 / 同步给新的商户，可包含：

- 宠物名称
- 头像
- 类型
- 品种
- 性别
- 出生日期 / 年龄
- 体重
- 是否绝育
- 性格
- 基础护理 / 健康提示
- 过敏等由客户维护的基础资料

默认不得跨商户迁移：

- 历史消费记录
- 会员余额
- 优惠券
- 商户内部备注
- 员工评价
- 经营分析标签

原宠物交友功能已退役。顾客明确授权的普通档案／服务护理历史导入按03g§5.5；独立的宠物跨商户风险共享采用“行为与服务安全档案”方向：门店自由文本内部备注继续按 Merchant 隔离；跨店只考虑结构化、与服务安全直接相关且经平台审核的行为信息，具体授权与可见范围见 `03h-customer-risk-feedback.md`。

## 6. 客户端微信小程序定位

客户端核心定位：

“服务过程透明 + 客户资料与资产查询 + 业务意向提交”。

客户端不承担真实线上支付，也不提供会员充值入口。V1.0 包含 Platform User 级平台积分、广告签到和积分商城，详细规则见 `03k-customer-loyalty-points.md`；平台积分与 Merchant Customer 的钱包、本金、赠送余额和商户优惠券账本分离。

主要方向：

- 查看洗护状态
- 查看美容状态
- 查看寄养状态
- 查看洗护 / 美容服务报告
- 查看寄养过程记录
- 查看宠物档案
- 查看消费记录
- 在“我的”页面直接查看当前可用余额
- 通过“我的钱包”查看余额明细和优惠券
- 使用本店邀请码兑换优惠券，或直接兑换本店服务／商品活动；按03c§9.3先领取活动券、到店由门店手动核销并保留原单关联，所有优惠券及活动在顾客详情可直接核销／删除、不先开单选订单，无日常误点撤销；仅整单取消／全额退款可退回原券、原有效期不变并留操作记录。优惠均在订单结算手动改价，不自动推荐计算或随结算核销，每码只含一个内容且数量1、系统生成码；老板管理／创建邀请码仅老板创建，结果页显示码／内容／兑换截止并支持复制分享；老板可直接经微信把码发给员工，不设置员工小程序未使用码查看／复制分享入口，员工顾客持有券操作能力不变。领取所得权益（含邀请码券）初始有效期一个月，履约剩余边界按该节待确认
- 通过独立积分入口进行广告签到、积分兑换和积分明细查询
- 浏览商品
- 提交商品购买需求
- 查看业务 / 订单处理状态
- 接收门店服务通知
- 在线预约洗护、美容、寄养等服务
- 浏览附近宠物门店 / 宠物食品风险反馈并提交投诉

客户端可以发起预约、商品购买需求、门店 / 食品投诉等业务请求，但不能自行把任何交易标记为“已支付 / 已收款”，也不能直接增加或扣减会员余额。

消费风险反馈 V1.0 采用“用户主张 + 商家回应 + 平台核验”模型。基础内容审核通过后可以公开用户反馈，但平台裁决前不得把用户陈述写成已证实事实；详细规则见 `03h-customer-risk-feedback.md`。

## 7. 商品业务原则

门店商品管理六项按03e§15／04§3.0.18确认：老板员工在业务／商品处理／商品管理维护商品SKU，最少名称分类售价初始库存、图片条码成本介绍选填；每商品固定只有一个规格、差异容量口味分开建商品、改售价不回写旧单，补货盘点留前后数量人时间／预占不覆盖，有销售库存历史不物理删除。入库按03e§15.1／04§3.0.19分“商品入库”和“AI拍照入库”，前者手填、后者识别填原入库表单，不设独立核对页，店员点击“一键入库”生效，共用原SKU库存一次确认，不自动记消费／供应商付款或改售价成本；当前无会员前置，后期仅AI路径接会员入口及后端验证，既有基础权限和防重不放松。 入库错误由本店老板／有效员工在库存管理沿原库存调整自行修改，原入库保留、调整前后值人时间留存，不新增原单作废撤销流程；详见03e§15.1.5。

V1.0 采用门店自提 / 到店购买，不做快递电商。

基本流程：

客户选择商品
→ 提交购买需求
→ 店员端收到待处理记录
→ 店员确认商品、数量和应收金额
→ 店员可在结算前进行人工调价
→ 顾客线下完成付款
→ 有权限店员确认已收款及支付方式
→ 形成正式交易记录
→ 扣减库存
→ 计入营业额
→ 客户端显示成交结果

上述为有实际收款的成交分支；最终应收为0时，必须由门店明确“确认免单”，实收与收入为0，不伪造支付；商品仍按真实交易一次出库，详见03d§10.1、03e。

### 人工修改总价

门店侧必须支持在结算完成（实际收款或零元免单确认）前修改本单最终应收总额，由系统计算调价差额，暂不增加逐项分摊算法。

所有到店服务／商品消费订单均适用，包括洗护、美容、护理、商品及原寄养到店消费结算：老板及有效在职员工可整单调价，不设业务金额／比例上限，不要求老板逐单审批；必须先展示调前／调后金额并确认、选择原因并留痕。参考价／SKU售价不锁定成交价，本单改价不回写主资料或其他订单；顾客不能在客户端改价。

系统不得直接覆盖原始计算金额，必须同时保留：

- 商品 / 服务明细原价
- 系统自动计算原始应收金额
- 人工调价金额（含优惠券／活动优惠，只记一次，不单列自动／券优惠重复扣减）
- 最终应收金额
- 调价原因
- 调价操作人
- 调价时间
- 可选备注

人工调价必须进入订单变更记录和操作日志，不得无痕修改。

确认已收款或确认免单成功后订单金额锁定；如发生错误，必须通过适用的撤销、冲正、退款或补收流程纠正，禁止直接修改已结算历史金额。免单无实际收款，不生成虚假支付或可退现金／余额；具体纠错流程继续按相应正式规则处理。

到店消费整单调价不限幅／无需逐单审批、原因与确认及零元免单规则已经确认，详见03d§10.1、04§3.0.9；不再作为待决项，也不重新引入逐员工权限配置。该确认不授予充值免单、余额任意调整、无痕冲正或积分免费兑换能力；消费退款另按03d§12，老板／有效员工均可登记且无需老板审批，其余未决账本规则继续按原决策收口。

## 8. 会员充值原则

客户端不提供充值入口，也不允许客户发起充值申请。

会员充值完全由门店侧发起：

店员选择客户
→ 填写本次实际充值本金、可选赠送余额及已有优惠券
→ 有任一赠送时填写备注
→ 客户线下付款
→ 有权限店员选择实际支付方式并确认已收款
→ 系统生成充值流水
→ 增加会员余额
→ 按本次确认内容增加赠送余额 / 发放所选优惠券
→ 客户端显示最新余额与相关记录

不设充值套餐；本金、赠送余额及赠券按本次充值记录保存，有赠送余额或赠券时备注必填，无赠送选填。具体规则见03c§2～4，不因此开放任意余额调整或充值退款。

## 9. 会员余额人工调整

允许本店老板／有效员工通过“修改余额”调整当前本金或赠送余额、原因必填；充值余额退还统一用此操作，不另设退款流程。系统按目标与当前余额差额生成流水并保存前后记录，禁止跳过流水及原因直接覆盖数字；见03c§4.3／04§3.0.14。

任何人工调整必须以独立余额流水方式记录，至少包含：

- 调整前余额
- 调整金额
- 调整后余额
- 调整原因
- 操作人
- 操作时间
- 关联客户
- 可选备注 / 凭证

历史余额流水原则上不得删除或覆盖。错误操作通过反向冲正处理。

原充值记错已按03c§4.2／04§3.0.13确认：本店老板／有效员工可更正该充值本金、赠送及赠券，原因必填、无需审批；界面修改当前有效内容，系统保留原值并追加差额或反向流水。需要撤回的本金／赠送不足或赠券已用，门店提示无法撤销、只能由Platform Super Admin在平台侧处理异常数据，前后值／原因／经办／时间同样留痕，后台具体细节另定。更正不当真实退款，收入按更正后真实本金及原实际收款日期；当前余额修改与充值余额退还已统一按03c§4.3／04§3.0.14处理，不另设充值退款申请；平台异常具体处置仍待确认。

## 10. 店员端定位

店员端是实际经营操作中心，商户老板也使用同一业务端并默认拥有全部店员权限。当前核心方向包括：

- 销售额统计
- 接单 / 订单处理
- 客户管理
- 宠物管理
- 洗护管理
- 美容管理
- 寄养管理
- 收银确认
- 人工调价
- 商品销售
- 库存管理
- 员工业绩
- 会员管理
- 会员余额调整
- 优惠券
- 经营统计及原交易明细核对（不做独立对账流程）
- 操作日志
- 服务状态更新
- 洗护 / 美容专业报告填写
- 客户通知
- 预约处理
- 退款 / 撤销 / 冲正
- 订单改单
- 必要时的客户欠款 / 挂账能力
- 本店成为投诉对象时的正式回应与举证，能力基线见03h及04§6.1；采用02统一店员资格，未确认的细分动作和菜单内部交互仍待确认

日常财务按04§3.0.10／3.0.10.1保持简单：本期不做独立日结、交接班或现金盘点流程，不要求每日确认日结或日结锁账。老板从现有经营统计查看当天真实已记账消费实收、消费退款、净消费，充值单列；正常记账及后续补录沿原实际发生日期规则，不能用营业结束或是否日结阻断。原已结算订单历史保护、权限及更正规则不放宽，对账沿用现有经营统计和原交易明细，本期不做独立对账流程；门店表格导入导出归Web后台后续设计，小程序本期不提供入口，具体Web契约及其他分工仍待确认。

提成功能已取消，V1.0不提供提成配置、计算、结算、明细、报表或导出；员工业绩统计与查看继续保留，不能将业绩功能视为提成模块的替代实现。

预约接单按04§3.7：当前需门店处理的申请即进入工作台，包括未来到店日期；完整记录归业务／预约管理，分组与筛选不是新状态。拒绝预约／建议改期原因选填，“其他”不强制文字，不编造默认原因；实际处理人／时间内部留痕。确认时有已知有权查看提醒须明确阅读，共享提醒暂不可用可直接继续并留痕，不要求门店核验资料或人工核对，不自动拒单／标无风险，不绕过共享授权、额度或身份冲突，也不自动生成正式服务或收费。

04§6.5.1于2026-10-25确认：预约提醒保留，新增顾客及确认预约的提醒适用于全部新老顾客；本店不核验资料真实性，明确保存Customer后提醒，提醒失败可直接继续且不回滚／重复建档。同次同顾客／宠物集合／内容只提醒一次，回退或网络重试不重扣查询额度；内容／宠物变化重新阅读，下一笔真实业务再次提醒，不把旧阅读当永久忽略。再次弹窗不自动再查跨店，原授权、每月3次、冲突与平台核验及线上身份安全继续适用，不因全部顾客而开放批量查询。

## 11. Web 管理后台定位

Web 后台按照登录身份展示不同范围的数据。

平台超级管理员可：

- 查看全部商户
- 查看全部门店
- 管理商户账号和状态
- 查看平台级运营数据
- 管理平台配置
- 处理异常商户 / 数据问题
- 查看关键审计日志
- 管理平台资源与使用限制

商户老板可：

- 管理自己门店
- 查看和管理本门店的订单、客户、宠物、员工、库存、会员、财务和统计数据
- 导入历史订单
- 管理员工邀请、停用、删除（移出本店名单）与恢复；店员权限采用02规定的统一默认集合

门店业务表格导出及Excel／CSV批量导入放Web后台后续设计，门店小程序本期不提供这些入口；已有历史订单导入方向及隔离／批次记录保留，具体页面模板字段、错误处理和权限校验契约在后台阶段收口，不因本条直接实施。AI拍照入库按03e／04原规则保持，不受表格导入分工限制；平台投诉批量审核表格规则不在本次门店端简化范围内。

普通商户不得访问其他商户数据。

## 12. 历史订单导入

系统支持从其他宠物店管理平台导入历史订单。

最低必需字段：

- 历史订单号
- 消费时间
- 客户手机号
- 消费金额

可选字段可包括客户姓名 / 昵称、宠物名称、服务项目、商品信息、原支付方式、来源系统名称、备注等。

每次导入必须建立导入批次，并记录导入人、导入时间、来源平台、原文件名、成功条数、失败条数、重复条数和错误原因。

历史导入订单与本系统原生订单必须明确区分。

历史订单默认可以参与：

- 客户累计消费
- 消费频次
- 最近消费时间
- 复购分析
- 客户价值分析

历史订单默认不得直接影响：

- 当前库存
- 今日 / 当期营业额
- 当前现金流
- 当前会员余额
- 当期经营统计及原交易明细核对

会员余额等资产迁移必须通过独立初始化 / 迁移流程完成。

## 13. 洗护 / 美容专业化方向

洗护／美容采用04§4.3的轻量人工状态：待开始、服务中、已完成、已取消、已中止。开单不自动开始；服务前检查强制完成，不强制按洗澡、吹干、修剪等工序逐步点击。专业过程通过检查、说明和真实素材记录，不增加工时核算或复杂排班。

洗美前检查固定皮肤、耳道、眼睛、口腔、指甲、毛发六项，异常／无法检查须先告知主人并记录真实决定，完成前再确认有无新增异常，不重填整套。过程支持备注、真实员工／时长；照片不强制、缺图真实提示、允许后补，不伪造素材。完成发布普通结果，AI仍按原资格与主动触发，不输出医疗诊断。

洗美正常完成后收款，不预收；中止允许明确实际应收／原因后中止结算，不伪记完成。全未开始即全取消不收费、不记免单成交。多宠一单／每宠独立服务，一起结算，不按宠拆账／分次付款；未结算可重新处理、原因选填，已结算不重开旧单。六项前检查、异常告知主人决定、完成前新增异常确认、每宠结果及再次发布按04§4.4；不把洗美收款顺序套到商品／加餐或其他未确认类型。

洗美不确认接走；原待交付改为待结算，完成未收款先待结算、店员手动挂单且原因必填，记清收款／免单后自动解除、历史保留；入口业务／订单与收银／挂单。结算改最终应收0后仍明确确认免单，不因保存0结算。全部消费同次最多两种支付方式；消费退款老板／有效员工均可登记、无需老板审批，消费先扣本金再扣赠送，退款按原付款渠道／原账户退回，按03d§1.1／12、04§4.4。自动联动不等于随意改余额或退款自动回库，不扩展充值退款／积分，也不改变寄养离店、奖励自提及其他未确认业务流程。

04§3.0.8项目入口固定洗护、美容、护理、商品四类：前三类服务项目填写名称／大类／参考价／说明，由老板新增、修改、停用、恢复；商品仅关联03e已有商品／SKU，不复制服务商品或绕过库存。护理仅门店开单、暂不开放客户端预约；寄养保持独立业务。表单校验、保存生效、旧预约停用例外及§7不限幅调价／免单已确认，不加入工时核算、排班或复杂服务套餐，实际服务时长保留；会员充值按03c§2～4逐次填写、可选赠送并记备注，不设充值套餐。

独立护理12项按04§4.5：工作台到店开单选择护理，完整订单和历史归业务／订单与收银，当天在做及异常归其他服务／其他异常，不进入洗美主导航。护理五态手动、一次整体强制前检查及完成前新增异常确认、照片／普通备注选填，完成即本人可看普通结果和护理注意事项、无护理AI。多宠同客一单／逐宠进度／一起结算，正常完成后收款；全未开始取消不收费，中止按原因及实际应收结算。未结算可重新处理原因选填、历史保留，已结算不重开。同宠洗美加护理共用原单／进度、不减免洗美六项；跨业务混结禁止；其他通知技术和寄养未决边界不因此开放。

## 14. 寄养方向

04§4.6确认洗美／护理／寄养挂单查询、补记收款与误挂撤销：历史欠款在业务／订单与收银／挂单持续查，不每天重放工作台；默认挂单时间升序，支持类型／未解除或已解除筛选及本店联系方式／宠物／订单搜索。仅门店自行联系，备注选填，无自动催款／滞纳金／跨天取消；原结算范围一次记清、最多两种方式。误挂撤销只回待结算、保留原应收及历史，不恢复服务／寄养、不造付款或免单，商品仍按原规则。

寄养模块作为独立核心业务设计，需覆盖入住、离店、位置管理、喂食、饮水、排便、遛宠、特殊照护、图片 / 视频、异常事件、客户通知、延住、提前离店、费用调整和交接记录等场景。

04§5.1已确认入住／日常照护16项：实际到店后门店明确确认，必填实际入住及晚于入住的预计离店，同宠有效在住防重，多宠独立记录；位置选填文字、重复位置仅提醒，不做房型预订或硬容量。入住做简短真实检查、核对饮食及本次资料，临时修改不自动改长期档案，未知不默认安全或允许零食。

日常照护用一个表单逐宠选择喂食／遛狗／清扫笼子、实际发生时间、选填照片，再确认；不批量完成、无每日照片配额。时间轴既有其他事件保留，需要时另记真实喂食，加餐商品销售不自动产生照护。动态可见性与主动通知独立，内部记录不公开；异常实际处理并有结果后明确关闭，到预计离店时间只提醒、不自动结束／续住／加费。寄养计费按04§5.2：北京时间03:00为截点，统计实际入住之后至实际离店之内（含离店时刻）的截点数，每过一晚收一天；0晚无寄养费，实际离店结算，延期／提前离店按实际重算，不因预计到点自动收费。日价由本店员工／老板在入住时逐宠设置、仅本次有效，同店同客多宠可一起结算，按各自日价×实际晚数逐宠计算后汇总。日价更正／免费及历史保护按04§5.2第14～18项；健康资料／特殊照护（含代喂药）及异常沟通按04§5.4；挂单查询／人工催款及误挂撤销按04§4.6；特殊交接、医疗处置／紧急升级等仍待对应DEC，不擅设最低一天或罚金。

04§5.2于2026-10-24确认寄养离店／挂单：订单结算页确认本批应收与真实离店时间，同次即记已离店，无额外确认接走；已离店未收款先待结算，员工手动挂单且原因必填。计费截止真实离店，补收款只更新原本批账本，不增加晚数或影响余宠。物品展示提醒交还，不强制逐件勾选／照片／签字；其他特殊交接仍待决。

寄养分批接走按04§5.2分别结算：只计本批实际离店且未结算宠物，未接走的继续在住、不预收；同时离店多宠仍可一起结算，不重复计已结算宠物。

## 16. 产品核心差异化

本项目不定位为单纯的宠物店收银软件。

核心定位为：

> 面向社区宠物店、基础经营免费并提供可选门店付费权益的SaaS经营系统，以服务过程透明、宠物服务报告、会员经营、寄养管理、数据迁移和经营审计为核心。

上门喂养当前边界见03j§8～9.3：保留用户自主接单，需求方仅发布／撤销、当前店仅确认／撤销，协商修改及实际服务在线下，不在APP跟踪四步进度或完成。门店确认后仅当前店老板／有效员工可读双方合法授权联系资料，需求方／接单用户不能互看；确认权限绑定当前负责版本。临时休息不影响功能，账号停用仍以原发布店位置自动接续最近有效店，publisher_store_id保留来源，current_coordination_store_id及coordination_assignment_version决定当前资格，新店须再次确认才读联系方式，原店失权。保留原单／接单人／历史，不迁移其他Customer／钱包／私有档案，不改用户全局当前门店，不公开旧店内部资料或原始审计，不将本例外扩展成03h任意风险查询。
