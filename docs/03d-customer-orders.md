## 1. 设计原则

- 预约与正式订单分离：预约管理未来服务意向，正式订单记录已经发生或正在发生的消费。
- 客户端订单分类必须简单，不暴露大量内部技术状态。
- 客户端订单页直接复用正式业务订单数据，不额外维护一套“客户展示订单”。
- 店员端线下快速开单后，若客户已绑定小程序，订单与服务状态自动同步到客户端。
- 已完成、取消、退款、冲正等历史记录不得被客户端真正删除。

### 1.1 财务仅作线下交易记账（已确认）

> status: confirmed
> status_scope: store_consumption_financial_ledger_only
> financial_mode: offline_transaction_ledger
> external_payment_integration: excluded
> financial_entry_timing: immediate_or_after_work
> operational_updates: timely_during_business
> ledger_side_effects: automatic_wallet_ledger_and_applicable_inventory_updates
> refund_owner_confirmation_required: false
> refund_roles: [merchant_owner, active_store_staff]
> refund_method_values: original_payment_methods
> refund_default_method: original_payment_methods
> refund_original_method_restriction: required
> refund_auto_restock: false
> wallet_deduction_order: principal_then_bonus
> wallet_refund_component_rule: restore_original_components
> partial_refund_allocation: pending

1. 微信、支付宝、现金等真实收付款在线下完成，本系统只记录实际方式与金额，不接入收银系统或第三方收款／退款接口，不设计自动打款、通道回调、支付处理中、未知结果对账和部分通道失败重试等流程。“收银／支付／已收款”在本项目指记账操作及结果，不是系统向外部账户扣款。
2. 老板或有效在职员工可以即时记账，也可以结束工作后录入已经发生的线下交易；实际交易时间与服务端录入时间区分保存，未录入前客户端不假装已结算。预约确认、接宠检查、服务状态、结果发布等仍在营业时及时操作，不改成事后补录。洗美正常完成后收款及中止例外仍有效，补录不是预收许可。
3. 确认记账后自动更新相应订单、资金流水、会员余额和适用商品库存／优惠券；无需再手动维护第二套账。会员余额是系统内资产，余额消费与退款入余额仍由服务端校验并实际扣增、形成独立流水，不是只登记一种付款名称。余额不足不能记负数，录入失败不假记完成，同一请求重试只记一次账、不重复扣增或出入库。
4. 保留原单、真实金额、实际经办人、原因和记录时间，不删除原交易或直接覆盖实付。已记账差错保留原记录并关联更正；具体冲正／更正界面等待DEC-STAFF-05，不引入老板审批或外部支付恢复状态机。
5. 现有商品预占、未结算超时和寄养加餐结算前提不因允许晚记账而取消；需要商品成交、客户端成交展示或加餐执行前提生效时，应先完成相应记账／免单确认，详见03e。本轮不允许用“晚补录”跳过实时库存校验或先投喂后伪造已结算。

## 2. 订单入口与分类

入口：我的 → 我的订单。

V1.0 只保留三个分类：

- 全部
- 服务
- 商品

其中“服务”统一包含洗护、美容、护理、寄养。护理仅由门店开单，暂不开放客户端预约；其消费事实仍进入服务订单，不增第四个订单Tab，不自动赋予洗美AI报告或新预约类型。

预约记录继续放在预约模块的“我的预约”中，不进入“我的订单”。

充值记录继续放在“我的钱包 → 余额明细”中，不作为普通消费订单分类。

## 3. 订单列表

订单列表默认按最新业务时间倒序展示；正在进行中的服务可置顶。

服务订单卡片展示：

- 日期 / 时间
- 宠物名称
- 服务类型 / 服务项目
- 客户可见状态
- 已结算时显示实付金额
- 查看详情 / 查看服务结果入口

商品订单卡片展示：

- 日期 / 时间
- 主要商品摘要
- 商品件数
- 客户可见状态
- 已结算时显示实付金额
- 查看详情入口

服务／商品订单免单结算成功时均明确显示“已免单，实付0元”，不只写一个0使顾客误以为尚未付款；免单不是现金／微信付款，具体服务与交付状态仍独立展示。

## 4. 客户可见状态

### 4.1 洗护 / 美容

客户端继续使用简化状态：

- 等待中
- 洗护中 / 美容中
- 洗护完毕 / 美容完毕
- 已取消

后台可保留更细内部状态，但不直接暴露给客户。

洗美内部五态按04§4.3，正常客户端显示等待中／洗护中或美容中／洗护完毕或美容完毕，取消显示已取消。未结算已完成服务可重新处理、原因选填，顾客恢复服务中，旧普通结果保留历史但非当前最终；再次完成产生新结果版本并可再通知一次，不重置AI权益。已结算不重开旧单；中止的具体顾客标签仍待DEC-STAFF-04，不假记正常完成。

同顾客多宠一单，按宠物分别显示项目／进度／结果、整单总金额；一宠完成或取消不覆盖其他宠物。全部服务结束且中止／取消费用明确后一起结算，不按宠拆账／分次付款。全未开始即全部取消不收费，整单取消、不记免单成交；已开始中止可明确实际应收及原因后中止结算，不伪记完成、不按比例自动算。

### 4.2 寄养

客户端显示：

- 寄养中
- 已完成
- 已取消

未入住的寄养仍属于预约，不提前作为正式消费订单展示。

### 4.3 商品订单

普通商品购买需求在客户端显示：

- 门店确认中
- 待线下付款
- 已完成
- 已取消

客户提交普通商品购买需求后进入“门店确认中”；门店确认商品、数量和当前应收金额后进入待结算阶段，有正金额时显示“待线下付款”，零元但未确认时提示“待门店确认免单”；有权限店员实际收款或明确确认免单后，普通商品订单进入“已完成”。免单付款状态单独为waived，不伪造实际收款。

`business_scenario = boarding_feed` 的寄养加餐仍使用同一商品订单，但付款状态与投喂执行状态必须分开。收款成功不代表已经投喂，订单列表 / 详情和寄养详情必须显示一致的执行结果：

| 场景 | 客户端主状态 / 阶段提示 | 付款信息 |
|---|---|---|
| 已提交，门店尚未确认 | 投喂请求处理中 · 待门店确认 | 未收款 |
| 已确认商品，正金额且尚未结算 | 投喂请求处理中 · 待线下付款 | 当前应收金额 |
| 已确认商品，应收0但未确认免单 | 投喂请求处理中 · 待门店确认免单 | 未结算，当前应收0元 |
| 已收款，尚未实际投喂 | 投喂请求处理中 · 待投喂 | 已收款及实付金额 |
| 已确认免单，尚未实际投喂 | 投喂请求处理中 · 待投喂 | 已免单，实付0元 |
| 已实际投喂且确认成功 | 已投喂 | 实际付款 / 退款记录 |
| 无法继续投喂，尚未处理完毕 | 投喂异常待处理 | 保留真实收款 / 退款状态 |
| 已取消执行且必要后续处理完成 | 投喂已取消 | 保留真实收款 / 退款状态 |

寄养加餐不得只因收款或免单结算成功而展示整体“已完成”。免单没有实际付款，付款／退款记录展示时保留“已免单，实付0元”，不产生虚假支付记录。执行及防重复按03e§17，不新增“投喂订单”或分类。

### 4.4 护理服务订单（仅门店开单）

护理按04§4.5已确认12项执行，不开放顾客预约，也不新增订单Tab、底部菜单或独立AI报告。独立护理从门店工作台“到店开单 → 护理”创建，完整订单／历史在门店“业务 → 订单与收银”；顾客继续从本人的“我的订单 → 服务”及宠物服务记录读取同一真实订单，不复制一套护理账本。

每宠独立进度，开单待开始、员工手动开始／完成；取消未开始、中止已开始，真实状态不可伪装完成。护理前仅需一次真实整体检查“未见明显异常／发现异常／无法检查”，默认未检查；异常或无法检查须说明及记录告知主人后的决定。完成前确认有无新增异常，有则说明；不强制完整洗美六项表，照片和普通过程备注选填。对本人显示真实项目、服务结果、护理注意事项，内部备注／评价／原审计不公开；没有素材不编造正常或AI结论。

正常完成后即发布本宠普通结果，不等收款；同客多宠一单、每宠独立记录、最后一起结算，不跨顾客合单或按宠分次付款。正常护理完成后才收款，中止按实际应收及原因结算、不自动按比例算；全未开始即全部取消不收费、不记免单成交。财务即时／工作结束后录入均按§1.1，未记账仍真实显示服务完成及未结算，不增线上支付。

已完成未结算可重新处理、原因选填、操作留痕；顾客当前恢复服务中，旧普通结果留历史、不冒充当前最终，再次完成发布真实结果，已结算不重开或改历史金额。护理的额外通知、其他状态恢复及挂单细则仍待04对应DEC，不把洗美通知或挂单政策整套套入。

同只宠物在洗美中增加护理项目是原单加项，共用该宠物原洗美进度，不另建护理流程、改原service_type或降低洗美六项检查要求。本例外不开放商品／寄养混单及其他未决组合；参考价可调、明确免单、先本金后赠送、无老板审批且原路退款按统一规则，部分退款分配仍待决。

## 5. 洗护 / 美容订单详情

订单详情至少展示：

- 宠物
- 服务状态
- 服务时间
- 服务项目明细
- 原始应收金额
- 优惠券优惠金额（如有）
- 人工调价金额（如有）
- 最终应收 / 实付金额
- 支付方式（结算后）
- 查看本次服务结果入口

“查看本次服务结果”直接进入同一笔服务的洗护 / 美容前后对比与 AI 报告页面，不额外建立独立报告列表。

首页“当前服务”和“我的订单”中的进行中服务，应打开同一个服务详情数据源和页面能力。

洗美强制六项前检查（皮肤、耳道、眼睛、口腔、指甲、毛发），异常／无法检查须如实记录并告知主人，店员记录主人同意继续或决定中止及说明，不默认正常／同意，不作医疗诊断。完成前确认是否出现新增异常，有则说明、不再重填全套。真实检查与护理注意事项向本人顾客展示，内部备注／员工评价／系统日志不公开。照片不强制、缺图如实提示，完成后发布普通结果、不等收款，不设确认接走按钮。

洗美正常完成后收款，中止费用明确后可按中止结算例外；不预收、不假记完成。完成未收款先待结算，店员手动挂单且原因必填；顾客显示待结算／真实金额、不展示内部备注或线上付款。实际付清／明确免单成功自动解除挂单标记、历史保留，不套商品超时删消费；结算可改最终应收0，保存0不结算，仍明确确认免单并校验本单结算前提。其他类型收款顺序不随洗美规则改变。

## 6. 寄养订单详情

寄养订单详情至少展示：

- 宠物
- 入住 / 离店日期时间
- 当前寄养状态
- 当前第几天
- 当日动态摘要
- 查看全部寄养动态入口
- 当前费用 / 预计费用或最终实付金额

寄养过程中可能发生延住、提前离店、加项或费用调整，因此正式结算前显示“当前金额 / 预计金额”，完成结算后显示最终实付金额。

## 7. 服务加项与改单

同一只宠物同一次服务过程中增加项目，不应生成多个独立小订单。

例如基础洗护 + 打结处理 + 剪指甲，应作为同一服务订单下的多个服务项。

同宠洗美中添加护理项目按04§4.5共用原单／进度，不再生成第二条护理流程；独立护理则按本文件§4.4办理。本例外不等于商品、寄养或其他服务可以任意混单，不改变停用项目／结算后历史保护。

系统必须保留原始项目、加项、价格变化、人工调价及操作记录。

## 8. 商品购买需求

客户端普通商品正金额实际收款流程如下；零元走第10.1节明确确认免单分支，不创建实际支付，仍一次出库／计0收入，详见03e§13。

首页推荐商品 / 商品列表
→ 商品详情
→ 选择数量
→ 提交购买需求
→ 我的订单显示“门店确认中”
→ 店员确认商品、数量和当前应收金额
→ 客户端显示“待线下付款”
→ 客户线下付款
→ 有权限店员确认已收款
→ 订单“已完成”
→ 扣减库存并计入营业额

客户不能在客户端自行确认付款或把订单标记为已完成。

寄养加餐复用上述商品确认、收银、库存与营业额流程；收款之后继续保留待投喂事项，实际投喂确认成功后才显示“已投喂”，详见第 4.3 节。

## 9. 店员修改商品需求

结算前店员可以根据库存或实际情况修改商品、数量和金额。

修改后客户端自动显示当前门店确认结果与最新金额，不要求客户额外点击“同意”；正金额以客户最终线下付款及门店确认实收成交，零元按第10.1节明确确认免单成交，不能将仅显示0当作完成。

系统必须保留原始购买需求与门店修改后的正式明细，禁止无痕覆盖。

## 10. 金额展示与财务留痕

订单至少保留并可按权限展示 / 审计：

- 商品 / 服务明细原价
- 系统原始应收金额
- 自动优惠金额
- 优惠券优惠金额
- 人工调价金额
- 最终应收金额
- 实付金额
- 支付方式及组合支付明细

不得只保存最终成交金额。

全部到店服务／商品消费订单必须支持在结算完成前调整本单最终应收总额，不能把项目参考价或SKU售价锁死为成交价。老板维护主资料与员工调本单金额是不同权限对象；原始单价／应收、预约参考快照及主资料不得被改写，规则见下节及04§3.0.9。

客户端详情读取本单服务端保存的原始应收、调价差额、最终应收及实付，不拿项目最新参考价回算历史。调价原因、操作人和服务端时间均保留，普通顾客仍不读取内部审计明细。

实际收款或明确确认免单成功后，金额均锁定；纠错按适用的撤销、冲正、退款或补收流程，不能直接改价或改回未付款。旧金额／状态、重复请求、并发结算的服务端校验不能省略。

### 10.1 全部到店消费订单的整单调价与免单（已确认）

> status: confirmed
> status_scope: onsite_order_price_adjustment_and_zero_waiver_only
> confirmed_by: user
> confirmed_on: 2026-10-22
> adjustment_scope: all_onsite_consumption_orders
> adjustment_business_limit: none
> adjustment_owner_approval: not_required
> adjustment_roles: [merchant_owner, active_store_staff]
> adjustment_input: final_receivable_amount
> waiver_payment_status: waived
> waiver_requires_explicit_confirmation: true
> waiver_actual_payment_amount: 0
> waiver_revenue_amount: 0
> checkout_max_payment_methods: 2
> refund_owner_confirmation_required: false

1. 本店老板及有效在职员工可对所有到店消费订单整单调价，包括洗护、美容、护理、商品及原寄养到店消费结算，不按小程序／电话／现场等来源分出另一套权限。只修改本单最终应收总额，由服务端按原价／优惠／目标总额计算人工调价差额，不新增逐项分摊算法，不回写项目参考价或SKU售价。
2. 不设业务金额／比例上限，不要求老板逐单审批；仍须本店角色、对象、有效状态、精确非负金额和最多两位小数校验。负数、非法数字或超精度不能按“不限额”放行，不静默截断／四舍五入。金额确认前显示调前／调后并由操作者明确确认，单纯输入不改变结算状态。
3. 调价原因必填，快捷原因是“实际护理情况、到店优惠、录入更正、其他”；“其他”需补文字。原因、操作者、服务端时间及前后金额留痕；原始明细、优惠、调价差额、最终应收、实收分别保存，重试不重复加差额。
4. 最终应收为0时必须明确执行“确认免单”，保留免单原因、操作者和服务端时间；门店老板及有效员工均可办理，无老板逐单审批。仅当本单未结算、无实际已收款且当前应收为0时成功；仅输入0、券优惠到0或页面显示0都不等于免单已经成立，也不能取消已发生付款来免单。
5. 免单成功后payment_status=waived，最终应收、实收、收入为0，settled_at记录成功结算时间；不创建现金／微信／支付宝等虚假支付或组合支付拆分，不扣会员余额。它是已结算的消费，不是取消、未付款、充值或退款；没有实际收款不能凭免单记录退现金／余额。
6. 免单后与实收后同样锁定金额。调价、实际收款、确认免单、取消／超时等并发使用当前订单金额版本和状态，只有一个合法转换成功：免单或收款先成功则拒绝直接调价／第二次结算；调价先成功则旧金额／版本的结算失败并提示重新核对。不得重复出库、核销优惠券、扣余额、生成收入或通知。
7. 普通商品免单仍在本来成交节点一次正式出库，金额收入为0，不因零元省略SKU、可售、预占及库存校验；已选优惠券按原消费结算规则一次处理。免单前未成功结算的0元订单仍按原未结算超时／取消规则处理；免单成功后不能被未付款超时任务取消或返还已出库库存。
8. 免单不自动完成洗美／护理／寄养、交付或实际投喂；寄养加餐以“实际收款或免单成功”为已结算前提，但仍须实际投喂、主人授权和饮食安全校验，不生成虚假动态。执行与财务结果分开。
9. 客户端读同一真实订单，免单显示“已免单，实付0元”及无实际支付，不伪造凭证；仅0元未确认不能标成已结算／免单成功。服务已真实完成仍如实显示服务完成及未结算，不能混淆服务与财务轴；普通商品交易完成仍须原结算规则。通知表达真实结果，失败不回滚结算。
10. 该调价权限不适用于充值免费入账、任意改余额、积分免费兑换或无痕冲正。洗美按04§4.4正常完成或中止实际费用明确后结算，全未开始即全取消不收费；未结算可重新处理、原因选填，已结算不重开。手动挂单原因必填，改0后明确免单；全部消费最多两种支付，消费退款由老板／有效员工按§12办理、无需老板审批。除§4.4同宠洗美护理加项外的未决混合业务及其余账本更正等待DEC-STAFF-05，不因不限额跳过顺序或退不存在的实收。

## 11. 支付方式展示

客户订单详情可以查看实际支付方式，例如：

- 会员余额
- 微信
- 支付宝
- 现金
- 其他允许的支付方式

组合支付应按实际金额拆分展示。

全部门店消费订单（洗护／美容／护理／寄养／商品）同次最多两种不同支付方式、合计等于应收，余额内部本金／赠送拆分仍算一种；不等于按宠／分次付款或合并商品服务单。免单不造拆分，不改各业务收款先后，也不扩展充值／积分。组合是一次记账中登记线下实收方式与系统余额扣款，不是两次在线支付调用；核对真实全额后确认，系统内订单／余额／流水的一次写账保持一致，不能留下半笔已记账后要求再付一次。

客户端不展示内部操作员工、内部收银备注、本金 / 赠送余额扣减细节或完整审计日志。

## 12. 退款 / 取消展示

订单模型预留客户可见状态：

- 已取消
- 已退款
- 部分退款

退款不能通过直接修改原实付金额来实现；客户端应保留原订单金额、退款金额和退款后实际消费结果。

全部门店消费订单的本店老板和有效在职员工均可登记退款，无需老板审批，不设置待老板确认、批准／拒绝／撤回批准流程。退款原因必填，关联原单并保存实际经办人、金额、方式、实际退款时间及服务端录入时间；不改写原实付。本次退款不得超过本单已实收扣除已退的剩余额，累计退款不得超过原实收；未实收或免单无可退资金。

退款全部原路退回，逐笔对应原消费的真实付款方式及原账户：会员余额退原商户／原顾客钱包，微信退原微信付款账户，支付宝退原支付宝付款账户，现金退现金，其他方式按原渠道。不能把微信／支付宝付款改退现金或钱包，也不能把原余额部分转为现金；不提供自由改退款渠道的选项。余额原扣本金退本金、原扣赠送退赠送，不相互转换，消费扣款顺序按03c§5先本金再赠送。

组合付款全额退款时分别退各原渠道实际已付未退的金额，例如原钱包60元＋微信40元且均未退，全退须钱包60元＋原微信40元；每个渠道及余额组成的累计退款不超过各自原实付／实际扣款。不得为临时顾客伪造User、另建接收钱包或退给其他顾客。组合付款部分退款及钱包本金／赠送的部分退款分配仍按03c§5／DEC-STAFF-05待确认，不擅定比例、优先次序或沿用消费扣款顺序来分配退款。

本系统仍只记账、不接外部支付退款接口。原微信／支付宝／现金等须由经办人在线下核实并实际原路退回后确认记账，不因选择原渠道就声称系统已打款；原会员余额部分在确认退款时由系统实际入原钱包并生成余额流水，退款前后金额和原交易关联保留。

沿用退款请求稳定标识和版本作为录入草稿／防重依据，不承载审批。同单同时最多一份未完成退款录入；该次完成后仍有可退金额可再次登记。保存草稿不表示已退款，确认时重新校验原单、剩余可退及当前版本；同一确认重复提交不重复退款、加余额或计流水。客户端只展示已经确认记入账本的真实退款结果，不把默认渠道、草稿或页面成功动画当到账。

退款不自动改写服务完成、实际投喂或库存。只有确实收回且可再次销售的商品，才按原SKU登记退货并由系统一次恢复库存；不需老板逐单审批。仅退款、不退货或不可再次销售均不自动回库，不涉及积分奖励库存。退款方式不改变03c§11既有优惠券规则，也不扩展充值退款、任意余额调整或积分补偿。

优惠券未核销锁定因订单取消／未完成结算释放时，按03c§11暂停有效期并补回实际锁定时长；实际收款或免单结算后不能按未付款超时释放已核销券。整单取消／全额退款和部分退款仍按03c§11区分；部分退款分配及其余账本更正规则在核心业务规则阶段统一确认，不再等待外部支付通道设计。

寄养加餐因提前离店、取消或其他原因无法投喂时，执行终止与财务处理分开记录。已经记收款的订单不得直接改为未付款、删除交易或自动无条件退款；由本店老板／有效员工按本节登记真实退款，无需老板审批，其他撤销／冲正仍按对应正式规则。客户端保留原因和可见结果，已经发生的实际投喂及其时间轴记录不得因退款而改写为未发生。
