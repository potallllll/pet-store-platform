## 1. 设计原则

- 预约与正式订单分离：预约管理未来服务意向，正式订单记录已经发生或正在发生的消费。
- 客户端订单分类必须简单，不暴露大量内部技术状态。
- 客户端订单页直接复用正式业务订单数据，不额外维护一套“客户展示订单”。
- 店员端线下快速开单后，若客户已绑定小程序，订单与服务状态自动同步到客户端。
- 已完成、取消、退款、冲正等历史记录不得被客户端真正删除。

1. 微信、支付宝、现金等真实收付款在线下完成，本系统只记录实际方式与金额，不接入收银系统或第三方收款／退款接口，不设计自动打款、通道回调、支付处理中、未知结果对账和部分通道失败重试等流程。“收银／支付／已收款”在本项目指记账操作及结果，不是系统向外部账户扣款。
2. 老板或有效在职员工可以即时记账，也可以结束工作后录入已经发生的线下交易；实际交易时间与服务端录入时间区分保存，未录入前客户端不假装已结算。预约确认、接宠检查、服务状态、结果发布等仍在营业时及时操作，不改成事后补录。洗美正常完成后收款及中止例外仍有效，补录不是预收许可。
3. 确认记账后自动更新相应订单、资金流水、会员余额和适用商品库存；结算选券由服务端自动校验，成功结算才核销并绑定原单；无需再手动维护第二套账。会员余额是系统内资产，余额消费与退款入余额仍由服务端校验并实际扣增、形成独立流水，不是只登记一种付款名称。余额不足不能记负数，录入失败不假记完成，同一请求重试只记一次账、不重复扣增、核销或出入库。
4. 结算成功后锁定最终应收、实收和原付款拆分，不提供“更正收款”或直接覆盖原金额。少收只能在原单登记一笔真实补收，多收或不应收只能按§12登记真实退款；两者均保留原单、原收款、真实经办人与服务端时间，不删除原交易。补收原因选填，退款原因必填；所有成功修改自动记录操作人、时间及改前改后，无老板审批。
5. 现有商品预占、未结算超时及成交记账规则不因允许晚记账而取消，加餐商品也按普通销售执行，详见03e。不得以晚补录跳过实时库存校验或伪造已结算；真实照护另记，不要求先有商品订单或先收款。

## 2. 订单入口与分类

入口：我的 → 我的订单。

V1.0 只保留三个分类：

- 全部
- 服务
- 商品

其中“服务”统一包含洗护、美容、护理、寄养。护理仅由门店开单，暂不开放客户端预约；其消费事实仍进入服务订单，不增第四个订单Tab，不自动赋予洗美AI报告或新预约类型。

预约记录继续放在预约模块的“我的预约”中，不进入“我的订单”。

充值记录继续放在“我的钱包 → 余额明细”中，不作为普通消费订单分类。

## 3. 订单列表

店员洗美另三个办理列表按04§3.0.1：待接宠仅已开单not_started、开单时间升序，未开单预约从业务／预约管理办理；服务中按真实service_started_at升序，待结算按原单开单时间升序、未处理跨天保留。三个列表不套历史15天，均支持本店顾客手机号搜索／洗护美容筛选，显示开单时间、顾客宠物、项目、服务状态、结算状态、F-ORD-014最终应收；未明确金额显示待确认，多宠标整单应收，不增加实收／分摊。点原详情再检查／开始／完成／结算，无列表一键完成／收款，不改原业务资格或结算前置；分组引用原服务／订单，不新增账目或顾客端订单分类。

## 4. 客户可见状态

### 4.1 洗护 / 美容

客户端继续使用简化状态：

- 等待中
- 洗护中 / 美容中
- 洗护完毕 / 美容完毕
- 已取消

后台可保留更细内部状态，但不直接暴露给客户。

洗美内部五态按04§4.3，正常客户端显示等待中／洗护中或美容中／洗护完毕或美容完毕，顾客端取消／中止显示“服务异常，已终止”。未结算已完成服务可重新处理、原因选填，顾客恢复服务中，旧普通结果保留历史但非当前最终；再次完成产生新结果版本并可再通知一次，不重置AI权益。已结算不重开旧单；正常已完成洗美补照片／改普通说明是独立内容补改，已结算亦可，不改账、不重开、不发补改通知，明细按04§4.4。店内老板／有效员工无审批可办、原因选填，旧内容／人／时间留历史、顾客默认最新；检查结论、实际时间及收费明细仍按原规则。AI报告由顾客主动选择并校验原资格，补改不自动运行AI／覆盖旧报告；洗美中止说明选填，顾客端无本次中止过程／过程照片或检查时间轴、不发布普通完成结果／AI报告，不发中止通知；店内原真实记录／审计保留，不假记正常完成。已取消／中止的顾客端提示统一为“服务异常，已终止”；洗美／独立护理取消或中止后不恢复原服务，包括误点和未结算情形，要再开始必须重新开单／新的service_record_id，从待开始重新检查、手动开始／完成。可选已有顾客宠物，原单状态／历史／账目保留，不复制旧检查为新检查或自动结清／退款／转移旧款，不发送恢复消息，明细见04§4.4。

同顾客多宠一单，按宠物分别显示项目／进度／结果、整单总金额；一宠完成或取消不覆盖其他宠物。全部服务结束且中止／取消费用明确后一起结算，不按宠拆账／分次付款。全未开始即全部取消不收费，整单取消、不记免单成交；已开始后中止说明选填；实际应收及独立收费原因明确后可按原例外结算，不伪记完成、不按比例自动算。

### 4.2 寄养

客户端显示：

- 寄养中
- 待结算
- 已完成
- 已取消

未入住的寄养仍属于预约，不提前作为正式消费订单展示。

### 4.3 商品订单

普通商品购买需求在客户端显示：

- 门店确认中
- 待线下付款
- 已完成
- 已取消

客户提交普通商品购买需求后进入“门店确认中”；门店确认商品、数量和当前应收金额后进入待结算阶段，有正金额时显示“待线下付款”，零元但未确认时提示“待门店确认免单”；有权限店员实际收款或明确确认免单后，普通商品订单进入“已完成”。免单付款状态单独为waived，不伪造实际收款。

寄养入口提交的business_scenario=boarding_feed加餐商品同样按上述普通商品状态展示：实际收款或明确免单后交易已完成，不再展示待投喂／已投喂或单独执行异常阶段。收款不是喂食事实，购买和结算不自动生成照护记录；店员需要时另从寄养照护登记真实喂食，见03e§17。

### 4.4 护理服务订单（仅门店开单）

护理按04§4.5已确认12项执行，不开放顾客预约，也不新增订单Tab、底部菜单或独立AI报告。独立护理从门店工作台“临时开单／会员开单 → 护理”创建，两种入口只改变顾客资料取得方式，完整订单／历史在门店“业务 → 订单与收银”；顾客继续从本人的“我的订单 → 服务”及宠物服务记录读取同一真实订单，不复制一套护理账本。

每宠独立进度；快速开单完成必要检查并提交后直接进入服务中，普通预约到店生成的服务仍由员工手动开始，完成继续由员工手动操作；取消未开始、中止已开始，真实状态不可伪装完成。护理前仅需一次真实整体检查“未见明显异常／发现异常／无法检查”，默认未检查；异常或无法检查须说明及记录告知主人后的决定。完成前确认有无新增异常，有则说明；不强制完整洗美六项表，照片和普通过程备注选填。对本人显示真实项目、服务结果、护理注意事项，内部备注／评价／原审计不公开；没有素材不编造正常或AI结论。正常已完成护理可由本店老板／有效员工补照片、改普通说明，已结算亦可、无审批、原因选填，保留前后内容／人／时间，顾客默认最新，检查结论／实际时间／收费明细仍按原规则，不重开不改账。护理开始发送普通通知，完成／重新完成发送重要通知；完成后补图或修改普通说明均不发送通知。中止说明选填、无本次顾客过程／结果、不发中止消息，门店已保存真实记录留存；中止独立收费原因仍按原规则。短信暂未开放、护理无AI，同宠洗美护理加项仍走原洗美消息，不另发护理消息。

正常完成后即发布本宠普通结果，不等收款；同客多宠一单、每宠独立记录、最后一起结算，不跨顾客合单或按宠分次付款。正常护理完成后才收款，中止操作说明选填、收费仍按实际应收及独立收费原因结算、不自动按比例算；全未开始即全部取消不收费、不记免单成交。财务即时／工作结束后录入均按§1.1，未记账仍真实显示服务完成及未结算，不增线上支付。

已完成未结算可重新处理、原因选填、操作留痕；顾客当前恢复服务中，旧普通结果留历史、不冒充当前最终，再次完成发布真实结果，已结算不重开或改历史金额。护理挂单／人工联系及撤销按04§4.6；护理开始／完成与再次完成／补改消息按04§4.5已定；取消／中止后重新开单按04§4.4已定，原服务不恢复且不发恢复通知。其他未列取消／更正消息和状态更正等仍待对应DEC，不把洗美其他通知整套套入。

同只宠物在洗美中增加护理项目是原单加项，共用该宠物原洗美进度，不另建护理流程、改原service_type或降低洗美六项检查要求。本例外不开放商品／寄养混单及本期禁止的其他跨业务组合；参考价可调、明确免单、先本金后赠送、无老板审批且原路退款按统一规则，部分退款分配按03c§5.1已定，跨业务混结禁止，特殊收款更正流程已排除，剩余数据与平台异常技术仍待设计。

## 5. 洗护 / 美容订单详情

订单详情至少展示：

- 宠物
- 服务状态
- 服务时间
- 服务项目明细
- 原始应收金额
- 人工调价差额（含券／活动优惠，只记一次；历史券优惠明细按原记录展示）
- 最终应收 / 实付金额
- 支付方式（结算后）
- 查看本次服务结果入口

“查看本次服务结果”直接进入同一笔服务的洗护 / 美容前后对比与 AI 报告页面，不额外建立独立报告列表。

首页“当前服务”和“我的订单”中的进行中服务，应打开同一个服务详情数据源和页面能力。

洗美强制六项前检查（皮肤、耳道、眼睛、口腔、指甲、毛发），异常／无法检查须如实记录并告知主人，店员记录主人同意继续或决定中止及说明，不默认正常／同意，不作医疗诊断。完成前确认是否出现新增异常，有则说明、不再重填全套。非中止的真实检查与护理注意事项向本人顾客展示；已中止按04§4.4不展示本次过程，内部备注／员工评价／系统日志不公开。照片不强制、缺图如实提示，完成后发布普通结果、不等收款，不设确认接走按钮。

洗美正常完成后收款，中止费用明确后可按中止结算例外；不预收、不假记完成。完成未收款先待结算，店员手动挂单且原因选填；顾客显示待结算／真实金额、不展示内部备注或线上付款。实际付清／明确免单成功自动解除挂单标记、历史保留，不套商品超时删消费；结算可改最终应收0，保存0不结算，仍明确确认免单并填写必填免单原因。其他类型收款顺序不随洗美规则改变。

### 5.1 挂单与后续收款的客户端结果

按04§4.6，护理完成或中止、实际费用明确后也可由门店主动挂单，原因选填；洗美／护理不按宠分次收款和寄养原分批范围保持。客户只读真实业务状态／待结算与应收，不看到内部挂单原因、人工联系备注或完整审计。误挂撤销只解除挂单标记，仍待结算；“已解除挂单”不能被映射为已收款／已免单或无欠款，也不重开服务／恢复在住。

跨天未解除记录在门店业务列表保留，默认挂单时间升序，可筛类型及未解除／已解除、按本店联系方式／宠物／订单查找；寄养按原结算批次，顾客其他在住宠物不被预收或结束。门店自行联系、备注／联系时间选填，无自动催款短信／微信、滞纳金或跨天取消；不新增分期／分几次还款，每个原批核对全额实际收款、最多两种方式，真实记账／免单后自动解除留历史。撤销、调价及收款竞态复用原对象／金额版本／幂等，不从旧请求伪造未付或重复收入；商品超时规则与其余未决更正保持。

## 6. 寄养订单详情

寄养订单详情至少展示：

- 宠物
- 入住 / 离店日期时间
- 当前寄养状态
- 当前第几天
- 当日动态摘要
- 查看全部寄养动态入口

2. 少收时，本店老板或有效员工在原单登记真实补收；补收是关联原订单的新收款记录，按真实金额、方式和发生时间累计到原单实收与业绩，不重做服务、库存、离店或券核销。补收原因选填，无审批。
3. 多收、不应收或原收款需要退回时，统一按§12登记退款；退款原因必填，无审批。不得把退款伪装为修改原实收、改余额或免单。
4. 补收与退款均在提交时重验本店身份、原订单、剩余应收／可退金额和F-ORD-032版本；同一请求重试不得重复收退款，并发不得造成超收、超退、重复钱包扣增或重复业绩。
5. 系统自动保留原收款、补收／退款记录、实际操作人、服务端时间和改前改后聚合金额。顾客端显示原订单当前累计实收及已退款结果，不显示内部审计详情。
6. 已免单订单如后来需要收费，不能修改原免单；须按真实情况重新开单。历史F-PAY-019仅兼容读取，V1.0不得再写入或提供`staff_order.correct_payment`入口。

## 12. 退款 / 取消展示

订单模型预留客户可见状态：

- 已取消
- 已退款
- 部分退款

退款不能通过直接修改原实付金额来实现；客户端应保留原订单金额、退款金额和退款后实际消费结果。

全部门店消费订单的本店老板和有效在职员工均可登记退款，无需老板审批，不设置待老板确认、批准／拒绝／撤回批准流程。退款原因必填，关联原单并保存实际经办人、金额、方式、实际退款时间及服务端录入时间；不改写原实付。本次退款不得超过本单已实收扣除已退的剩余额，累计退款不得超过原实收；未实收或免单无可退资金。

退款全部原路退回，逐笔对应原消费的真实付款方式及原账户：会员余额退原商户／原顾客钱包，微信退原微信付款账户，支付宝退原支付宝付款账户，现金退现金，其他方式按原渠道。不能把微信／支付宝付款改退现金或钱包，也不能把原余额部分转为现金；不提供自由改退款渠道的选项。余额原扣本金退本金、原扣赠送退赠送，不相互转换，消费扣款顺序按03c§5先本金再赠送。

组合付款全额退款时分别退各原渠道实际已付未退的金额，例如原钱包60元＋微信40元且均未退，全退须钱包60元＋原微信40元；每个渠道及余额组成的累计退款不超过各自原实付／实际扣款。不得为临时顾客伪造User、另建接收钱包或退给其他顾客。组合付款部分退款按03c§5.1已确认：本店老板／有效员工分别填写各原渠道金额，合计本次退款且不超各自原实付减已退；钱包退款部分系统先退原扣未退本金、不足再退原扣未退赠送，不按比例、不跨渠道／组成互转。确认重新校验原款与历次退款，草稿不算已退，重复／并发不重退或超退；原历史实付、归属及其他账本更正边界保持。

员工业绩金额统一按04§3.0.10＝实际消费实收－已确认消费退款：原单100元退30元计70元、全退计0，不将退款记成正业绩或重复扣减。原单实付／退款分别保留，归属沿原038，不归退款经办人；跨期仍按各真实收退款发生日期统计，退款期可负数，不回写原收款期或改原实收字段为净额。

本系统仍只记账、不接外部支付退款接口。原微信／支付宝／现金等须由经办人在线下核实并实际原路退回后确认记账，不因选择原渠道就声称系统已打款；原会员余额部分在确认退款时由系统实际入原钱包并生成余额流水，退款前后金额和原交易关联保留。

沿用退款请求稳定标识和版本作为录入草稿／防重依据，不承载审批。同单同时最多一份未完成退款录入；该次完成后仍有可退金额可再次登记。保存草稿不表示已退款，确认时重新校验原单、剩余可退及当前版本；同一确认重复提交不重复退款、加余额或计流水。客户端只展示已经确认记入账本的真实退款结果，不把默认渠道、草稿或页面成功动画当到账。

退款不自动改写服务完成、实际投喂或库存。只有确实收回且可再次销售的商品，才按原SKU登记退货并由系统一次恢复库存；不需老板逐单审批。仅退款、不退货或不可再次销售均不自动回库，不涉及积分奖励库存。退款方式不改变03c§11既有优惠券规则，也不扩展充值退款、任意余额调整或积分补偿。

所有优惠券和活动券都在结算页选择，由服务端自动校验归属、状态、期限、适用范围、门槛和并发锁定，并按券配置计入本次结算。只有结算成功才自动核销并绑定原订单；结算失败、取消或旧版本不得核销。顾客详情仅可删除未使用且未锁定的券，不提供手工核销。

加餐商品取消／退款按普通商品规则处理，不因离店自动退款或回库，不产生专用投喂异常流程；已收款不直接改未付款或删除交易，实际退款按本节留痕。需要时另记的真实寄养照护不因商品退款而抹去。
