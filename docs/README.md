# 需求文档阅读指南

本目录是 `pet-store-platform` 的正式需求文档区。

## 1. 对人和 AI 都适用的规则

1. 聊天记录、临时原型、旧 AI 方案、外部参考和其他仓库内容，不自动成为正式需求。
2. 只有本仓库中标记为 `已确认` 的需求，才能作为正式实现依据。
3. `讨论中` 可以调整；`待确认` 不可当作冻结实现依据；`以后版本` 不进入当前 V1.0 实现。
4. 若已确认文档之间出现明确冲突，不得自行推断“哪个大概对”，必须提出并通过需求变更解决。
5. 需求修改必须记录：原规则、新规则、影响范围。

## 2. 文档职责与优先级

不同文档职责不同，不应简单用“最后修改时间”覆盖全部规则：

- `REQUIREMENTS-STATUS.md`：只负责当前阶段、完成状态和已确认基线。
- `00-project-workflow.md`：负责需求治理、开发流程和全局低操作负担原则。
- `01-project-positioning.md`：负责产品边界、多租户、各端定位和跨模块总原则。
- `02-roles-and-accounts.md`：负责正式角色、账号归属和员工生命周期。
- `03-customer-miniapp.md`：阶段 03 客户端总纲和跨子模块汇总。
- `03a` ～ `03h`：客户端各业务子模块的详细规则。

同一客户端子模块的具体行为，以对应 `03x` 详细文档解释总纲；但多租户隔离、财务审计、权限、安全等上层强制原则仍同时生效。

若两条规则无法同时满足，应停止实现并提出冲突，不允许静默覆盖。

## 5. 当前关键产品结论

为避免新成员从旧术语产生误解，当前基线特别明确：

- V1.0 为多商户 SaaS；一个 Merchant 对应一家 Store。
- 管理角色只有平台超级管理员、商户老板、店员；没有独立“店长”角色。
- 老板可使用店员端小程序，并默认拥有全部店员权限。
- 客户端底部导航固定为：预约 / 首页 / 我的。
- 客户端“我的会员”已经改名为“我的钱包”。
- 当前可用余额直接显示在“我的”页面；钱包主要放余额明细、优惠券、邀请码兑换。
- 客户端没有充值入口、没有积分体系、没有真实线上支付。
- 商品模块是轻商城 / 购买需求，正式成交由门店线下确认收款。
- 宠物交友只展示主人主动授权公开的宠物资料，不公开主人联系方式，也不做客户之间直接聊天。
- 自己的宠物可在本人首页第 4 位私有展示；未开启交友不代表公开给其他客户，也不能作为好友邀请发起方。
- 预约与正式订单分离。
- 财务、余额、库存、退款、冲正等必须可审计，不允许无痕覆盖历史数据。

## 6. 文件命名约定

- 数字前缀表示阶段，例如 `03` 为客户端阶段。
- 字母子编号表示该阶段子模块，例如 `03a`、`03b`。
- 文件名应与当前对外产品术语一致；旧术语不应继续作为新文件名或入口名称。

## 7. 暂不放入仓库的内容

除非明确要作为正式资产，否则以下内容不应混入需求目录：

- 临时 H5 / UI 演示文件
- 聊天导出
- 其他 AI 的原始方案
- 未确认 brainstorm
- 与本项目无关的其他仓库资料
- 生成过程中的临时文件

这些内容如果未来需要保留，应单独建立明确标注为 `reference` / `archive` 的目录，且不得与正式已确认规格混放。

## 8. 需求变更记录位置

当前不维护一份与模块文档重复的中央 `CHANGELOG.md`，以避免两套需求记录长期不一致。

- 具体业务需求变更：写入对应模块文档的“需求变更记录”。
- 阶段完成 / 基线状态：写入 `REQUIREMENTS-STATUS.md`。
- 跨项目治理规则：写入 `00-project-workflow.md`、本文件或根目录 `AGENTS.md`。

如未来确有必要建立中央变更索引，应只做链接 / 摘要索引，不再复制完整业务规则。
