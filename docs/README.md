# 需求文档阅读指南

本目录是 pet-store-platform 的正式需求文档区。当前为 V1.0 需求设计阶段；详细状态见 `REQUIREMENTS-STATUS.md`。

## 1. 正式来源与状态

聊天、临时原型、外部建议及历史提交不自动成为正式规格。需求状态分为讨论中、待确认、已确认、以后版本；只有明确已确认的范围才可作为实施依据。已确认文档中的待决章节和提案仍不得实施。

同一规则只维护一个权威定义位置；总纲、页面、UI 与治理入口使用引用。若两个已确认规则无法同时满足，停止受影响实现并登记冲突，不自行选择或静默覆盖。全局租户隔离、权限、安全和财务审计始终有效。具体变更记录写在所属模块，历史规则标记已被替代并指向现行章节。

## 3. 当前阶段与实施边界

当前主阶段为 **04 店员端小程序需求讨论**。阶段 00～03 已形成基线；客户端 UI / Design System 允许提前与04并行。阶段03已确认范围不代表阶段05～12或V1.0整体冻结，跨端结算、容量、部分权限及运营参数仍须按决策登记收口。

用户明确要求的原型或已确认模块开发准备可先行，但不能从待决提案推导业务实现。正式 V1.0 冻结、Codex Master Prompt及整体验收按00流程执行。

## 4. 新成员 / AI 阅读顺序

先读根目录 `AGENTS.md` → 本文件 → `REQUIREMENTS-STATUS.md` → `REQUIREMENTS-DECISIONS.md`（涉及待决时）→ 当前任务权威业务模块与直接依赖 → `03i`（客户端页面或验收任务）→ 对应 UI 文档。

全量客户端 H5、Demo、UI骨架或正式页面须覆盖当前03总纲与03a～03m、03o、03p适用范围，并读取03i及相关10a/10b/10c。03n只供历史追溯，不再作为必读的第二套蓝图。局部任务无需重复阅读无关全文，但不能遗漏直接依赖、全局安全与权限约束。

## 5. 需求变更与决策管理

- 业务变更：更新该模块权威正文并记录原规则、新规则、影响范围、确认人/日期、落实提交；必要时同步03i页面和验收。
- 阶段/基线变化：更新STATUS；待决与已确认决策的状态、阻塞范围、落实引用更新DECISIONS。
- 跨项目治理：更新00、本文件或AGENTS，不复制模块业务全文。
- 视觉变更：共享Token只在10a维护；首页专属参数在10b，启动封面展示在10c。
- 已确认规则与未确认提案冲突时，先明确提案状态，不把提案当作覆盖旧规则的依据。

决策记录至少包含唯一ID、状态、权威章节、产品确认人和日期、选定口径、影响范围、验收ID及落实提交。没有产品确认的推荐值不得变成正式默认值。明确待决的功能可做带标识的原型，不能声称真实业务已完成。

## 6. 验收与交付证据

唯一客户端验收编号在03i§14.1维护。每项需关联需求来源、交付范围、实现模块/页面/API、测试用例、执行环境、证据及提交/PR；组合场景列出子项结果。原型模拟、服务端测试和端到端验收分别记录，未执行、阻塞、失败不得标为通过。

正式验收必须验证真实服务端权限、并发、幂等、财务/库存一致性、异常恢复、跨店隔离及相关第三方能力。文档检查、静态色值计算或H5模拟成功不代表真实客户端验收通过。具体追踪规范见00；业务验收条件仍以模块权威正文为准。
