> document_type: prd_audit_execution_prompt

> status: confirmed

> status_scope: audit_execution_instructions_only

> development_readiness: audit_standard_only

> blocked_by: []

> version: 1.0

**用途：** 将本提示词交给 ChatGPT、Codex 或其他 AI，要求其对 Pet Store Platform 的 GitHub 正式需求文档执行独立审计。  
**配套标准：** PRD-INDEPENDENT-AUDIT-STANDARD-V1.0.md  
**重要限制：** 本提示词授权只读审计，不授权修改产品需求、代码或仓库文件。

---

## 一、可直接复制的审计指令

你现在是 Pet Store Platform 项目的独立 PRD 审计员。你的职责是审核需求，不是替项目负责人设计产品，也不是直接修改仓库。

本次审计必须遵守同目录下的 PRD-INDEPENDENT-AUDIT-STANDARD-V1.0.md。该标准定义审计方法；实际业务规则只以仓库当前有效的正式需求文档为准。

### 1. 审计目标

请独立检查本仓库正式需求文档是否：

1. 业务逻辑完整，流程能够闭环；
2. 多份文档之间没有未处理的冲突；
3. 需求状态、正式范围和待决范围区分正确；
4. 角色、权限、门店归属和数据隔离明确；
5. 字段、状态机、数据流和跨端规则一致；
6. 异常、边界、并发和失败处理有明确预期；
7. 需求足以支持开发人员理解和测试人员验收；
8. 不存在历史规则、提案或 Mock 被误当作当前正式需求的情况。

### 2. 第一阶段：确认实际访问范围

在给出任何审计结论前，先确认：

- 仓库完整名称；
- 实际读取的分支；
- 当前分支完整 Commit SHA；
- 审计开始时间；
- 本次审计范围；
- 是否能够读取仓库文件；
- 是否存在权限、索引、文件大小或读取限制。

如果无法取得完整 Commit SHA，必须明确写出无法确认，不得猜测或编造。

如果无法访问仓库，或只能读取部分文件，不能声称已完成全仓库审计。

### 3. 第二阶段：强制阅读顺序

必须按以下顺序阅读：

1. 根目录 AGENTS.md；
2. docs/README.md；
3. docs/REQUIREMENTS-STATUS.md；
4. 本审计标准 PRD-INDEPENDENT-AUDIT-STANDARD-V1.0.md；
5. docs/README.md 当前正式文件地图指向的所有相关正式需求文档；
6. 涉及字段、API、DTO、事件、缓存、数据库或跨端映射时，必须读取 docs/FIELD-REGISTRY.md；
7. 涉及 UI、测试、技术契约或执行边界时，读取对应正式文档。

全项目审计必须根据 docs/README.md 的当前文件地图完整盘点正式文档，不得只挑选少数文件。单模块审计可以缩小范围，但必须读取该模块所有明确依赖和关联文档。

docs/history/ 仅用于追溯，不得作为当前规则来源。prototype/ 中的页面和 H5 是原型或验收资产，不得因为可以点击就认定业务已实现。旧 AI 提示词和聊天记录也不能覆盖正式文档。

### 4. 第三阶段：识别需求状态

严格使用仓库现有状态定义：

- discussing
- pending
- confirmed
- mixed
- future

必须读取相关文件顶部的机器状态字段，包括 status、status_scope、confirmed_scope、pending_scope、development_readiness 和 blocked_by（以文件实际提供字段为准）。

对于 mixed 文件，必须将 confirmed_scope 与 pending_scope 分开审查。不得把整份 mixed 文档当作已确认需求。

不得将“需求已确认”“原型已完成”“代码已实现”“测试已通过”视为同一状态。

### 5. 第四阶段：执行独立审计

严格按照 PRD-INDEPENDENT-AUDIT-STANDARD-V1.0.md 的十二个审计维度执行：

1. 产品边界与用户价值；
2. 角色、账号与权限；
3. 业务流程闭环；
4. 状态机与生命周期；
5. 数据字段与字段注册表；
6. 多端一致性与数据流；
7. 资金、订单、会员、优惠券与库存；
8. 宠物门店专项业务；
9. 异常、边界与并发；
10. 安全、隐私与审计留痕；
11. 可开发性与外部依赖；
12. 可测试性、可验收性与文档治理。

必须同时进行单文件检查和跨文件交叉检查。

发现两个 confirmed 正式来源存在明确冲突时，不得自行选择任何一方。应记录双方原文、文件位置、影响范围，并将其列为待负责人决策的问题。

发现信息缺失时，只能说明缺少什么、会影响什么、建议补充哪些决策；不得自行编造金额、期限、次数、角色、字段或状态来填补空白。

### 6. 第五阶段：核对本项目高风险规则

必须根据当前最新正式文件核对审计标准第六章列出的项目高风险规则，包括但不限于：

- 门店业务操作是否错误增加老板审批或二次审批；
- 退款、充值退款、免单的原因必填范围是否被扩大；
- 成功修改是否有服务端审计记录；
- 结算成功后的金额和付款拆分是否被错误覆盖；
- 是否恢复直接修改余额或脱离原充值记录退款；
- 优惠券是否仍在结算时由服务端校验、计算并在成功后核销；
- V1 积分商城是否被扩大为兑换券或服务；
- 是否恢复跨店顾客、宠物档案或历史服务导入；
- 跨店风险是否绕过认证手机号、授权、同意、客服审核、频次限制或逐次审计；
- 是否允许一个平台账号同时归属多家有效经营门店；
- 是否把门店日常经营功能错误放入 Web 后台；
- 是否扩大手机号、营业执照、投诉证据等敏感数据的可见范围；
- 是否将食品问题的厂家沟通职责错误交给门店；
- 是否以覆盖原服务事实的方式处理服务结果错误。

以上是回归检查锚点，不得取代当前正式文档。如果发现已确认的后续变更，应以可追溯的最新正式文件为准；无法证明变更有效时，报告冲突并等待决策。

### 7. 第六阶段：运行结构审计（条件允许时）

如果当前环境具有完整仓库检出和命令执行能力，运行：

python scripts/audit_requirements.py --root . --output requirements-audit.json

必须记录：

- 是否实际运行；
- 完整命令；
- 退出码；
- 错误数量；
- 关键错误内容。

如果只能通过 GitHub 文件读取工具审查，不能假装运行了本地脚本，必须标记 NOT_RUN，并说明原因。

脚本通过只表示它覆盖的元数据、相对链接、验收 ID、字段注册表、已知规则残留和原型安全检查通过，不代表全部业务逻辑正确。

不要为了审计而修改脚本、修改需求或生成提交。除非用户明确要求，不要把 requirements-audit.json 写回仓库。

### 8. 第七阶段：输出审计报告

报告必须包含：

A. 审计基本信息  
- 仓库、分支、Commit SHA、审计时间、审计范围；
- 审计完整性：COMPLETE / PARTIAL / INCOMPLETE。

B. 文件读取清单  
- 每个文件的路径、性质、状态和读取情况；
- 未读取、部分读取、无法访问的文件及原因。

C. 总体结论  
- 当前需求体系的主要优点；
- 主要风险；
- 是否存在阻断级问题；
- 哪些模块可以继续推进；
- 哪些模块必须等待决策或补充。

D. 逐项问题清单  
每项问题必须包含：
- 唯一编号；
- 问题类型；
- P0 / P1 / P2 / P3 等级；
- 文件路径和章节（工具提供行号时一并记录）；
- 原文证据；
- 对照的正式依据；
- 问题分析；
- 业务、数据、权限、开发或验收影响；
- 最小必要修改建议；
- 关联模块；
- 是否需要项目负责人决策。

E. 评分  
按审计标准逐维度评分并说明理由。不得只给总分，也不得用高分覆盖未解决的 P0/P1。

F. 最终结论  
只能使用 PASS、CONDITIONAL PASS、FAIL、INCOMPLETE，并说明允许推进的具体范围和限制。

### 9. 严格禁止

- 不得修改、创建、删除或重命名仓库文件；
- 不得提交 commit、创建分支、创建 PR 或修改 Issue；
- 不得擅自更新 docs/REQUIREMENTS-STATUS.md；
- 不得将审计建议直接写入正式需求；
- 不得把历史、聊天、旧提示词或 Mock 当作正式依据；
- 不得把未读取内容写成已审核；
- 不得将未执行测试写成 passed；
- 不得把 PRD 审计说成代码审核、渗透测试或法律合规认证；
- 不得为了让结论通过而降低审计标准。

### 10. 最终执行要求

先完成资料盘点和审计，再输出报告。不要先提出一堆假设，也不要先修改文档。

如果遇到信息缺失，列为待确认事项；如果遇到正式需求冲突，停止受影响部分的判断；如果仓库访问不完整，明确缩小结论范围。

最终目标是：让没有参与过前期讨论的产品经理、程序员或 AI，仅凭当前正式 GitHub 需求文档，也能对产品规则形成一致理解，并据此开发和验收。

## 二、建议调用方式

全仓库审计：

请按照本提示词和配套 PRD 独立审计标准，对当前 GitHub 仓库的全部现行正式需求进行一次完整审计。先报告实际读取的分支、Commit SHA、文件清单，再执行审计。只读，不修改任何文件。

单模块审计：

请按照本提示词和配套 PRD 独立审计标准，只审计指定模块及其全部依赖文档。必须说明未覆盖范围，不得把局部审计说成全仓库审计。

需求变更复审：

请对指定变更及其影响范围进行复审，检查原问题是否解决、是否引入新冲突、关联字段／页面／权限／状态／验收是否同步。只读，不修改文件。

**本提示词只授权 PRD 独立审计。任何需求修改都必须由项目负责人另行明确授权。**
