## 1. 目的与适用范围

本标准用于在需求进入开发或需求冻结前，对 PRD 进行独立、可追溯、可复核的审计。审计目标不是润色文字，而是发现会导致产品理解不一致、业务流程断裂、数据错误、越权访问、开发返工或无法验收的问题。

审计覆盖：

1.  单份需求文档的完整性、明确性和可测试性。
2.  多份正式文档之间的规则一致性。
3.  客户端、店员端、平台后台之间的业务与数据一致性。
4.  字段注册表、状态机、权限、流程、异常和验收标准。
5.  新旧规则、正式需求、提案、历史材料及原型之间的边界。
6.  需求变更对关联模块的影响。

本仓库当前是 V1.0 正式需求文档仓库，不应仅凭页面原型或文档内容声称已有可运行、可部署的完整应用。审计 PRD 不等于审计代码；没有读取或执行的内容必须明确标注未检查。

## 2. 权威来源与读取顺序

审计前必须先读取并遵守以下来源：

1.  根目录 `AGENTS.md`：仓库级强制约束、禁止事项和阶段边界。
2.  `docs/README.md`：正式文档地图、职责边界、阅读顺序和权威关系。
3.  `docs/REQUIREMENTS-STATUS.md`：当前阶段、需求状态、待决项和开发准备度。
4.  `docs/README.md` 指向的当前正式模块文档。
5.  `docs/FIELD-REGISTRY.md`：涉及字段、API、DTO、事件、缓存、数据库或跨端数据映射时必须读取。
6.  对应的 UI、测试、技术或执行文档：仅在审计范围涉及这些内容时读取。

以下内容默认不是当前正式需求来源：

-   `docs/history/` 中的历史归档；
-   聊天记录、口头讨论和未同步到正式文档的决定；
-   旧 AI 方案、外部参考材料；
-   临时 H5、Mock、截图和演示页面；
-   其他仓库中的相似实现。

如果正式文档明确引用某项历史材料作为追溯证据，可以阅读，但不得把历史材料当作现行规则。若原型与正式需求冲突，以正式需求为准，并将原型偏差列为问题。

### 2.1 必须动态识别当前基线

不得把本标准制定时的阶段状态永久写死。每次审计都必须重新读取 `REQUIREMENTS-STATUS.md`，确认：

-   `current_stage`
-   `stage_status`
-   各模块状态
-   `development_readiness`
-   `blocked_by`
-   当前有效的业务基线和后续阶段边界

不得因为某一模块 `confirmed`，就推断整个项目已经冻结或所有模块都可以开发。

## 3. 需求状态识别

本项目使用的需求状态枚举以仓库正式规则为准，包括：

-   `discussing`
-   `pending`
-   `confirmed`
-   `mixed`
-   `future`

不得自行创造另一套状态枚举并覆盖仓库现有定义。

### 3.1 `confirmed`

只有明确标记为 `confirmed` 的范围，才能作为已确认需求依据。若文件同时存在范围限定字段，必须遵守 `status_scope` 等元数据，不能把局部确认扩大为整份文档确认。

### 3.2 `mixed`

必须分别读取：

-   `confirmed_scope`
-   `pending_scope`
-   `blocked_by`
-   `development_readiness`

只允许将 `confirmed_scope` 作为已确认依据。`pending_scope` 不得被推断、补齐或转写成正式需求。

### 3.3 其他状态

-   `discussing`：仍在讨论，不作为已冻结规则。
-   `pending`：等待决策或依赖条件，不得自行关闭。
-   `future`：未来范围，不得误写为 V1.0 已交付要求。

### 3.4 需求状态与实现状态分离

需求已确认，不代表代码已实现；页面可交互，不代表后端、微信能力、支付、权限或数据持久化已实现。审计报告必须分别描述需求状态、设计状态、原型状态和实现证据，不得混为一谈。

## 4. 独立审计的基本原则

审计员必须：

1.  先确认仓库、分支、提交 SHA 和审计范围。
2.  先读权威来源，再读被审计文档。
3.  对问题提供可定位的原文证据。
4.  区分确定性错误、信息缺失、潜在风险和优化建议。
5.  对两个已确认来源的明确冲突停止推断，提交决策问题。
6.  仅提出建议，不擅自改变产品规则。
7.  不以行业惯例、个人偏好或技术便利代替产品决策。
8.  不将未读取文件描述为已审计。
9.  不将结构脚本通过等同于业务逻辑正确。
10. 不因问题数量少而降低审计深度，也不为了显示价值而制造问题。

**默认只读：** PRD 审计任务不得直接修改正式需求、字段注册表、状态文件、原型或代码。用户另行明确授权修改时，必须先列出拟修改文件与变更内容，再按授权范围执行。

## 5. 十二维度审计清单

### 5.1 产品边界与用户价值

-   功能解决什么实际经营问题？
-   目标用户、使用场景和触发条件是否明确？
-   是否超出当前 V1.0 范围？
-   是否与产品定位或已确认的简化原则冲突？
-   是否为了"功能完整"而增加小型门店不必要的操作？
-   是否存在重复功能或职责重叠？

### 5.2 角色、账号与权限

-   每个操作由谁发起、谁能查看、谁能修改？
-   老板、员工、顾客、平台管理员的边界是否明确？
-   页面权限、操作权限和数据权限是否分别定义？
-   是否存在只隐藏前端按钮、未约束服务端访问的设计？
-   账号、认证手机号、微信凭据和门店归属是否混用？
-   是否存在跨门店读写或越权导出风险？

### 5.3 业务流程闭环

每个重要流程都应检查：

-   触发条件；
-   前置条件；
-   操作角色；
-   正常路径；
-   成功结果；
-   失败处理；
-   取消、中止、重试和恢复规则；
-   对关联对象的影响；
-   操作记录和通知要求；
-   完成条件及验收方式。

不得只审查正常流程。流程图、文字说明和页面入口必须相互一致。

### 5.4 状态机与生命周期

对订单、服务、寄养、会员、投诉、审核、库存、兑换等有生命周期的对象，检查：

-   状态定义和含义；
-   状态转换触发条件；
-   有权触发转换的角色；
-   是否允许跳转、回退、重复操作；
-   终态及终态后的行为；
-   并发状态变化；
-   失败或取消后的数据处理；
-   各端展示是否一致。

只有状态列表、没有转换规则，不视为完整状态机。

### 5.5 数据字段与字段注册表

涉及字段、API、DTO、事件、缓存 Key、数据库字段、导入导出或跨端映射时，必须对照 `FIELD-REGISTRY.md`。

检查：

-   是否复用已有永久注册号和逻辑字段名；
-   是否存在同义字段、重复字段或一字段多义；
-   类型、单位、精度、枚举、默认值和可空性是否明确；
-   字段来源、归属、写入者和读取者是否明确；
-   修改后是否影响历史记录或其他模块；
-   金额、时间、数量和状态的口径是否一致。

不得为了局部方便新造第二套字段名。注册表负责字段标识和含义，不得覆盖业务模块中的权限、状态迁移和业务规则。

### 5.6 多端一致性与数据流

对客户端、店员端和平台 Web 后台进行横向核对：

-   同一业务对象是否使用统一概念；
-   同一状态是否具有相同含义；
-   同一字段是否存在不同解释；
-   各端操作权限是否冲突；
-   数据更新、同步和失败反馈是否明确；
-   是否出现一端允许操作、另一端无法识别的状态；
-   页面蓝图与详细业务文档是否一致。

平台 Web 后台与门店日常经营后台必须区分，不得擅自把门店经营功能扩展到 Web 端。

### 5.7 资金、订单、会员、优惠券与库存

重点检查：

-   应收、实收、付款拆分、退款和补收的口径；
-   结算成功后的数据锁定规则；
-   原单、原充值记录和退款记录之间的关联；
-   会员余额、赠送金额、积分的来源和去向；
-   优惠券适用范围、校验、并发占用和核销时点；
-   商品库存的入库、销售、退货、调拨和纠错来源；
-   重复提交、重复扣减、重复退款和并发结算；
-   财务与库存记录是否可追溯。

不得以直接覆盖余额、覆盖原收款或删除历史记录的方式掩盖业务错误。

### 5.8 宠物门店专项业务

检查客户与宠物档案、洗护、美容、寄养、上门喂养、员工待办、员工业绩、宠物食品风险反馈、平台积分实物等业务的边界。

特别核对：

-   客户与宠物关联及资料冲突处理；
-   服务开单、开始、完成、取消和重新开单；
-   寄养计费、实际离店和照护记录；
-   门店停用后的未完成服务或待办处理；
-   员工业绩归属、退款扣减和历史归属；
-   食品问题平台处理与门店知悉的职责边界；
-   投诉证据、人工裁决、集中反馈和风险提示；
-   积分实物异常及领取门店停用后的处理。

不得把不同业务对象的规则混用，也不得恢复已废弃的平行流程。

### 5.9 异常、边界与并发

至少考虑与功能相关的以下情形：

-   网络中断、超时、恢复；
-   重复点击、重复提交、请求重放；
-   两名员工同时修改；
-   旧页面提交过期数据；
-   数据不存在、失效或已终结；
-   权限变化或门店停用；
-   库存不足、余额不足、金额不一致；
-   第三方服务失败、消息发送失败；
-   部分成功、补偿和重试；
-   时区、跨日、计费边界和限频。

不是每个边界都需要单独新增功能，但重要边界必须有明确的预期行为。

### 5.10 安全、隐私与审计留痕

检查：

-   租户隔离是否在服务端落实；
-   手机号、宠物资料、营业执照和投诉证据的可见范围；
-   数据导出和分享权限；
-   关键操作是否记录操作者、服务端时间、修改前值和修改后值；
-   日志是否可追溯且不被普通用户篡改；
-   账号停用、身份变更和门店关系变化后的访问控制；
-   通知内容是否泄露不应公开的信息。

### 5.11 可开发性与外部依赖

检查需求是否足以让开发人员理解业务约束，并识别：

-   第三方支付、微信登录、订阅消息、广告等外部能力；
-   AppID、环境、权限、服务端接口和供应商依赖；
-   API、DTO、数据模型和错误码是否属于后续技术设计；
-   哪些是业务需求，哪些是技术方案；
-   未定义的技术契约是否被错误地当成已确定事实。

业务需求不必提前写成代码设计，但必须明确业务结果、约束、权限和验收要求。

### 5.12 可测试性、可验收性与文档治理

检查：

-   每项重要需求能否形成测试用例；
-   验收结果是否客观可观察；
-   是否存在"正常、合理、及时、方便"等无定义词；
-   客户端验收 ID 是否沿用 `03i` 的唯一来源；
-   需求与页面、字段、权限、状态和测试是否可追踪；
-   相对链接、文件职责和阅读顺序是否正确；
-   归档内容是否被误当作现行规则；
-   正式文档与原型、执行提示词是否发生漂移。

## 6. 本项目必须重点防止的规则回退

每次审计都必须重新对照当前正式文档，至少核查以下高风险规则。以下是审计检查锚点，不取代详细模块文档；如当前正式文件已依法变更，以最新确认版本为准。

1.  所有门店业务操作不设置老板审批或二次审批；只有消费退款、充值退款和免单的原因必填，其他原因选填。
2.  每次成功修改由服务端自动记录操作人、服务端时间、修改前值和修改后值。
3.  消费结算成功后，最终应收、实收、付款拆分和收款时间锁定；少收走原单补收，多收或不应收走退款。
4.  不提供"更正收款"或直接修改余额；已入账充值退款必须关联原充值记录。
5.  优惠券和活动券在结算时选择，由服务端校验和计算，结算成功后自动核销并关联原单。
6.  V1 积分商城只兑换实物，不兑换券、服务活动或商品活动。
7.  V1 不提供跨店顾客／宠物档案或服务护理历史导入。
8.  跨店顾客风险按认证手机号匹配，并遵守双方门店授权、顾客分项同意、真实业务触发、客服审核、每个查看门店对同一顾客每自然月最多3次及逐次审计；顾客端不展示风险记录，也不提供自助申诉。
9.  同一平台账号同一时刻只能归属一家有效经营门店。
10. 门店日常经营和老板设置在店员小程序；网页后台只供平台使用。
11. 员工可查看本店顾客完整手机号；营业执照仅本店老板和平台管理员可查看。
12. 投诉证据等级由审核员人工判断，不得把证据等级变成算法自动定责。
13. 食品问题由平台联系厂家，门店仅接收知悉通知，不承担前置核实或厂家沟通。
14. 服务结果错误不得通过覆盖原服务事实来修正；按正式规则重新开单或处理。
15. 原型、Mock、截图和静态检查不能证明真实后端、权限、支付、微信能力或财务流程已验收。

若审计发现正式文档与上述锚点冲突，先检查是否存在更新的已确认变更；无法证明变更有效时，列为冲突并等待负责人决策，不得自行选择。

## 7. 问题分类与严重程度

### 7.1 问题类型

-   `CONFLICT`：正式来源之间存在冲突。
-   `AMBIGUITY`：表述可能产生两种或以上合理解释。
-   `MISSING`：缺少实现或验收所必需的信息。
-   `INCONSISTENCY`：跨端、跨字段或跨文档口径不一致。
-   `DUPLICATION`：重复定义或存在多个权威来源。
-   `SCOPE_LEAK`：把提案、未来范围、历史或 Mock 当作正式需求。
-   `SECURITY`：权限、隐私、租户隔离或审计风险。
-   `DATA_INTEGRITY`：资金、库存、会员、状态或数据关联风险。
-   `TESTABILITY`：无法形成客观测试或验收。
-   `FEASIBILITY`：技术依赖或实现前提不成立。
-   `DOC_GOVERNANCE`：文件地图、元数据、链接或变更记录问题。
-   `IMPROVEMENT`：非阻断优化建议。

### 7.2 严重程度

-   **P0 阻断：** 核心业务无法成立，或存在重大资金、安全、隐私、租户隔离风险；必须先解决。
-   **P1 严重：** 重要规则缺失或冲突，会造成不同实现、严重返工或核心功能错误；受影响模块原则上不得进入开发。
-   **P2 一般：** 局部不明确、边界遗漏或文档不一致，可能增加返工或维护成本；应安排修复。
-   **P3 建议：** 可读性、体验或结构优化，不构成明确需求错误。

严重程度必须结合影响范围和证据判断。不能仅凭"看起来复杂"评为 P0，也不能因问题只出现在一个文件就忽略其跨模块影响。

## 8. 审计执行流程

### G0：确认审计基线

记录：

-   仓库完整名称；
-   分支；
-   完整 Commit SHA；
-   审计日期；
-   审计范围；
-   可访问性和读取限制。

审计期间若分支头发生变化，应停止继续沿用旧基线，重新确认 SHA。

### G1：文件盘点与分类

列出实际读取的正式需求、技术、字段、UI、测试、执行、历史和原型文件，并标注：

-   已读取；
-   部分读取；
-   未读取；
-   无法访问；
-   正式来源；
-   历史来源；
-   提案；
-   原型 / Mock。

不得根据文件名推断文件状态。

### G2：建立需求追踪

对重要需求建立审计索引，记录需求原文、文件路径、章节、状态、关联模块和验收来源。客户端验收 ID 沿用 `03i`，不得另造冲突的 C-ID；字段 ID 沿用 `FIELD-REGISTRY.md`。

### G3：单文档审计

按第五章十二个维度检查每份纳入范围的文档。

### G4：跨文档审计

至少建立以下交叉关系：

-   总纲 ↔ 详细业务模块；
-   客户端 ↔ 店员端 ↔ 平台后台；
-   业务规则 ↔ 字段注册表；
-   业务流程 ↔ 状态机；
-   需求 ↔ UI 页面蓝图；
-   需求 ↔ 测试与验收；
-   当前正式文档 ↔ 历史归档边界；
-   正式需求 ↔ 原型 / Mock 边界。

### G5：结构检查与专项检查

如果仓库检出和执行环境可用，运行：

`python scripts/audit_requirements.py --root . --output requirements-audit.json`

记录原始退出码和结果。若无法执行，写明 `NOT_RUN` 及原因。该脚本通过只代表其覆盖的元数据、链接、验收 ID、字段和当前规则检查通过，不代表全部业务逻辑正确。

### G6：形成报告与决策清单

问题必须有唯一编号、证据、影响、建议和是否需要负责人决策。对证据不足的内容标记"待确认"，不得包装成确定性缺陷。

### G7：复审

只有在正式需求被授权修改后，才复核原问题是否关闭、是否引入新冲突、是否更新关联文件和验收依据。审计员不得自行关闭未验证的问题。

## 9. 审计报告格式

### 9.1 基本信息

| 字段 | 内容 |
|---|---|
| 仓库 | `owner/repository` |
| 分支 | 实际分支 |
| Commit SHA | 完整 SHA |
| 审计范围 | 实际路径 / 模块 |
| 审计日期 | 实际日期 |
| 审计员 | 实际执行者 |
| 审计完整性 | COMPLETE / PARTIAL / INCOMPLETE |

### 9.2 读取清单

| 路径 | 文件性质 / 状态 | 读取情况 | 备注 |
|---|---|---|---|
| `AGENTS.md` | 仓库规则 | 完整 / 部分 / 未读 | |
| `docs/README.md` | 文件地图 | 完整 / 部分 / 未读 | |
| `docs/REQUIREMENTS-STATUS.md` | 当前基线 | 完整 / 部分 / 未读 | |
| 其他文件 | 按实际填写 | | |

### 9.3 问题清单

每个问题采用以下结构：

-   **ID：** `AUDIT-模块-序号`
-   **类型：** 上述问题类型之一
-   **等级：** P0 / P1 / P2 / P3
-   **位置：** 文件路径、章节、行号（如工具提供）
-   **证据：** 原文短摘录或可定位的内容
-   **依据：** 对照的正式来源及其状态
-   **问题分析：** 为什么构成问题
-   **影响：** 对用户、业务、数据、权限、开发或验收的影响
-   **建议：** 最小必要修改方向，不直接代替产品决策
-   **关联项：** 受影响文件、字段、页面、状态、测试
-   **决策要求：** 是否需要项目负责人确认

### 9.4 总结

报告必须包括：

-   已审计范围和未覆盖范围；
-   文件读取完整性；
-   P0 / P1 / P2 / P3 数量；
-   十二维度评价及理由；
-   核心冲突与待决事项；
-   受影响模块；
-   建议优先级；
-   是否允许相关模块进入下一阶段。

### 9.5 结论

只允许使用以下结论：

-   **PASS（通过）：** 范围完整，未发现未解决 P0/P1，且满足约定准入条件。
-   **CONDITIONAL PASS（有条件通过）：** 无 P0，但存在明确列出的 P1/P2 或待决事项；必须说明允许推进的具体范围和禁止推进的范围。
-   **FAIL（不通过）：** 存在未解决 P0，或关键业务规则无法确定。
-   **INCOMPLETE（不完整）：** 仓库、文件或审计范围不完整，无法作出可靠结论。

评分不能覆盖阻断问题。即使分数很高，只要存在未解决 P0，仍不得判定 PASS。

## 10. 审计评分（辅助，不替代结论）

每个维度按 0–5 分评价：

-   0：缺失或存在重大错误；
-   1：严重不完整；
-   2：存在较多问题；
-   3：基本完整，仍有局部缺口；
-   4：完整，仅有少量非阻断问题；
-   5：完整、明确、可追溯、可验证。

可按十二维度分别评分并给出理由。若汇总为百分制，必须公开权重和计算方法。不得只给总分；不得用分数掩盖 P0/P1 或资料不完整。

## 11. 禁止事项

审计员不得：

1.  直接修改正式需求或把建议自动合并为需求。
2.  将 `pending`、`discussing`、`future` 或 `mixed` 中未确认部分当作正式规则。
3.  从历史文件、旧提示词或旧原型恢复已废弃规则。
4.  因行业惯例而擅自补充期限、金额、次数、角色或状态。
5.  自行解决两个已确认文件之间的冲突。
6.  把 Mock、H5、截图或静态脚本结果当作真实业务验收。
7.  把 PRD 审计说成代码安全审计、渗透测试或法律合规认证。
8.  对未读取、未执行或无法访问的内容声称已验证。
9.  删除难实现需求或通过降低需求标准让审计通过。
10. 为了提高评分而新增不必要的产品功能。

## 12. 版本与变更

-   本标准只定义审计方法，不定义新的产品业务规则。
-   本标准修改必须记录版本、日期、修改原因和影响范围。
-   业务规则变更必须回到对应正式模块文档，不得只修改本标准。
-   当本标准与 `AGENTS.md`、`docs/README.md` 或正式业务模块冲突时，遵守仓库权威来源，并将标准冲突列为治理问题。

**本标准的核心要求：有证据才报告，有冲突不猜测，有建议不代替决策，未审计不声称通过。**
