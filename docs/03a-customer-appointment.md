## 1. 设计原则

- 客户端尽量少步骤。
- 店员确认预约尽量一屏完成。
- 预约不在线支付，显示价格仅为参考价。
- 预约与正式服务订单分离。
- 不要求商户维护复杂员工个人排班。
- 能自动带出的客户、宠物、寄养资料不重复填写。
- 线下临时到店客户可由店员直接快速开单，不强制先建预约。

## 2. 预约类型

V1.0 支持：

- 洗护
- 美容
- 寄养

## 3. 洗护 / 美容预约

客户流程：选择宠物 → 选择服务 → 选择日期和时间 → 确认预约。

规则：

- 只有一只宠物时自动预选。
- 无宠物档案时可在当前流程添加，保存后自动返回预约流程。
- 支持一次预约多只宠物，系统内部为每只宠物建立独立服务项。
- 服务项目由商户配置，可只配置洗护 / 美容大类，也可配置细分项目。
- 所有预约价格均为参考价，最终金额以实际结算为准。
- 客户不能自由输入预约时间，只能选择门店开放的预约时段。
- 商户设置营业时间、预约间隔、每时段最大预约量。
- 商户可关闭单个时间段、半天或全天。

## 4. 预约确认

客户提交后状态为“待门店确认”，不直接视为预约成功。

店员预约卡片直接提供：

- 确认
- 调整时间
- 拒绝

正常预约一键确认。

调整时间时系统优先推荐附近可用时间，门店发送建议后由客户接受或重新选择；门店不得无提示直接修改客户时间。

拒绝预约优先使用快捷原因，选择“其他”时才要求输入文字。

## 5. 客户侧预约状态

- 待确认
- 待确认新时间
- 已确认
- 已取消
- 已完成

预约状态与服务状态分开。客户到店并由店员开始服务后，才进入等待中 / 洗护中 / 洗护完毕等正式服务状态。

## 6. 修改与取消

- 服务尚未开始时客户可取消预约。
- 修改已确认预约后需重新由门店确认。
- 商户可设置距预约开始前 X 小时后禁止客户自行修改 / 取消。
- 平台 V1.0 不设置预约订金、违约金。

## 7. 寄养预约

流程：选择宠物 → 入住日期时间 → 离店日期时间 → 确认寄养资料 → 填写本次特殊要求 → 提交 → 门店确认。

宠物档案中的长期寄养资料自动带出，客户只需确认或做本次临时修改。

商户可设置建议最大寄养容量；预计超量时系统提示客户和门店，但 V1.0 不强制禁止提交，由门店人工确认。

## 8. 防重复与并发

- 提交按钮需防重复点击。
- 同一宠物存在高度重叠预约时提醒客户，但不绝对禁止。
- 时段名额以后端提交时实时校验为准。
- 时段刚被占满时直接提示并推荐附近可用时间。

## 9. 线下快速开单

店员端必须支持：选择客户 / 宠物 → 选择服务 → 立即开始。

系统后台自动创建正式订单和服务记录，避免线下临时客户被迫经过预约流程。

## 10. V1.0 暂不实现

- 员工个人预约日历
- 客户指定美容师
- 复杂员工排班匹配
- 预约订金 / 违约金
- 自动候补
- AI 自动排班
- 复杂寄养房型预订

## 11. 预约容量与改期逻辑提案（待确认）

> 提案日期：2026-09-08。用户要求设计第 3 项预约逻辑；本节是推荐方案，不属于第 1～10 节已确认基线。待用户确认后才同步正式状态、接口和验收，不能因本文件主体已确认而自动实施本节。

### 11.1 推荐原则与代价

采用“申请不占正式名额，双方确认后占位；改期成功才释放原预约”的轻量模型。

理由：V1 需要门店人工确认、没有订金、不做复杂排班。让未处理申请长期占位会压住可预约时段，还需要额外的占位计时、营业时间暂停及释放规则。推荐方案把承诺时点放在正式确认，门店只需处理确认 / 建议时间 / 拒绝三个动作。

代价必须向客户说明：提交申请并不保留名额；多笔待确认申请可能竞争同一个剩余名额，先完成有效确认者获得名额，其余重新选时间。提交成功页固定表达“预约申请已提交，等待门店确认；当前尚未保留名额”，不能显示“预约成功”或虚假的名额保留倒计时。

### 11.2 容量口径

- 洗护 / 美容以“门店 + 到店时段”的宠物数量计算共享到店容量；一只宠物的一次到店服务占 1 个名额，同次护理加项不额外占位。两只宠物同批到店占 2 个名额。
- 该容量限制到店量，不代表员工工时安排或服务完成时间；不新增个人排班、自动候补、服务时长算法。
- 待确认申请不占正式名额；已确认预约占位。服务开始后，原时段名额标记为已使用，不因进入服务中或服务完成而重新出售该时段。
- 新申请提交时校验当前正式容量和开放状态，已满则不提交并推荐其他时段；提交、门店确认、客户接受门店新时间都必须重新以服务端实时容量校验。
- 同一批多宠提交 / 确认 / 改期均全部成功或全部失败，禁止在客户不知情时只确认其中一只。需要分批或分时段时，客户明确同意后拆成独立预约。
- 寄养继续沿用第 7 节“建议容量、超量提示、门店人工确认”；不套用本节洗护 / 美容硬名额逻辑。

### 11.3 状态与名额表

| 业务状态 / 操作 | 客户看到什么 | 原名额 | 新名额 | 处理结果 |
|---|---|---|---|---|
| 新申请待门店确认 | 申请已提交，尚未保留名额 | 无 | 不占位 | 门店确认时原子校验并占位；失败仍未确认并引导改时段 |
| 门店确认新申请 | 已确认，显示实际日期 / 时段 | 无 | 占 N 个宠物名额 | 确认与占位一次成功，失败不能先通知预约成功 |
| 客户修改未确认申请 | 更新后的申请待确认 | 无 | 不占位 | 原申请版本失效，门店不能操作旧版本 |
| 客户申请修改已确认预约 | 改期待门店确认；原预约仍有效 | 保留 | 不占位 | 门店同意时，一次完成新占位与原释放；新时段满则保留原预约 |
| 门店提出新时间 | 待确认新时间；展示原预约是否仍有效 | 若原本已确认则保留 | 不占位 | 客户接受时校验并完成切换；失败保留原承诺，不静默改时段 |
| 改期建议被拒绝 / 撤回 / 失效 | 原预约仍有效；或原申请仍待确认 | 保持原状 | 无需释放 | 仅关闭改期提议，不隐含取消整笔预约 |
| 取消 / 门店拒绝，且未开始服务 | 已取消 + 真实原因 | 如有则释放一次 | 不占位 | 权限 / 截止按第 6 节校验，保留操作人与历史 |
| 到店开始服务 | 进入正式服务进度 | 标记已使用 | 不占位 | 幂等关联正式服务记录；预约与订单继续分离 |
| 未到店 | 店员核实后显示已取消·未到店 | 结束占位记录，不重开过去时段 | 不占位 | 不仅凭到点自动认定失约，不产生虚假服务订单 |

### 11.4 改期必须保住原预约

- 任一时刻最多一个有效改期提议，保存提议版本、发起人、原时段、建议时段和状态。对过期提议或旧消息的“接受”不生效，返回当前详情。
- 客户自己选的新时间，经门店同意即可完成；门店提出的新时间必须由客户接受后完成。系统按动作双方已经表达的同意识别确认方，不要求重复确认一遍。
- 原时段与新时段相同时，按宠物数量差额 Δ 校验：Δ > 0 只校验追加名额；Δ ≤ 0 不要求重新取得自己已持有的名额，即使门店降低容量至低于现有占用也应允许合法减宠。
- 新占位、原名额释放、预约版本更新应作为一次不可分割的业务成功；重复点击或响应丢失后重试返回同一结果。
- 原预约在改期期间仍有效，客户可按原时段到店。同批任一宠物服务开始，整批尚未接受的改期提议即失效；名额按实际开始的服务项标记已使用，其余维持预约占位。开始与改期必须校验同一预约版本：改期先成功时，基于旧版本 / 旧时段的开始请求同样失败并返回当前预约，不能两边都成功。
- 若门店确实无法履行原预约，必须明确说明并按取消 / 拒绝流程处理，不得一边表示“原预约仍有效”一边实际停止履行。

### 11.5 超时、关店与截止

- 未确认申请到所申请时段开始仍未确认：结束为“已取消·确认超时”，不标记“未到店”。若仍需到店服务，按现有快速开单或重新申请流程处理。
- 改期提议的有效截止不晚于建议时段开始；有已确认原预约时，也不晚于原时段开始。门店发起、等待客户接受的提议，还须取第 6 节对应客户接受截止的最早值；创建时已过截止不得发送无法接受的提议。任一方及时主动关闭提议同样保留历史。
- 建议失效只影响改期提议；原预约或原申请继续按自身状态处理。原申请本身到时仍未确认，适用上一条确认超时规则。
- 客户操作继续遵循第 6 节已确认的可修改 / 取消截止配置。客户已在允许时间提出、等待店员确认的改期，不因客户自助截止到达而自动禁止店员确认；仍需满足原 / 新时段开始前、未开始服务等条件。每次接受 / 确认都以服务端当前时间重新校验，不依赖超时任务是否及时执行。
- 门店关闭某时段后，禁止新申请，也禁止将已有待确认申请或其他时段提议确认到该时段；原已确认预约继续有效，不静默取消。原时段内不新增占位的资料修改 / 减宠不视为新占位。受影响记录进入门店处理清单并逐笔通知，降低容量不能把已有预约无痕挤掉。
- 各时间判断使用服务端权威时间并按全局业务时区 `Asia/Shanghai` 计算；本提案不引入任意“30 分钟自动作废”等额外默认值。

### 11.6 典型推演（提案验收，尚未成为正式门槛）

| 场景 | 预期结果 |
|---|---|
| 10:00 容量 2，已有 1 只确认；A / B 都提交 1 只申请 | 两笔均可待确认且不占位；门店先确认 A 成功后，B 确认失败并获得其他时段建议，最终占用不超过 2 |
| 剩 1 个名额，客户一次申请 2 只 | 整批不提交 / 不确认，不能偷偷确认 1 只；客户可主动拆分 |
| 已确认 10:00，申请改 11:00；11:00 被他人先确认满 | 改期失败，10:00 仍有效，原名额未释放 |
| 两只宠物从 10:00 成功改到 11:00 | 同次操作在 11:00 占 2 个、在 10:00 释放 2 个；超时重试不重复处理 |
| 客户收到新时间消息，但之后门店更新了提议 | 旧消息接受失败并展示最新提议，不更改当前预约 |
| 客户接受改期与店员开始原预约服务同时发生 | 只有一个合法状态转移成功；任一宠物开始服务后整批提议失效，改期先成功则旧版本开始请求失败 |
| 提议目标时段随后关闭，客户从旧消息接受 | 拒绝改入关闭时段，原已确认预约保留；同原时段合法减宠不被当作新增占位 |
| 新申请到时仍未确认 | 显示确认超时；不占位、不认定客户失约、不生成服务单 |
| 已确认预约到时，店员尚未核实客户是否到店 | 保留真实状态，不能自动标记客户失约；后续由店员确认开始服务或未到店 |

本提案待确认的核心决策为 `DEC-APPT-01`：是否采用以上“待确认不占正式名额”的整套模型。确认前不改写现有预约状态或实施接口；第 1～10 节继续作为已确认事实来源，其中原有未闭合处仍需按提案决策处理。
