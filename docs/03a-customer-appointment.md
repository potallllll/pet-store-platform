## 1. 设计原则

- 客户端尽量少步骤。
- 店员确认预约尽量一屏完成。
- 预约不在线支付，显示价格仅为参考价。
- 预约与正式服务订单分离。
- 不要求商户维护复杂员工个人排班。
- 面向老板加少量店员的社区小店，以门店人工判断忙闲为准；不把典型“两个人”写成员工人数上限。
- 能自动带出的客户、宠物、寄养资料不重复填写。
- 线下临时到店客户可由店员直接快速开单，不强制先建预约。

## 2. 预约类型

V1.0 支持：

- 洗护
- 美容
- 寄养

客户端预约类型仍仅以上三类。店员项目管理新增“护理”“商品”不扩张本列表：护理仅供门店开单，商品继续走03e购买需求，不伪装为预约服务；原寄养预约不删除。

## 3. 洗护 / 美容预约

客户流程：选择宠物 → 选择服务 → 选择日期和期望到店时间 → 提交申请 → 等待门店确认。

规则：

- 只有一只宠物时自动预选。
- 无宠物档案时可在当前流程添加，保存后自动返回预约流程。
- 支持一次预约多只宠物，系统内部为每只宠物建立独立服务项。
- 服务项目由本店老板按04§3.0.8配置，可只建洗护／美容基础项目或自行命名细分项目；顾客预约只选择其中洗护／美容项目，护理仅供门店开单，商品不进入预约列表。
- 服务项目支持新增／修改／停用／恢复，顾客预约与门店开单共用主资料。停用阻止全新预约；停用前已提交且未终结的待确认／已确认预约可按原项目／原宠物继续确认和转开单，不自动取消。原提交快照是例外依据，不允许新加停用项目／宠物、复制或复活取消／超时预约；其他营业、6小时截止、双方确认等规则仍须校验。
- 所有预约价格均为参考价，最终金额以实际结算为准。
- 服务项目四项表单及校验按04§3.0.8；参考价必填、大于0、最多两位小数，不用0元表示待定。门店可按03d§10.1不限幅整单调价或明确确认零元免单，不回写预约参考事实／全店参考价；顾客不能在客户端改价。
- 客户选择营业范围内的期望到店日期时间；它是申请，不代表门店已承诺接待，不要求对应预生成的固定间隔时段。
- 门店只设置营业时间及临时关闭（某段时间、半天或全天），入口及老板操作规则见04§3.0.7；客户端、店员端和后台均不设置固定预约间隔、每时段名额或隐藏的默认容量。
- 取消洗护／美容按时段名额自动拦截、确认占位和改期释放名额；同一时间有其他申请或已确认预约，不自动使新申请“已满”。是否接待由门店人工确认，不能改成系统自动确认。
- 服务端仍校验营业范围、临时关闭、预约版本、业务状态和操作资格；提交申请、门店确认、提出／接受新时间均需校验目标时间。客户端不能用手输时间或旧页面绕过关闭限制。

## 4. 预约确认

客户提交后状态为“待门店确认”，不直接视为预约成功。

提交成功页固定提示“预约申请已提交，等待门店确认；实际到店时间以门店确认结果为准”。不显示“预约成功”、剩余名额、抢位或保留名额倒计时。

店员预约卡片直接提供：

- 确认
- 调整时间
- 拒绝

正常预约一键确认。

门店根据当前预约与实际忙闲提出营业范围内、未临时关闭的新时间，由客户接受或重新选择；门店不得无提示直接修改客户时间，也不由系统推算剩余名额或承诺某个时间必能接待。

门店拒绝预约或建议改期时原因选填，空原因可提交；快捷原因也可不选，选择“其他”不强制补文字。填写时向顾客展示真实原因，未填只显示处理结果，不自动补忙碌等理由；前端、API、服务端及持久化均不得以缺原因为由阻断，详见04§3.7。

人工确认、改期、开始服务及并发一致性按第11节执行；取消的是容量占位机制，不取消正式确认及原预约保护。

## 5. 客户侧预约状态

- 待确认
- 待确认新时间
- 已确认
- 已取消
- 已完成

预约状态与服务状态分开。客户到店并由店员开始服务后，才进入等待中 / 洗护中 / 洗护完毕等正式服务状态。

## 6. 修改与取消

- 服务尚未开始时客户可取消预约。
- 修改已确认预约后需重新由门店确认。
- 已确认预约进入改期流程后，原预约继续有效；只有双方所需确认完成且新时间原子切换成功后才替换原预约，不先取消再申请。
- 客户只能在预约开始时间6小时以前自助修改；距开始时间等于或不足6小时后禁止修改。修改包括改时间、宠物、服务项目、宠物数量，以及接受会改变有效预约时间的门店建议。
- 已确认预约改期时，以当前有效预约开始时间与建议新开始时间中的较早者计算6小时截止；未确认申请以当前申请的预约开始时间计算，存在建议新时间时同样取两者较早者。每次提交／接受均使用服务端时间重新校验，不能以页面已打开或旧消息绕过。
- 6小时规则只限制客户修改，不自动禁止取消；服务尚未开始时的取消规则继续按本节第一条执行。门店不得静默代改，确实无法履行时须走明确取消／拒绝流程。
- 平台 V1.0 不设置预约订金、违约金。

## 7. 寄养预约

流程：选择宠物 → 入住日期时间 → 离店日期时间 → 确认寄养资料 → 填写本次特殊要求 → 提交 → 门店确认。

宠物档案中的长期寄养资料自动带出，客户只需确认或做本次临时修改。

商户可设置建议最大寄养容量；预计超量时系统提示客户和门店，但 V1.0 不强制禁止提交，由门店人工确认。

## 8. 防重复与并发

- 提交按钮需防重复点击。
- 同一宠物存在高度重叠预约时提醒客户，但不绝对禁止。
- 服务端实时校验营业时间与临时关闭，不按预约间隔或时段名额判定能否提交／确认。
- 确认、改期、开始服务及多宠批次仍按第11节校验同一预约版本，重试返回同一结果。
- 同一时间多个不同客户的申请可同时等待人工处理，不因先确认一笔而自动拒绝其他申请；门店需逐笔决定是否接待或建议改期。

## 9. 线下快速开单

店员端必须支持：选择客户 / 宠物 → 选择服务 → 立即开始。

系统后台自动创建正式订单和服务记录，避免线下临时客户被迫经过预约流程。

快速路径不免除相应检查和明确业务动作：洗美／护理仍按04§4.3～4.5，寄养按04§5.1在实际到店、核对与入住检查完成后明确确认，不能只因选服务或预约到点自动入住。原寄养预约的计划入住／离店时间与正式寄养的实际入住／预计离店分开；同宠有效寄养防重不等于预约重叠提示变成硬拦截。

## 10. V1.0 暂不实现

- 员工个人预约日历
- 客户指定美容师
- 复杂员工排班匹配
- 预约订金 / 违约金
- 自动候补
- AI 自动排班
- 复杂寄养房型预订

## 11. 人工确认预约与改期逻辑（已确认）

> 决策 ID：`DEC-APPT-01`，已关闭。当前生效版本由产品方于2026-10-22确认：营业时间内提出期望到店时间，门店人工确认；取消固定预约间隔与时段名额限制。阶段04/06/09落实人工处理、营业／关闭校验及原子状态转换；第6节6小时修改截止继续有效。本次不改变寄养建议容量提醒，也不冻结无关财务、退款或商业化参数。

### 11.1 原则与客户承诺

采用“顾客提出期望时间 → 门店按实际忙闲确认／提出新时间／拒绝；改期成功才替换原预约”的轻量模型。

V1需要门店人工确认、没有订金、不做复杂排班、固定间隔或时段容量计数。正式承诺发生在有效确认时，不以取消名额机制为由跳过人工确认。

提交成功页固定表达“预约申请已提交，等待门店确认；实际到店时间以门店确认结果为准”。同一时间的多笔预约由门店逐笔人工判断，不提供自动抢位、余量或保留名额倒计时；人工确认也不能越过营业／临时关闭限制。

### 11.2 时间与批次校验

- 同一门店目标到店时间须处于营业范围内且未临时关闭，不要求与固定间隔网格对齐；营业时间和临时关闭使用04§3.0.7同一份配置，不为各端复制第二套。
- 不新增个人排班、自动候补、服务时长算法、硬容量计数或按名额自动确认／拒绝的后台任务。
- 新申请、门店确认及接受改期均重新校验当前营业／关闭设置、预约版本、操作资格和业务截止；其他预约的宠物数量不作为硬容量拦截条件。
- 同一批多宠提交 / 确认 / 改期均全部成功或全部失败，禁止在客户不知情时只确认其中一只。需要分批或分时段时，客户明确同意后拆成独立预约。
- 寄养继续沿用第7节“建议容量、超量提示、门店人工确认”；该独立建议提醒不属于本次取消的洗护／美容固定时段名额，也不加入04§3.0.7的两项设置菜单。

### 11.3 状态与处理表

| 业务状态 / 操作 | 客户看到什么 | 处理结果 |
|---|---|---|
| 新申请待门店确认 | 申请已提交，等待门店确认 | 不等于已确认；门店人工处理，不计算剩余名额 |
| 门店确认新申请 | 已确认，显示实际到店日期时间 | 校验目标营业／关闭状态及申请版本后一次成功；成功后才通知，不自动确认其他申请 |
| 客户修改未确认申请 | 更新后的申请待确认 | 原申请版本失效，门店不能操作旧版本；继续校验第6节截止 |
| 客户申请修改已确认预约 | 改期待门店确认；原预约仍有效 | 门店同意时原子切换新时间／宠物项及预约版本，失败保留原预约 |
| 门店提出新时间 | 待确认新时间；展示原预约是否仍有效 | 客户接受时校验并完成切换，失败保留原承诺，不静默改时间 |
| 改期建议被拒绝 / 撤回 / 失效 | 原预约仍有效；或原申请仍待确认 | 仅关闭改期提议，不隐含取消整笔预约 |
| 取消 / 门店拒绝，且未开始服务 | 已取消；门店拒绝原因有填写才展示，不编造原因；其他取消按第6节 | 权限／截止按第6节校验，保留操作人与历史，重试不生成第二次取消 |
| 到店开始服务 | 进入正式服务进度 | 幂等关联正式服务记录，预约与订单继续分离，不因确认预约提前生成服务 |
| 未到店 | 店员核实后显示已取消·未到店 | 不仅凭到点自动认定失约，不产生虚假服务订单 |

### 11.4 改期必须保住原预约

- 任一时刻最多一个有效改期提议，保存提议版本、发起人、原到店时间、建议到店时间和状态。对过期提议或旧消息的“接受”不生效，返回当前详情。
- 客户自己选的新时间，经门店同意即可完成；门店提出的新时间必须由客户接受后完成。系统按动作双方已经表达的同意识别确认方，不要求重复确认一遍。
- 修改服务项目或增减宠物也须按第6节由门店重新确认并执行多宠批次一致性；不按宠物数量差额进行名额校验。
- 新时间／宠物项、双方确认结果、提议状态及预约版本更新作为一次不可分割的业务成功；重复点击或响应丢失后重试返回同一结果，失败不得先更改原预约。
- 原预约在改期期间仍有效，客户可按原时间到店。同批任一宠物服务开始，整批尚未接受的改期提议即失效；开始与改期校验同一预约版本。改期先成功时，旧版本／旧时间的开始请求失败并返回当前预约，不能两边都成功。
- 若门店确实无法履行原预约，必须明确说明并按取消 / 拒绝流程处理，不得一边表示“原预约仍有效”一边实际停止履行。

### 11.5 超时、关店与截止

- 未确认申请到所申请时段开始仍未确认：结束为“已取消·确认超时”，不标记“未到店”。若仍需到店服务，按现有快速开单或重新申请流程处理。
- 改期提议的有效截止取“当前有效预约开始前6小时”和“建议新时段开始前6小时”中的较早时间；未确认申请没有有效原预约时，只取当前申请时段与建议新时段对应截止中的较早时间。创建时已到或已过截止不得发送无法接受的提议。任一方及时主动关闭提议同样保留历史。
- 建议失效只影响改期提议；原预约或原申请继续按自身状态处理。原申请本身到时仍未确认，适用上一条确认超时规则。
- 客户操作继续遵循第6节已确认的6小时修改截止。客户在截止前已提交并等待门店确认，不代表截止后仍可完成改期；门店确认、客户接受和原子切换都必须在截止前再次校验。取消不因本次6小时修改规则自动受限，仍须满足服务未开始等既有条件。所有判断使用服务端当前时间，不依赖超时任务是否及时执行。
- 门店临时关闭或修改营业时间后，禁止向非营业／关闭时间新申请，也禁止将待确认申请或改期提议确认到这些时间。原已确认预约继续有效，不静默取消；不改变原到店时间、服务项目且仅更正资料／减宠时，仍按第6节的双方确认和截止规则处理，不把它伪装为新时间预约。受影响记录进入门店处理清单并逐笔通知，由门店明确处理原承诺，不批量自动取消。
- 营业设置更新与新申请／确认／改期发生竞态时，服务端按配置版本及预约版本保证一致：关闭先成功则新的申请／确认／改入关闭时间失败；已确认预约先成功则保留原预约并进入受影响处理流程。不允许读取旧营业设置后越过关闭限制。
- 各时间判断使用服务端权威时间并按全局业务时区 `Asia/Shanghai` 计算；本次确认不引入任意“30 分钟自动作废”等额外默认值。

### 11.6 典型推演与正式验收边界

以下场景均为已确认人工确认模型的正式验收依据，统一归入03i的 `C-APPT-01` 组合场景。每个子场景必须分别记录结果，不能用一次总通过掩盖未执行项。

| 场景 | 预期结果 |
|---|---|
| 门店营业中，客户选择10:13等不在旧固定间隔网格上的期望到店时间 | 在其他条件有效时可提交待确认，不要求先配置预约间隔 |
| A／B同一时间各提交申请，门店已人工确认A | B仍可由门店确认、建议改期或拒绝；不因A先确认而自动报满，也不自动确认B |
| 客户一次申请2只宠物，门店认为不能同时接待 | 门店人工建议新时间或拒绝，不能偷偷只确认1只；明确同意拆分后才分别办理 |
| 已确认10:00，申请改11:00；门店拒绝新时间或11:00随后关闭 | 改期不成功，10:00原预约继续有效 |
| 两只宠物从10:00成功改到11:00，超时后重试 | 时间、宠物项及提议／预约版本一次切换；重试不重复改期，不生成名额计数或正式服务订单 |
| 客户收到新时间消息，但之后门店更新了提议 | 旧消息接受失败并展示最新提议，不更改当前预约 |
| 客户接受改期与店员开始原预约服务同时发生 | 只有一个合法状态转移成功；任一宠物开始服务后整批提议失效，改期先成功则旧版本开始请求失败 |
| 提议目标时间随后关闭，客户从旧消息接受 | 拒绝改入关闭时间，原已确认预约保留；同原时间合法减宠仍按第6节处理，不当作新增时间申请 |
| 关闭时间与门店确认预约并发 | 关闭先成功则确认失败；确认先成功则原预约保留并进入受影响处理，不出现静默取消 |
| 同一申请由老板和店员同时确认／拒绝或响应丢失后重试 | 仅一个合法版本转换成功，其他请求返回真实当前结果，不重复通知或生成业务记录 |
| 新申请到时仍未确认 | 显示确认超时，不认定客户失约、不生成服务单 |
| 已确认预约到时，店员尚未核实客户是否到店 | 保留真实状态，不能自动标记客户失约；后续由店员确认开始服务或未到店 |
| 距当前有效预约开始正好6小时，客户尝试改时间／宠物／项目或接受新时间 | 服务端拒绝修改，原预约保持不变；仍可按既有条件取消，不能把修改失败伪装成取消 |

`DEC-APPT-01` 已关闭，当前正式模型为人工确认、不设固定预约间隔或硬名额、改期成功才替换原预约、多宠同批全成全败。实现不得恢复退役的时段容量、占用计数或名额状态，也不得省略状态表、并发、超时、关闭时间和6小时截止规则；旧规则仅在变更历史中追溯。

### 11.7 已确认：店员接单、选填原因与提醒人工继续

04§3.7于2026-10-24确认8项：当前需要门店处理的有效申请进入工作台预约确认，即使到店日期在未来；等待顾客接受新时间不算待门店确认。完整记录归业务／预约管理，按待处理、已确认待到店、历史记录分组及日期／洗护／美容／寄养筛选，分组不新增业务状态。待处理按申请／改期期望到店时间升序，同时间按提交先后；原预约承诺在改期成功前仍有效。

详情展示本店有权查看的联系方式、各宠物、项目、期望时间、寄养预计离店及本次要求。拒绝预约／建议改期原因均选填，空值合法；快捷原因可不选，“其他”也不强制说明。有填展示真实原因，无填只展示处理结果，不自动编造门店忙碌或其他理由。此变化不免除挂单、调价、退款等其他业务必填原因。老板／有效员工均可处理，内部保留实际处理人／时间，顾客展示门店及结果、不展示员工个人联系方式。

确认预约时有明确关联且本店有权查看的护理注意事项／风险提醒，独立弹窗须点击“已阅读，继续”，阅读本身不确认预约、不解除风险或自动拒单。共享暂无法核验统一提示“共享提醒未完成核验”，员工人工核对后可继续当前预约并留痕，不记成查询成功／已查无风险；授权、同意、每月3次、身份冲突阻断及原本店身份／营业／6小时／版本／状态校验仍生效。不得为取共享资料擅自合并身份、补授权、换员工重置次数，亦不暴露可枚举他店记录的差异原因。新增顾客确认／失败接续和重复提醒频率未在本轮确认。

复用原预约、提议、快照和原审计，阅读确认及人工继续只关联当前预约动作，不造第二预约或伪造共享查询；确认预约不自动到店、开服务、入住或收款。C-APPT-01按03i扩展子场景，不改变DEC-APPT-01已确认模型或宣布其他待决业务可实现。
