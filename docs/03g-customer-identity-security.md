## 1. 设计原则

- 客户首次进入小程序时尽量不强制完成完整登录 / 手机号绑定流程。
- 浏览当前门店首页、推荐商品、商品列表和商品详情等公开内容时，可先不建立 Customer 关系。
- 当客户首次使用预约、宠物、钱包 / 会员资产、订单、消息、提交购买需求、提交投诉等个人业务时，再要求完成必要身份验证。
- 平台账号与商户客户身份分离：稳定平台 User 绑定微信登录凭据及已认证手机号；User 与具体 Merchant 建立商户级 Customer 关系，换微信不重新生成原有身份。
- 已认证手机号用于查找登录账号及其有效老板／员工身份，同时作为联系方式和历史客户匹配依据；稳定平台主键仍是platform_user_id，不把号码直接用作主键或Customer归属。
- 历史客户匹配必须以已验证手机号为前提，禁止仅凭手工输入手机号直接展示余额、订单、宠物等隐私数据。
- 多商户 Customer、会员资产和经营数据严格隔离；平台公开投诉 / 食品风险反馈不因为切店而被改造成某一 Merchant 私有数据。

## 2. 平台 User 与商户 Customer

系统区分：

- User：平台级稳定账号身份；当前微信是其登录绑定，可按§3.1换绑而不改变原platform_user_id。
- Customer：某一Merchant的客户业务记录／关系，可由门店在线下先建；在安全绑定前可以没有关联的User。

同一User可以在多个Merchant下分别关联经安全确认的Customer；同一Customer至多绑定一个当前有效User。Customer不等于登录账号，未绑定User的线下Customer仍可承载本店宠物、服务、充值和消费记录，但不得向未完成安全绑定的User暴露私有资料。每个Merchant只能访问自己Customer关系下的私有业务数据；03h明确授权的跨店服务信息使用独立校验，不合并Customer或转移客户关系。

切换商户时，首页当前服务、预约、钱包 / 会员资产、优惠券、订单、商品和门店消息均整体切换至目标商户上下文，不允许跨商户串数据。消费争议中的公开门店 / 食品反馈属于平台公开内容，不因当前商户切换而丢失；平台个人消息、平台积分和本人上门喂养记录继续归属于 Platform User；消息时间流范围见 `03f`。

## 3. 身份验证触发时机

无需先绑定手机号即可：

- 浏览当前门店首页
- 浏览推荐商品
- 搜索 / 浏览商品
- 查看商品详情
- 浏览不涉及个人业务数据的公开内容（包括已公开的门店 / 宠物食品风险反馈）

首次进行以下个人业务时要求完成必要身份验证和手机号验证：

- 提交预约
- 新增 / 管理宠物
- 查看当前可用余额、钱包明细或优惠券
- 查看订单
- 查看消息
- 提交商品购买需求
- 提交门店 / 宠物食品投诉或补充本人投诉证据
- 在本人原争议详情提交／追加处理情况（03h§6.2）
- 通过邀请卡片提交／追加第三方佐证（03h§7.1）
- 其他需要访问个人业务数据的操作

验证成功后尽量一次完成后续 User / Customer 识别，不重复要求客户填写已有信息。仅访问平台个人业务时不因此给任意门店建立 Customer 关系；门店业务在明确目标 Merchant 后按第 5 节识别。

身份验证前保留用户原始目标和必要的业务 / 门店标识。验证成功后重新校验目标可见性并继续原操作，不一律跳首页；拒绝 / 中断验证时保留可再次进入的原目标，不伪造成功、不提交个人业务。退出登录或切换 User 后不得向新会话暴露前一 User 的私有草稿或页面内容。

第三方佐证邀请卡片按03h§7.1进入原争议：公开内容浏览不额外强制验证；提交／追加时沿用现有User与必要手机号验证，不另传身份证，不要求本店会员／Customer关系或消费订单。验证完成恢复原目标，重新校验原3天补证截止与实际邀请状态：按03h§7.2新建佐证不得使用已撤回卡片，既有作者在原窗口追加不要求原卡片仍有效；追加资格来自当前User与既有佐证，不能借此让新顾客绕过。拒绝验证不提交，晚验证不延长窗口。以稳定Platform User识别同人同争议的一份佐证，不能以昵称、手填电话、邀请员工或切店生成多份；邀请不自动建立Customer／绑定资产，也不继承门店私有材料权限。

03h§6.2处理情况由本案投诉人的稳定Platform User身份提交；不能借相同手机号、Customer候选或第三方邀请冒用投诉人。验证成功返回原争议并重验当前访问权及平台尚未确认解决的状态；原3天已过不阻断合法实际处理进展，也不重开证据窗口。未公开材料的作者读取仍须核对当前身份与该条实际作者，切账号不沿用旧缓存；是否由平台确认已解决不由客户端反馈或手机号验证决定。

本节适用于客户端与老板／员工共用的小程序登录，不定义平台管理员Web登录。全平台账号唯一按已认证手机号约束；顾客和店员使用同一平台账号。同一平台账号在同一时刻只能归属一个有效经营门店：已经是某店老板或店员时，不能同时成为另一家店的老板或店员。存在该唯一有效经营身份才默认进店员界面，否则进客户端，不把历史停用身份当有效任职。换绑不再要求用户检查旧账号或核验旧微信，旧身份与资料保留；同一人在各店的Customer是店内业务关系，不是重复登录账号。§3公开浏览仍无需先登录；一旦执行登录，则必须满足本节手机号认证条件。

1. **微信登录后检查认证**：服务端检查当前微信绑定账号是否已有有效手机号认证。已认证且绑定未变化，可直接登录，不要求每次进入重复认证；未认证则提示完成手机号认证，成功后才建立可访问个人业务的登录会话。拒绝／失败不冒充已登录，不开放个人或门店私有数据，原安全目标按§3保留。
2. **按手机号确定身份**：只能使用服务端核验的手机号，查找其当前绑定的平台账号及该账号的现行经营关系。有唯一有效老板／员工身份则进入该门店；如果已存在其他门店有效经营身份，新的入职邀请或老板关系创建必须拒绝并提示先结束原关系；没有有效经营身份时，普通登录进入客户端；从真实员工入职邀请进入则恢复原邀请确认页并按02§6.0.1重验资格、本人明确确认后才加入，不在认证时自动入职。不新增“客户”经营角色，不自动创建任意门店Customer。账号停用／注销仍按原规则阻断；员工停用／移出、门店停用不因认证或换绑恢复权限，返聘仍需02§6.1的新邀请。
3. **重复号码提示**：新微信完成该手机号所有权认证后，如号码已绑定其他微信，标题提示“手机号异常”，正文“该手机号已绑定其他微信，是否换绑？”，提供“换绑”和“更换手机号”两种处理；选择新手机号须重新认证，未成功前不授予原号码身份。未认证不查询／展示他人绑定情况；提示不透露原微信、姓名、门店或资产。退出本次处理不改变原绑定，新微信不能用该号码取得原身份。全平台同一认证手机号只绑定一个当前有效平台账号，不能因新微信再建同号顾客／员工登录账号；手机号码仍不是业务主键，旧资料不删除。
4. **确认换绑**：本轮明确采用“当前手机号认证成功＋本人明确确认”完成换绑，不另增加旧微信核验或平台人工审批前置。新微信绑定该手机号对应的原平台账号，沿用其稳定platform_user_id、原员工／老板关系及已有业务历史；解除旧微信登录绑定并使旧微信的原登录会话失效。旧微信此后不能沿旧认证状态或旧缓存继续进入；历史订单、业绩、Customer、余额和作者／经办事实均不重建、复制、合并或改归属。
5. **边界及防重**：换绑以服务端当前绑定和认证结果为准，一致完成新绑定、旧解绑及会话失效，并保留实际操作人、时间和前后绑定审计；失败不半换绑，同请求重试不重复迁移，冲突并发不得让两个微信同时持有同一有效绑定。若新微信已关联另一个有业务历史的账号，或手机号对应多个账号等非唯一情况，不能猜选、覆盖或自动合并；独立账号合并／异常处置技术方案另行收口，本节不授权其自动处理。
6. **身份与资料分开**：匹配的是已认证登录手机号与账号绑定，不是Customer手填联系方式、门店注册号码、微信联系号、昵称或前端role参数。查到经营身份后仍逐请求校验当前角色、任职及租户；平台管理员权限不由此入口发放。微信身份标识作用域、账号绑定／版本、认证证明、会话失效及异常接口的数据映射在阶段09／11先登记FIELD后实现，不复用Customer绑定凭证冒充经营身份授权，也不自行设定固定会话时长。
7. **与其他身份流程的关系**：本节是“原账号换登录微信”，保持原User及已绑定Customer关系；§5／§7／§9处理“不同User争取绑定某份历史Customer”，不得借同号直接转移Customer。未绑定的本店线下资料仍按唯一安全匹配，跨店共享仍按03h授权、限频及冲突规则；成功换绑不等于解除跨店身份冲突、顾客重新同意共享或增加查询额度。

员工入职邀请中的本人手机号引用当前认证账号的verified_mobile，不从Customer联系资料或门店注册号带入；门店名称／地址仅为真实邀请目标展示，不授权未入职用户读经营数据。员工称呼按02§6.0.1及F-STAFF-015，仅实际可用微信昵称默认／手填修改，不把昵称作为登录身份、返聘关联或权限依据，也不强制昵称授权才能入职。

## 4. 手机号定位

手机号是登录账号及其有效身份的查询依据，不等于稳定平台账号ID；更换号码不重建User或业务身份。

手机号用途：

- 按§3.1查找登录账号及其当前有效老板／员工身份；无有效经营身份则进入客户端
- 已验证联系方式
- 当前商户历史 Customer 匹配依据
- 门店线下客户记录与线上 User 的关联依据之一

不允许仅根据手机号相同就跨商户共享或自动合并数据。

## 5. 历史客户自动识别

客户完成手机号所有权验证后，仅在当前 Merchant 范围内查找历史 Customer。

### 5.1 唯一明确匹配

若仅找到一个可安全绑定、且未发生账号冲突的历史 Customer，则系统自动建立 User ↔ Customer 关联。

关联后客户可直接看到该商户中原有的宠物、当前可用余额、优惠券、订单和服务记录，无需店员再次手工迁移。

### 5.2 无匹配

若当前商户没有匹配的历史 Customer，则自动创建新的 Customer 关系。

### 5.3 多个候选历史客户

若同一已验证手机号在当前商户中对应多个可能的历史 Customer，系统不得自动合并或任意绑定。

客户端提示存在待门店确认的历史资料；由门店侧后续通过人工识别 / 合并 / 绑定能力处理。

在冲突解除前不得暴露候选 Customer 的余额、订单等敏感数据。

### 5.4 已绑定其他 User

若目标 Customer 已绑定其他平台 User，不同User即使验证了相同手机号，也不得自动抢绑、覆盖或转移Customer。§3.1明确确认换绑并沿用原User时，既有Customer绑定保持，不属于不同User之间转移。

进入账号绑定冲突 / 恢复流程，V1.0 可由商户老板辅助处理；所有换绑必须保留审计记录。

本节处理的是“当前Merchant内历史Customer与Platform User如何绑定”，不等于03h跨店顾客风险查询。跨店顾客风险只按服务端核验的认证手机号匹配；号码存在多候选、换号／回收疑点、验证过期或其他冲突时必须阻断结果并转平台核验。不得再使用微信身份、昵称、手填联系方式或Customer文本作为第二匹配条件；商户老板和普通店员不能用本节的本店绑定能力解除跨店冲突，也不能借此合并其他门店Customer。

## 6. 线下先建客户、线上后绑定

门店可在客户尚未使用小程序时先由店员建立 Customer、宠物、服务、充值和消费记录。

客户之后首次使用小程序并验证手机号时，如符合唯一安全匹配条件，系统自动关联已有 Customer，使历史资料直接出现在客户端。

不得要求门店为了线上账号预先让所有客户注册。

04§4.1已确认临时顾客可由店员在线下办理宠物服务开单，顾客手机号或微信号至少留一个，宠物昵称／品种齐全；不强制先注册／绑定小程序。手工填写的联系手机号和微信号属于当前Merchant的Customer联系资料，不是已验证手机号、微信登录OpenID／稳定平台身份，不能据此自动生成／绑定User、合并同号Customer或开放线上资产。仅留微信号不取消本模块线上个人业务的必要身份／手机号验证要求，也不赋予跨店查询或宠物共享授权。

04§6.5.1明确本店线下新增Customer不要求核验顾客资料真实性，不增加短信／微信所有权证明或门店人工核对审批；原填写完整性／格式及重复记录处理仍适用。明确保存成功后展示本店有权查看的注意事项／风险提醒，查询失败可直接继续，不回滚或重复建档、不声称无风险；新老顾客确认预约仍有提醒，同次相同内容去重／变化重读／新业务再提醒及留痕按该节执行。

本地手工录入不写成F-AUTH的已验证身份，不把提醒阅读／选择继续当作顾客共享同意，也不绕过本文件线上登录、历史匹配、资产读取、User绑定／换绑或03h的共享授权／限额／冲突规则。“全部顾客”是适用提醒流程，不是批量查他店资料的授权。

## 7. 店员辅助绑定兜底

V1.0 支持门店针对复杂历史数据提供“绑定客户小程序”能力。

流程：

店员打开明确的 Customer
→ 生成一次性绑定二维码 / 绑定凭证
→ 客户使用当前微信账号扫码并确认
→ 后端校验后建立 User ↔ Customer 关联

安全要求：

- 一次性使用
- 短有效期
- 使用后立即失效
- 绑定目标 Customer 明确
- 记录生成员工、生成时间、使用时间和绑定结果
- 在绑定成功前不得因为扫描凭证而向错误 User 暴露目标 Customer 的余额、订单等敏感数据

## 8. 更换手机号

已登录User更换手机号时，应验证新手机号并更新该账号联系方式，不得因此重新创建User／Customer或从另一账号转来员工／老板权限。若新号码已归另一登录账号，不能当普通联系方式更新直接覆盖；按§3.1的冲突边界处理，不自动合并两个既有账号。

原有宠物、余额、优惠券、订单、服务报告等业务关系保持不变。

手机号首次绑定和变更都必须记录审计。

## 9. 更换微信账号 / 账号恢复

更换登录微信按§3.1处理：验证手机号、明确确认换绑后沿用该号码对应原User及身份，原Customer关系保持；不要求旧微信确认或门店老板／平台审批。

若涉及两个不同既有User之间转移历史Customer，仍按§5.4／§7的客户绑定冲突处理，V1.0可采用商户老板辅助确认作为兜底，不建设复杂独立申诉中心；该辅助能力不授予转移老板／员工身份或解除03h跨店冲突的权限。不能把原账号换微信与两个账号合并写成同一动作。

## 10. 退出登录与账号注销

退出登录仅结束当前登录会话，不删除 User、Customer、宠物、余额、订单或历史关联。

账号注销与退出登录严格分开。

账号注销时：

- 可删除 / 匿名化应被删除的个人身份数据；
- 财务、订单、退款、审计等依法或业务需要保留的交易事实不得因注销而被无痕删除；
- 具体保留周期和匿名化规则在后续数据 / 隐私规则阶段统一确定。

## 11. 多商户切换

客户直接打开小程序且没有本次明确目标时，使用最近一次仍有效的 Merchant；本次扫码 / 门店业务深链指定的有效门店优先于历史门店。

客户可在已建立关系的商户之间切换。切换后所有商户业务数据必须整体切换，不允许出现 A 店页面与 B 店资产混合展示。

首次扫描新的商户二维码时可先浏览公开内容；首次进行个人业务时再建立该商户 Customer 关系。

### 11.1 启动与目标门店选择

- 本次有效扫码 / 深链目标 → 优先解析目标及其真实所属门店；后台回前台且无新外部目标 → 恢复原页面和同一会话的未提交内容；普通冷启动且无明确目标 → 最近有效门店首页。
- 没有历史门店、历史门店失效或需要门店但当前未选择时，展示扫码 / 选择有效门店入口。选店过程保留原始可恢复目标，不伪造默认门店、Customer、余额或服务。
- 明确指向失效门店或无权业务的链接，先说明该目标不可用；用户可返回或选择其他有效门店，但不得静默替换为历史门店并把链接业务当成该店业务。
- 平台公开上门喂养详情可直接浏览，不强制把用户当前门店切到发布门店；发布时仍须明确有效当前门店并永久绑定。查看个人平台记录按身份校验，进入门店私有资料则另外校验 Customer 权限。
- 门店业务的目标门店、业务所属门店和读取权限均由服务端确认；切店时整体刷新门店数据，旧页面请求结果不得覆盖新门店页面。
- 启动封面广告不改变上述优先级；关闭、失败或等待结束后按 `03p` 恢复目标，登录 / 绑定结束后继续同一目标。

### 11.2 边界验收补充

- 首次打开且无门店，能进入扫码 / 选店；不展示虚构门店资产。
- 历史为 A 店，本次有效 B 店深链进入 B 店对应业务；未建立 B 店关系时先完成必要校验，不能读取 A 店资产作为 B 店数据。
- 登录后恢复消息 / 分享目标；目标无权限、已失效或门店停用时显示可理解的原因与返回路径。
- 后台回前台不丢当前页面和未提交内容；新外部目标优先时不自动提交或丢弃原草稿，草稿只在同一账号及原业务上下文恢复。
- 切店后平台个人消息保留、其他门店私有消息隔离，消息未读按 `03f` 的可见范围更新。

## 12. V1跨店宠物基础档案授权一次性复制边界

V1不提供跨店Customer档案、商户订单／消费、会员资产、宠物服务报告或护理历史的导入、复制、持续同步或自动合并。唯一例外是按01§5由顾客主动发起并明确授权的宠物基础档案一次性复制：

1. 顾客必须使用当前已验证的Platform User，确认其有权管理源宠物档案，并明确选择目标Merchant及本次要复制的宠物基础字段；可复制字段仅限01§5列出的宠物基础资料，不得扩展为Customer完整档案或商户业务数据。
2. 服务端校验源宠物及顾客管理权限、目标Merchant有效性和目标Customer关系；校验通过后，在目标Merchant的Customer关系下创建独立Pet档案。不得转移、合并或改写源Customer关系。
3. 源Merchant原Pet及其业务关系保持不变；目标Pet是本次授权时点的一次性资料快照。源／目标任一侧后续编辑或删除均不自动同步到另一侧；不建立持续同步关系。再次复制必须由顾客重新明确发起并授权。
4. 明确禁止复制其他商户订单／消费金额、会员余额／优惠券、服务报告／护理历史、商户内部备注、员工评价、经营分析标签及其他商户私有资料。
5. 本次复制不得由门店人员凭手机号、手工声明或平台风险查询代替顾客授权；不能唯一确认顾客及源宠物管理权限时，停止复制，不猜测、不自动合并。

宠物相关服务安全事件已经并入统一顾客风险，按`03h-customer-risk-feedback.md`§10.1～10.5执行认证手机号匹配、顾客服务履约分项同意、双方门店授权、平台审核、顾客不可见及期限规则。该最小范围风险查询不是档案复制，也不能写回目标门店完整档案或历史。

## 13. 客户端账号设置

“我的”中提供轻量的“账号与设置”入口，至少可承载：

- 当前已验证手机号
- 更换手机号
- 隐私相关入口
- 减少动态效果（按 10a 的系统偏好与用户设置规则，控制轮播及非必要动画）
- 账号注销
- 退出登录

V1.0 不设计用户名 / 密码 / 忘记密码 / 密码重置体系，主要使用微信身份与必要的手机号验证。

## 14. 家庭共享

V1.0 不实现多人 / 家庭成员共同管理同一宠物或共享同一会员资产的复杂权限体系。

V1.0 采用主要 User 管理宠物和商户关系；架构可在以后版本预留多关系能力。

## 15. 身份安全审计

以下关键动作必须保留审计：

- 手机号首次绑定
- 手机号更换
- 历史 Customer 自动匹配
- Customer 人工绑定
- 重复 Customer 合并
- User / Customer 换绑
- 解绑
- 账号恢复
- 注销申请

至少自动记录操作时间、操作方式、操作主体、原关系和新关系；原因选填，人工操作另记录实际员工／老板。

## 16. 减少操作原则

- 新客户尽量先浏览、后验证，不以登录墙阻断公开浏览。
- 老客户验证手机号后由后端自动识别历史 Customer，不要求客户或店员重复迁移数据。
- 线下先建客户、线上后绑定是正常路径，不强制客户预注册。
- 复杂重复数据通过门店辅助绑定兜底，不让客户处理内部数据问题。
- 高风险换绑必须安全优先；普通低风险登录流程则尽量少步骤。

上门喂养当前边界见03j§8～9.3：保留用户自主接单，需求方仅发布／撤销、当前店仅确认／撤销，协商修改及实际服务在线下，不在APP跟踪四步进度或完成。门店确认后仅当前店老板／有效员工可读双方合法授权联系资料，需求方／接单用户不能互看；确认权限绑定当前负责版本。临时休息不影响功能，账号停用仍以原发布店位置自动接续最近有效店，publisher_store_id保留来源，current_coordination_store_id及coordination_assignment_version决定当前资格，新店须再次确认才读联系方式，原店失权。保留原单／接单人／历史，不迁移其他Customer／钱包／私有档案，不改用户全局当前门店，不公开旧店内部资料或原始审计，不将本例外扩展成03h任意风险查询。
