### 3.1 五个入口的建议职责

下表一级入口及洗护美容/寄养归属遵循§3.0；其余职责细化与二级菜单内容仍为提案。

| 一级入口 | 唯一主职责 | 二级菜单与主要内容 | 不混入 |
|---|---|---|---|
| 工作台 | 当天需要处理的事项与办理快捷入口 | 分组和组内顺序以§3.2为准；其他布局与辅助入口仍待确认 | 不新建第二套订单；不靠“已读”结束任务 |
| 业务 | 包含寄养的综合业务办理与历史查询 | 预约管理 → 商品处理 → 寄养 → 上门喂养 → 消费争议 → 订单与收银（菜单及顺序已确认，内部流程按来源细化） | 不复制洗美模块；预约独立于正式订单；实物奖励不混普通销售库存；寄养位置不是复杂房型预订，收款不是实际投喂 |
| 洗美 | 洗护、美容业务办理 | 快速开单、接宠检查、过程记录、照片/报告、交付、服务历史 | 不承载寄养；服务完成、已收款、已接走分别记录 |
| 客户 | 当前商户客户及关联宠物 | 客户搜索/列表、客户详情、宠物档案、客户会员资产/流水/优惠券、消费与服务历史、资料匹配异常 | 不跨商户共享资产/内部记录；不可由页面直接改余额 |

工作台只专注当天需要处理的事项，不承担完整业务目录和历史记录浏览；保留已确认的四类区块及快捷操作。“业务”不是第二个工作台：用于其所属业务的完整办理与历史查询。两处复用同一业务对象、列表与详情，工作台只带入当天处理所需的筛选上下文。

“当天处理”不等于“今天创建”：跨天仍未完成、逾期、在住寄养等持续中的事项，若当天仍需处理或关注，不能因创建日期早于今天而消失。已完成且当天无需再处理的历史事项在所属业务入口查询。各类任务具体进入／退出条件与日期筛选仍由对应业务规则及DEC-STAFF-03收口，不擅自以午夜清空待办。

| 区块 | 按顺序展示的项目 | 归属说明 |
|---|---|---|
| 待处理 | 预约确认 → 商品处理 → 上门喂养 → 其他 | 商品处理包含商品购买需求及奖励收货／自提待办；其他包含待回应消费争议、食品风险待办 |
| 服务中 | 今日洗美 → 在住寄养 → 待执行加餐 → 其他服务 | 是工作台业务分组，不把组名当作底层统一服务状态 |
| 异常与临期 | 投诉回应 → 寄养异常 → 洗护异常 → 其他异常 | 投诉回应用于关联回应的异常／临期事项；具体触发条件、预警阈值仍按业务规则及待决项收口 |
| 快捷操作 | 查客户／宠物 → 到店开单 → 寄养入住 → 洗美开单 | 四个入口均保留；到店开单为先选商品或服务项目的通用入口，洗美开单直接进入洗护／美容，复用同一套开单能力 |

已确认的“商品处理”分类：

> goods_processing_categories: [商品需求, 奖励收货, 奖励自提]

| 分类 | 处理内容 | 原业务依据 |
|---|---|---|
| 商品需求 | 处理客户端提交的商品购买需求 | 03e商品需求与订单规则 |
| 奖励收货 | 确认平台寄到本店的奖励实物实际收货 | 03k积分奖励履约规则 |
| 奖励自提 | 核验客户领取本店待自提奖励 | 03k积分奖励自提规则 |

三类事项分别展示、分别处理，进入各自业务详情；入口合并不合并订单、库存或业务状态。奖励收货不等于客户已领取，不可用普通商品收款／销售完成代替奖励自提核验。具体列表交互、收货及核验人员权限仍待后续确认，不因本节分类确认授予所有员工操作权。

已确认的开单入口分工：

- **到店开单**：通用入口，先选择商品或服务项目，再进入对应开单流程。
- **洗美开单**：直接进入洗护／美容开单，省去业务类型选择；不默认选定某个具体项目、价格或宠物。
- 两个入口复用同一套开单能力：从到店开单选择洗护／美容，应进入与洗美开单一致的业务流程；不因入口不同建立两套独立订单模型或重复创建订单。
- 复用开单能力不等于合并商品订单与服务订单的业务含义；各类型继续遵守原业务规则。此处不确认商品与服务混合结算、必填字段、收款时点或新增权限。

已确认边界：

- 奖励收货／自提待办合并进“商品处理”入口，不在待处理区块另列同级奖励入口；仍保留普通商品需求、平台奖励收货、奖励自提的业务类型和对应详情，不把奖励混成普通销售订单、库存或收款。菜单合并不授予总仓发货、退积分或未确认的核销权限。
- “其他”不是删除功能或新增业务的授权：待处理区块仍须承接待回应消费争议和食品风险待办。“其他服务”“其他异常”的具体类型仍待逐项确认，不自动创建新业务状态。
- 同一投诉可由待处理与异常／临期入口进入同一正式对象；不能因此复制投诉或形成相互独立的回应流程。跨区块计数／去重与展示细节待确认。
- 快捷入口复用原业务对象，不新建第二套订单；名称和位置不意味着自动授权，也不意味着点击即创建订单。
- 争议门店归属、全体有效在职员工正式回应及短信使用门店注册号码，继续按§6.1／6.5执行。

工作台不扩展为营业额／业绩排行看板或完整功能目录；这些统计与管理能力并未从产品中删除，具体入口仍待确认。区块最终视觉位置、通知入口、卡片展示字段、红点计数、空态及具体任务排序算法仍待确认；组内入口顺序不等于每个业务列表内任务记录的排序规则。

### 6.1 已确认：投诉回应与门店内部风险记录基线

当当前门店成为公开投诉对象时，店员端 / 老板端必须能进入正式投诉处理对象，而不是通过私聊替代。本店所有在职且账号 / 门店关系有效的员工均可提交正式回应，老板同样可回应；不得要求只由指定员工提交或额外设置老板审批作为回应前提。离职 / 停用后的访问限制继续有效，其他门店员工不能回应本店投诉。

门店可：

- 选择回应立场：认可 / 部分认可 / 不认可 / 无法确认；
- 提交正式回应文字；
- 上传图片 / 视频等证据；
- 邀请多名第三方顾客提供佐证；
- 在平台规定的 3 天补证期继续补充材料；
- 查看平台最终裁决和申诉状态。

门店不得：

- 删除用户原投诉；
- 把“已回应”写成“投诉已解决”；
- 自行把投诉改为不成立；
- 用第三方人数投票覆盖平台裁决。

7 天回应期由平台投诉模块计算。逾期后仍可回应，但历史逾期状态保留。

门店内部可以维护顾客 / 宠物的本店备注。主观顾客人格评价只允许本 Merchant 私有；跨门店方向仅允许平台审核后的客观风险事件。宠物跨店方向使用结构化“行为与服务安全档案”，不直接传播自由文本“凶 / 难搞”等评价。

投诉裁决、跨店顾客风险和宠物安全共享详细边界见 `03h-customer-risk-feedback.md`。

- 投诉提醒与逾期处理增加短信，保留原站内 / 微信通知，短信发给争议门店注册号码，不另设争议通知手机号；发送配置仍待确认，注册号码变更 / 验证按账号管理规则收口，见03f§13.2。
- 主人食品风险提醒必须另行形成店员待办；待办归属争议门店；食品投诉未明确争议门店时的映射、店内责任人、数据范围、去重、流转和关闭仍待确认，见03f§13.3。不能默认推给所有关联门店，也不能以通知发送成功作为待办完成。
