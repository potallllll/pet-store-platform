## 1. 总体原则

V1.0 不设计复杂的多级职位体系。

经营管理侧只保留三个正式角色：

1. 平台超级管理员 Platform Super Admin
2. 商户老板 Merchant Owner
3. 店员 Staff

客户端顾客使用独立的 Customer / User 身份体系，不属于经营管理角色，因此不计入上述三个后台角色。

不创建“店长、收银员、美容师、洗护师、寄养员”等独立系统角色。V1.0有效在职店员统一默认拥有本店全部店员业务权限，不设置逐员工权限配置；老板专属能力、平台专属能力及记录可见性边界仍须按角色由服务端校验。

对外产品与文档统一使用“店员端小程序”称呼；商户老板也使用店员端，并默认拥有本门店全部店员权限。“店长端”不代表一个独立系统角色。

## 2. 平台超级管理员

平台超级管理员拥有整个平台的最高权限，可跨商户查看和管理所有数据。

主要能力包括：

- 查看全部商户
- 查看全部门店
- 查看平台级经营 / 使用数据
- 管理商户状态
- 查看平台审计日志
- 处理异常数据
- 管理系统级配置
- 管理平台资源限制
- 使用 `reward_fulfillment.manage` 权限管理平台积分实物奖励的总仓发货任务
- 在平台Web后台录入厂家对食品投诉的回信，保留来源与审计；录入不自动等于正式回应或平台裁决，见03h§2.4
- 必要时协助商户进行数据处理

平台超级管理员不受单商户数据隔离限制。

V1.0 不新增“总仓人员”系统角色。`reward_fulfillment.manage` 只能授予 Platform Super Admin，用于创建 / 更新总仓发货任务和确认发货；该权限本身不授予取消兑换、取消发货或积分返还能力，这些动作仍受 `DEC-POINTS-01` 约束。后续规则允许的每次操作都必须记录操作者、时间、原状态、新状态及关联兑换单。Merchant Owner 与 Staff 不得取得该权限。

## 3. 商户老板

一个商户仅对应一名主要商户老板账号和一家门店。

V1.0 不支持同一老板拥有多家门店。

商户老板：

- 只能访问 `merchant_id = 当前老板所属 merchant_id` 的租户数据；记录若以门店隔离，还必须满足 `store_id = 当前经营门店 store_id`
- 默认拥有本门店全部经营权限
- 可使用 Web 管理后台
- 可使用店员端小程序
- 可管理客户、宠物、订单、库存、会员、员工、财务、统计等
- 可邀请店员加入
- 可在员工列表中停用、删除（移出本店名单）和恢复被停用店员
- 可查看操作日志
- 可执行需要老板级权限的高风险操作

老板默认拥有所有店员权限，不需要重复配置。

## 4. 店员

店员只能属于一个商户和一家门店。

V1.0 明确禁止：

- 一个店员同时加入多个商户
- 一个店员同时在多个门店工作
- 店员跨店访问数据

账号及门店关系有效的在职店员统一使用同一本店店员业务权限集合，加入或恢复后自动取得当前有效集合；不要求老板逐人配置，也不提供“配置权限”菜单或接口。默认全部权限仅指已经确认属于店员职责的本店业务，不能推导为可进入老板管理、平台管理、操作其他门店，或执行尚待确认的业务动作。

权限集合统一不改变订单状态、真实收款、金额锁定、幂等、业务审批与各模块明确禁止的动作；调价幅度、退款／冲正流程等仍按对应业务决策确认，不能把“默认全部”实现为绕过业务条件。

记录可见性固定如下，所有读取路径均由服务端校验：

| 记录类别 | 可查看主体 | 范围与限制 |
|---|---|---|
| 工作记录 | 本店所有有效在职员工、本店老板及平台管理员 | 接宠、洗美、商品处理等业务经办记录，可查看本店其他员工的经办事实；不因此返回系统审计详情。 |
| 员工业绩 | 店员查看本人业绩；本店老板、平台管理员按职责查看 | “我的业绩”正常保留，指标、统计口径及归属算法在后续业务规则阶段细化。 |
| 系统操作日志 | 本店老板、平台管理员 | 调价、退款、删除员工等审计详情；普通员工即使是该次操作者，也不能读取系统日志。 |

工作记录中的真实经办人、业务状态与发生时间可正常展示；底层仍产生完整审计，由有权角色查看。“我的工作记录”是查看工作记录的入口，不将其强制限定为仅本人。提成功能已取消，老板及平台管理员也不提供其配置、计算、结算或查看入口；不能从业绩、工作记录、统计或导出接口重新生成提成功能。

本店所有在职且账号 / 门店关系有效的员工均可在店员端提交本店争议的正式回应，老板同样可回应；此项已确认，不再等待逐人授权或老板审批。不得跨店回应，不获得平台裁决或Web后台厂家回信录入权限。已有回应的修订和其他细分业务动作继续按03h§2.4、04§6及对应待决项收口；阶段08落实统一店员资格与老板／平台专属边界，不重新引入逐员工权限开关。

## 5. 商户注册流程

商户老板采用自助注册方式加入平台，不要求平台人工审核后才能创建门店。

V1.0 注册主流程：

老板进入商户注册入口
→ 完成可用的账号身份验证
→ 创建商户
→ 填写门店基础资料
→ 系统创建 Merchant
→ 系统创建与 Merchant 一一对应的 Store
→ 当前账号成为 Merchant Owner
→ 进入初始化设置
→ 开始使用系统

身份验证具体采用微信、手机号或其组合，由后续技术架构与安全实现细化，但不得改变“老板自助注册、不依赖平台人工审批”的已确认业务规则。

必要的风控、滥用限制和异常商户停用机制后续单独设计。

## 6. 店员邀请流程

新增店员采用邀请二维码 / 邀请链接方式。

基本流程：

老板在系统创建邀请
→ 系统生成一次性或限时邀请二维码 / 链接
→ 店员使用微信扫码 / 打开链接
→ 店员完成登录或注册
→ 确认加入该门店
→ 系统以 `staff.merchant_id` 建立 Staff 的唯一租户归属，并以 `staff_store_assignment.store_id` 表达可工作的门店范围；V1.0 虽为一商户一门店，也不得用 `Merchant / Store` 单一模糊字段代替二者
→ 自动取得当前统一店员业务权限
→ 店员开始使用店员端

邀请必须具有安全控制，至少考虑：

- 邀请过期时间
- 是否一次性使用
- 邀请状态
- 创建人
- 使用人
- 使用时间
- 已撤销邀请不得继续使用

### 6.1 被删除员工重新回本店入职

老板重新创建本店邀请 → 原员工完成登录及身份验证 → 明确接受本次邀请 → 按已验证的平台账号及原Merchant／Store关联原员工稳定身份 → 建立本轮有效门店关系 → 重新出现在员工列表并取得当前统一店员业务权限。

- 必须使用新邀请，不复活删除前的旧邀请、旧会话或已终止门店关系；仍校验邀请有效性及一员工不能同时在多店工作的约束。
- 同一人重新加入原店时沿用原`staff_id`，不得为返聘新建重复员工身份，也不能仅因姓名、昵称或未核验手机号相同而自动关联。
- 原删除及历史任职关系保留，本轮加入记录新邀请、实际生效时间及操作审计；重复接受同一邀请返回同一加入结果，不重复建立有效关系。
- 原订单、服务、业绩、工作记录和系统操作日志继续关联原员工，不因返聘覆盖原发生时间或重复记作本期新增业绩。历史记录读取仍遵循§4的角色范围。

## 7. 店员管理规则

V1.0本店员工管理仅由商户老板操作，不设置独立“店长”角色；平台管理员的管理范围沿用平台职责。

商户老板可以：

- 邀请新店员
- 查看店员
- 停用店员
- 删除店员（移出本店员工名单，保留身份引用与历史）
- 恢复被停用店员

普通店员不能创建、删除或管理其他店员。

员工管理只在“老板管理”中操作，内部设置“员工列表”和“邀请员工”；员工列表承载停用、删除、恢复三个选项，不将这三个动作另列为同级菜单，也不提供配置权限入口。

## 8. 员工离职 / 停用 / 删除

员工管理区分“停用”和“删除”：停用保留本店员工列表中的记录并关闭该员工的本店访问，老板可从该条记录恢复；删除是移出本店当前员工名单并终止当前有效门店关系，保留稳定员工身份和全部历史业务关联，不物理删除账号、订单或经营记录。删除不等于注销该自然人的平台账号。

停用或删除后：

- 店员不能继续登录店员端访问该门店数据
- 已授权 Token / Session 应失效
- 历史订单继续保留原服务员工
- 历史业绩及工作记录继续关联原员工
- 历史操作日志继续显示原操作人
- 历史洗护 / 美容报告继续显示原服务员工
- 历史寄养记录继续保留原员工

禁止因为员工离职而删除、匿名覆盖或重写已经发生的经营记录。

如员工误停用，可由老板在员工列表中恢复；恢复时再次校验账号和当前门店关系，使用当前统一店员业务权限，不恢复旧的逐人权限配置。“恢复员工”适用于被停用记录；已删除员工重新回本店统一走§6.1新邀请流程，沿用原员工身份并保留历史，不能直接将已终止关系恢复为有效。

## 9. 顾客账号 / 客户身份

顾客虽然不是经营管理角色，但必须拥有客户端身份。

系统必须区分：

- User：平台级自然人账号，用于微信身份、手机号等登录信息。
- Customer：某个Merchant的客户业务记录／关系，可由门店在线下先建；在安全绑定前可以没有关联的User。

一个User可以在多个Merchant下分别关联经安全确认的Customer；同一Customer至多绑定一个当前有效User。未绑定User的Customer仍可承载本店宠物、服务、充值和消费记录，但不能据此冒充线上身份或向任意User开放私有资料。不同商户只能查看自己Customer关系下的数据；跨店服务信息必须走03h明确的独立授权与查询规则。

顾客使用客户端小程序可查看本人被授权的数据和发起业务请求，不拥有任何经营管理权限。

## 10. 账号与业务记录分离原则

任何账号停用、离职、注销或失效，不得破坏历史业务数据。

订单、支付确认、余额流水、库存调整、操作日志、服务报告、寄养记录、业绩及工作记录等必须保留当时的操作者 / 服务者身份快照或稳定关联。取消功能不执行历史数据清除；如已有外部导入或旧系统遗留材料，按历史数据保留规则隔离保存，不因此新增已取消功能的页面、计算或接口。

## 11. 阶段结论

V1.0 正式采用：

- 3 个经营管理角色：平台超级管理员、商户老板、店员
- 1 个独立客户端身份：顾客 Customer / User
- 一个 Merchant 对应一家 Store
- 一个 Owner 只管理一家 Store
- 一个 Staff 只能属于一家 Store
- 老板默认拥有本店全部权限
- 有效在职店员统一默认拥有本店店员业务权限，不配置逐员工权限；老板／平台专属边界继续生效
- 商户老板自助注册并创建门店
- 店员通过邀请二维码 / 链接加入
- 本店员工管理仅老板可用，平台管理员按平台职责管理
- 员工列表支持停用、删除（移出本店名单）、恢复；历史身份与业务数据不删除
- 工作记录本店有效员工均可看，业绩查看保留，系统操作日志仅本店老板和平台管理员可看
- 提成功能取消；已删除员工返聘由老板重新邀请，关联原员工身份并保留历史
