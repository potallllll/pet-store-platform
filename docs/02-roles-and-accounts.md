# 02 用户角色与账号体系

> 状态：已确认
> 版本：V1.0

## 1. 总体原则

V1.0 不设计复杂的多级职位体系。

经营管理侧只保留三个正式角色：

1. 平台超级管理员 Platform Super Admin
2. 商户老板 Merchant Owner
3. 店员 Staff

客户端顾客使用独立的 Customer / User 身份体系，不属于经营管理角色，因此不计入上述三个后台角色。

不创建“店长、收银员、美容师、洗护师、寄养员”等独立系统角色。店员之间的能力差异通过后续的细粒度权限配置实现。

## 2. 平台超级管理员

平台超级管理员拥有整个平台的最高权限，可跨商户查看和管理所有数据。

主要能力包括：

- 查看全部商户
- 查看全部门店
- 查看平台级经营 / 使用数据
- 管理商户状态
- 查看平台审计日志
- 处理异常数据
- 管理系统级配置
- 管理平台资源限制
- 必要时协助商户进行数据处理

平台超级管理员不受单商户数据隔离限制。

## 3. 商户老板

一个商户仅对应一名主要商户老板账号和一家门店。

V1.0 不支持同一老板拥有多家门店。

商户老板：

- 只能访问自己商户 / 门店的数据
- 默认拥有本门店全部经营权限
- 可使用 Web 管理后台
- 可使用店员端小程序
- 可管理客户、宠物、订单、库存、会员、员工、财务、统计等
- 可邀请店员加入
- 可配置店员具体权限
- 可停用店员
- 可查看操作日志
- 可执行需要老板级权限的高风险操作

老板默认拥有所有店员权限，不需要重复配置。

## 4. 店员

店员只能属于一个商户和一家门店。

V1.0 明确禁止：

- 一个店员同时加入多个商户
- 一个店员同时在多个门店工作
- 店员跨店访问数据

店员的具体能力不通过新增角色实现，而通过权限项控制。

后续权限体系至少需要考虑是否允许某店员：

- 查看营业额
- 查看财务数据
- 查看客户手机号
- 创建 / 修改订单
- 人工调价
- 确认已收款
- 会员充值确认
- 会员余额调整
- 库存调整
- 退款 / 撤销 / 冲正
- 查看其他员工业绩
- 修改宠物 / 客户资料
- 操作寄养记录
- 填写洗护 / 美容报告
- 导出数据

具体权限矩阵在阶段 08 统一确定。

## 5. 商户注册流程

商户老板采用自助注册方式加入平台，不要求平台人工审核后才能创建门店。

建议流程：

老板进入商户注册入口
→ 使用手机号 / 微信等完成账号身份验证
→ 创建商户
→ 填写门店基础资料
→ 系统创建 Merchant
→ 系统创建与 Merchant 一一对应的 Store
→ 当前账号成为 Merchant Owner
→ 进入初始化设置
→ 开始使用系统

必要的风控、滥用限制和异常商户停用机制后续单独设计。

## 6. 店员邀请流程

新增店员采用邀请二维码 / 邀请链接方式。

基本流程：

老板在系统创建邀请
→ 系统生成一次性或限时邀请二维码 / 链接
→ 店员使用微信扫码 / 打开链接
→ 店员完成登录或注册
→ 确认加入该门店
→ 系统建立 Staff 与 Merchant / Store 的绑定关系
→ 老板配置该店员权限
→ 店员开始使用店员端

邀请必须具有安全控制，至少考虑：

- 邀请过期时间
- 是否一次性使用
- 邀请状态
- 创建人
- 使用人
- 使用时间
- 已撤销邀请不得继续使用

## 7. 店员管理规则

由于 V1.0 不设置独立“店长”角色，因此默认只有商户老板负责员工管理。

商户老板可以：

- 邀请新店员
- 查看店员
- 修改店员权限
- 停用店员
- 恢复被停用店员

店员默认不能创建、删除或管理其他店员。

如未来需要把部分员工管理能力授权给某个店员，应作为细粒度权限增加，而不是新增一个系统角色。

## 8. 员工离职 / 停用

员工离职后不得物理删除员工数据，只能停用账号与门店关系。

停用后：

- 店员不能继续登录店员端访问该门店数据
- 已授权 Token / Session 应失效
- 历史订单继续保留原服务员工
- 历史提成继续保留原员工
- 历史操作日志继续显示原操作人
- 历史洗护 / 美容报告继续显示原服务员工
- 历史寄养记录继续保留原员工

禁止因为员工离职而删除、匿名覆盖或重写已经发生的经营记录。

如员工误停用，可由老板恢复；恢复后是否恢复原权限应有明确系统策略，后续权限阶段细化。

## 9. 顾客账号 / 客户身份

顾客虽然不是经营管理角色，但必须拥有客户端身份。

系统建议区分：

- User：平台级自然人账号，用于微信身份、手机号等登录信息。
- Customer：User 与具体 Merchant 之间的客户关系。

同一个 User 可以分别成为多个商户的 Customer，但不同商户只能查看自己 Customer 关系下的数据。

顾客使用客户端小程序可查看本人被授权的数据和发起业务请求，不拥有任何经营管理权限。

## 10. 账号与业务记录分离原则

任何账号停用、离职、注销或失效，不得破坏历史业务数据。

订单、支付确认、余额流水、库存调整、操作日志、服务报告、寄养记录、提成记录等必须保留当时的操作者 / 服务者身份快照或稳定关联。

## 11. 阶段结论

V1.0 正式采用：

- 3 个经营管理角色：平台超级管理员、商户老板、店员
- 1 个独立客户端身份：顾客 Customer / User
- 一个 Merchant 对应一家 Store
- 一个 Owner 只管理一家 Store
- 一个 Staff 只能属于一家 Store
- 老板默认拥有本店全部权限
- 店员通过权限开关控制能力，不增加职位型角色
- 商户老板自助注册并创建门店
- 店员通过邀请二维码 / 链接加入
- 默认只有老板管理员工
- 员工离职只停用，不删除历史数据
