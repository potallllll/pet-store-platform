## 1. 产品定位

V1.0 新增平台级「上门喂养」需求市场。

该功能不是某一家门店内部私有列表，而是平台级公开需求：

- 平台用户均可浏览公开需求。
- 用户可发布上门喂养需求。
- 其他已完成必要身份验证的用户可接单。
- 需求发布时以 `publisher_store_id` 永久绑定发布者当前 Store；所属 Merchant 通过 Store 关系解析，不使用 `Merchant / Store` 模糊归属字段。
- 有人接单后，只向该绑定门店的店员端生成对接待办，由该门店负责协调发布者与接单者。
- 不因此向其他门店开放发布者的客户资料、联系方式、订单、余额等私有数据。

V1.0 不建设平台在线支付、资金托管、抽佣、自动分账或保证金体系。

## 2. 客户端入口

首页新增「上门喂养」区域。

当前首页正式顺序为：

> 当前门店 → 当前服务 → 宠物交友 → 上门喂养 → 推荐商品

因此上门喂养固定位于“宠物交友”之后、“推荐商品”之前。

首页可展示近期公开需求摘要，并提供：

- 查看更多
- 发布需求
- 我的发布
- 我的接单

底部导航仍保持：预约 / 首页 / 我的，不新增独立底部 Tab。

## 3. 发布需求

发布页至少支持：

- 宠物：选择已有宠物；可支持多只宠物
- 宠物类型 / 数量
- 宠物照片：选填
- 开始日期
- 结束日期
- 每日喂养时间或时间段
- 每日上门次数
- 地点
- 每日预算
- 喂养要求
- 特殊注意事项：选填

提交前应明确该需求会公开展示给平台用户，并由当前门店在有人接单后负责对接。

发布确认页展示绑定门店，提交时由服务端重新校验门店有效性、发布者身份、日期和必要字段。未选门店时按 `03g` 引导扫码 / 选店；绑定门店已停用时不得继续向该店发布。重复提交须返回同一发布结果，不重复创建需求。

## 4. 地址与隐私

公开列表 / 详情不得直接展示精确住宅地址、门牌号、手机号、微信、真实姓名等敏感信息。

公开位置只展示到足以判断接单距离的模糊层级，例如：

- 城市 / 区县
- 小区名称或附近区域

精确地址和必要联系方式只允许在接单后，由绑定门店在合法、必要、获得相应授权的对接流程中使用。

## 5. 公开需求卡片

至少展示：

- 宠物类型 / 数量或宠物摘要
- 上门喂养日期范围
- 每日喂养时间
- 模糊地点
- 每日预算
- 喂养要求摘要
- 当前状态

不得在公开卡片上泄露发布者商户私有客户信息。

### 5.1 本地无需求时的跨城市补充展示

若当前城市 / 当前区域没有可展示的有效公开上门喂养需求，客户端不得伪造或凭空生成假的用户需求。

应从平台其他城市中仍处于允许公开展示状态的**真实上门喂养需求**里随机抽取若干条作为补充内容，并明确展示其真实城市 / 区县等模糊位置。

规则：

- 只允许使用平台真实存在且当前可公开浏览的需求。
- 不修改原需求绑定的 `publisher_store_id`、城市、预算、时间、状态等事实。
- 不把其他城市需求伪装成本地需求。
- 随机展示只影响推荐 / 排序，不创建新业务记录。
- 若全平台也没有可公开需求，则显示正常空状态与“发布需求”入口。

## 6. 分享到微信群

发布成功后支持分享该需求到微信聊天 / 群。

分享卡至少表达：

- 上门喂养需求
- 宠物类型
- 日期范围
- 模糊地点
- 每日预算

点击分享卡应深链进入对应需求详情，而不是只进入普通首页。

## 7. 接单规则

- 已登录并完成必要身份验证的用户可点击「我要接单」。
- 发布者不能接自己的需求。
- 同一需求同一时刻只允许一个有效接单者。
- 第一个接单成功的用户由服务端原子锁定当前需求。
- 其他用户随后看到“已有人接单 / 等待门店对接”，不得重复形成有效接单。
- 并发接单必须由服务端原子校验，前端状态不可作为最终依据。

## 8. 状态流转

底层业务至少支持：

待接单
→ 已接单待门店对接
→ 门店对接中
→ 已确认
→ 服务中
→ 已完成

并支持：

- 已取消
- 接单取消后重新回到待接单（由门店按规则处理）

客户端正常主流程统一聚合展示为：

1. `待接单`
2. `已接单待门店对接`
3. `进行中`
4. `已完成`

其中门店对接中 / 已确认 / 服务中等底层进行态在客户端统一显示为“进行中”。已取消属于历史 / 终止状态，查看对应记录时仍如实显示“已取消”。

具体可修改 / 取消权限、截止时间及门店响应时限仍在阶段 06 核心业务规则中确认，见本节待决清单；本次补充不把未确认权限或时间写成正式常数。

### 8.1 状态、主体与动作

下表定义客户端读取、已确认动作及结果边界。标注“待决”的操作须完成对应决策后才能成为可用按钮，不由前端自行推断开放条件。

| 底层状态 / 条件 | 主体 | 动作与校验 | 结果 / 客户端反馈 |
|---|---|---|---|
| 待接单且仍有效 | 已验证、非发布者用户 | 接单；提交时复核状态、本人身份、需求有效性和绑定门店可接续性 | 首个有效请求锁定接单者，进入已接单待门店对接；其余请求返回最新状态，不新增有效接单 |
| 待接单 | 发布者 | 查看本人发布；修改 / 取消入口与截止待 `DEC-FEED-01` | 未获服务端成功确认前不把页面改为修改成功或已取消 |
| 已接单待门店对接 / 门店对接中 / 已确认 | 发布者、有效接单者 | 查看进度、绑定门店和本人相关信息；退出接单 / 取消条件待 `DEC-FEED-01` | 显示真实主状态与下一步说明，不以客户端按钮直接释放接单锁 |
| 已接单待门店对接 / 后续非终止状态 | 绑定门店有权限人员 | 按已确认店员流程协调、更新状态；其他门店不可操作 | 保留操作者、时间、原 / 新状态，按 `03f` 通知相关用户 |
| 接单取消已按权限与规则生效 | 绑定门店有权限人员 | 校验需求仍有效后重新开放；不得静默改派给另一接单者 | 原接单记录保留，建立可区分的新接单轮次；新一轮仍只允许一个有效接单者 |
| 服务中 | 发布者、有效接单者 | 查看状态 / 联系绑定门店；取消条件待 `DEC-FEED-01` | 不因客户端退出页面或时间经过自动改成已完成 |
| 已完成 / 已取消 / 已不满足有效条件 | 相关用户；公开分享访问者仅限仍允许公开的字段 | 查看真实历史状态；不允许新接单或重复完成 | 隐藏或禁用接单动作并说明原因，提供返回需求列表入口 |
| 请求提交中 / 结果未知 | 本次请求用户 | 暂停重复提交，重进或重试先查原请求结果 | 展示“正在确认结果”；不能把网络超时直接当作接单失败后新建第二次请求 |

### 8.2 并发、失效与门店停用

- 接单、有效取消、重新开放均由服务端按当前状态和接单轮次校验。接单与取消同时发生时，只能提交一条符合状态前提的结果，另一方刷新最新状态；不能同时显示已取消又保留有效接单者。
- 同一用户重复接单请求返回原结果；旧轮次的迟到请求或回调不能影响重新开放后的新轮次。已取消、已完成以及服务日期范围已全部结束的需求不得接受新接单。
- 首页和需求列表只推荐当前有效且允许公开的需求。更早的接单截止、自动失效时间及是否另设失效底层状态待 `DEC-FEED-03`；前端不得仅靠缓存继续显示可接单。
- 旧分享链接读取最新状态和公开权限：业务仍可公开时显示已取消 / 已完成 / 不可接单的只读状态；已不允许公开时显示需求不可用，不泄露精确地址、联系方式或新的接单者资料。
- 绑定门店停用后停止向该店新发布和新接单；已发布 / 已接单记录和审计继续保留，相关用户看到“绑定门店暂不可对接”的原因和进度说明。不得静默改绑其他门店、向其他门店开放资料、自动完成服务或据此产生平台资金操作。
- 已有需求的接续、人工处理主体和响应时限由 `DEC-FEED-02` 收口；未决期间不把新的改派 / 资金权限伪装为已有能力。

### 8.3 待决清单（不属于已确认可执行规则）

| 决策 ID | 待确认内容 | 收口阶段 / 影响 |
|---|---|---|
| DEC-FEED-01 | 各状态下发布者 / 接单者的修改、取消、退出权限，截止时间，门店确认条件 | 阶段 06；决定客户端按钮和取消状态迁移 |
| DEC-FEED-02 | 门店对接响应时限、超时提醒、停用门店已有需求的接续主体与处理流程 | 阶段 04 / 06；决定待对接异常页和门店待办，不自动扩展平台收款权限 |
| DEC-FEED-03 | 服务日期全部结束之前的接单截止、公开失效时间、底层失效状态及自动任务规则 | 阶段 06；决定可接单判定、列表过滤和历史状态映射 |

## 9. 门店对接

有人接单后：

- 系统向 `publisher_store_id` 对应门店生成待处理事项。
- 店员可以查看发布需求、发布者、接单者及必要的对接信息。
- 除 `publisher_store_id` 对应 Store 外，其他 Store 均不得获得该内部对接任务；即使属于同一 Merchant 也不自动共享。
- 门店完成协调后更新状态。

该机制不改变平台多商户数据隔离原则。

## 10. 订单 / 数据边界

客户端可以使用“上门喂养订单 / 需求”的产品文案，但底层建议独立建模为平台级 `home_feeding_job` / `home_feeding_request`，不得直接复用商户普通商品订单或洗护 / 寄养服务订单表。

原因：

- 需求为平台公开数据。
- V1.0 不发生平台线上支付。
- 成交后由绑定门店负责协调，不应污染门店现有商品销售、洗护或寄养营业额。

后续如需要门店线下收款，可在阶段 06 明确与正式订单 / 结算域的关联方式。

## 11. 故障隔离

上门喂养属于独立业务域。该模块故障不得导致：

- 洗护 / 美容不可用
- 寄养不可用
- 商品销售不可用
- 钱包不可用
- 普通预约不可用

## 12. V1.0 关键验收场景

### C-FEED-01：发布

用户填写时间、地点、每日预算、喂养要求并发布成功。

### C-FEED-02：公开浏览

其他平台用户可看到需求，但看不到精确地址、手机号、微信和商户内部资料。

### C-FEED-03：接单

第一个用户接单成功后需求锁定，其他用户不能重复接单。

### C-FEED-04：门店对接

接单成功后，仅发布时绑定的门店收到待办。

### C-FEED-05：分享

发布者可分享到微信群，点击后直接进入该需求详情。

### C-FEED-06：本地无需求跨城补充

当前城市无有效公开需求时，首页可随机展示其他城市真实、可公开的需求；城市信息必须如实显示，不得伪造本地需求。若全平台均为空，则显示正常空状态。

### 状态边界验收补充

- 重复点击 / 断网重试同一接单请求只产生一次有效接单，结果未知时可恢复查询。
- 接单与已获权限的取消同时发生，只接受符合最新状态的结果；旧轮次请求不影响重新开放后的新接单。
- 服务日期范围已结束、已取消、已完成或绑定门店停用时不可新接单；旧分享页显示真实状态及返回路径。
- 切换当前门店不改变需求永久绑定门店，平台个人进度与消息仍可查询；其他门店不能获得内部对接资料。
- 待决权限、取消截止和响应时限在对应决策确认前，不被验收脚本或原型预置为已确认规则。
