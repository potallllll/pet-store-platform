## 1. 产品定位

V1.0 新增平台级「上门喂养」需求市场。

该功能不是某一家门店内部私有列表，而是平台级公开需求：

- 平台用户均可浏览公开需求。
- 用户可发布上门喂养需求。
- 其他已完成必要身份验证的用户可接单。
- 需求发布时以 `publisher_store_id` 永久绑定发布者当前 Store；所属 Merchant 通过 Store 关系解析，不使用 `Merchant / Store` 模糊归属字段。
- 发布时以publisher_store_id保留原始来源；当前负责门店唯一取current_coordination_store_id，初始等于发布门店。有人接单后向当前负责门店生成对接待办；账号停用按§9.2自动转最近有效门店，不覆盖原始来源或接单人。
- 不因此向其他门店开放发布者的客户资料、联系方式、订单、余额等私有数据。

V1.0 不建设平台在线支付、资金托管、抽佣、自动分账或保证金体系。

## 2. 客户端入口

首页新增「上门喂养」区域。

当前首页正式顺序为：

> 当前门店 → 当前服务 → 消费争议 / 风险反馈 → 上门喂养 → 推荐商品

因此上门喂养固定位于“消费争议 / 风险反馈”之后、“推荐商品”之前。

首页可展示近期公开需求摘要，并提供：

- 查看更多
- 发布需求
- 我的发布
- 我的接单

底部导航仍保持：预约 / 首页 / 我的，不新增独立底部 Tab。

## 3. 发布需求

发布页至少支持：

- 宠物：选择已有宠物；可支持多只宠物
- 宠物类型 / 数量
- 宠物照片：选填
- 开始日期
- 结束日期
- 每日喂养时间或时间段
- 每日上门次数
- 地点
- 每日预算
- 喂养要求
- 特殊注意事项：选填

提交前说明需求摘要公开、其他用户可自主接单，门店确认后仅当前店查看双方必要联系方式并线下协调；不将联系方式公开给对方或分享访客。发布提交后不支持编辑，需求方仅保留发布／撤销两个业务操作。

发布确认页展示绑定门店，提交时由服务端重新校验门店有效性、发布者身份、日期和必要字段。未选门店时按 `03g` 引导扫码 / 选店；绑定门店已停用时不得继续向该店发布。重复提交须返回同一发布结果，不重复创建需求。

## 4. 地址与隐私

公开列表 / 详情不得直接展示精确住宅地址、门牌号、手机号、微信、真实姓名等敏感信息。

公开位置只展示到足以判断接单距离的模糊层级，例如：

- 城市 / 区县
- 小区名称或附近区域

双方联系方式只在当前负责门店确认后，向该店老板／有效员工展示，见§9；需求方、接单用户即使已登录、已接单或门店已确认，也不能通过本功能互看对方手机号／微信等联系资料。精确地址沿原接单后合法必要且授权的门店对接范围使用，不因确认向双方或公开页面开放；停用接续仍按§9.2。

## 5. 公开需求卡片

至少展示：

- 宠物类型 / 数量或宠物摘要
- 上门喂养日期范围
- 每日喂养时间
- 模糊地点
- 每日预算
- 喂养要求摘要
- 当前状态

不得在公开卡片上泄露发布者商户私有客户信息。

### 5.1 本地无需求时的跨城市补充展示

若当前城市 / 当前区域没有可展示的有效公开上门喂养需求，客户端不得伪造或凭空生成假的用户需求。

应从平台其他城市中仍为有效待接单且未到首次上门截止、允许公开展示的**真实上门喂养需求**里随机抽取若干条作为补充内容，并明确展示其真实城市 / 区县等模糊位置。

规则：

- 只允许使用平台真实存在且当前可公开浏览的需求。
- 不修改原需求绑定的 `publisher_store_id`、城市、预算、时间、状态等事实。
- 不把其他城市需求伪装成本地需求。
- 随机展示只影响推荐 / 排序，不创建新业务记录。
- 若全平台也没有可公开需求，则显示正常空状态与“发布需求”入口。

## 6. 分享到微信群

发布成功后支持分享该需求到微信聊天 / 群。

分享卡至少表达：

- 上门喂养需求
- 宠物类型
- 日期范围
- 模糊地点
- 每日预算

点击分享卡应深链进入对应需求详情，而不是只进入普通首页。

## 7. 接单规则

- 已登录并完成必要身份验证的用户可点击「我要接单」。
- 发布者不能接自己的需求。
- 同一需求同一时刻只允许一个有效接单者。
- 第一个接单成功的用户由服务端原子锁定当前需求。
- 其他用户随后看到“已有人接单 / 等待门店对接”，不得重复形成有效接单。
- 并发接单必须由服务端原子校验，前端状态不可作为最终依据。

## 8. 状态、入口与操作

当前唯一入口名为“上门喂养”。状态统一为：待接单 → 待门店确认 → 已确认 → 已结束；终止状态为已撤销、已过期。

- 需求方只有发布、撤销；用户保留自主接单；当前负责门店只有确认、撤销。所有动作均无需审批，撤销原因选填。
- 门店确认前不返回双方联系方式；确认后只有当前负责门店老板／有效员工能查看双方合法授权的完整联系资料，需求方和接单用户不能互看。
- APP不跟踪开始、打卡、完成或线上修改；线下安排由门店协调。到需求结束日期的服务端日界线后，未撤销记录自动变为“已结束”，只表示系统展示周期结束，不证明逐次服务完成或收付款。
- 结束、撤销、过期后停止新接单、确认和联系方式的新读取；历史只读保留。要重新开始必须发布新需求。

## 9. 门店匹配、异常与自动接续

1. 定位成功时按原绑定门店位置寻找当前有效平台门店；附近没有可用门店，提示“附近暂无服务门店”并结束本次发布引导，不创建待处理需求。
2. 定位失败时提示顾客手动选择区县；选择后重新查找，仍无候选则按第1条结束。不得静默随机选店或无限扩大范围。
3. 门店临时休息不影响本功能正常运行。
4. 当前负责门店账号停用时，尚未结束的需求及待办、原接单人和历史自动转给最近的其他有效平台门店；新店可查看原需求和接单关系。
5. 联系方式权限绑定当前负责版本：新店必须重新点击确认，确认成功后可查看双方完整联系方式；原店立即失去新读取和操作资格，历史确认记录保留。
6. 转店无候选时不创建虚假新店，保留原记录并显示“附近暂无服务门店”，停止继续对接；不得恢复停用门店权限。
7. 发布、接单、确认、撤销、自动结束、过期和转店均由服务端按最新状态、当前负责版本与幂等请求原子处理，系统自动记录操作主体、时间和前后状态。

### 9.1 接单截止与自动结束

- 接单截止仍为首次约定上门开始时间；服务端当前时间严格早于截止才可接单。截止时仍无人接单的需求变为已过期。
- 已有接单者的待确认／已确认记录不因接单截止而过期，但到需求结束日期后自动变为已结束。
- 旧分享与本人记录只读显示最新真实状态，不公开精确地址或参与方联系方式。

## 10. 订单 / 数据边界

客户端可以使用“上门喂养订单 / 需求”的产品文案，但底层建议独立建模为平台级 `home_feeding_job` / `home_feeding_request`，不得直接复用商户普通商品订单或洗护 / 寄养服务订单表。

原因：

- 需求为平台公开数据。
- V1.0 不发生平台线上支付。
- 成交后由绑定门店负责协调，不应污染门店现有商品销售、洗护或寄养营业额。

本功能APP只作发布／接单／门店确认／撤销与必要联系，不生成门店收款或消费账本入口；真实线下协商与交易不自动回写APP服务状态。

## 11. 故障隔离

上门喂养属于独立业务域。该模块故障不得导致：

- 洗护 / 美容不可用
- 寄养不可用
- 商品销售不可用
- 钱包不可用
- 普通预约不可用

## 12. V1.0 关键验收场景

### C-FEED-01：发布

用户填写时间、地点、每日预算、喂养要求并发布成功。

### C-FEED-02：公开浏览

其他平台用户可看到需求，但看不到精确地址、手机号、微信和商户内部资料。

### C-FEED-03：接单

第一个用户接单成功后需求锁定，其他用户不能重复接单。

### C-FEED-04：门店确认与联系方式门槛

当前负责店老板／有效员工只有确认／撤销；有效用户接单后才可确认，确认绑定当前负责版本，随后仅本店可查双方已有合法授权联系资料。需求方／接单用户始终不能互看，确认前店家也不可取双方号码；公开列表、详情、我的记录、消息／分享、直接API与缓存同样过滤。撤销后关闭新取数，重复／越店／停用／旧版本拒绝，不伪造缺失联系资料。原四步进度、APP修改／重新开放／备注媒体／开始完成及相关通知退役。

### C-FEED-05：分享

发布者可分享到微信群，点击后直接进入该需求详情。

### C-FEED-06：本地无需求跨城补充

当前城市无有效公开需求时，首页可随机展示其他城市真实、可公开的需求；城市信息必须如实显示，不得伪造本地需求。若全平台均为空，则显示正常空状态。

### 状态边界验收补充

- 需求方仅发布／撤销，接单用户原自主接单保留；发布后任何状态无编辑接口，线下协商不回写原内容或截止。门店仅确认／撤销，不恢复服务状态跟踪或退出／重新开放。
- 同一需求一位有效接单者；接单／撤销／确认／过期／迁移竞态与重复请求不多建需求、确认／通知或放出错误门店版本的联系方式。
- 临时休息不影响运行；账号停用按原发布店距离转最近有效店，原需求／接单人／历史不改，新店再确认才取联系方式，旧店失权，无候选保持原单并待平台异常处理。
- 首次上门起始截止，等于及之后不接单；无有效接单者到点过期，已有有效接单者不自动结束。仅有效待接单推荐，旧分享最新真实状态只读且无双方私密资料，原历史保留。
- 文档确认与审计不是实际功能验收；附近无服务门店提示与定位失败手动选区已确认，但真实定位和门店距离接口仍须在技术阶段实现与验收，不能用Mock宣称已接通。
