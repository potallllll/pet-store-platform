## 1. 产品定位

V1.0 新增平台级「上门喂养」需求市场。

该功能不是某一家门店内部私有列表，而是平台级公开需求：

- 平台用户均可浏览公开需求。
- 用户可发布上门喂养需求。
- 其他已完成必要身份验证的用户可接单。
- 需求发布时以 `publisher_store_id` 永久绑定发布者当前 Store；所属 Merchant 通过 Store 关系解析，不使用 `Merchant / Store` 模糊归属字段。
- 发布时以publisher_store_id保留原始来源；当前负责门店唯一取current_coordination_store_id，初始等于发布门店。有人接单后向当前负责门店生成对接待办；账号停用按§9.2自动转最近有效门店，不覆盖原始来源或接单人。
- 不因此向其他门店开放发布者的客户资料、联系方式、订单、余额等私有数据。

V1.0 不建设平台在线支付、资金托管、抽佣、自动分账或保证金体系。

## 2. 客户端入口

首页新增「上门喂养」区域。

当前首页正式顺序为：

> 当前门店 → 当前服务 → 消费争议 / 风险反馈 → 上门喂养 → 推荐商品

因此上门喂养固定位于“消费争议 / 风险反馈”之后、“推荐商品”之前。

首页可展示近期公开需求摘要，并提供：

- 查看更多
- 发布需求
- 我的发布
- 我的接单

底部导航仍保持：预约 / 首页 / 我的，不新增独立底部 Tab。

## 3. 发布需求

发布页至少支持：

- 宠物：选择已有宠物；可支持多只宠物
- 宠物类型 / 数量
- 宠物照片：选填
- 开始日期
- 结束日期
- 每日喂养时间或时间段
- 每日上门次数
- 地点
- 每日预算
- 喂养要求
- 特殊注意事项：选填

提交前应明确该需求会公开展示给平台用户，并由当前门店在有人接单后负责对接。

发布确认页展示绑定门店，提交时由服务端重新校验门店有效性、发布者身份、日期和必要字段。未选门店时按 `03g` 引导扫码 / 选店；绑定门店已停用时不得继续向该店发布。重复提交须返回同一发布结果，不重复创建需求。

## 4. 地址与隐私

公开列表 / 详情不得直接展示精确住宅地址、门牌号、手机号、微信、真实姓名等敏感信息。

公开位置只展示到足以判断接单距离的模糊层级，例如：

- 城市 / 区县
- 小区名称或附近区域

精确地址和必要联系方式只允许在接单后，由当前负责门店在合法、必要、获得相应授权的对接流程中使用；账号停用后的限定资料接续按§9.2。

## 5. 公开需求卡片

至少展示：

- 宠物类型 / 数量或宠物摘要
- 上门喂养日期范围
- 每日喂养时间
- 模糊地点
- 每日预算
- 喂养要求摘要
- 当前状态

不得在公开卡片上泄露发布者商户私有客户信息。

### 5.1 本地无需求时的跨城市补充展示

若当前城市 / 当前区域没有可展示的有效公开上门喂养需求，客户端不得伪造或凭空生成假的用户需求。

应从平台其他城市中仍处于允许公开展示状态的**真实上门喂养需求**里随机抽取若干条作为补充内容，并明确展示其真实城市 / 区县等模糊位置。

规则：

- 只允许使用平台真实存在且当前可公开浏览的需求。
- 不修改原需求绑定的 `publisher_store_id`、城市、预算、时间、状态等事实。
- 不把其他城市需求伪装成本地需求。
- 随机展示只影响推荐 / 排序，不创建新业务记录。
- 若全平台也没有可公开需求，则显示正常空状态与“发布需求”入口。

## 6. 分享到微信群

发布成功后支持分享该需求到微信聊天 / 群。

分享卡至少表达：

- 上门喂养需求
- 宠物类型
- 日期范围
- 模糊地点
- 每日预算

点击分享卡应深链进入对应需求详情，而不是只进入普通首页。

## 7. 接单规则

- 已登录并完成必要身份验证的用户可点击「我要接单」。
- 发布者不能接自己的需求。
- 同一需求同一时刻只允许一个有效接单者。
- 第一个接单成功的用户由服务端原子锁定当前需求。
- 其他用户随后看到“已有人接单 / 等待门店对接”，不得重复形成有效接单。
- 并发接单必须由服务端原子校验，前端状态不可作为最终依据。

## 8. 状态流转

底层业务至少支持：

待接单
→ 已接单待门店对接
→ 门店对接中
→ 已确认
→ 服务中
→ 已完成

并支持：

- 已取消
- 接单取消后重新回到待接单（由门店按规则处理）

客户端正常主流程统一聚合展示为：

1. `待接单`
2. `已接单待门店对接`
3. `进行中`
4. `已完成`

其中门店对接中 / 已确认 / 服务中等底层进行态在客户端统一显示为“进行中”。已取消属于历史 / 终止状态，查看对应记录时仍如实显示“已取消”。

修改／取消／退出及重新开放按§9.1，门店临时休息不影响本功能，账号停用按§9.2自动接续；接单截止、公开到期及其他剩余边界仍见§8.3，不填写未确认时间常数。

### 8.1 状态、主体与动作

下表定义客户端读取、已确认动作及结果边界。标注“待决”的操作须完成对应决策后才能成为可用按钮，不由前端自行推断开放条件。

| 底层状态 / 条件 | 主体 | 动作与校验 | 结果 / 客户端反馈 |
|---|---|---|---|
| 待接单且仍有效 | 已验证、非发布者用户 | 接单；提交时复核状态、本人身份、需求有效性和绑定门店可接续性 | 首个有效请求锁定接单者，进入已接单待门店对接；其余请求返回最新状态，不新增有效接单 |
| 待接单且仍有效 | 发布者本人 | 无需门店审批可直接修改或取消；服务端与接单竞争校验当前状态 | 修改保存原值历史，取消成功才显示已取消，不因响应丢失重复操作 |
| 已接单待门店对接 / 门店对接中 / 已确认 | 发布者、有效接单者 | 不直接改日期／地址／次数等内容，变更／取消／退出通过联系当前门店协调，无新增线上申请审批 | 门店按§9.1办理；仅联系或口头提出未成立前不释放接单锁 |
| 已接单待门店对接 / 门店对接中 / 已确认 / 服务中 | current_coordination_store_id对应店老板／有效员工 | 按§9推进，按§9.1办理取消／退出或重新开放；版本／轮次／角色及新旧门店范围服务端校验 | 结果通知双方，留实际人／时间／前后状态，旧门店失权后不能继续处理 |
| 接单取消已按权限与规则生效 | 绑定门店有权限人员 | 校验需求仍有效后重新开放；不得静默改派给另一接单者 | 原接单记录保留，建立可区分的新接单轮次；新一轮仍只允许一个有效接单者 |
| 服务中 | 发布者、有效接单者 | 查看进度／联系当前负责门店；需要提前结束由门店按§9.1登记 | 已取消并标服务开始后提前结束，保留已发生事实，不假记完成或重新开放原需求 |
| 已完成 / 已取消 / 已不满足有效条件 | 相关用户；公开分享访问者仅限仍允许公开的字段 | 查看真实历史状态；不允许新接单或重复完成 | 隐藏或禁用接单动作并说明原因，提供返回需求列表入口 |
| 请求提交中 / 结果未知 | 本次请求用户 | 暂停重复提交，重进或重试先查原请求结果 | 展示“正在确认结果”；不能把网络超时直接当作接单失败后新建第二次请求 |

### 8.2 并发、失效与门店停用

- 接单、有效取消、重新开放均由服务端按当前状态和接单轮次校验。接单与取消同时发生时，只能提交一条符合状态前提的结果，另一方刷新最新状态；不能同时显示已取消又保留有效接单者。
- 同一用户重复接单请求返回原结果；旧轮次的迟到请求或回调不能影响重新开放后的新轮次。已取消、已完成以及服务日期范围已全部结束的需求不得接受新接单。
- 首页和需求列表只推荐当前有效且允许公开的需求。更早的接单截止、自动失效时间及是否另设失效底层状态待 `DEC-FEED-03`；前端不得仅靠缓存继续显示可接单。
- 旧分享链接读取最新状态和公开权限：业务仍可公开时显示已取消 / 已完成 / 不可接单的只读状态；已不允许公开时显示需求不可用，不泄露精确地址、联系方式或新的接单者资料。
- 门店临时休息／临时关闭预约不影响本功能的浏览、发布、接单、对接及已有服务，不能当作账号停用触发迁移。账号停用时停止该店新操作，未完成需求按§9.2自动接续；不自动取消／完成／更换接单人或产生资金操作。
- current_coordination_store_id与coordination_assignment_version由服务端管理，普通用户切店不改变原始发布门店或负责门店；账号停用的系统迁移是限定例外，原请求及历史不复制。

1. **入口与待办**：“业务 → 上门喂养”查完整记录。其他用户有效接单、确需绑定门店对接后才形成工作台待处理，归current_coordination_store_id，初始为publisher_store_id；工作台按当前需办事项，不只查今天新建。只浏览公开需求、发布但未接单不自动形成门店对接待办，其他门店不获得内部任务。
2. **查询分组与排序**：待对接、进行中、历史记录为查询分组，不新增底层状态；待对接按当前有效轮次accepted_at早到晚排列，不用需求修改时间改排序。开始对接后进入进行中，已确认／服务中仍在进行中，完成／取消等终止记录查历史；分组不代替真实状态，不因切组或跨天自动完成。
3. **经办资格**：绑定门店老板和有效在职员工均可处理，无老板逐单审批、不限定原经办人。服务端仍校验当前负责门店／coordination_assignment_version、有效员工关系、当前状态及有效接单者／轮次；停用员工／越店或旧轮次请求不能推进。账号停用的系统接续按§9.2，其他随意改派／跨店查看／资金操作不因此开放；取消权限按§9.1。
4. **详情**：集中展示本需求发布者／当前有效接单者、宠物、服务起止日期、每日时间／次数、预算及要求。精确地址及必要联系方式只在接单后合法必要、获得相应授权的门店对接范围使用，不能公开、扩大给其他门店或凭打开详情自动认定授权。
5. **人工联系**：门店自行电话／微信联系双方；沟通备注及照片选填，不强制录音、截图或聊天记录。备注／媒体留在原需求及轮次的门店对接记录，更新保留历史，不自动成为公开卡片／分享页或对双方公开的内容；相关用户读取有权查看的真实进度结果。
6. **手动进度**：在原需求上依次执行开始对接→确认安排→开始服务→完成，对应既有门店对接中→已确认→服务中→已完成，不建第二订单／独立状态机。每次按真实沟通和服务事实操作，服务端校验最新状态及轮次，记录实际人／时间／前后值；只打开详情、联系一次、日期到点或消息已读不自动推进／完成。重复提交读取原结果，不重复状态事件及通知；不以本条推导跳步、重开或未决恢复能力。
7. **记录从简**：不增加逐次上门打卡、定位、强制照片、签字或顾客验收。门店根据实际沟通结果更新整体进度，选填备注／照片不成为开始／完成必填门槛；每日次数等需求原信息保留，不因未建逐次打卡就伪记每次服务已执行。
8. **完成与财务**：实际服务结束后，老板／有效员工点击完成，保留本轮需求、经办和服务端确认时间，相关用户看到真实已完成及结果通知。不要求顾客额外验收，不以时间经过或无备注自动结束；完成不自动形成商户销售订单、收款、余额扣款或门店营业额，平台不托管／抽佣／分账。

复用F-FEED-001～023、原需求／接单轮次及F-AUD记录动作，不另建每次上门订单或员工派单／排班系统。门店沟通备注与媒体唯一字段见FIELD-REGISTRY§15；原special_notes是发布者需求，不能覆盖为店员内部备注。F-FEED-024独立更细对接状态仍待决，本节四步使用原home_feeding_status，不据此新增另一状态机。

本节基本8项继续有效，取消／退出／重新开放及不设固定响应时限按§9.1，临时休息和账号停用自动接续按§9.2；接单截止／公开失效与其余协调修改／更正细节仍按§8.3，不整体关闭决策。

### 9.1 已确认：取消、退出、重新开放与响应规则

> status: confirmed
> status_scope: home_feeding_cancellation_exit_reopening_and_no_response_timer
> home_feeding_unaccepted_edit_cancel: publisher_direct_without_store_approval
> home_feeding_accepted_content_change: contact_current_store_no_direct_edit
> home_feeding_acceptor_exit: manual_store_coordination_no_online_approval_request
> home_feeding_cancel_roles: [merchant_owner, active_store_staff]
> home_feeding_cancel_reason_required: false
> home_feeding_reopen: explicit_store_action_after_acceptor_exit_and_publisher_still_needs_service
> home_feeding_started_cancellation: canceled_with_early_end_label_preserve_actual_service
> home_feeding_started_request_reopen: excluded
> home_feeding_response_deadline: none
> home_feeding_automatic_chasing: excluded
> home_feeding_timeout_auto_cancel: false

- 无有效接单者且仍为待接单时，发布者可修改／取消，无门店审批。提交与接单原子竞争，接单先成功则旧编辑／取消失败，转联系门店；取消先成功则新接单失败，不产生又已取消又有效接单的结果。
- 有人接单后，发布者不直接改日期、地址、次数等内容，须联系当前负责门店；接单者退出亦联系门店，由门店协调后实际登记，不增加线上申请／审批链。已开始服务后提前结束按本节终止原需求，不伪装为未开始退出；协调修改具体重确认流程仍属剩余待决。
- 开始服务前，当前负责店老板／有效员工可取消需求，无老板审批，通知双方；取消需求终止原单，不借重新开放恢复已取消原单。
- 接单者退出且服务未开始时，记录原人／轮次及退出时间，清除当前有效接单者，需求保留门店对接中并显示“原接单者已退出，待门店处理”，不自动公开接单。发布者仍需要服务且需求符合现行有效接单条件时，门店明确重新开放才回待接单，使用新接单轮次；原轮历史不删除，不自动指定他人。
- 已开始服务后提前结束，原需求记已取消，同时向相关用户明确“服务开始后提前结束”；实际已开展的服务及原服务中状态历史保留，不假记全部完成，不重新开放这笔原需求。区分提示复用原轮次状态历史与取消事实，不另造已中止底层状态。
- 取消／退出原因选填，前端／API／DTO／服务端／持久化不因空值阻断；实际操作人／时间／原新状态和结果仍保留，填了保存真实说明，不填不编造理由。操作人与时间留痕复用原F-AUD，选填原因用audit_reason，不开放通用日志给顾客。
- 不设固定门店响应时限，不增加自动催办／超时取消；待办跨天保留直到实际处理，进度／结果的原有通知仍保留。不得把“未回复／日期到点／已读”当作取消、退出或完成。
- 不照搬预约6小时修改截止；本功能更早接单截止、公开失效时间仍待§8.3。合法取消／退出／重新开放／完成均校验当前负责店、coordination_assignment_version、需求状态、有效轮次及幂等，旧轮迟到操作不能污染新轮。

### 9.2 已确认：临时休息不影响运行，停用自动转最近门店

> status_scope: home_feeding_temporary_rest_and_disabled_store_automatic_reassignment
> home_feeding_temporary_rest_effect: no_effect_on_feature_operations
> home_feeding_disabled_store_effect: automatic_reassignment_of_unfinished_requests
> home_feeding_reassignment_anchor: original_publisher_store_effective_location
> home_feeding_reassignment_candidates: other_active_platform_stores_with_usable_location
> home_feeding_reassignment_scope: original_unfinished_request_acceptance_and_coordination_todo
> home_feeding_reassignment_preserve: original_publisher_store_acceptor_round_progress_and_history
> home_feeding_current_responsible_store: current_coordination_store_id
> home_feeding_reassignment_access: current_assignee_necessary_request_scope_only
> home_feeding_reassignment_no_candidate: preserve_request_and_pending_platform_exception
> home_feeding_reassignment_notification: notify_participants_and_new_store_after_success

- 门店临时休息不影响上门喂养正常运行，包含新发布、接单及后续对接；临时关闭预约不是账号停用，不触发自动转店。
- 当前负责门店账号停用后，服务端自动将其未完成需求、原接单关系和对接待办交给最近的其他正常使用平台门店。距离起点为原始publisher_store_id门店的有效地址位置，不取上门地点、顾客定位或上一任接续店；候选排除停用／失效店与不可定位店，临时休息不等于停用。最近距离计算的地理接口／结构化坐标契约后续技术设计收口，不使用假坐标冒充已验证最近店；等距按稳定store_id顺序确定。
- 发布门店publisher_store_id永久保留，当前对接资格唯一依据current_coordination_store_id。初始负责店等于发布店；自动转店只更新负责店及coordination_assignment_version，原需求ID、发布者、宠物、接单者、接单轮次、服务内容／进度及历史保持，不复制订单，不重新抢单、不回退服务、不标完成。后续接续店再次停用，仍以原发布店位置选择当前有效候选。
- 待接单需求也属于未完成范围，转店后按原有效性开放；已接单／服务中的需求保留原接单人和当前进度。已完成／已取消历史不转店复活；新发布入口遇停用店时转最近有效店，在发布确认页展示实际发布店，按03g完成原必要身份／选店流程，不继续向停用店发布。
- 新负责店获得处理本需求所需的原需求／有效接单关系、必要资料及真实对接进度历史，业务记录继续留在原需求，不迁移其他顾客档案、钱包、券、宠物私有服务相册或原门店全部数据。原店内部沟通备注／照片按原所属门店保留，不自动扩给新店；原状态／经办工作事实可在本需求授权视图追溯，不向普通员工返回原始审计日志。精确地址／联系资料仍按必要且已获授权范围取用，不因候选搜索批量开放给周边门店。
- 自动转店不改变用户全局当前门店或商户资产归属；该需求页面展示当前对接门店及“原门店停用，已转由××门店对接”，成功后通知发布者、原有效接单者（如有）及新店。新店从原进度继续办理，不新增老板审批；原店失去当前处理及新取数资格，旧页面／缓存／旧版本请求不能再操作，新店也不能越权读无关旧店资料。
- 负责店切换、权限生效及原待办路由更新须同一版本一致完成；提交切换时再次校验候选店仍正常有效，否则重新选择。系统记录原新店、触发原因、发生时间及coordination_assignment_version并幂等。并发转店／取消／接单／服务更新重新校验最新负责版本与状态；只路由一份有效待办，不重复需求、接单、通知或资金事件。
- 找不到可用门店、原店位置无法计算或迁移结果尚未成功时，保留原需求／接单／历史，显示“门店接续处理中”并形成平台异常处理事项，不伪造最近店、泄露给任意店、恢复停用员工操作或自动取消／完成／退款；重试按原迁移事件办理。具体异常人工界面、坐标技术契约仍待后续阶段，不以Mock标联调完成。

## 10. 订单 / 数据边界

客户端可以使用“上门喂养订单 / 需求”的产品文案，但底层建议独立建模为平台级 `home_feeding_job` / `home_feeding_request`，不得直接复用商户普通商品订单或洗护 / 寄养服务订单表。

原因：

- 需求为平台公开数据。
- V1.0 不发生平台线上支付。
- 成交后由绑定门店负责协调，不应污染门店现有商品销售、洗护或寄养营业额。

后续如需要门店线下收款，可在阶段 06 明确与正式订单 / 结算域的关联方式。

## 11. 故障隔离

上门喂养属于独立业务域。该模块故障不得导致：

- 洗护 / 美容不可用
- 寄养不可用
- 商品销售不可用
- 钱包不可用
- 普通预约不可用

## 12. V1.0 关键验收场景

### C-FEED-01：发布

用户填写时间、地点、每日预算、喂养要求并发布成功。

### C-FEED-02：公开浏览

其他平台用户可看到需求，但看不到精确地址、手机号、微信和商户内部资料。

### C-FEED-03：接单

第一个用户接单成功后需求锁定，其他用户不能重复接单。

### C-FEED-04：门店对接

接单成功后，仅当前负责门店收到待办（初始为发布店，停用后按§9.2接续）；按§9查待对接／进行中／历史，待对接以本轮accepted_at升序，查询组不新增状态。老板／有效员工均可依原需求手动四步处理，无老板审批或原经办限制；备注照片可空、不强制打卡／定位／签字／顾客验收，真实结束后才手动完成，记录人／时间且不自动记收入。

覆盖越店／停用员工、旧状态／旧轮次、重复提交、无备注照片、授权地址不公开、状态通知不泄露内部备注及日期到点不自动完成；取消／退出／重新开放与无固定响应时限按§9.1，临时休息／自动转店按§9.2；其余协调修改／更正、截止及公开失效仍按§8.3待决，不因文档审计标成功能通过。

### C-FEED-05：分享

发布者可分享到微信群，点击后直接进入该需求详情。

### C-FEED-06：本地无需求跨城补充

当前城市无有效公开需求时，首页可随机展示其他城市真实、可公开的需求；城市信息必须如实显示，不得伪造本地需求。若全平台均为空，则显示正常空状态。

### 状态边界验收补充

- 重复点击 / 断网重试同一接单请求只产生一次有效接单，结果未知时可恢复查询。
- 接单与已获权限的取消同时发生，只接受符合最新状态的结果；旧轮次请求不影响重新开放后的新接单。
- 服务日期范围已结束、已取消、已完成时不可新接单；原负责门店停用后只经§9.2成功接续的有效需求可继续接单；旧分享页显示真实状态及返回路径。
- 切换当前门店不改变需求永久绑定门店，平台个人进度与消息仍可查询；未取得当前负责资格的其他门店不能获得内部对接资料，停用后的限定接续按§9.2。
- 本轮取消／退出／重新开放、不设响应时限及自动转店按§9.1／9.2验收；剩余协调修改／更正、接单截止／公开失效不得预置为已确认或已通过。
