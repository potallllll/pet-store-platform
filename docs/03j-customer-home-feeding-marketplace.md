# 03J 客户端「上门喂养需求市场」模块

> 状态：已确认子模块
> 所属阶段：03 客户端微信小程序
> 版本：V1.0

## 1. 产品定位

V1.0 新增平台级「上门喂养」需求市场。

该功能不是某一家门店内部私有列表，而是平台级公开需求：

- 平台用户均可浏览公开需求。
- 用户可发布上门喂养需求。
- 其他已完成必要身份验证的用户可接单。
- 需求发布时永久绑定发布者当前所在的 Merchant / Store。
- 有人接单后，只向该绑定门店的店员端生成对接待办，由该门店负责协调发布者与接单者。
- 不因此向其他门店开放发布者的客户资料、联系方式、订单、余额等私有数据。

V1.0 不建设平台在线支付、资金托管、抽佣、自动分账或保证金体系。

## 2. 客户端入口

首页新增「上门喂养」区域。

当前首页正式顺序为：

> 当前门店 → 当前服务 → 宠物交友 → 上门喂养 → 推荐商品

因此上门喂养固定位于“宠物交友”之后、“推荐商品”之前。

首页可展示近期公开需求摘要，并提供：

- 查看更多
- 发布需求
- 我的发布
- 我的接单

底部导航仍保持：预约 / 首页 / 我的，不新增独立底部 Tab。

## 3. 发布需求

发布页至少支持：

- 宠物：选择已有宠物；可支持多只宠物
- 宠物类型 / 数量
- 宠物照片：选填
- 开始日期
- 结束日期
- 每日喂养时间或时间段
- 每日上门次数
- 地点
- 每日预算
- 喂养要求
- 特殊注意事项：选填

提交前应明确该需求会公开展示给平台用户，并由当前门店在有人接单后负责对接。

## 4. 地址与隐私

公开列表 / 详情不得直接展示精确住宅地址、门牌号、手机号、微信、真实姓名等敏感信息。

公开位置只展示到足以判断接单距离的模糊层级，例如：

- 城市 / 区县
- 小区名称或附近区域

精确地址和必要联系方式只允许在接单后，由绑定门店在合法、必要、获得相应授权的对接流程中使用。

## 5. 公开需求卡片

至少展示：

- 宠物类型 / 数量或宠物摘要
- 上门喂养日期范围
- 每日喂养时间
- 模糊地点
- 每日预算
- 喂养要求摘要
- 当前状态

不得在公开卡片上泄露发布者商户私有客户信息。

### 5.1 本地无需求时的跨城市补充展示

若当前城市 / 当前区域没有可展示的有效公开上门喂养需求，客户端不得伪造或凭空生成假的用户需求。

应从平台其他城市中仍处于允许公开展示状态的**真实上门喂养需求**里随机抽取若干条作为补充内容，并明确展示其真实城市 / 区县等模糊位置。

规则：

- 只允许使用平台真实存在且当前可公开浏览的需求。
- 不修改原需求绑定的 `publisher_store_id`、城市、预算、时间、状态等事实。
- 不把其他城市需求伪装成本地需求。
- 随机展示只影响推荐 / 排序，不创建新业务记录。
- 若全平台也没有可公开需求，则显示正常空状态与“发布需求”入口。

## 6. 分享到微信群

发布成功后支持分享该需求到微信聊天 / 群。

分享卡至少表达：

- 上门喂养需求
- 宠物类型
- 日期范围
- 模糊地点
- 每日预算

点击分享卡应深链进入对应需求详情，而不是只进入普通首页。

## 7. 接单规则

- 已登录并完成必要身份验证的用户可点击「我要接单」。
- 发布者不能接自己的需求。
- 同一需求同一时刻只允许一个有效接单者。
- 第一个接单成功的用户由服务端原子锁定当前需求。
- 其他用户随后看到“已有人接单 / 等待门店对接”，不得重复形成有效接单。
- 并发接单必须由服务端原子校验，前端状态不可作为最终依据。

## 8. 状态流转

底层业务至少支持：

待接单
→ 已接单待门店对接
→ 门店对接中
→ 已确认
→ 服务中
→ 已完成

并支持：

- 已取消
- 接单取消后重新回到待接单（由门店按规则处理）

客户端正常主流程统一聚合展示为：

1. `待接单`
2. `已接单待门店对接`
3. `进行中`
4. `已完成`

其中门店对接中 / 已确认 / 服务中等底层进行态在客户端统一显示为“进行中”。已取消属于历史 / 终止状态，查看对应记录时仍如实显示“已取消”。

具体可修改 / 取消截止时间在阶段 06 核心业务规则中进一步确定。

## 9. 门店对接

有人接单后：

- 系统向 `publisher_store_id` 对应门店生成待处理事项。
- 店员可以查看发布需求、发布者、接单者及必要的对接信息。
- 其他 Merchant / Store 不得获得该内部对接任务。
- 门店完成协调后更新状态。

该机制不改变平台多商户数据隔离原则。

## 10. 订单 / 数据边界

客户端可以使用“上门喂养订单 / 需求”的产品文案，但底层建议独立建模为平台级 `home_feeding_job` / `home_feeding_request`，不得直接复用商户普通商品订单或洗护 / 寄养服务订单表。

原因：

- 需求为平台公开数据。
- V1.0 不发生平台线上支付。
- 成交后由绑定门店负责协调，不应污染门店现有商品销售、洗护或寄养营业额。

后续如需要门店线下收款，可在阶段 06 明确与正式订单 / 结算域的关联方式。

## 11. 故障隔离

上门喂养属于独立业务域。该模块故障不得导致：

- 洗护 / 美容不可用
- 寄养不可用
- 商品销售不可用
- 钱包不可用
- 普通预约不可用

## 12. V1.0 关键验收场景

### C-FEED-01：发布

用户填写时间、地点、每日预算、喂养要求并发布成功。

### C-FEED-02：公开浏览

其他平台用户可看到需求，但看不到精确地址、手机号、微信和商户内部资料。

### C-FEED-03：接单

第一个用户接单成功后需求锁定，其他用户不能重复接单。

### C-FEED-04：门店对接

接单成功后，仅发布时绑定的门店收到待办。

### C-FEED-05：分享

发布者可分享到微信群，点击后直接进入该需求详情。

### C-FEED-06：本地无需求跨城补充

当前城市无有效公开需求时，首页可随机展示其他城市真实、可公开的需求；城市信息必须如实显示，不得伪造本地需求。若全平台均为空，则显示正常空状态。

## 13. 需求变更记录

### 2026-09-06：新增平台级上门喂养需求市场

【需求变更】

- 原规则：客户端没有平台级公开服务需求市场。
- 新规则：新增所有平台用户可见的上门喂养需求；发布时绑定当前门店，有人接单后由绑定门店负责对接；公开数据严格限制住宅地址和联系方式暴露。
- 影响范围：首页、客户端页面地图、店员端待办、平台数据模型、多租户隔离、分享、消息、后续统计与架构。

### 2026-09-06：首页位置调整

【需求变更】

- 原规则：上门喂养曾确定放在首页“当前服务”之后、“宠物交友”之前。
- 新规则：首页最终调整为“当前服务 → 宠物交友 → 上门喂养 → 推荐商品”，因此上门喂养改为宠物交友之后。
- 影响范围：首页、客户端总纲、`03i` / `03n` 产品蓝图、H5 / UI 原型和验收。

### 2026-09-06：客户端状态简化与跨城市真实需求补充

【需求变更】

- 客户端正常流程状态统一为：待接单 → 已接单待门店对接 → 进行中 → 已完成；底层细状态继续保留用于店员流程与审计。
- 当前城市无可展示需求时，允许随机补充其他城市真实公开需求；禁止生成虚假需求或伪造本地位置。
- 影响范围：首页推荐、上门喂养列表、状态映射、H5 / UI 原型、后端推荐查询与测试验收。
