# 03 客户端微信小程序

> 状态：已确认
> 版本：V1.0

## 1. 客户端定位

客户端核心定位：

> 服务过程透明 + 客户资料与资产查询 + 业务意向提交。

客户端用于：

- 查看洗护 / 美容 / 寄养服务状态
- 查看洗护 / 美容前后对比与 AI 分析报告
- 查看寄养动态
- 在线预约洗护 / 美容 / 寄养
- 查看和维护宠物基础档案
- 在“我的”页面直接查看当前可用余额
- 通过“我的钱包”查看余额明细、优惠券并使用邀请码兑换优惠券
- 查看服务订单、商品订单与消费记录
- 浏览商品、使用购物车并提交购买需求
- 浏览当前门店已授权参与交友的宠物并发起好友邀请
- 接收站内消息和重要微信业务通知

客户端不承担真实线上支付，不提供会员充值入口，不设计积分机制。

## 2. 门店进入、多商户与身份

采用“一套平台小程序 + 商户专属二维码”模式。

- 每个商户拥有专属客户二维码。
- 扫码后进入对应 Merchant / Store 上下文。
- 公开首页和商品浏览可先不建立 Customer 关系。
- 首次使用预约、宠物、钱包、订单、消息、提交购买需求、宠物交友邀请等个人业务时，再完成必要的微信身份与手机号验证。
- 平台 User 与商户 Customer 分离。
- 已验证手机号用于当前商户历史 Customer 匹配，不作为平台唯一主身份。
- 同一 User 可成为多个 Merchant 的 Customer，但各商户余额、优惠券、订单、服务记录、商品业务、宠物交友和消息严格隔离。
- 直接打开小程序时优先进入最近一次使用的商户。
- 切换商户时所有业务上下文整体切换，禁止跨商户串数据。

完整规则见 `03g-customer-identity-security.md`。

## 3. 底部导航

V1.0 底部只保留三个一级导航，顺序固定为：

1. 预约
2. 首页
3. 我的

正常直接打开时默认进入“首页”。

不新增“服务”“商城”“宠物”“门店信息”等底部一级导航。

## 4. 预约

预约独立于正式订单，管理未来服务意向。

V1.0 支持：

- 洗护预约
- 美容预约
- 寄养预约

客户提交后进入“待门店确认”，门店可一键确认、调整时间或拒绝。

预约与服务订单状态分离；客户到店并由门店开始正式服务后，才生成 / 进入正式服务订单流程。

线下临时到店客户允许店员直接快速开单，不强制先建预约。

完整规则见 `03a-customer-appointment.md`。

## 5. 首页

首页承载四类核心信息：

- 当前门店
- 当前服务
- 宠物交友
- 推荐商品

### 5.1 当前门店

首页顶部仅突出显示当前商户 / 门店名称，并在客户关联多家商户时提供切换入口。

为减少顶部空间占用，不额外显示“当前门店”“已绑定客户”等辅助说明文字。

### 5.2 当前服务

当前服务为首页最高优先级内容。

同一客户最多直接展示 3 条进行中服务，更多通过“查看全部当前服务”进入完整列表。

洗护 / 美容客户侧仅展示简化状态：

- 等待中
- 洗护中 / 美容中
- 洗护完毕 / 美容完毕

不暴露店员内部细分步骤。

无当前服务时使用轻量预约引导，不显示空白业务卡片。

服务首次完成时显示完成提示，并提供“查看本次服务对比图”。完成卡保留到客户查看本次服务结果后，再退出当前服务区域进入历史记录。

### 5.3 寄养当前服务

寄养首页卡片展示：

- 当前寄养状态
- 日期范围
- 当前第几天
- 今日动态数量
- 最近动态
- 新图片 / 视频提示

### 5.4 宠物交友

首页原临时原型中的“快捷入口”区域改为“宠物交友”。

规则：

- 横向滚动 / 轮播展示。
- 每屏同时展示 3 只宠物。
- 一轮最多展示 12 只不同宠物，不重复。
- 当前客户自己的主展示宠物固定出现在本轮第 4 个位置，即第二屏第 1 个位置。
- 自己的第 4 位宠物卡片可以仅对本人展示，不代表已自动向其他客户公开。
- 只有主人主动开启宠物交友后，该宠物才进入其他客户可见的公开展示池，并可作为好友邀请发起方。
- 若本人宠物尚未开启交友，第 4 位明确标识“未开启交友 / 仅自己可见”；客户发送邀请前需先开启交友。
- 若客户没有宠物，不伪造自己的宠物，第 4 位可显示添加宠物 / 开启交友引导。
- 其余位置只从当前门店符合公开展示条件的宠物中选择。
- 若当前门店符合展示条件的宠物不足 12 只，则展示全部，不重复凑数。
- 提供“更多”入口，进入当前门店完整宠物交友列表。
- 完整列表仅展示主人已明确授权参与宠物交友的当前门店宠物，不默认公开未经授权的全部客户宠物。
- 点击宠物进入交友详情，展示宠物社交昵称和允许公开的洗护 / 美容服务后照片。
- 客户可发送好友邀请；不直接公开双方主人联系方式。
- 同一对宠物只允许一条邀请记录，再次发送提示“已发送过邀请”。
- 对方可选择“同意”或“不同意”。
- 对方同意后，系统通知双方“对方已同意，已告知店员，请等待店员回复”，同时向店员端生成待处理任务。
- 对方不同意或不回复时，不向邀请方发送拒绝 / 未回复结果消息。

完整规则见 `03h-customer-pet-social.md`。

### 5.5 推荐商品

首页展示当前门店 3～6 个推荐商品，并提供“查看更多”进入完整商品列表。

## 6. 洗护 / 美容结果与 AI 报告

服务完成后先形成普通服务结果页，**此时不得自动调用 AI，也不得因为“服务完成”就把宠物照片提交给 AI Provider。**

普通服务结果页无需观看广告即可查看：

- 本次洗护 / 美容状态
- 本次服务基本信息
- 完成时间
- 结算信息
- 店员上传的洗护 / 美容前后照片
- 前后照片拖动对比
- “查看报告”入口

### 6.1 N 组前后照片对比

店员端按“对比组”上传本次服务前后照片；客户端根据后端返回的完整对比组数量动态生成页面。

规则：

- 店员上传 N 组完整的“服务前 + 服务后”照片，客户端就生成 N 组对应的拖动对比。
- 不写死固定 1 组、4 组或其他固定数量。
- 每组前图和后图必须属于同一对比组；客户端不得自行跨组拼接。
- 每组可有可选标题 / 角度，例如正面、背面、左侧、右侧、头部、四肢。
- 只有前后图均齐备的组才能生成拖动前后对比。
- 某组缺前图或缺后图时不得伪造另一张图片，也不得假装形成完整对比；可按后续 UI 规则显示为不完整素材。
- 各组共用同一笔服务数据，不额外建立独立服务订单。

底层按有序“对比组”建模，至少需要表达 `before_asset`、`after_asset`、`sort_order` 以及可选标题 / 角度；具体数据库表结构和字段在阶段 09 确定。

### 6.2 AI 报告按需生成

AI 报告不是服务完成时预生成，而是客户真正请求查看后才生成。

标准广告路径：

服务完成
→ 客户查看普通服务结果 / N 组前后对比
→ 点击“查看报告”
→ 展示 AI 报告广告说明
→ 播放激励视频广告
→ 客户完整观看成功
→ 服务端确认本次报告查看资格
→ 此时才创建 / 启动 AI 分析任务，并把本次可用于分析的前后照片提交给 AI Provider
→ 客户端显示真实生成进度
→ AI 分析完成并经过结果复核
→ 当前页面直接展示报告

客户端广告弹窗文案统一为：

- 弹窗标题：`查看 AI 洗护报告`
- 说明文案：`本功能采用国际领先AI助手分析，相关费用已由赞助商赞助，观看完整广告后即可免费查看本次 AI 洗护报告。`

AI 报告卡片可使用简洁说明：

> 结合本次洗护前、洗护后照片，生成专业护理观察报告。

并保留：

> 报告生成期间可停留在本页等待。本报告不作为医疗诊断。

客户端不展示“服务完成后不会提前调用 AI”“完整观看后才开始 AI 分析”等后台技术解释；这些属于内部业务规则，不作为面向顾客的页面文案。

如果以后存在有效的免广告查看资格，该资格只替代“观看广告”这一授权步骤；**无论通过广告还是免广告资格，均应在客户真正请求查看并获得查看资格后才启动 AI 分析**，不得提前预生成。

缺少足够分析素材时不得启动伪分析，也不得伪造对比结论。

### 6.3 AI 生成状态与等待体验

报告至少区分：

- `not_requested`：客户尚未请求 AI 报告，未调用 AI
- `authorization_pending`：等待完成广告或其他有效查看资格
- `queued`：已获得查看资格，AI 任务已创建 / 排队
- `image_quality_checking`：宠物影像质量检测中
- `before_after_comparing`：洗护前后特征比对中
- `care_state_analyzing`：毛发与清洁状态分析中
- `knowledge_retrieving`：专业护理知识检索中
- `report_reviewing`：结果复核与报告生成中
- `completed`：报告已完成
- `failed`：生成失败，可按规则重试

客户完成广告后，如果 AI 结果尚未返回，客户端留在当前服务结果页，根据后端实际处理阶段展示以下专业化文案：

1. 宠物影像质量检测中
2. 洗护前后特征比对中
3. 毛发与清洁状态分析中
4. 专业护理知识检索中
5. 结果复核与报告生成中
6. 完成后直接展示 AI 报告

进度必须对应服务端真实任务流程；客户端动画不得自行宣称后台已经完成某阶段。

等待体验规则：

- 正常体验目标为约 30～60 秒。
- AI 真实结果如果提前完成，立即展示，不为了填满动画而故意延迟。
- 客户可在生成期间停留在本页等待。
- 若约 60 秒后后台任务仍未完成，不让客户继续原地无限等待，页面改为：

> 报告仍在生成中
>
> 分析已提交，可稍后返回本页面查看结果。

- 超过约 60 秒不代表取消后台任务，任务继续执行。
- 客户之后重新进入同一服务结果页时，从服务端读取真实任务状态。

客户在生成过程中离开页面后重新进入：

- 未完成 → 显示仍在生成 / 当前真实状态
- 已完成 → 直接显示已获得查看资格的报告
- 失败 → 显示失败状态与重试入口

若客户已完整观看广告并获得查看资格，但后续 AI 提交、网络或 Provider 调用失败，重试本次同一报告时**不得要求客户再次观看广告**。

AI 任务创建、重试和最终写入必须幂等，避免网络抖动导致同一报告重复调用多次 AI、重复计费或生成多份互相冲突的结果。

AI 失败不得影响订单完成、普通服务结果或前后照片查看。

### 6.4 AI 报告内容定位

AI 报告定位为宠物护理 / 外观观察，不作为兽医医疗诊断。

报告结构至少覆盖：

- 整体变化
- 毛发整洁 / 蓬松变化
- 打结 / 毛发状态观察
- 可见皮肤区域观察
- 清洁变化
- 后续护理关注事项
- 总结
- AI 免责声明

## 7. AI Provider 与安全

AI 模型不得写死单一供应商。

平台超级管理员可在 Web 后台配置：

- API Key / Credential
- Base URL
- Model ID
- 启用状态
- 默认 Provider / Model
- 超时
- 重试

系统使用统一 AI Adapter / Provider 层。

敏感凭证只能位于服务端，前端不得获得明文；日志不得输出完整凭证；敏感值采用加密保存或独立 Secret 管理。

AI 调用必须由服务端发起。客户端不得直接获得第三方 AI Credential，也不得自行把照片直接提交给第三方模型。

## 8. AI 报告激励广告解锁

客户主动点击“查看报告”后，根据当前查看资格决定是否触发激励视频广告。

规则：

- 服务完成本身不生成 AI 报告。
- 需要广告授权时，广告完整观看成功前，不启动本次 AI 分析，不把本次照片提交给 AI Provider。
- 中途关闭广告，不解锁、不启动 AI。
- 完整观看成功后，服务端先幂等记录本次查看资格，再启动 / 排队 AI 分析任务。
- 同一用户对同一份已成功获得查看资格的报告，后续查看或 AI 失败重试无需重复观看广告。
- 广告观看成功、查看资格、AI 任务状态必须分开记录，不能把“广告完成”直接等同于“AI 报告已经生成”。

内部可先创建不触发外部 AI 调用的轻量报告 / 访问记录，以便获得稳定 `report_id`；真正的照片提交和 AI Provider 调用必须等到查看资格确认后才发生。

至少记录：

- report_id / service_id
- user_id
- authorization_status
- authorized_at
- authorization_source
- ai_status
- ai_requested_at
- ai_completed_at

具体数据库字段在阶段 09 确定。

### 8.1 广告加载失败降级

若广告出现加载失败、无填充、网络错误等非“完整观看成功”结果：

- 不视为已获得本次广告查看资格。
- 不启动 AI 分析。
- 不向 AI Provider 提交本次宠物照片。
- 客户端明确提示“广告暂时无法加载，请稍后重试”。
- 允许客户之后重新尝试。
- 洗护 / 美容前后对比、普通服务结果、订单状态均保持正常可查看，不受广告失败影响。

### 8.2 广告成功后 AI 失败

若广告已经完整观看并成功记录查看资格，但随后出现：

- AI Provider 超时
- 网络异常
- 任务队列异常
- 结果生成失败
- 结果复核失败

则：

- 已获得的查看资格不得回滚。
- 不要求客户重新观看广告。
- 客户端显示失败 / 重试状态。
- 重试同一报告不得重复创建计费任务；服务端保证幂等。
- 普通服务结果和订单不受影响。

## 9. 寄养动态

寄养动态按真实发生时间形成时间轴，不使用固定模板时间。

每条动态至少包含：

- 实际发生时间
- 动态类型
- 可选文本
- 可选图片 / 视频
- 操作员工
- 系统创建时间

“实际发生时间”和“系统录入时间”分开保存，以支持补录与审计。

动态类型可包括：

- 喂食
- 喝水
- 遛狗 / 遛宠
- 排便
- 排尿
- 玩耍
- 休息
- 用药 / 特殊照护
- 清洁
- 图片 / 视频
- 异常情况
- 自定义事件

## 10. 我的宠物

入口：我的 → 我的宠物。

核心规则：

- 第一次建档尽量少填。
- 客户和店员都可以在各自权限范围内维护宠物基础资料。
- 客户资料与门店内部备注分离。
- 体重保留历史记录，不只覆盖当前值。
- 洗护 / 美容前后照片自动沉淀为宠物服务相册，不增加额外上传动作。
- 宠物档案中的长期护理 / 寄养信息可在后续预约和服务中自动带出。
- 宠物有历史业务记录时不物理删除，以归档 / 移除方式处理。
- 店员侧客户搜索支持按宠物名查找。
- 宠物基础资料跨商户复用必须由客户主动授权，商户内部业务数据不得跨店共享。
- 每只宠物可独立控制是否参与当前门店宠物交友，并配置社交昵称与允许公开的服务后照片。

完整规则见 `03b-customer-pet-profile.md`。

## 11. 我的页面与我的钱包

“我的”页面直接展示当前商户的当前可用余额，客户无需先进入二级页面即可查看余额。

入口：我的 → 我的钱包。

“我的钱包”主要承载：

- 余额明细
- 我的优惠券
- 邀请码兑换

“我的钱包”不重复展示当前可用余额大卡片，以减少信息重复和页面占用空间。

V1.0 明确不设计积分机制。

客户端不提供充值入口。充值由门店侧选择客户和老板预先配置的充值套餐，客户线下付款后由有权限店员确认收款。

后台区分充值本金余额与赠送余额，客户端对客户展示总可用余额。

优惠券 V1.0 类型：

- 满减券
- 无门槛 / 指定范围金额券
- 折扣券（可配置最高优惠金额）

优惠券来源只包括：

- 充值套餐自动赠送
- 老板 / 有权限员工手动赠送
- 客户邀请码兑换

不做系统活动自动赠券，不做复杂领券中心。

每个订单最多使用一张优惠券；收银时系统自动匹配并默认推荐对客户最优惠的一张。

完整规则见 `03c-customer-wallet.md`。

## 12. 我的订单

入口：我的 → 我的订单。

只保留三个分类：

- 全部
- 服务
- 商品

其中服务包含洗护、美容、寄养。

预约不进入普通订单列表；充值记录归入钱包中的余额明细。

订单直接复用正式业务数据，不单独维护一套客户端订单。

洗护 / 美容订单可直接进入同一笔服务的服务结果与 AI 报告页面。

寄养正式结算前显示当前 / 预计金额，结算后显示最终实付。

订单退款、取消、冲正不得通过删除或无痕覆盖原订单实现。

完整规则见 `03d-customer-orders.md`。

## 13. 商品浏览与购买需求

商品模块定位为轻商城，不做完整电商。

V1.0 支持：

- 商品搜索
- 商户自定义分类
- 商品 / SKU
- 商品详情
- 数量选择
- 购物车
- 提交购买需求

不支持：

- 在线支付
- 快递
- 收货地址
- 运费
- 物流状态

客户侧库存只显示：

- 有货
- 库存紧张
- 暂时无货

不默认显示精确库存。

商品需求流程：

提交购买需求
→ 门店确认中
→ 门店一键确认 / 必要时改单
→ 系统自动预占库存
→ 自动匹配优惠券
→ 待线下付款
→ 店员确认实际收款
→ 正式扣库存并计入营业额

门店确认后默认保留 24 小时；超时未收款自动取消并释放预占库存、恢复尚未核销优惠券。商户后续可按已确认规则调整保留时间。

完整规则见 `03e-customer-products.md`。

## 14. 消息中心与微信通知

入口：我的 → 消息。

消息中心使用单一时间流，不做复杂多 Tab。

业务状态变化自动产生站内消息，重要事件再尝试微信通知。微信通知失败不得影响正式业务。

V1.0 不做：

- 即时聊天
- 在线客服
- 客户 / 店员私聊
- 宠物好友双方主人直接聊天
- 营销群发

重要消息包括预约关键变化、服务完成、寄养异常、商品确认 / 取消、收到宠物好友邀请等。

普通寄养动态不逐条微信推送；短时间连续动态由系统尽量合并。寄养异常默认通知客户，店员可在仅内部记录时主动取消。

洗护 / 美容服务完成消息只表示普通服务结果已可查看，不代表 AI 报告已生成。AI 报告必须由客户主动请求查看后才开始生成。

宠物好友邀请由现有消息中心承载：被邀请方可同意 / 不同意；同意后双方收到“已告知店员，请等待店员回复”，同时生成店员端待办；不同意或不回复不向邀请方发送结果消息。

消息点击直接进入关联业务详情。

完整规则见 `03f-customer-messages.md`。

## 15. 登录、历史客户识别与账号安全

V1.0 不设计用户名 / 密码体系。

微信身份作为平台 User 主身份，手机号作为已验证联系方式和当前商户历史客户识别依据。

历史匹配规则：

- 当前商户仅一个明确安全匹配 → 自动绑定历史 Customer。
- 无匹配 → 创建新 Customer。
- 同手机号多个候选 → 不自动合并，由门店处理。
- Customer 已绑定其他 User → 不自动抢绑，进入安全恢复 / 换绑流程。

支持店员通过短时、一次性绑定二维码作为复杂历史数据的辅助绑定兜底。

更换手机号不重新创建 Customer 或新的会员资产关系；账号换绑、历史合并、人工绑定、注销等关键身份动作必须留审计。

V1.0 不实现家庭共享账号。

完整规则见 `03g-customer-identity-security.md`。

## 18. 需求变更记录

### 2026-08-31：钱包与首页顶部

【需求变更】

- 原规则：入口为“我的 → 我的会员”，当前可用余额主要在该二级页面展示；首页门店名称下可显示“当前门店 / 已绑定客户”等辅助文字。
- 新规则：入口改为“我的 → 我的钱包”；当前可用余额直接显示在“我的”页面；“我的钱包”不重复展示余额大卡；首页顶部只突出门店名称和必要的门店切换入口，不显示“当前门店 / 已绑定客户”等辅助文字。
- 影响范围：客户端 UI / 信息架构；不影响数据库、API、余额财务规则、多商户隔离、充值和优惠券业务规则。

### 2026-08-31：新增宠物交友

【需求变更】

- 原规则：首页不包含正式宠物交友模块，临时 H5 原型中的该位置为“快捷入口”。
- 新规则：首页该区域改为“宠物交友”，一轮最多展示 12 只不同宠物、每屏 3 只，自己的主展示宠物固定为第 4 只；支持查看更多、查看宠物服务后照片和昵称、发送好友邀请、对方同意 / 不同意、邀请去重、同意后通知双方并自动提示店员处理。
- 隐私规则：完整列表仅展示主人主动授权参与交友的当前门店宠物；不公开主人联系方式；客户之间不直接聊天。
- 影响范围：客户端首页、宠物档案、消息中心、店员端待办、数据库、API、隐私与审计。

### 2026-08-31：宠物交友授权边界补充

【需求变更】

- 原规则：自己的主展示宠物固定第 4 位，同时公开展示池要求主人授权，未明确未开启交友时如何同时满足两条规则。
- 新规则：第 4 位自己的宠物卡可以仅对本人显示；只有主人主动开启交友后才进入其他客户可见的公开展示池并可发起邀请；没有宠物时显示添加 / 开启引导，不伪造宠物。
- 影响范围：客户端首页、宠物交友、宠物档案、身份体系、消息和隐私。

### 2026-09-01：洗护 / 美容对比改为 N 组动态生成

【需求变更】

- 原规则：服务结果页按单组前图 / 后图描述。
- 新规则：店员上传 N 组完整前后照片，客户端自动生成 N 组独立拖动对比；不固定组数，缺图组不得伪造完整对比。
- 影响范围：客户端服务结果页、店员端报告上传、服务相册、数据库、API、AI 输入。

### 2026-09-01：AI 报告改为广告完成后按需生成

【需求变更】

- 原规则：服务完成且前后照片齐备后即可在后台预生成 AI 报告，客户观看广告主要用于解锁查看。
- 新规则：服务完成不调用 AI；客户点击“查看报告”并完整观看广告 / 获得有效查看资格后，才提交本次照片并启动 AI；等待期间显示真实任务阶段，完成后直接展示。
- 失败处理：广告已成功获得的查看资格不因 AI 失败而失效，同一报告重试不得再次强制观看广告。
- 影响范围：客户端服务结果页、广告、AI 调用时机、消息、后端任务、数据库、API、AI 成本、隐私与幂等。

### 2026-09-01：AI 报告客户端文案与等待体验最终确认

【需求变更】

- 原规则：按钮使用“观看视频后查看报告”，广告说明和生成等待文案仍偏技术化；生成进度为 3 段，前台最长等待未明确。
- 新规则：入口统一为“查看报告”；广告弹窗标题为“查看 AI 洗护报告”，赞助说明为“本功能采用国际领先AI助手分析，相关费用已由赞助商赞助，观看完整广告后即可免费查看本次 AI 洗护报告。”；生成进度升级为 5 段专业流程，正常体验目标 30～60 秒，真实结果提前返回立即展示，约 60 秒仍未完成则提示稍后返回查看。
- 影响范围：客户端服务结果页、广告文案、AI 状态模型、API、消息和异常体验。
