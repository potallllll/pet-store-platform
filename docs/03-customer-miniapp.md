## 1. 客户端定位

客户端核心定位：

> 服务过程透明 + 客户资料与资产查询 + 门店业务意向提交 + 平台级社区 / 权益 / 广告能力 + 条件式 AI 辅助能力。

V1.0 客户端已确认支持：

- 查看洗护 / 美容 / 寄养服务状态；
- 查看洗护 / 美容 N 组前后对比与按需 AI 洗护报告；
- 查看寄养动态时间轴、图片 / 视频，并在寄养中发起“投喂零食 / 寄养加餐”；
- 在线预约洗护 / 美容 / 寄养；
- 查看和维护宠物档案，包括记录宠物当前食用的宠物食品品牌；
- 浏览商品、购物车并提交购买需求；
- 查看会员资产摘要、钱包、优惠券、订单与消息；
- 宠物食品争议 / 风险反馈与附近门店投诉 / 差评反馈；
- 平台级公开上门喂养需求市场；
- 平台积分、广告签到、积分商城与总仓到店自提；
- 首页底部微信 Banner 广告曝光；
- 小程序启动封面广告；
- **仅对符合付费门店权益条件的客户开放养宠顾问**。

客户端不承担真实线上支付，不提供会员充值入口。

门店财务也不接入外部收银／支付／退款系统，只记录线下真实交易；老板／有效员工可即时或工作结束后录入，系统自动更新会员余额、资金流水及适用库存，客户端只显示已记账结果。预约和服务操作仍及时进行，不改为事后补录。消费退款无需老板审批，消费先扣本金再扣赠送，退款原渠道／原账户退回，具体边界按03d§1.1／12及03c§5。

详细规则以 `03a`～`03m`、`03o`～`03p` 为准；页面蓝图以 `03i` 为准。原 `03n` 已归档，不属于现行需求。

## 2. 门店、多商户与身份

- 一套平台小程序 + 商户专属二维码。
- V1 当前约束 `1 Merchant = 1 Store`。
- 平台 User 与商户 Customer 分离。
- 同一 User 可成为多个 Merchant 的 Customer，但商户余额、优惠券、订单、服务记录、内部备注等严格隔离。
- 已认证手机号对应全平台唯一当前登录账号，并识别有效店员端身份；有有效身份才默认进入店员界面，否则客户端，稳定主键仍platform_user_id。重复绑定提示手机号异常，可换绑或更换新号码认证，旧资料保留；店内Customer资金关系不与其他店合并。
- 切换门店时，所有门店业务上下文必须整体切换。
- 平台积分属于 Platform User；商户钱包属于 Merchant Customer，两者严格分离。
- 养宠顾问的**用户额度**属于 Platform User，但**使用资格**由当前门店 `pet_advisor` Feature Entitlement + 门店开关 + Customer 关系共同决定。
- 公开浏览不强制立即登录；进入个人业务时按需触发微信身份 / 手机号验证。
- 本人发现其他门店服务记录时可明确确认“一键导入本店”，只导入顾客／宠物档案和顾客可见服务护理历史；金额、钱包、充值、券资产及内部备注仍各店独立，详见03g§5.5，不能由店员代点授权或将历史导入当本店成交。

完整身份规则见 `03g-customer-identity-security.md`。

## 3. 启动流程与封面广告

小程序启动 / 符合频控的重新进入时，可在恢复正式业务目标前展示独立 `launch_cover_ad`。

支持：

- `custom_image`：平台自定义图片；
- `custom_video`：平台自定义视频；
- `wechat_ad`：微信官方广告。

Platform Super Admin 可单独配置：

- 开关；
- 广告来源模式；
- 图片 / 视频素材；
- 微信广告单元；
- 生效时间；
- 频控；
- 跳过策略；
- 测试 / 正式环境。

广告关闭、过期、无填充、素材加载失败或 SDK 失败时恢复原入口目标（无明确目标时进入首页），不得阻塞小程序正常使用。

预约 / 首页 / 我的及内部详情页之间跳转，不重复弹启动广告。

先保存分享 / 通知目标及关联门店；广告关闭、失败、超时后继续目标，无明确目标才进入首页。后台恢复保留原页面与安全草稿；无有效门店时按 03g 进入选店 / 扫码引导。详细规则见 `03p-customer-launch-cover-ad.md`。

底部一级导航固定：

1. 预约
2. 首页

> 当前门店 → 当前服务 → 消费争议 / 风险反馈 → 上门喂养 → 推荐商品

## 5. 当前服务与寄养动态

### 5.1 洗护 / 美容

客户侧状态简化为：

- 等待中
- 洗护中 / 美容中
- 洗护完毕 / 美容完毕

首页最多直接展示 3 条当前服务，更多进入完整列表。

服务首次完成时首页提示查看结果；用户真正查看过结果后，该完成卡退出首页当前服务区域，但历史记录继续保留。

### 5.2 寄养

寄养卡至少展示：

- 日期范围；
- 当前第几天；
- 今日动态数量；
- 最近动态；
- 新图片 / 视频提示；
- `查看寄养动态`。

寄养详情按**真实发生时间倒序**展示时间轴：最新在上，历史向下，并按今天 / 昨天 / 具体日期分组。

动态可包含喂食、饮水、排泄、遛宠、玩耍、休息、清洁、特殊照护（含代喂药）、图片 / 视频、寄养加餐、异常和自定义事件。

实际发生时间与系统录入时间分离；补录事件按真实发生时间插回正确位置。

按04§5.1，门店统一新增照护记录的表单为“单选喂食／遛狗／清扫笼子 → 选择实际发生时间 → 上传照片（选填）→ 确认”，逐宠记录，不批量完成或设置每日照片配额。时间轴仍能展示已有其他事件，不把三个录入动作当成删除饮水、排泄、媒体、异常等类型的理由。顾客只查看本人有权看到的动态，内部备注不计入数量／缩略图／时间轴；关闭主动通知不隐藏原本可见动态。需要时另记真实喂食，加餐商品销售不自动生成照护记录。

健康资料／特殊照护及异常沟通按04§5.4：疫苗资料和照片不强制上传，未提供／待核实不默认为已完成疫苗，资料缺失由门店核实后决定接收。代喂药统一放特殊照护，主人要求、门店接收及实际执行记录分开；顾客仅查看本人有权查看的记录，不因通知勾选公开内部备注。异常提前接走按实际离店计费，不自动免单或退款。

寄养只有实际到店并经门店确认入住后才显示在住；预计离店到点仅提醒，不自动展示完成、续住或加费。多宠独立记录，本次临时寄养资料不静默改长期档案；未知饮食／零食授权标待核实，当前加餐须读取本次有效资料而非长期旧允许值。计费按04§5.2北京时间03:00截点，每个满足实际入住<截点≤实际离店的截点收一天寄养费；0晚不收寄养费，实际离店结算，延期／提前离店据实重算。不把预计金额当实收或录入时间当离店；入住由本店员工逐宠设置本次日价，同店同客多宠可一起结算，逐宠日价×各自实际晚数后汇总，不合并照护记录／时间。日价更正与免费按04§5.2第14～18项：离店确认前可留痕更正整次日价，不分段计价；日价大于0，免费须最终应收调0并明确免单。已离店未收款保留原基础费用、只调最终应收，已收款／免单不直接改账。挂单查询／人工联系及误挂撤销按04§4.6，内部原因／联系备注不向顾客公开；撤销挂单仍待结算，不表示已付或免单。特殊交接与其余历史更正仍待04对应DEC。

寄养多宠分批接走时，各批分别按实际离店结算；已离店已结算宠物保留历史，尚在住宠物继续显示自己的动态与未结算事实，不因同客其他宠物结算而被标结束／已付。

寄养状态与付款分离：本批结算费用确认后即显示已离店；尚未收款可显示已离店／待结算，手动挂单的内部原因不公开。按每宠实际接走时间截止计费，未收款／挂单／晚录账不继续增加寄养天数。后续收款／免单只更新原账本与挂单标记，不把离店时间改成收款时间；已离店宠物不再作为当前在住／加餐入口，历史可见动态保留。

## 6. 寄养加餐

寄养详情保留“投喂零食”购买入口，须本宠有效在住、主人允许额外零食及本店存在可投喂SKU，本次授权／饮食限制按03b及03e§17读取。

选择商品／SKU／数量 → 提交普通商品需求 → 门店确认与预占 → 线下收款记账或明确免单 → 商品交易已完成。复用source_channel及business_scenario=boarding_feed、原boarding_id／pet_id，不建立第二套订单或独立投喂执行流程。

不设置待执行加餐／确认已投喂，不因销售自动写寄养动态。店员需要时从原寄养照护表单另记真实喂食，照片选填；照护不要求先收款，也不产生商品交易。新真实购买按普通商品规则，原请求幂等／库存规则保留，详见03e§17。

## 7. 消费争议、投诉与跨店风险信息

客户端投诉入口为“我的 → 投诉与建议”；首页“消费争议”用于公开信息浏览。门店正式回应在店员端，食品投诉由后台发现问题后客服邮件联系厂家；具体规则与待决边界以03h§2.4、03f§13为准。

原“宠物交友”功能已从 V1.0 当前客户端中移除，由“宠物食品争议 + 附近门店争议”替代。

首页进入后至少可查看：

- 附近宠物门店公开投诉 / 风险反馈；
- 宠物食品投诉 / 风险反馈及问题热度；
- 商家回应状态；
- 平台核验状态；
- 是否已经解决；
- 同一食品同一批次的“出现集中反馈”提示（满足规则时）。

用户可仅以文字提交门店或食品投诉，不强制上传证据。投诉通过基础内容审核后立即公开为“用户反馈”，但在平台裁决前不得展示为已成立事实。

商家正式回应期限为 7 天；逾期只显示“商家逾期未回应”，不自动等于投诉成立。商家首次正式回应后双方有 3 天补证。门店在店员端选择立场并填写文字直接提交，无回应草稿、媒体选填；原回应保留且不可覆盖／删除，老板或任一有效员工可在原3天窗口追加说明／材料，无审批或原经办限制。回应成功自动切换为补证并突出截止，追加不延长原截止、历史逾期保留，见03h§4与04§6.1.2。最终由单名持有平台裁决权限的审核员按事实点作出：成立 / 部分成立 / 证据不足 / 现有证据不支持。

第三方顾客可通过门店分享的邀请卡片进入原争议；只看当前公开及已脱敏内容，提交沿现有账号／必要手机号验证，不另传身份证。佐证文字与事件关系必填、媒体／订单选填，由平台审核、不经门店筛选审批；同一顾客同一争议一份佐证可在原3天窗口追加、原文保留，到期关闭提交但仍可读公开内容。详见03h§7.1。邀请撤回按03h§7.2只阻止该卡片新建佐证，其他有效邀请不受影响；既有佐证保留、实际作者仍可在原3天窗口追加，公开仍可读。邀请不授予非公开材料权限，不代表已正式回应／裁决。

是否成立与是否已解决均由平台有权人员最终确认，使用独立状态；本案门店和投诉人只能提交处理情况／材料／意见，不能直接结案。顾客反馈已处理好、门店回应／退款或事实裁决都不自动标记已解决，详见03h§6.1。

本案门店老板／有效员工和投诉人可在原争议详情“提交处理情况”：说明必填、图片视频选填，逐次追加、更正不覆盖原文；平台未确认解决时，3天补证后仍可记录实际处理进展，不重开补证或代替联系客服。未审材料仅实际提交者和平台有权人员可见，公众只见平台审核脱敏副本；该操作不自动结案或产生退款／扣余额。详见03h§6.2。

所有公开投诉长期保留；未解决记录整体优先，已解决记录整体后置，各组内部按时间倒序。

同一食品同一批次最近 2 天必须实际达到至少 3 条独立投诉，才显示“出现集中反馈”。3 条为硬门槛；跨不同门店来源只提高风险优先级 / 排序，不得把 2 条折算为 3 条。`not_supported` 仍计入“反馈数量”；风险提示保留 2 个月，历史记录不删除。

宠物档案中可选择当前食用的宠物食品标准品牌；品牌列表没有时选择“其他”并填写自定义品牌。自定义品牌经平台归一到标准品牌后参与自动风险匹配。与用户宠物当前品牌匹配的新食品投诉通过基础审核并公开后，立即生成站内风险提醒；可用且已授权时再尝试微信通知。同一用户对同一投诉只提醒一次。食品投诉列表 / 详情必须展示服务端提供的“问题热度”，但具体热度算法由 `DEC-FOOD-HEAT-01` 后续冻结。

门店内部主观顾客备注仍属 Merchant 私有；跨店方向仅允许平台审核后的客观风险事件，不传播“脾气差 / 难搞 / 爱投诉”等人格标签。宠物跨店方向改为“行为与服务安全档案”，使用结构化行为标签而不是主观“凶 / 难搞”定性；具体共享范围仍待确认。

完整规则与待决项见 `03h-customer-risk-feedback.md`.

## 8. 上门喂养

上门喂养保留平台公开需求市场、用户自主接单、发布／我的发布／我的接单／分享入口。需求方业务操作只有发布、撤销，发布后不编辑；店员端当前负责门店仅确认、撤销。任何安排修改均由门店线下协商，不在APP录入修改／重确认、备注媒体、重新开放或开始／完成服务。

状态为待接单、待门店确认、已确认、已撤销、已过期；已确认仅为门店撮合确认，不表示实际服务开始／完成。当前店老板／有效员工确认后，仅该店可查看双方必要联系资料；需求方与接单用户不能互看，公开详情／分享／消息不含双方手机号或微信，查看本人原有资料不受此限制。精确地址仍沿原必要授权，联系方式门槛不能只靠前端遮罩。

首位有效接单者由服务端原子锁定，接单后仅当前负责店收到待确认事项。原publisher_store_id保留，current_coordination_store_id及负责版本决定处理权限。临时休息不影响功能；账号停用仍以原发布店位置转最近有效其他平台店，原单／接单人／历史保持，旧店失权，新店需确认后才读双方联系方式，不转顾客钱包或用户全局当前门店。

北京时间首次约定上门起始为接单截止，不提前小时数，可当天发布未来首访；now≥截止不可接单。无有效接单者到点过期，已有有效接单不按日期自动终止；无重新开放、APP修改或原单复活，需要新公开内容由需求方撤销后新发布。公开推荐仅有效待接单，旧分享最新状态只读及原隐私权限，历史保留。

V1无平台资金托管／抽佣／分账／保证金，不由门店确认自动销售／收款。详细规则统一见03j§8～9.3，原服务跟踪与APP修改／恢复决策已退役，DEC-FEED-02仅剩地理技术及异常界面范围。

## 9. 预约

预约与正式订单严格分离。

支持洗护、美容、寄养预约。

客户提交后进入待门店确认；门店可确认、提出新时间或拒绝。提出新时间后必须由客户确认，不能静默改约。客户只可在预约开始6小时以前修改或接受改期；等于或不足6小时时禁止修改，但本规则不自动禁止服务开始前取消。

洗护／美容由顾客选择营业时间内、未临时关闭的期望到店时间，门店根据实际忙闲人工确认；不设固定预约间隔、每时段名额或自动占用／释放名额，不显示抢位或剩余名额。已有同一时间的其他预约不自动报满；临时关闭不自动取消已确认预约，改期成功前原预约继续有效。详细状态、并发及营业设置联动按03a§11、04§3.0.7。

线下临时到店允许店员直接快速开单，不强制先预约。

详细规则见 `03a-customer-appointment.md`。

---

预约处理按04§3.7／03a§11.7：门店拒绝预约或建议改期原因选填，有填才展示真实内容，无填只显示处理结果；不自动补理由，“其他”不强制说明。处理人留内部记录，顾客看门店及结果、不展示员工个人联系方式。门店新增顾客保存后及确认预约的提醒按04§6.5.1适用于新老顾客，不增加本店资料真实性核验；提醒不可用可直接继续，阅读／选择继续不改变顾客6小时修改截止、营业／关闭、原预约保护、共享授权／限额／冲突规则，也不生成已开始服务或付款。

新增顾客保存后提醒与确认预约提醒按04§6.5.1对全部新老顾客适用，本店不核验资料真实性、提醒不可用无需先人工核对即可继续；客户已保存资料不因提醒失败丢失或重复创建。实际有权展示内容仍明确阅读，同次同内容去重，内容／宠物变化重新阅读、新业务再次提醒；员工阅读不等于顾客分项共享同意，不改变线上账号安全和跨店授权／额度限制。

## 10. 洗护 / 美容结果与 AI 报告

洗美中止按04§4.4：中止说明选填，顾客端无本次中止的服务过程、过程照片／检查时间轴或普通完成结果，不发中止通知、不生成中止报告／AI任务；门店已真实保存的记录保留，不假记完成或自动收退款。终止结果统一显示“服务异常，已终止”，不新增消息；取消／中止后按04§4.4重新开单，不恢复原服务，独立护理中止按04§4.5对应已确认规则，寄养不自动套用。

顾客端已取消／已中止服务统一提示“服务异常，已终止”，页面提示不产生中止通知，底层状态及财务仍分开。洗美／独立护理取消或中止后，要再开始必须重新开单、建立新的服务记录，从待开始重新检查、手动开始和完成；即使误点或原单未结算也不恢复。可选择已有顾客／宠物，旧单状态、真实记录和账目保留；不复制旧检查为本次已检查，不自动结清／退款／转移旧款，不生成恢复消息。新单真实业务通知和顾客主动选择AI仍按原规则，见04§4.4。

服务完成后先形成普通结果，AI报告由顾客主动选择生成，不自动调用AI，仍须原有效资格／授权及真实后端任务。正常已完成洗美允许本店老板／有效员工补照片、改普通说明，已结算亦可、无需审批且原因选填；保留前后内容／人／时间，顾客默认读最新有权内容。补改不重开服务、不改账、不发通知、不自动重生成AI；旧报告保留且不冒充已分析新素材。检查结论、实际时间与收费更正仍按原规则，AI新素材再次分析的版本／复用／资格契约仍待后续，见04§4.4。

结果页顺序：

1. 服务状态 / 基本信息
2. N 组前后对比
3. 本次服务摘要 / 服务记录
4. 结算信息
5. AI 洗护分析

N 组由后端数据驱动，不写死固定组数；缺前 / 后素材不得伪造完整对比。

AI 标准流程：

查看普通结果 → 点击 `查看报告` → 完整观看激励广告 / 获得有效资格 → 后端启动 AI → 显示真实处理阶段 → 完成后展示报告。

广告文案与 5 段生成状态按已确认规则执行；约 60 秒仍未完成时提示稍后返回，后台任务继续。

AI 已获资格后失败重试不得重复要求广告。

报告定位为护理 / 外观观察，不作为医疗诊断。

## 12. 商品、订单与消息

### 商品

轻商城 / 购买需求，不做完整线上电商。

每种商品只有一个规格，支持搜索、分类、商品详情、购物车、提交购买需求；选择商品后直接使用其唯一SKU，不再选择规格，不同容量口味分别为不同商品，详见03e§3／15.6；不支持客户端在线支付、地址、快递、运费、用户物流页。

### 订单

“我的订单”只保留：全部 / 服务 / 商品。

预约不进入普通订单；充值记录归钱包流水。

店员端项目入口的大类为洗护、美容、护理、商品，不等于客户端预约类型列表：护理只供门店开单，暂不增加护理预约；商品继续为真实商品／SKU购买需求，寄养预约保留。护理12项流程按04§4.5／03d§4.4已确认，实际消费归服务订单；照片和普通备注选填，完成即本人可看项目／普通结果／护理注意事项，不等财务记账、不新增护理AI报告，内部备注不公开。同宠洗美加护理共用原单／进度、不降低洗美六项检查，不据此开放商品／寄养混单或跨店共享。 独立护理开始为普通通知、正常完成／重新完成为重要通知、完成后补图／普通文字更正为普通通知；站内必有，微信已授权可用时尝试，短信暂未开放，按真实事件／有变化保存去重。中止说明选填，顾客无本次过程／结果且不发中止消息，门店原真实记录保留。正常已完成可补改（含已结算），本店有效人员无审批、原因选填、留历史／默认最新、不重开不改账；同宠洗美加项不另发护理消息，详见04§4.5／03f。

全部门店到店消费订单可由本店老板／有效员工在结算前整单调价，不设业务幅度上限或老板逐单审批；客户端只显示本单真实金额，不提供改价／免单按钮。最终应收0元须门店明确确认免单，显示“已免单，实付0元”而不是已发生微信／现金付款；免单不自动完成服务或投喂，详见03d§10.1。

订单、退款、取消、冲正不得删除或无痕覆盖历史。

### 消息

全部小程序通知等级仅“普通通知／重要通知”，统一复用F-MSG-012；业务分类和站内／微信渠道规则分别保留；当前阶段业务短信不发送，相关入口显示“暂未开放”，以后开放另行确认（03f§13.2）。等级不代表已读或已处理，食品重新知悉仍须明确平台新要求，见03f§10／13.3.2。

使用单一时间流，展示当前用户的平台个人消息与当前门店个人消息；其他门店私有消息继续隔离。未读 / 全部已读范围和跨店深链按 03f / 03g 执行。重要业务变化产生站内消息，必要时尝试微信通知；通知失败不得影响正式业务。

V1 不做客户 / 店员私聊、在线客服、客户直接聊天或营销群发。

## 13. 养宠顾问：付费门店权益

养宠顾问不再是全平台默认开放能力。

当前门店显示 / 允许使用至少同时满足：

1. Platform Super Admin 已给当前 Store 授予有效 `pet_advisor` 付费权益；唯一归属字段为 `owner_type=store`、`owner_id=store_id`，Merchant 仅作为购买、管理和审计主体；
2. 权益未过期 / 未停用；
3. 门店已向本店客户开启；
4. 当前 Platform User 已与本店建立有效 Customer 关系；
5. 服务端资格校验通过。

未满足条件时不显示可用养宠顾问悬浮入口。

同一用户切换门店时必须重新校验：A 店付费不代表 B 店可用。

满足条件时使用已确认的圆形悬浮按钮：默认左侧、可拖动、松手吸附最近左右边缘，不遮挡微信系统区、底部导航、首页底部广告和主要按钮。

### 用户额度

本次门店付费变更不修改原有用户额度：

- 同一 Platform User 终身前 3 次有效提问免费；
- 第 4 次前看 `pet_advisor` 激励广告；
- 每次广告解锁 3 次；
- AI 成功回答才消耗 1 次；
- AI 失败不扣；
- 切换到另一家付费门店不重新赠送前三次。

门店资格与用户额度分开判断：有额度不代表可以在未付费门店使用。

门店付费也不代表 Merchant Owner / Staff 自动获得客户聊天正文查看权限。

详细规则见 `03l-customer-pet-advisor.md`。

## 14. 广告体系

V1 当前至少包含三类广告能力：

### 14.1 激励广告

placement：

- `ai_report`
- `daily_checkin`
- `pet_advisor`

完整观看并经可信校验后发放对应权益，要求幂等。

`pet_advisor` 激励广告不能绕过当前门店付费 Feature Entitlement。

### 14.2 首页底部 Banner 广告

placement：`home_bottom_banner`

位置：精选商品后、底部导航前。

用于曝光 / 点击变现，不发 Reward Entitlement；失败 / 无填充 / 关闭时自动收起。

### 14.3 启动封面广告

placement：`launch_cover_ad`

小程序启动 / 符合频控的重新进入时，在恢复本次业务目标前按配置展示；没有明确目标时，目标才是最近有效门店首页。支持平台自定义图片、自定义视频或微信官方广告。

图片 / 视频可单独替换；微信广告单元独立配置；支持时效、频控、跳过和测试 / 正式环境。

失败 / 无填充 / 关闭不得阻塞进入目标页（无目标时进入首页）。

三类广告必须在代码、配置、统计和业务权益上区分，不能因为都叫“广告”就共用错误的状态模型。

详细规则见 `03m`、`03o`、`03p`。

## 15. 故障隔离

任何辅助模块故障不得拖垮核心业务。

特别是：

- AI 失败不影响服务 / 订单；
- 养宠顾问 / 门店权益校验失败只影响顾问；
- 首页 Banner 广告失败只收起广告；
- 启动封面广告失败恢复原入口目标（无明确目标时进入首页）；
- 积分故障不影响钱包 / 收银；
- 上门喂养故障不影响洗护 / 寄养 / 商品。
