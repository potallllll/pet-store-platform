# 03 客户端微信小程序

> 状态：已确认
> 版本：V1.0

## 1. 客户端定位

客户端核心定位：

> 服务过程透明 + 客户资料与资产查询 + 业务意向提交。

客户端用于：

- 查看洗护 / 美容 / 寄养服务状态
- 查看洗护 / 美容前后对比与 AI 分析报告
- 查看寄养动态
- 在线预约洗护 / 美容 / 寄养
- 查看和维护宠物基础档案
- 查看会员余额、余额明细和优惠券
- 使用邀请码兑换优惠券
- 查看服务订单、商品订单与消费记录
- 浏览商品、使用购物车并提交购买需求
- 接收站内消息和重要微信业务通知

客户端不承担真实线上支付，不提供会员充值入口，不设计积分机制。

## 2. 门店进入、多商户与身份

采用“一套平台小程序 + 商户专属二维码”模式。

- 每个商户拥有专属客户二维码。
- 扫码后进入对应 Merchant / Store 上下文。
- 公开首页和商品浏览可先不建立 Customer 关系。
- 首次使用预约、宠物、会员、订单、消息、提交购买需求等个人业务时，再完成必要的微信身份与手机号验证。
- 平台 User 与商户 Customer 分离。
- 已验证手机号用于当前商户历史 Customer 匹配，不作为平台唯一主身份。
- 同一 User 可成为多个 Merchant 的 Customer，但各商户余额、优惠券、订单、服务记录、商品业务和消息严格隔离。
- 直接打开小程序时优先进入最近一次使用的商户。
- 切换商户时所有业务上下文整体切换，禁止跨商户串数据。

完整规则见 `03g-customer-identity-security.md`。

## 3. 底部导航

V1.0 底部只保留三个一级导航，顺序固定为：

1. 预约
2. 首页
3. 我的

正常直接打开时默认进入“首页”。

不新增“服务”“商城”“宠物”“门店信息”等底部一级导航。

## 4. 预约

预约独立于正式订单，管理未来服务意向。

V1.0 支持：

- 洗护预约
- 美容预约
- 寄养预约

客户提交后进入“待门店确认”，门店可一键确认、调整时间或拒绝。

预约与服务订单状态分离；客户到店并由门店开始正式服务后，才生成 / 进入正式服务订单流程。

线下临时到店客户允许店员直接快速开单，不强制先建预约。

完整规则见 `03a-customer-appointment.md`。

## 5. 首页

首页只承载三类核心信息：

- 当前门店
- 当前服务
- 推荐商品

### 5.1 当前门店

顶部显示当前商户 / 门店，并在客户关联多家商户时提供切换入口。

### 5.2 当前服务

当前服务为首页最高优先级内容。

同一客户最多直接展示 3 条进行中服务，更多通过“查看全部当前服务”进入完整列表。

洗护 / 美容客户侧仅展示简化状态：

- 等待中
- 洗护中 / 美容中
- 洗护完毕 / 美容完毕

不暴露店员内部细分步骤。

无当前服务时使用轻量预约引导，不显示空白业务卡片。

服务首次完成时显示完成提示，并提供“查看本次服务对比图”。完成卡保留到客户查看本次服务结果后，再退出当前服务区域进入历史记录。

### 5.3 寄养当前服务

寄养首页卡片展示：

- 当前寄养状态
- 日期范围
- 当前第几天
- 今日动态数量
- 最近动态
- 新图片 / 视频提示

### 5.4 推荐商品

首页展示当前门店 3～6 个推荐商品，并提供“查看更多”进入完整商品列表。

## 6. 洗护 / 美容结果与 AI 报告

服务结果页展示：

- 洗护 / 美容前照片
- 洗护 / 美容后照片
- 前后对比
- 本次服务基本信息
- 完成时间
- “查看本次 AI 分析报告”入口

AI 报告使用本次服务前图和后图作为独立图像输入，由服务端调用平台配置的 AI Provider 生成。

生成条件：

- 服务已完成
- 前后照片齐备

缺少前图或后图时不得伪造对比结论。

报告状态至少包括：

- pending
- processing
- completed
- failed

AI 失败不得影响订单和服务完成。

AI 报告定位为宠物护理 / 外观观察，不作为兽医医疗诊断。报告结构至少覆盖：

- 整体变化
- 毛发整洁 / 蓬松变化
- 打结 / 毛发状态观察
- 可见皮肤区域观察
- 清洁变化
- 后续护理关注事项
- 总结
- AI 免责声明

## 7. AI Provider 与安全

AI 模型不得写死单一供应商。

平台超级管理员可在 Web 后台配置：

- API Key / Credential
- Base URL
- Model ID
- 启用状态
- 默认 Provider / Model
- 超时
- 重试

系统使用统一 AI Adapter / Provider 层。

敏感凭证只能位于服务端，前端不得获得明文；日志不得输出完整凭证；敏感值采用加密保存或独立 Secret 管理。

## 8. AI 报告激励广告解锁

客户主动点击“查看本次 AI 分析报告”后触发激励视频广告。

规则：

- 必须完整观看成功后才解锁该份报告。
- 中途关闭不解锁。
- 同一 `user_id + report_id` 成功解锁一次后永久解锁，后续查看无需重复观看。
- 至少记录 `report_id`、`user_id`、`unlocked`、`unlocked_at`。
- 解锁写入必须幂等，避免广告已完整观看但因重复请求 / 网络抖动造成状态错误。

### 8.1 广告加载失败降级

若广告出现加载失败、无填充、网络错误等非“完整观看成功”结果：

- 不免费解锁 AI 报告。
- 不视为已观看。
- 客户端明确提示“广告暂时无法加载，请稍后重试”。
- 允许客户之后重新尝试。
- 洗护 / 美容前后对比、普通服务结果、订单状态均保持正常可查看，不受广告失败影响。
- 广告失败不得影响 AI 报告本身的后台生成。

## 9. 寄养动态

寄养动态按真实发生时间形成时间轴，不使用固定模板时间。

每条动态至少包含：

- 实际发生时间
- 动态类型
- 可选文本
- 可选图片 / 视频
- 操作员工
- 系统创建时间

“实际发生时间”和“系统录入时间”分开保存，以支持补录与审计。

动态类型可包括：

- 喂食
- 喝水
- 遛狗 / 遛宠
- 排便
- 排尿
- 玩耍
- 休息
- 用药 / 特殊照护
- 清洁
- 图片 / 视频
- 异常情况
- 自定义事件

## 10. 我的宠物

入口：我的 → 我的宠物。

核心规则：

- 第一次建档尽量少填。
- 客户和店员都可以在各自权限范围内维护宠物基础资料。
- 客户资料与门店内部备注分离。
- 体重保留历史记录，不只覆盖当前值。
- 洗护 / 美容前后照片自动沉淀为宠物服务相册，不增加额外上传动作。
- 宠物档案中的长期护理 / 寄养信息可在后续预约和服务中自动带出。
- 宠物有历史业务记录时不物理删除，以归档 / 移除方式处理。
- 店员侧客户搜索支持按宠物名查找。
- 宠物基础资料跨商户复用必须由客户主动授权，商户内部业务数据不得跨店共享。

完整规则见 `03b-customer-pet-profile.md`。

## 11. 我的会员

入口：我的 → 我的会员。

V1.0 客户端展示：

- 当前可用余额
- 余额明细
- 我的优惠券
- 邀请码兑换

V1.0 明确不设计积分机制。

客户端不提供充值入口。充值由门店侧选择客户和老板预先配置的充值套餐，客户线下付款后由有权限店员确认收款。

后台区分充值本金余额与赠送余额，客户端通常只展示总可用余额。

优惠券 V1.0 类型：

- 满减券
- 无门槛 / 指定范围金额券
- 折扣券（可配置最高优惠金额）

优惠券来源只包括：

- 充值套餐自动赠送
- 老板 / 有权限员工手动赠送
- 客户邀请码兑换

不做系统活动自动赠券，不做复杂领券中心。

每个订单最多使用一张优惠券；收银时系统自动匹配并默认推荐对客户最优惠的一张。

完整规则见 `03c-customer-membership.md`。

## 12. 我的订单

入口：我的 → 我的订单。

只保留三个分类：

- 全部
- 服务
- 商品

其中服务包含洗护、美容、寄养。

预约不进入普通订单列表；充值记录归入会员余额明细。

订单直接复用正式业务数据，不单独维护一套客户端订单。

洗护 / 美容订单可直接进入同一笔服务的服务结果与 AI 报告页面。

寄养正式结算前显示当前 / 预计金额，结算后显示最终实付。

订单退款、取消、冲正不得通过删除或无痕覆盖原订单实现。

完整规则见 `03d-customer-orders.md`。

## 13. 商品浏览与购买需求

商品模块定位为轻商城，不做完整电商。

V1.0 支持：

- 商品搜索
- 商户自定义分类
- 商品 / SKU
- 商品详情
- 数量选择
- 购物车
- 提交购买需求

不支持：

- 在线支付
- 快递
- 收货地址
- 运费
- 物流状态

客户侧库存只显示：

- 有货
- 库存紧张
- 暂时无货

不默认显示精确库存。

商品需求流程：

提交购买需求
→ 门店确认中
→ 门店一键确认 / 必要时改单
→ 系统自动预占库存
→ 自动匹配优惠券
→ 待线下付款
→ 店员确认实际收款
→ 正式扣库存并计入营业额

门店确认后默认保留 24 小时；超时未收款自动取消并释放预占库存、恢复尚未核销优惠券。商户后续可按已确认规则调整保留时间。

完整规则见 `03e-customer-products.md`。

## 14. 消息中心与微信通知

入口：我的 → 消息。

消息中心使用单一时间流，不做复杂多 Tab。

业务状态变化自动产生站内消息，重要事件再尝试微信通知。微信通知失败不得影响正式业务。

V1.0 不做：

- 即时聊天
- 在线客服
- 客户 / 店员私聊
- 营销群发

重要消息包括预约关键变化、服务完成、寄养异常、商品确认 / 取消等。

普通寄养动态不逐条微信推送；短时间连续动态由系统尽量合并。寄养异常默认通知客户，店员可在仅内部记录时主动取消。

消息点击直接进入关联业务详情。

完整规则见 `03f-customer-messages.md`。

## 15. 登录、历史客户识别与账号安全

V1.0 不设计用户名 / 密码体系。

微信身份作为平台 User 主身份，手机号作为已验证联系方式和当前商户历史客户识别依据。

历史匹配规则：

- 当前商户仅一个明确安全匹配 → 自动绑定历史 Customer。
- 无匹配 → 创建新 Customer。
- 同手机号多个候选 → 不自动合并，由门店处理。
- Customer 已绑定其他 User → 不自动抢绑，进入安全恢复 / 换绑流程。

支持店员通过短时、一次性绑定二维码作为复杂历史数据的辅助绑定兜底。

更换手机号不重新创建会员或 Customer；账号换绑、历史合并、人工绑定、注销等关键身份动作必须留审计。

V1.0 不实现家庭共享账号。

完整规则见 `03g-customer-identity-security.md`。

## 16. 阶段 03 V1.0 边界

V1.0 客户端不实现：

- 真实线上支付
- 会员充值入口
- 积分体系
- 系统活动自动发券
- 复杂营销中心 / 领券中心
- 多张优惠券叠加
- 即时聊天 / 在线客服
- 营销群发
- 快递 / 物流 / 收货地址
- 客户删除正式订单
- 客户指定美容师与复杂员工预约排班
- 预约订金 / 违约金
- 家庭共享账号
- 复杂独立账号申诉中心
