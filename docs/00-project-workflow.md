# 项目需求与 Codex 开发总流程

## 1. 总原则

项目采用“需求先冻结、开发后执行”，允许产品方明确批准的独立原型和已确认模块开发准备提前并行。完整流程：需求讨论 → 角色与业务设计 → 多端功能设计 → 业务规则 → 权限 → 数据库 → UI → 技术架构 → 测试验收 → V1.0冻结 → Codex Master Prompt → Codex开发 → 审查整改 → 最终验收。

GitHub已确认规格为正式来源。聊天、外部方案、旧AI提案和H5原型不能自动成为正式需求。文档地图见`README.md`，执行约束见根目录`AGENTS.md`，阶段见`REQUIREMENTS-STATUS.md`，待决见`REQUIREMENTS-DECISIONS.md`。

## 2. 正式需求管理

需求状态为讨论中、待确认、已确认、以后版本。已确认文档内的待决章节仍为待确认，不因所在文件已确认就自动生效。

每个业务规则只维护一个权威定义位置。总纲负责范围，业务模块负责细节，03i负责页面地图和验收ID，10a负责共享UI，10b/10c负责专项布局。上层全局安全、租户隔离、财务审计与权限原则始终有效。明确冲突不得自行选择、脑补或静默覆盖，须停止受影响实现并登记决策。

### 2.1 需求变更

真正修改已确认规则时，至少记录：原规则、新规则、原因、影响范围、产品确认人及日期、权威章节、关联DEC/验收ID和落实提交。修改对应模块正文并同步必要的页面、状态及验收引用。历史条款保留追溯价值，但须标记已被替代并指向现行规则。不得建立重复完整业务内容的中央CHANGELOG。

文字清理、引用修复与新的业务决策分开提交。不得因为消除歧义而擅自确定金额算法、权限、时间、收费、退款或第三方能力；无法在原规则内确定的事项进入决策登记。

### 2.2 待决事项

`REQUIREMENTS-DECISIONS.md`记录唯一DEC ID、状态、权威位置、负责人、确认人/日期、选择口径、影响范围、阻塞的开发/验收、验收ID及落实提交。状态包括待确认、已确认待同步、已落实、已取消；外部能力可标注待验证。

待确认提案不得当作正式实现依据；已确认待同步只有在权威正文更新后才可标记已落实。任何默认值、示例或推荐算法均不得因写入登记而自动冻结。相关正式实现和验收必须在对应决策收口后进行，不依赖该决策的能力可继续推进。

## 3. 产品与交互设计总原则

项目优先降低社区宠物店实际使用门槛。店员端与老板端应减少步骤、重复录入和不必要跳转，在不牺牲财务安全、权限和审计的前提下让后端承担复杂度。

1. 能自动带出的客户、手机号、宠物、会员、订单资料不重复填写。
2. 高频操作尽量在1～3个主要动作完成；普通低风险操作避免重复确认。
3. 同一业务支持快速路径与完整路径；临时到店可直接开单并开始服务，不强制先预约。
4. 常用选项采用快捷按钮、最近使用、默认值、模板和常用语减少文字输入。
5. 状态、时间、归属及可确定金额自动生成；关键财务动作仍由有权限人员确认。
6. 一个页面可安全完成的连续操作不拆成无必要多层页面。
7. 系统流程应贴近真实门店顺序，避免员工因繁琐而绕开系统。
8. 审计尽量后台自动记录操作人、时间、前后值、设备/来源及业务对象，不通过大量人工步骤实现。
9. 退款、余额调整、作废、收款确认等危险操作保留必要权限和确认。
10. 老板拥有本店全部店员能力，使用店员端时同样遵循低操作负担原则。
11. 后端复杂度可为明显减少前端步骤服务，但不得牺牲关键一致性。
12. 旧方案和外部参考不是兼容要求，最终以当前已确认规格为准。

每个功能讨论额外检查：完成任务需要几步、是否重复输入、能否自动带出/合并页面/提供快捷入口、员工是否可能绕开系统，以及是否存在更安全更简单的方案。

## 4. 需求设计阶段

1. 项目定位
2. 用户角色与账号体系
3. 客户端小程序
4. 店员端小程序（老板也可使用）
5. Web管理后台
6. 核心业务规则
7. 完整业务流程
8. 权限体系
9. 数据库设计
10. UI / Design System
11. 技术架构
12. 测试与验收

阶段03与客户端部分阶段10允许经确认提前并行，但不代表整个阶段10或V1.0已经完成。核心业务规则阶段应形成唯一结算契约，明确金额计算、优惠、库存、钱包、券、支付确认、退款、冲正及异常恢复的权威关系；待决项不得由实现者猜测。架构阶段需区分核心一致性链路和辅助故障隔离，不能以模块独立为由允许部分财务成功却宣称整笔交易完成。

## 5. V1.0冻结与Codex阶段

最终需求分为V1.0必须实现、V1.1预留、V2.0未来功能。V1.0整体冻结前确认全部阻塞决策、跨端规则、权限、数据契约、第三方能力和验收范围。冻结后原则上不新增功能；确需变更按正式流程处理。

生成完整Codex Master Prompt后，要求Codex按合理工程顺序执行初始化、数据库、后端、权限、业务模块、客户端、店员端、Web、第三方能力、测试、Build、修复、README和部署文档。不得删减需求、用Mock/TODO冒充实现、绕过权限或数据校验、因报错注释功能或修改规则来通过测试。

## 6. 需求—实现—测试追踪

客户端唯一验收ID在03i§14.1；其他端在其正式阶段建立对应唯一索引。每项需求的交付记录至少包含：

| 字段 | 要求 |
|---|---|
| Requirement ID / Authority | 唯一需求或验收ID、现行权威章节 |
| Decision dependency | 关联DEC及是否已落实；未决不能标为已通过 |
| Delivery scope | 原型、真实服务端、端到端、第三方接入等明确范围 |
| Implementation | 真实页面/API/业务模块、提交或PR；未实现如实标记 |
| Test case | 对应测试ID、场景、前置条件与预期结果 |
| Execution | 环境、运行时间、实际结果、证据链接及执行人/工具 |
| Result | 未执行、阻塞、通过、失败、不适用及原因；不适用须有依据 |

组合场景明确列出子项，不得仅以总场景通过掩盖未执行子项。原型允许标注Mock并演示成功/失败状态，但不能作为真实业务后端或端到端通过证据。文档检查、静态色值计算、编译通过也不等于业务验收通过。

正式验收至少覆盖适用的成功、失败、并发、重复提交、响应丢失、离开返回、切店、权限失效、资产冲正与恢复。关键业务未知结果先查询同一请求，不能因重试产生第二笔。收款、余额、优惠券、库存、收入必须遵循统一一致性契约；辅助AI、广告、通知、统计故障不得成为核心经营错误成功的理由。测试结果须真实可复现，不得伪造日志、截图或通过结论。

## 7. 审查与整改

Codex第一轮完成后，审查架构、业务、数据库、权限、安全、遗漏功能、测试结果及部署恢复能力，形成可追踪整改清单。每项整改关联需求、缺陷、受影响模块、修复提交和复验结果，直到符合V1.0标准。未解决的阻塞项不得隐藏为完成，后续决定仍由产品方确认。

### 2026-09-08 治理变更

原规则：需求变更与验收只描述原则，缺少统一DEC登记和可追溯证据字段。新规则：明确单一权威、待决状态、变更记录、核心一致性边界和需求—实现—测试追踪。影响所有阶段及AI交付；不改变已确认业务功能、正式角色或当前主阶段。
