# 项目需求与 Codex 开发总流程

## 总原则

项目采用“需求先冻结、开发后执行”的方式：

需求讨论 → 角色与业务设计 → 多端功能设计 → 业务规则 → 权限 → 数据库 → UI → 技术架构 → 测试验收 → V1.0 冻结 → Codex Master Prompt → Codex 开发 → 审查整改 → 最终验收。

聊天中的内容属于讨论草稿；只有经过确认并同步到本仓库正式文档的内容才进入正式规格。

## 产品与交互设计总原则

项目整体以“降低社区宠物店实际使用门槛”为最高优先级之一。

尤其是店员端和商户老板端，设计任何功能时均必须优先考虑减少操作难度、减少点击次数、减少重复录入和减少不必要页面跳转。

具体原则：

1. 能自动带出的数据不得要求员工重复填写，例如客户手机号、宠物资料、会员信息、订单基础信息等。
2. 高频操作尽量在 1～3 个主要动作内完成，不为形式完整而增加确认层级。
3. 同一业务应支持“快速路径”和“完整路径”。例如临时到店客户可以直接开单并开始服务，而不强制先创建预约。
4. 常用选项优先使用快捷按钮、最近使用、默认值、模板或常用语，减少文字输入。
5. 系统可自动判断的状态、金额、时间、归属和关联关系尽量自动生成，但关键金额和财务动作仍必须由有权限人员确认。
6. 一个页面能够安全完成的连续操作，不拆成多个无必要页面。
7. 店员不得因为系统流程复杂而被迫绕开系统、先线下记录后补录；产品设计应尽量贴近真实门店工作顺序。
8. 审计能力不能通过增加大量人工步骤实现。应优先依靠后台自动记录操作人、操作时间、修改前后值、来源设备 / 业务对象等信息。
9. 对危险操作（退款、余额调整、删除 / 作废、收款确认等）保留必要确认和权限控制；普通低风险操作避免重复确认。
10. 老板拥有店员全部业务操作能力，但老板使用店员端时同样遵循低操作负担原则。
11. 新功能若能明显减少员工操作次数，即使后端实现更复杂，也优先选择“前端简单、后端承担复杂度”的方案。
12. 任何旧方案、外部参考方案只作为设计参考，不要求兼容；最终以本项目当前确认规格为准。

在后续每个功能讨论中，除业务正确性外，应额外检查：

- 店员完成一次任务需要几步？
- 是否存在重复输入？
- 是否能自动带出？
- 是否能合并页面？
- 是否能提供快捷入口？
- 是否会让员工因为麻烦而绕开系统？
- 在不牺牲财务安全、权限和审计的前提下，是否还能进一步减少操作？

## 需求设计阶段

1. 项目定位
2. 用户角色与账号体系
3. 客户端小程序
4. 店员端小程序（老板也可使用）
5. Web 管理后台
6. 核心业务规则
7. 完整业务流程
8. 权限体系
9. 数据库设计
10. UI / Design System
11. 技术架构
12. 测试与验收

## V1.0 冻结

所有需求最终分为：

- V1.0 必须实现
- V1.1 预留
- V2.0 未来功能

V1.0 冻结后原则上不继续新增功能。

## Codex 阶段

冻结后生成完整 `Codex Master Prompt`，要求 Codex 自主按合理工程顺序执行项目初始化、数据库、后端、权限、业务模块、客户端、店员端、Web 后台、第三方能力、测试、Build、修复、README 和部署文档。

Codex 不得自行删减需求、用 Mock/TODO 冒充正式实现、绕过权限或数据校验、因报错而注释功能。

## 验收

Codex 第一轮完成后，对架构、业务、数据库、权限、安全、遗漏功能和测试结果进行审查，形成整改清单并再次修复，直到符合 V1.0 验收标准。
