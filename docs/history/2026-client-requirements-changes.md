## 03b-customer-pet-profile.md


### 2026-08-31：新增宠物交友设置

【需求变更】

- 原规则：宠物档案用于基础资料、护理、寄养、服务记录与服务相册，不包含宠物交友公开展示控制。
- 新规则：新增每只宠物独立的交友展示开关、社交昵称和公开服务后照片设置；只有主人明确授权的宠物才进入当前门店宠物交友公开展示池。
- 影响范围：客户端宠物档案、首页宠物交友、服务相册、隐私、数据库、API。

### 2026-08-31：明确交友授权主体

【需求变更】

- 原规则：客户和店员均可维护宠物基础资料，可能被误读为店员也可开启宠物公开交友。
- 新规则：交友公开开关和公开照片范围必须由宠物主人客户端主动授权；店员不能默认代开。自己的主宠物可仅对本人显示在首页第 4 位，不等于公开授权。
- 影响范围：宠物档案、宠物交友、隐私、店员端权限边界。

### 2026-09-01：服务相册支持 N 组前后对比关系

【需求变更】

- 原规则：服务相册仅描述服务前 / 服务后照片归档。
- 新规则：同一次洗护 / 美容可保存 N 组前后照片，并保留服务、对比组、前后类型与排序关系；客户端按完整组动态生成拖动对比，缺图组不得伪造成完整对比。
- 影响范围：客户端服务结果、宠物服务相册、店员端上传、数据库、API、AI 输入。

### 2026-09-01：寄养资料增加零食投喂授权与饮食注意事项

【需求变更】

- 原规则：寄养资料包含喂食习惯、过敏、用药和特殊照护等信息，但没有明确控制寄养期间额外购买零食投喂。
- 新规则：寄养资料增加“寄养期间是否允许额外投喂零食”和禁食 / 忌口信息；允许时可进入寄养加餐购买流程，不允许时不得提供可提交投喂入口。投喂过程中必须展示相关饮食注意事项。
- 影响范围：宠物档案、寄养详情、商品购买需求、店员待办、库存、收银、API 与后续数据库设计。

- 新规则：入口名称改为“我的钱包”；当前可用余额直接展示在“我的”页面；“我的钱包”不重复展示余额大卡，主要承载余额明细、优惠券和邀请码兑换。
- 影响范围：客户端信息架构 / UI；不改变余额数据库模型、充值流程、支付规则、财务流水或商户隔离规则。

### 2026-09-01：“我的”资产卡展示资产构成

【需求变更】

- 原规则：“我的”页面主要直接展示总可用余额，本金 / 赠送构成通常不在首页直接展示。
- 新规则：“我的”页面使用资产摘要卡，同时展示当前可用余额、当前可使用优惠券数量、本金余额和赠送余额；总可用余额为主金额，其他三项为辅助信息。整张卡可进入余额明细。
- 视觉边界：参考图只确认信息层级和版式方向，不冻结背景颜色、渐变、高光、字体、圆角或阴影，具体视觉在阶段 10 确定。
- 影响范围：客户端“我的”页面、页面蓝图、钱包资产摘要、API 返回字段与 H5 / UI 验收；不改变充值、余额记账、财务流水或商户隔离规则。

### 2026-09-08：同步平台积分与兑换优惠券来源

- 原规则：钱包保留“不设计积分”的旧总结，优惠券来源仅列充值赠送、人工赠送和邀请码兑换。
- 新规则：同步 `03k` 已确认的平台积分体系，明确积分不进入商户资金卡和钱包账本；优惠券来源补充平台积分兑换，保留兑换关联、适用商户及幂等补偿边界。
- 影响范围：钱包资产展示、优惠券来源与发放、积分商城兑换、退款边界、API 和验收；不改变会员充值和余额支付权限。

## 03d-customer-orders.md


### 2026-09-08：寄养加餐区分付款与投喂执行状态

- 原规则：商品订单统一以确认收款作为客户端“已完成”，未明确寄养加餐仍待实际投喂时的展示。
- 新规则：普通商品流程保持不变；寄养加餐在同一商品订单上分别记录付款与执行，已收款未投喂继续显示处理中，实际确认后显示已投喂；取消 / 异常单独展示并保留真实财务记录。
- 影响范围：订单列表 / 详情、寄养加餐、店员待办、时间轴、退款展示和关键交互验收；不新增订单分类或独立投喂订单。

## 03e-customer-products.md


### 2026-09-01：新增寄养加餐 / 投喂零食场景

【需求变更】

- 原规则：客户端商品购买需求仅从推荐商品、商品列表、详情和购物车等普通商品路径发起；寄养详情没有直接购买零食并请求店员投喂的能力。
- 新规则：宠物处于寄养中且主人允许额外零食时，寄养详情增加“投喂零食”入口；客户选择门店允许寄养投喂且有库存的商品后提交，系统提示已通知店员，并生成统一商品购买需求，通过 `business_scenario = boarding_feed` 关联 `boarding_id / pet_id`。店员按普通商品购物、库存和收银规则处理，实际投喂完成后自动写入寄养动态。
- 财务边界：寄养加餐成交只计入商品销售，不重复计入寄养收入；不建立第二套投喂订单、库存或支付模型。
- 影响范围：客户端寄养详情、宠物寄养资料、商品 / SKU、商品购买需求、店员待办、库存、订单 / 收银、钱包、寄养时间轴、消息通知、统计、API 与数据库设计。

### 2026-09-08：闭合寄养加餐的收款、执行与异常处理

- 原规则：寄养加餐复用商品订单，但商品收款即完成与实际投喂后写动态之间缺少明确状态映射，“处理完成”解除重复提交限制的时点不清晰。
- 新规则：同一商品订单区分付款和投喂执行；已收款未投喂持续显示处理中并保留待办，实际确认仅写一次动态且不重复记账；执行完成或取消及必要后续处理完成后，重新校验入口条件再解除限制。
- 异常规则：提前离店、撤回允许和无法投喂时停止执行，取消与财务处理分别留痕；已收款事项按统一权限、确认 / 审批和退款规则处理，不新增无条件退款政策。
- 影响范围：商品订单、收银展示、寄养详情、店员投喂待办、寄养动态、库存 / 优惠券 / 余额、API 幂等和关键验收；不建立独立投喂订单。

## 03f-customer-messages.md


### 2026-09-08：平台消息范围与目标恢复

【需求变更】

- 原规则：消息统一按门店保存和切换，保留“V1.0 无积分”的旧表述，新增平台业务通知的可见范围、未读口径和目标校验未收口。
- 新规则：同一时间流展示本人平台消息与当前门店本人消息；补充 scope、接收人、已读范围、平台事件及深链权限校验，启动 / 登录后恢复原目标；删除无积分旧表述。
- 影响范围：首页 / 我的消息入口、身份与跨店上下文、上门喂养、积分兑换、微信通知、消息 API 和验收。

### 2026-09-01：AI 报告改为客户主动触发生成

【需求变更】

- 原规则：服务完成后可提前生成 AI 报告，客户点击时主要负责广告解锁。
- 新规则：服务完成只生成普通服务结果和前后照片对比，不启动 AI；客户获得报告查看资格后才提交照片并创建 AI 任务；生成过程中显示阶段化处理状态，完成后直接展示结果。
- 影响范围：客户端服务结果页、AI 调用时机、消息、后端任务、API、成本与隐私。

### 2026-09-01：AI 报告等待体验最终确认

【需求变更】

- 原规则：生成中使用“宠物图片对比中 → 专业数据库查询中 → 结果复核中”等 3 段状态，未明确前台最长等待体验。
- 新规则：改为 5 段专业流程文案：宠物影像质量检测 → 洗护前后特征比对 → 毛发与清洁状态分析 → 专业护理知识检索 → 结果复核与报告生成；真实结果提前完成则立即展示，正常目标 30～60 秒，约 60 秒仍未完成则提示客户稍后返回查看。
- 影响范围：客户端服务结果页、消息、AI 任务状态映射、API 与异常体验。

## 03g-customer-identity-security.md


### 2026-09-08：首开选店、深链优先级与平台个人数据

【需求变更】

- 原规则：直接打开默认最近门店，消息随门店整体切换；无有效门店、明确门店深链和登录后原目标恢复缺少统一规则。
- 新规则：本次有效目标优先于历史门店；无有效门店提供扫码 / 选店；后台与登录后恢复原目标并重新鉴权，平台个人消息和业务保留，门店私有业务仍整体隔离。
- 影响范围：首次进入、登录 / Customer 识别、门店切换、启动广告、消息 / 分享深链、草稿与权限验收。

## 03h-customer-pet-social.md


### 2026-08-31：新增宠物交友

【需求变更】

- 原规则：首页临时 H5 原型存在“快捷入口”区域，正式规格未设计宠物交友模块。
- 新规则：首页该区域改为“宠物交友”；每轮滚动展示最多 12 只不同宠物、每屏 3 只，自己的主展示宠物固定为第 4 只；支持查看更多、宠物详情、好友邀请、对方同意 / 不同意、去重以及同意后自动通知双方并提示店员处理。
- 隐私补充：完整列表仅展示主人已授权参与交友的当前门店宠物，不默认公开未经授权的全部宠物；不公开主人联系方式。
- 影响范围：客户端首页、宠物档案、消息中心、店员端待办、数据库、API、隐私与审计。

### 2026-08-31：公开授权边界补充

【需求变更】

- 原规则：自己的主展示宠物固定第 4 位，同时公开展示池又要求主人授权，存在未开启交友时的解释歧义。
- 新规则：自己的第 4 位卡片可对本人私有展示；只有主人主动开启交友后，宠物才进入其他客户可见的公开展示池并可发起好友邀请。目标宠物主人必须具备可用客户端身份才能加入公开交友池。
- 影响范围：客户端首页、宠物交友、宠物档案、身份体系、消息和隐私。

### 2026-09-01：首页宠物交友明确自动轮播

【需求变更】

- 原规则：首页宠物交友写为“横向滚动 / 轮播”，可能被实现为仅支持用户手动横向滑动。
- 新规则：首页宠物交友默认自动滚动 / 自动轮播，同时支持用户手动横向滑动；用户主动操作时优先响应手势，并在交互后自动恢复轮播。
- 影响范围：客户端首页交互、UI / Design System、前端实现与验收。

### 2026-09-01：首页宠物交友卡片角标改为“可发送邀请”

【需求变更】

- 原规则：临时原型在宠物交友卡片图片角标中使用“洗护后”，容易被理解为图片类型说明，不能直接表达该卡片可以发起交友邀请。
- 新规则：对当前客户可正常邀请的其他宠物，卡片能力角标统一改为“可发送邀请”；图片仍可使用主人授权公开的洗护 / 美容服务后照片。自己的宠物或当前不可邀请的宠物不得错误显示该角标。
- 影响范围：客户端首页宠物交友、页面蓝图、H5 / UI 原型和阶段 10 视觉设计；不改变照片来源、隐私授权或好友邀请业务规则。

### 2026-09-08：少量宠物边界与可控轮播

- 原规则：无条件每屏 3 只、本人固定第 4 位，少于 4 只时如何满足未说明；交互后默认恢复，缺少显式暂停与减少动态效果规则。
- 新规则：按去重后的真实数量展示，1～3 只单屏且不自动播放，本人第 4 位只在至少 4 只且包含本人时生效；少量时本人排实际末位，添加引导独立于宠物序号；多屏保留默认自动、手动滑动与点按切屏，并明确暂停 / 恢复优先级及减少动态效果。能力提示统一为既定底部浅色“可发送邀请”标签。
- 影响范围：首页卡片排序、数量与页码、轮播共享组件、访问性设置、原型及验收；不改变公开授权、门店隔离、邀请去重、消息和照片来源。
