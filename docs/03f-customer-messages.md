## 1. 设计原则

- 不新增底部一级导航，入口位于首页右上角及“我的 → 消息”，两个入口进入同一消息中心。
- 所有重要业务事件优先自动生成站内消息；真正需要客户及时知道的事件再尝试发送微信通知。
- 绝大多数通知由业务状态变化自动触发，不要求店员额外点击“发送通知”。
- 微信通知属于附加通知渠道，发送失败不得影响预约、订单、服务、余额、优惠券等正式业务状态。
- V1.0 不做即时聊天系统，不做在线客服系统，不做营销群发。
- 消息点击后应直接进入对应业务详情页，避免客户再次手工查找。

## 2. 消息中心

入口：首页右上角 / 我的 → 消息。

消息中心采用单一时间流，不设计复杂多 Tab。消息可标识业务类型，例如：预约、服务、寄养、商品、钱包 / 会员资产、投诉 / 风险反馈、上门喂养、平台积分。

每条消息至少保存：

- scope：`platform`（平台个人消息）/ `merchant`（门店个人消息）
- recipient_user_id：平台个人消息必填，指向明确接收用户；门店消息在 Customer 尚未安全绑定 User 前允许为空，必须保留明确的 merchant_id + customer_id，不猜测接收账号
- merchant_id / customer_id：门店消息必填；平台消息不以这两个字段作为接收人或可见性依据
- related_store_id：平台业务关联的绑定 / 领取门店（如有），仅表达业务关联，不自动授予门店私有数据权限
- message_type
- title
- summary / content
- related_business_type
- related_business_id
- message_priority（F-MSG-012，普通通知／重要通知；不另建priority同义字段）
- read_status
- created_at
- read_at（可选）
- jump_target / 跳转目标

门店在客户首次使用小程序前产生的业务消息，可先关联该门店 Customer。按 03g 完成安全绑定后，服务端校验当前 User 与该 Customer 的有效关系，才允许读取 / 关联待识别消息；不因相同手机号、扫描凭证或候选匹配而提前暴露内容。已明确属于其他 User 的消息不得自动改接收人；换绑 / 合并按正式身份规则处理，保留审计。平台消息始终需要明确的接收 User。

客户端支持未读数量展示及“全部标记已读”。V1.0 不提供客户端删除业务消息能力。

### 2.1 展示范围与切店

- 当前时间流由“当前 User 的平台个人消息 + 当前 Merchant 下属于当前 User / Customer 的门店个人消息”组成。
- 切换门店后保留本人的平台个人消息，仅替换门店消息部分。没有有效当前门店时，只能展示本人的平台个人消息，并提供选择门店入口。
- 其他门店私有消息不混入当前门店列表。上门喂养和平台积分消息不会因为用户切店而消失；绑定门店名称可作为业务说明展示。
- 服务端分别校验接收用户、消息作用域和目标业务权限；不得为了读取平台消息而取消门店消息的租户过滤。

### 2.2 未读与已读

- 首页和“我的”的消息未读数采用同一可见范围：本人平台未读 + 当前门店本人未读，不包含其他门店私有消息。
- “全部标记已读”只作用于操作时当前 User、当前门店和该次操作截止时间之前的可见消息；操作期间切店或新增的消息不得被扩大范围误标。
- 点击消息并成功打开消息内容或有权限的业务详情后标记已读；仅滚过列表不标记。读取失败、权限校验失败时不因前端已点击就写入已读。
- 已读状态由服务端保存，重复操作幂等；切店不重置历史已读状态。

## 3. 预约消息

以下事件自动生成站内消息：

- 预约提交成功
- 门店确认预约
- 门店建议修改时间
- 预约拒绝
- 预约取消
- 客户修改预约后重新进入待确认

微信通知优先用于需要客户及时处理或知晓的预约变化，例如：门店确认、建议新时间、拒绝、取消。

门店调整营业时间或临时关闭后，受影响预约进入门店处理清单并逐笔通知，按03a§11.5处理；通知只说明真实变更及待处理情况，不表示预约已被自动取消或静默改期。提交成功消息只表示等待人工确认，不发送抢位成功、余量或名额保留倒计时；同次业务事件重试不重复生成通知，渠道失败不回滚预约。

04§3.7／03a§11.7的门店拒绝／建议改期原因选填，消息中有真实填写才展示，不自动补理由；空原因不阻止真实业务结果产生原适用通知，不新增短信渠道。共享提醒不可用、阅读或选择继续都不表示预约已确认，只有实际合法确认成功才发送原确认结果；不将内部处理人／个人联系方式、核验日志或可枚举他店记录的差异原因写进客户消息。

04§6.5.1新老顾客共同提醒是原流程中的独立弹窗，不新增短信、微信群发或每次回退重复通知任务。新增顾客先明确保存，再提醒；提醒不可用统一提示可继续，不发送已核验／无风险或假查询成功消息，不要求门店人工核对。阅读及选择继续分别留内部记录；再次弹窗、返回页面或网络重试不自动追加跨店查询或重复扣次数，实际业务通知仍按原成功事实生成。

## 4. 洗护 / 美容消息

客户侧不对员工内部每个服务步骤逐条推送。

V1.0 主要消息节点：

- 服务开始
- 服务完成

其中“服务完成”为重要通知，应优先尝试微信通知。

服务完成消息直接跳转本次服务结果页，可查看 N 组前后照片对比，并由客户主动决定是否查看 AI 洗护报告。

按04§4.4，完成洗美即发布本宠普通结果／原完成通知，不等收款或接走确认；照片缺失如实提示。未结算重新处理后当前显示服务中，旧普通结果保留历史、非当前最终，再次完成形成新版本并可再通知一次；同一转换／结果版本的重试不重复发，也不能把旧版已读当新版已读。AI权益不自动重置，不因重新完成自动AI。洗美中止不生成站内／微信／短信通知，也不改发完成通知；不公开本次中止过程或生成结果／AI报告，门店既有真实记录保留，中止说明选填，见04§4.4。先前合法消息不删除，不影响以后真实收款等独立事件按原规则通知；正常已完成洗美补照片／改普通说明不发站内／微信／短信通知、不产生新完成事件，既有首次／重开后再完成通知规则保留；顾客读取原结果最新有权内容，补改不自动重置已读、旧已读不冒充看过新内容。AI由顾客主动选择生成，原资格保留，补改不自动生成／重生成，不新增报告更新通知；其他内容更正及独立护理未列的取消／更正事件通知仍待对应DEC；挂单按04§4.6仅门店自行联系，不自动发送短信／微信催款；挂单不发收款成功，退款录入草稿不发到账消息。财务仅作线下交易记账、消费退款无需老板审批；原微信／支付宝／现金等在线下原路退回并记账，原余额本金／赠送按原归属入原钱包后展示结果，未录入前不伪造成功通知，不新增外部支付回调。通知失败不回滚真实状态／资金。

**服务完成本身不启动 AI 分析，也不把本次服务照片提交给 AI Provider。**

独立护理按04§4.5：真实开始成功生成普通通知；正常完成／重新完成成功生成重要通知；正常已完成后补照片／更正普通说明成功生成普通通知，已结算也允许补改。各真实状态事件／一次有内容变化的补改保存生成一条站内消息，并在已授权且微信可用时尝试发送；消息失败不回滚业务，短信当前暂未开放。不对草稿、无变化保存、失败或同次请求重试重复发；F-MSG-012只用普通通知／重要通知。补改用原F-AUD事件／稳定请求及F-SVC-019版本去重，不伪造新完成轮次；新的补改消息独立未读，旧服务已查看不代表新消息已读。中止护理不生成站内／微信／短信消息、无本次顾客过程／普通完成结果，说明选填，原内部事实保留。普通护理完成结果不等收款、不新增护理AI；开始／完成／补改不改变资金。正常已完成护理的补改人／权限／留历史／顾客默认最新／不重开不改账按04§4.5。同宠洗美的护理加项仍复用原洗美进度及消息，不能另发第二条护理消息；洗美补改依旧按§4.4不通知，本轮不把“其他都发送”扩大到所有业务或其他未列护理取消／更正事件。

客户在服务结果页点击“查看报告”，完成有效广告观看 / 获得有效查看资格后，后端才创建 AI 分析任务并提交本次可用于分析的前后照片。

如果客户仍停留在结果页，客户端显示与真实处理流程对应的阶段状态：

1. 宠物影像质量检测中
2. 洗护前后特征比对中
3. 毛发与清洁状态分析中
4. 专业护理知识检索中
5. 结果复核与报告生成中

AI 结果一旦实际完成，应立即展示，不得为了填满等待动画而故意延迟。

正常体验目标为约 30～60 秒。若约 60 秒后后台任务仍未完成，客户端不继续让客户原地无限等待，改为提示：

> 报告仍在生成中
>
> 分析已提交，可稍后返回本页面查看结果。

AI 报告生成完成后默认不额外重复发送微信通知。客户之后再次进入同一服务结果页时读取服务端真实任务状态：

- 未完成 → 显示仍在生成
- 已完成 → 直接展示已获得查看资格的报告
- 失败 → 显示失败状态与重试入口

若客户已经完成广告并获得查看资格，后续 AI 失败或超时重试不得要求再次观看广告。

04§4.6挂单只由门店自行电话／微信联系，系统不自动发催款短信／微信消息或定时催办；选填联系时间和备注内部可见。误挂撤销仍待结算，不发收款成功／免单／欠款消除通知，不因跨日发自动取消消息。当前阶段投诉等业务短信也按§13.2暂未开放；实际收款／明确免单仍按真实结果发送原适用消息。

## 5. 寄养消息

04§5.2离店费用确认、实际离店和财务收款分别记录；已离店未收款／挂单也不再展示在住，不继续计费。消息发送／顾客已读不能代替结算页确认本批应收或真实收款。内部挂单原因／催款备注不对顾客展示；本次未新增离店短信、自动催款或额外微信模板，不能从可查看状态推导新的通知权限。

普通寄养动态不逐条发送微信通知。

适合形成站内消息或重要通知的事件包括：

- 办理入住
- 新增图片 / 视频动态
- 异常情况
- 寄养即将结束 / 已结束

多个短时间内连续新增的普通图片、视频或寄养动态由后端尽量合并提示，例如“旺财有 3 条新的寄养动态”，减少消息轰炸。

寄养异常记录默认勾选“通知客户”；是否可见与是否通知分开，按04§5.1／F-BOARD-025明确区分顾客可见动态和本店内部备注。顾客可见动态关闭通知仍在本人有权查看的时间轴；内部记录即使勾选通知，也不得泄露内容、缩略图、数量或跳转。内部记录可关闭通知，不得仅凭取消通知就把公开动态当作已隐藏。

统一照护录入选择喂食／遛狗／清扫笼子、实际发生时间、选填照片后保存；没有照片也可记真实事件，补录按实际时间排序。普通照护不新增逐条微信轰炸、每日上传配额或批量完成，原动态提示与合并原则继续有效。异常须员工实际处理、填写结果并明确标记已处理，发送成功／已读不能关闭异常；预计离店到点仅提醒核对，不自动宣布已离店、续住或加费，费用／实际离店按04§5.2，特殊照护／异常沟通按§5.4；医疗处置与紧急升级继续待决。

04§5.4的代喂药属于特殊照护，不新增独立喂药消息类别或定时用药通知任务。异常可记录已联系／暂未联系上、沟通结果与主人明确决定；消息成功／已读不代表联系确认、主人同意或异常已处理。原通知与动态可见性规则保持，不默认向顾客公开内部沟通备注，也不新增短信、自动催办或紧急升级通道。

异常通知直接进入对应寄养详情 / 时间轴。

## 6. 商品消息

商品购买需求可产生以下站内消息：

- 购买需求已提交
- 门店已确认
- 门店已调整商品 / 数量
- 订单即将自动取消
- 订单已取消
- 订单已完成
- 订单已免单结算（明确已免单、实付0元，不伪造收款成功）

微信通知优先用于：

- 门店已确认，可到店线下付款
- 门店修改商品 / 数量
- 订单即将超时取消
- 门店取消订单

商品订单按库存预占及03d§10.1结算规则执行。默认24小时仍未结算时按原规则提醒／取消；实际收款或免单已成功的订单不再走未付款催付／超时取消。仅输入0而未确认免单仍未结算，文案提示待门店确认免单，不引导顾客支付0元。取消后释放预占库存；所有券独立手动核销，不随商品超时取消解锁／核销，也不暂停有效期或新延期；普通券退款原则及历史旧锁定处置按03c§11，不复活原已过期券。

免单消息读取真实waived结果及原订单，重试只产生一次同业务事件通知；通知失败不回滚结算、不二次出库，也不自动生成投喂或服务完成消息。

## 7. 钱包 / 会员资产消息

V1.0 已包含独立的平台积分体系。积分消息按平台个人作用域展示，不混入商户钱包账本；详细业务见 `03k-customer-loyalty-points.md`。

钱包 / 会员资产相关消息包括：

- 充值完成
- 余额人工调整
- 优惠券到账
- 邀请码兑换成功
- 优惠券即将过期（普通通知，可选；仍默认仅站内提醒）

充值完成后系统自动生成站内消息，展示本次到账金额、当前余额以及自动赠送的优惠券。

邀请码兑换在当前页面直接展示结果，同时保留站内消息记录；不再额外发送微信通知。

优惠券即将过期默认仅做站内提醒，不主动发送营销性质微信通知。

## 8. 消息跳转

消息必须尽量直接跳到对应业务页面：

- 预约消息 → 预约详情
- 洗护 / 美容完成 → 服务结果页
- 寄养消息 → 寄养时间轴 / 寄养详情
- 商品消息 → 商品订单详情
- 优惠券到账 → 我的优惠券
- 余额变动 → 余额明细
- 投诉审核、商家回应、补证、裁决及申诉消息 → 对应投诉详情
- 当前食用品牌风险提醒 → 对应食品投诉 / 风险详情（按第13节重新校验可见性）
- 上门喂养状态 → 对应需求详情 / 本人的发布或接单记录
- 积分兑换、实物发货／领取结果、取消返还 → 对应积分兑换详情 / 积分明细

消息目标必须由服务端关联业务校验，不可信任客户端传入的门店或业务 ID。平台业务详情不因关联门店不同而自动切换当前门店；进入门店私有业务详情时，先以该业务所属门店解析上下文并校验当前 User / Customer 权限，再整体切换门店数据。消息本身不能授予该门店权限。

从微信通知或外部入口打开时，启动封面、登录 / 手机号验证完成后仍须恢复原消息目标，规则见 `03p`、`03g`。目标已取消或结束时展示其真实历史状态；目标不可见、失效或无权限时显示明确提示及返回消息入口，不返回一个看似成功但无关的首页，也不泄露其他客户信息。

### 8.1 平台业务消息事件

| 业务事件 | 接收对象 | scope | 站内结果 / 跳转 |

客户端与店员端的全部小程序通知，等级统一只有**普通通知、重要通知**。等级复用F-MSG-012 `message_priority`，不新增同义等级字段或第三档。业务类型仍用F-MSG-007 `message_type`，预约、商品、钱包、投诉等类型及原消息作用域、权限、单一时间流规则均保留；业务风险严重程度、工作台分组不等于通知等级。

### 重要通知

已明确的事件包括：预约改时间、服务完成、寄养异常、商品确认／取消、当前食用食品品牌出现新的公开投诉风险。

- 按原事件规则生成站内消息。
- 食品品牌风险提醒必须生成站内消息；微信在用户已授权且渠道可用时按事件配置尝试发送。
- 重要等级本身不强制微信／短信、重复催办或重开任务；当前阶段业务短信按§13.2暂未开放，不发送。

### 普通通知

包括：服务开始、商品完成、充值完成、优惠券到账、一般投诉状态更新、普通寄养动态、优惠券即将过期。

- 服务开始等事件生成站内消息，微信仍按具体事件决定。
- 普通寄养动态、优惠券即将过期沿原规则仅站内消息或业务页面提示，默认不主动微信通知；过期提醒仍为可选，不新增短信或营销。
- 既有较低一档的当前等级统一归入普通通知；已有历史原始审计保留，后续展示／取数映射到两档，不再产生第三种当前等级。

通知等级、业务类型、发送渠道、已读及待办是否完成分别判断。新增事件未明确等级、渠道或业务动作时继续待确认，不能仅按名称猜成重要／普通或自动开放发送。食品原投诉的后续普通通知／重要通知按§13.3.2，不据此将最初的新公开投诉风险提醒降级；重新知悉／误点恢复是操作，不是第三类通知。

## 11. 微信通知失败处理

微信通知发送与正式业务状态必须解耦。

例如服务完成后：

1. 服务订单正常进入完成状态。
2. 生成站内消息。
3. 尝试发送微信通知。
4. 即使微信通知失败，订单和服务状态也不得回滚。

后台记录发送结果及失败原因，用于审计和问题排查。

客户未授权或无法接收微信通知时，站内消息、订单状态、服务结果、食品品牌风险提醒等功能仍应正常工作。

## 13. 投诉与风险反馈消息

消费争议模块继续复用统一消息中心，不建设用户与门店的即时聊天。

投诉相关至少支持以下消息：

- 当前宠物食用品牌出现新的公开食品投诉风险提醒；
- 基础内容审核通过 / 退回修改 / 拒绝；
- 商家已提交正式回应；
- 商家回应后 3 天补证期开始及必要到期提醒；
- 平台已经作出成立 / 部分成立 / 证据不足 / 现有证据不支持结论；
- 平台明确确认后，处理状态变为已解决；
- 申诉进入处理或申诉结论更新。

门店首次正式回应由服务端成功受理后自动进入双方共用3天补证期，相关通知读取实际首次回应及evidence_window_ends_at；原待回应提示切换为补证截止／真实剩余时间，历史逾期保留，见04§6.1.2。不因点击提交、失败、换员工、追加说明／材料或通知重试再开窗口；同一状态事件重试不重复通知。补充记录保留原回应，不据此认定已解决；不新增每次补充必发短信的规则，短信频率／预警阈值仍按后续通知设计收口。

### 13.1 当前食用品牌风险提醒

当一条宠物食品投诉满足以下全部条件时，服务端立即创建品牌风险站内消息：

1. 投诉已经通过基础内容审核并进入公开状态；
2. 投诉对象已经绑定稳定标准 `brand_id`；
3. 当前 Platform User 至少有一只未归档宠物的“当前食用品牌”与该 `brand_id` 一致。

通知规则：

- 站内消息为必需渠道；消息创建不依赖微信通知是否成功；
- 用户已授权且微信渠道可用时，可同时尝试微信订阅 / 服务通知；
- 同一 `Platform User + complaint_id` 只生成一条品牌风险提醒，不因多只宠物或重复回调重复通知；
- 一条提醒可列出受影响宠物摘要；
- 点击提醒直接进入对应食品投诉 / 风险详情；
- 用户自定义品牌尚未归一到标准品牌时，不进行不可靠的模糊投诉推送；
- 通知文案必须使用“出现新的投诉 / 风险反馈”等中性表达，不得在平台裁决前写成“该品牌已确认有质量问题”。

“第一时间通知”指在投诉基础审核通过并公开这一可信触发事件发生后立即创建系统消息；外部微信渠道的实际到达时间受用户授权、平台接口和网络影响，不作为投诉业务状态成功的前提。

消息点击进入对应投诉详情，并重新校验当前 User 是否为投诉人或该内容本身是否属于公开可见范围。

公开投诉本身不意味着向任意门店公开投诉人的手机号、微信、会员资产、订单等其他个人业务数据。

商家回应、第三方佐证与平台裁决都发生在正式投诉对象中，不通过私聊消息修改事实状态。

第三方佐证入口按03h§7.1使用门店分享的邀请卡片，指向原争议，不是新建私聊／群聊或新增短信邀请渠道。卡片和后续读取只含当前公开内容，不携联系方式、内部备注、未脱敏原件或后台记录；分享／打开不代表已提交。登录／必要手机号验证后恢复原佐证目标并复查原截止；重复分享、消息送达／已读、验证或重试均不再起3天、不产生多份佐证。到期停止新增／追加，原目标仍可读取当前允许公开的内容；平台审核通过前不显示为已公开或已采信，不因本次确认新增佐证短信频率／模板。

邀请撤回按03h§7.2：已转发卡片的副本在读取／首次提交时查询同一原邀请状态，不靠撤回微信消息或静态卡片按钮实现。撤回后该卡片只失去新建佐证入口，公开内容仍可读，其他有效邀请不受影响；已提交佐证保留、实际作者在原窗口仍可追加。撤回不把已提交／已审结果改写成未提交／无效，也不因此新增短信或自动通知渠道；消息送达／已读、重复操作和再次邀请不重置期限。

是否已解决按03h§6.1由平台有权人员明确确认，只有服务端成功保存对应解决状态后才生成已解决消息；门店／顾客提交处理情况、表示同意或已读，及回复／退款／事实裁决均不触发自动结案消息。平台确认失败不假发成功，同次事件重试不重复；通知失败不回滚真实状态。解决状态变化不覆盖事实结论、清除逾期或更改原7天／3天截止，不新增短信频率／催确认时限。

提交处理情况按03h§6.2单列handling_progress用途，不当作商家首个正式回应、重新补证、已解决或线下退款到账事件；不重置7天／3天、不触发自动结案／收退款消息。未审／未公开原文与附件只允许该条实际提交者及平台有权人员读取，消息／分享／摘要／附件引用／缓存不能向投诉对方、其他店员或老板夹带私有内容；公众读取只用已审核脱敏的公开副本，不能回退原件。该更新是否另发站内提醒及其频率后续收口，本次不新增短信渠道、群发或催办默认值。

消费争议工作台按04§3.2.1派生同一原complaint_id的一张当前卡：待回应→逾期待回应移异常→回应后补证中回待处理；补证结束无门店需办时移出，有真实补材料要求再显示，平台确认已解决后移出。消息送达／已读／重试、换员工或提交处理进展不新增重复卡、不自动完成仍需办理事项，跨天不清空。移出不删除消息或原争议，不写成已回应／已解决，不影响独立食品风险待办；短信当前暂未开放，未来发送规则待确认；提前预警仍待确认。

详细状态与 7 天 / 3 天规则见 `03h-customer-risk-feedback.md`.

“已知悉”只表示门店收到并了解本提醒，不表示食品安全、厂家已回应、投诉成立／不成立或已解决；不替门店正式回应，不修改7天／3天截止、投诉裁决／解决状态、品牌风险信号／热度，也不自动停卖、退款、变更余额／库存。反过来，消费争议卡移出、平台确认投诉已解决或通知已读也不自动写该提醒已知悉。未完成且仍需知悉的提醒跨天保留，不按午夜清空；新投诉仍按原触发与归属规则独立承接，不因同品牌旧提醒已知悉而永久忽略。原投诉普通通知／重要通知和误点恢复按§13.3.2执行；其他已知悉后备注更正、已派后改店／多店及平台具体界面仍待确认，重复通知不作为复活理由。

3. **误点恢复**：本店老板／任一当前有效员工可将当前已知悉提醒恢复“待知悉”，无需审批、不限原确认人，原因选填。成功后开新轮并回原工作台位置，原操作／备注仍为历史，不篡改为从未知悉；已待知悉时重复恢复不再开轮。同一请求重试返回原结果，不重复恢复或覆盖首次恢复事实；其他已知悉后直接改备注的方式仍待确认。
