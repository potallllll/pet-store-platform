## 1. 文档职责

本文件取代原“宠物交友”模块，负责当前客户端以下能力：

- 宠物食品争议 / 风险反馈；
- 附近宠物门店争议 / 风险反馈；
- 顾客对门店或宠物食品提交投诉；
- 门店回应、举证、邀请第三方顾客佐证；
- 平台内容审核、事实裁决、异议联系客服和证据留痕；服务履约风险记录申诉另按§10.1.3。
- 同一食品同一批次的集中反馈风险提示；
- 平台批量人工审核工作流；
- 门店私有顾客风险备注与跨店“顾客风险”的边界；“顾客风险”统一承载顾客相关事件和宠物相关服务安全事件，不再设置第二个“宠物行为与服务安全”跨店分类。

原 `docs/03h-customer-pet-social.md` 已归档至 `docs/history/`，不得继续作为当前产品或实现依据。

本模块不是“谁差评多谁有罪”的排行榜。投诉首先是用户事实主张；商家回应、第三方佐证、平台数据与其他证据共同进入核验，最终事实结论由平台审核员作出。

## 2. 客户端入口与对象

原首页“宠物交友”位置改为消费争议 / 风险反馈入口，至少提供两个一级分类：

1. **附近门店**
2. **宠物食品**

### 2.1 附近门店

用户可查看附近宠物门店的公开投诉 / 差评反馈和处理状态。

公开信息至少区分：

- 用户原始反馈；
- 商家回应状态；
- 平台核验结论；
- 是否已经解决。

不得在平台尚未核验时把用户主张写成平台事实结论。

### 2.2 宠物食品

用户可搜索 / 查看宠物食品风险反馈。

食品投诉的数据对象不能只有自由文本商品名。后续数据模型至少需要能够区分：

- 品牌；
- 商品主体；
- SKU / 规格；
- 批次 / 生产批次信息（用户可提供时）。

同一商品不同批次不得默认合并为同一质量事实。

### 2.3 宠物当前食品品牌与风险订阅

宠物档案可记录当前食用的宠物食品品牌，用于建立“正在食用 → 相关投诉提醒”的明确订阅关系。

- 标准品牌必须使用稳定 `brand_id` 关联，不以展示文本做唯一匹配；
- 品牌列表没有时允许选择“其他”并填写原始品牌名称；
- 自定义品牌可通过平台别名 / 品牌归一规则映射到标准品牌；
- 不能可靠归一时保持待识别状态，不得用模糊相似度强行推送风险；
- 一条新食品投诉通过基础内容审核并公开后，服务端按标准 `brand_id` 查找当前仍在食用该品牌的宠物主人；
- 同一用户即使有多只宠物匹配，同一 `complaint_id` 只提醒一次；
- 站内消息立即创建；微信渠道仅在已授权且可用时追加尝试；
- 通知只表达“出现新的投诉 / 风险反馈”，在平台事实裁决前不得写成已确认质量问题。

宠物品牌编辑细节见 `03b`，通知渠道见 `03f`。

### 2.4 已确认的跨端职责与入口

- 客户端投诉入口为“我的 → 投诉与建议”；首页“消费争议”用于浏览附近门店与宠物食品的公开争议信息。“建议”的分类、处理与关闭流程尚未确认，不得直接套用公开投诉流程。
- 门店正式回应在店员端处理，不放在客户端。争议门店所有在职且账号 / 门店关系有效的员工均可提交本店正式回应，老板同样可回应；不要求另行指定少数回应人员，不因此获得跨店操作或平台裁决权。原回应不可覆盖／删除，3天补证期内可由本店老板／任一有效员工追加说明或材料，无草稿、无需审批或原经办人操作，见04§6.1.2；第三方邀请人员及邀请人可见范围已按04§6.1.3确认，被邀请人的查看／提交6项按本文件§7.1已确认，邀请撤回按§7.2已确认，其余未决细分不因此开放。
- 食品投诉／食品风险由平台管理员先联系涉事门店核实，确认后再联系相关厂家，调查与厂家沟通由后台处理；邮件仍按客服工作职责发送，客服是工作职责描述，不据此新增系统角色。厂家真实回信由管理员在平台Web后台关联原食品投诉录入并保留来源、原文／附件和录入审计，不由店员录入，也不得冒充厂家账号直接提交。投诉对象明确为门店销售或门店处理行为时，该争议门店须按原规则在7天内正式回应；对象仅为品牌、厂家或产品质量时，不给门店生成7天正式回应待办，只生成食品风险提醒／已知悉。一个投诉同时涉及门店与厂家时拆分处理：门店只回应涉及本店的部分，品牌／厂家部分由后台处理，各自状态和期限独立。厂家未回复时显示“厂家暂未回应／平台核查中”，不得记成门店逾期或默认认定投诉成立；任何一方回应都不能自动结案，事实与解决状态仍由平台决定。
- 店员不能新增、修改或删除宠物当前食用品牌，也不能维护食品品牌／厂家主资料；只有本店原本有权查看该顾客／宠物资料的老板和有效员工可读取。未填写时显示“主人暂未填写”，信息可能过期时只引导顾客在客户端更新，不提供代填。寄养本次粮食品牌只属于本次寄养资料，商品购买和跨店历史导入均不得自动覆盖主人维护的当前品牌。
- 给宠物主人的食品品牌风险提醒在明确争议门店时另行形成该店独立待办，不是主人消息副本。按03f§13.3已确认：无明确门店时平台承接原案、暂不派店；之后平台有事实依据明确争议门店再生成该店待办，同案同店不重复，不推给主人当前店或全部关联店。主人提醒不受暂未派店影响；后台调查按先联系涉事门店、确认后再联系相关厂家的顺序，真实回信由Web后台录入；派发不认定门店责任，不改变食品正式回应待决映射。门店知悉操作按03f§13.3.1已确认：本店老板／有效员工均可，无领取转交审批；看品牌／公开风险及当前核验状态，顾客宠物限原权限，明确点已知悉后移出工作台并留历史、备注选填，不强制全员联系或上传证明。知悉不改变投诉／食品安全结论；普通通知／重要通知与误点恢复按03f§13.3.2已确认；已派后改店／多店、备注纠错的平台处理契约及平台界面等仍待确认。
- 当前阶段投诉提醒与逾期处理不发送短信，相关短信入口／状态显示“暂未开放”，不排队、重试或以后自动补发；站内消息及已授权且可用的微信通知保留。未来如开放，接收方向仍为争议门店注册号码，需另行确认发送规则，见03f§13.2。未开放不阻断原系统通知与正式回应、补证、逾期、裁决规则。

## 3. 用户投诉提交

用户可以针对：

- 宠物门店；
- 宠物食品；

提交投诉 / 风险反馈。

### 3.1 最低提交要求

允许**仅提交文字**，不强制上传图片、视频、订单或其他证明。

无附件不等于投诉无效，但公开页面必须把它表达为“用户反馈 / 用户陈述”，不能因为已经公开就显示“事实成立”。

用户可在后续流程补充：

- 图片；
- 视频；
- 聊天记录；
- 订单 / 付款材料；
- 其他证据。

### 3.2 同一食品同一批次重复投诉

同一 `Platform User + product + batch` 已存在未终结投诉时，不允许创建第二条未处理投诉。

客户端固定提示：

> 已有投诉未处理

并引导进入原投诉补充文字或证据。

同一用户在同一统计窗口内默认只贡献 1 个独立投诉单位。

投诉已经最终裁决 / 解决后，同一用户何时可以再次针对同一批次创建新投诉，仍由 `DEC-COMPLAINT-08` 确认。

## 4. 投诉状态机与公开规则

投诉不能用一个模糊 `status` 同时表达内容审核、商家回应、事实结论和解决情况。至少分开保存：

- workflow_status：流程所处阶段；
- business_response_status：商家回应状态；
- decision_status：平台事实核验结论；
- resolution_status：是否已解决；
- 消费争议不设小程序申诉状态／提交入口，原complaint_appeal_status退役仅保留历史；异议提示联系客服。

### 4.1 提交与基础内容审核

主流程：

`draft`
→ `submitted`
→ `pending_content_review`

基础内容审核至少检查：

- 是否泄露手机号、微信、家庭地址等无关隐私；
- 是否存在明显辱骂、威胁、人肉；
- 是否能够识别投诉对象；
- 是否明显属于广告、垃圾内容；
- 是否需要升级人工审核。

基础审核结果至少支持：

- `rejected_content`
- `needs_revision`
- `pending_business_response`

### 4.2 审核通过后立即公开

已确认：

**投诉通过基础内容审核后立即公开。**

公开时默认表达：

- 用户反馈；
- 商家回应：待回应；
- 平台核验：尚未核验。

不得在平台裁决前显示“投诉成立”“门店已确认有问题”“食品已确认存在质量问题”等结论。

### 4.3 7 天商家回应规则

7 天是**正式回应期限**，不是事实成立期限。

计时应在以下条件完成后开始：

- 基础内容审核通过；
- 投诉对象识别正确；
- 对已入驻可回应主体完成系统通知；
- 系统生成 `response_due_at`。

平台自身审核耗时不得占用商家的 7 天回应期。

正式回应至少包含：

- 回应立场：认可 / 部分认可 / 不认可 / 无法确认；
- 正式回应文字；
- 证据可选。

门店选择立场并填写文字后直接提交，不设回应草稿；图片／视频等证据选填。服务端成功受理的原回应（立场、正文、附件及首次回应时间）保留，不提供覆盖编辑／删除；后续说明或材料在本节有效补证期内逐条追加，权限与提交一致性见04§6.1.2。

仅点击“已阅”、空内容、表情、私下电话或者只邀请第三方但门店自身不回应，不算正式回应。

7 天到期仍未正式回应：

- 标记 `business_response_overdue`；
- 记录逾期时间；
- 公开显示“商家逾期未回应”；
- 可进入平台裁决队列；
- **不得自动判定投诉成立。**

商家逾期后仍可补交回应；历史逾期事实继续保留。若平台已经作出最终裁决，后续异议提示“如有异议，请联系客服处理”，不提供小程序申诉／复议提交、申诉状态或申诉消息，也不无痕覆盖原结论。

店员端应将“请在7天内正式回应”作为重点信息，在工作台争议待办卡片、业务消费争议列表及详情顶部展示，并紧邻显示同一response_due_at具体截止与按服务端时间计算的真实剩余时间；不是每次打开重新给7天。逾期突出“已逾期，仍需正式回应”，不推导投诉成立；已正式回应后展示实际补证阶段，不继续假报待回应。期限重点展示按04§6.1.1，工作台归组／去重／移出按04§3.2.1，列表四组／筛选／历史按04§6.1.8。食品投诉仅明确涉及门店销售／处理行为的门店部分使用本期限，品牌／厂家后台部分不生成门店逾期。

### 4.4 商家回应后的 3 天补证

已确认：

**商家提交首个正式回应后，投诉双方统一获得 3 天补证期。**

首次正式回应由服务端成功受理后，同次记录首次回应时间、已回应状态及补证阶段／截止；原待回应事项自动转为补证信息。店员端相关卡片、业务列表及详情顶部突出evidence_window_ends_at具体截止与真实剩余时间，历史逾期保留，不再显示尚未正式回应。工作台同一卡片按04§3.2.1改为补证中并回到待处理；补证结束且无需门店办理时移出，仅有平台明确补材料要求等真实需办事项时再按原争议显示，不因仅等待平台长期占卡。重复请求或多人并发不得覆盖原回应或再开一轮；后来的首次提交提示已有回应，不能静默当作补充。

本店老板／所有账号及任职关系有效的员工均可在有效窗口内追加说明或材料，无老板审批、不限原经办人；逐条关联原投诉并保留提交人和时间，复用F-EVD及审计。补充不覆盖原立场／正文／附件，不重置首次回应时间或原3天截止；媒体选填不等于跳过原有内容审核／隐私边界。

补证期内允许：

- 投诉人补充材料；
- 商家补充材料；
- 商家邀请第三方顾客提供佐证；
- 平台关联自身订单 / 预约 / 退款 / 服务事实；
- 平台按需要要求进一步材料。

补证期结束后进入 `pending_platform_decision`。

平台主动要求补材料形成的额外期限必须单独记录；不能静默修改原 3 天规则。

§6.2的“提交处理情况”是实际处理进展：平台尚未确认解决时可在原补证期后追加，但不重开原补证窗口、不把裁决异议当普通补证重新受理。门店正式回应、原争议证据及第三方佐证仍分别执行原门槛与截止，不因处理进展入口放宽。

## 5. 平台裁决

### 5.1 谁可以判定

投诉人只能提出主张。

被投诉门店 / 品牌只能回应和举证。

第三方顾客只能提供佐证。

AI 可以用于内容分类、摘要、重复检测和风险提示，但 V1.0 不单独作出“成立 / 不成立”裁决。

已确认：

**所有案件均允许由 1 名持有平台投诉裁决权限的审核员独立作出结论。**

建议权限键：

`complaint_review.decide`

审核员必须记录：

- 审核人；
- 审核时间；
- 裁决理由；
- 所依据的关键证据；
- 被拆分事实点的逐项结论。

允许审核员主动升级复核，但不设置“严重案件强制双人裁决”硬规则。

### 5.2 平台事实结论

至少支持：

- `established`：成立；
- `partially_established`：部分成立；
- `insufficient_evidence`：证据不足；
- `not_supported`：现有证据不支持。

“证据不足”不等于投诉人撒谎，也不等于商家已经证明无责。

### 5.3 事实点拆分

一个投诉可以拆为多个可判断事实点，不能强制整篇投诉只有“真 / 假”一个结果。

例如：

> 美容师把狗剪伤了、拒绝承认、还多收 100 元。

可拆为：

1. 是否发生剪伤；
2. 是否存在拒绝处理；
3. 是否实际多收 100 元。

各事实点可以分别得到成立、证据不足或不支持，最终形成“部分成立”。

## 6. 是否解决与公开排序

- `established + resolved`
- `partially_established + resolved`
- `insufficient_evidence + resolved`

已确认：

排序固定：

1. 未解决投诉整体优先；
2. 未解决投诉内部按时间倒序，越新越靠前；
3. 已解决投诉整体排在未解决投诉之后；

2. **只影响该卡片新建佐证**：撤回成功后，该邀请卡片不能再用于新建一份佐证，仍可读当前允许公开的争议内容；其他有效邀请不受影响，不将该顾客拉黑、关闭整条争议或撤回同店全部邀请。原卡片多次转发仍是同一邀请，撤回对这些副本一致生效；使用另一有效邀请首次提交仍须满足原身份、状态与截止校验。
3. **既有佐证与追加不受撤回阻断**：已成功提交的原文、附件和记录保留，不因撤回邀请删改、下架或假记为无效，不改变原平台审核结果。该实际作者仍可在原3天有效窗口内明确追加；服务端依据既有佐证与当前User／原投诉授权，不再把原卡片仍有效设为追加前提。其他人不能借该例外新建佐证、冒用作者或查看其非公开材料；撤回也不延长补证期。
4. **并发／重复与再次邀请**：撤回与通过该卡片新建某位顾客首份佐证，须由服务端校验同一最新邀请状态并协调受理顺序，以先成功的操作为准。撤回先成功，该卡片首次提交被拒绝；首次提交先成功，佐证保留，随后撤回仍只阻止该卡片后续新建，不阻止该作者合法追加。不能只禁用前端按钮或按页面点击时间判定。首次提交已成功但响应丢失时，同次请求重试返回原成功结果，不因其后撤回改报失败或重复创建；新的首次提交仍校验当前邀请状态。重复撤回返回原结果，不重复事件／审计业务效果，也不覆盖原撤回时间／人／原因。再次邀请不修改原撤回记录、不重新启动3天；是否可提交始终沿原evidence_window_ends_at。

字段唯一归属：F-EVD-012 witness_invitation_id标识一张逻辑邀请卡片，F-EVD-013 witness_invitation_complaint_id关联原complaint_id；本店归属由原投诉target_store_id判定，不新增卡片所属门店副本。F-EVD-014 witness_invitation_withdrawn_at记录第一次实际撤回成功的服务端时间；撤回人、前后值、选填原因及幂等请求复用F-AUD-002～011，首次提交审计关联实际使用的邀请与证据记录。withdrawn_at不是证据删除时间、公开失效时间或补证截止，不新建另一套邀请3天期限。历史摘要按原业务权限展示，不因此向员工／顾客开放原始审计。

本节不改变平台审核／脱敏或证据权重等剩余待决；食品投诉门店与品牌／厂家分工按§2.4，仅对已明确归属争议门店的门店部分邀请执行，不据此猜测食品主体对应门店。

## 8. 食品同批次“出现集中反馈”

### 8.1 硬触发门槛

已确认：

同一食品 + 同一批次，在**最近 2 天滚动窗口**内，必须实际达到至少 **3 条独立投诉**，才显示：

> 出现集中反馈

3 条是硬门槛。

不得：

- 将 2 条跨门店投诉通过加权折算成 3 条；
- 将 1 条严重投诉折算成多条；
- 使用风险分绕过独立投诉数量门槛。

### 8.2 不同门店来源加权

达到 3 条硬门槛后，再计算来源分散度。

来自不同门店 / 销售来源的独立投诉应提高：

- 风险优先级；
- 风险列表排序；
- 平台审核队列优先级；
- 后续内部风险等级（如启用）。

具体权重系数尚未冻结；但加权与门槛判断必须是两个独立步骤。

### 8.3 not_supported 仍计入集中反馈

已确认：

即使单条投诉最终被判定为 `not_supported`，仍不从“近期反馈数量”中剔除。

因此“出现集中反馈”只表达：

> 近期出现多起独立投诉 / 反馈。

它不表达：

> 近期出现多起已成立投诉。

数据层应分别统计总反馈、成立、部分成立、证据不足、不支持等数量，避免公开文案混淆。

### 8.4 风险提示有效期

已确认：

“出现集中反馈”风险提示自生成后保留 **2 个月**，到期自动解除公开提示。

历史投诉、聚合记录和审计记录继续保留。

提示有效期内若再次出现新的 2 天 / 3 条集中反馈，是否重新计算 2 个月，受 `DEC-COMPLAINT-07` 阻塞，当前不得自行实现滚动续期。

### 8.5 对外措辞

自动提示只允许表达：

> 出现集中反馈

不得自动写成：

- 该批次存在质量问题；
- 该食品有毒；
- 已确认产品缺陷；
- 已确认厂家责任。

### 8.6 问题热度

宠物食品投诉列表与详情必须展示 **问题热度**。

问题热度是“该问题当前被关注 / 反馈的活跃程度”展示指标，不等于投诉成立概率、产品危险等级、事实严重程度或平台裁决结果。

前端不得自行根据投诉条数拼出热度值，必须使用服务端返回的热度展示结果。服务端计算可以考虑近期独立投诉数、时间衰减、来源分散度、未解决反馈等信号，但具体数值范围、计算公式、信号权重、更新频率以及最终显示纯数字 / 等级 / 组合，仍由 `DEC-FOOD-HEAT-01` 冻结。

在该决策关闭前，H5 / 视觉原型可以使用明确标注的 Mock 数值演示视觉，例如“问题热度 86”，但不得把该数值或公式写成生产业务规则。

## 9. 平台批量审核工作流

需要平台审核后才能公开 / 跨门店共享的记录，可以先采用批量审核方式：

> 待审核队列 → 下载 XLSX / CSV → 审核员在审核列批注 → 上传 → 系统预检查 → 审核员确认 → 批量落库

### 9.1 导出原则

每条必须存在稳定 `review_item_id`，不能以 Excel 行号定位。

导出至少包含：

- review_item_id
- review_batch_id
- row_version
- submitted_at
- submitter_merchant_id
- submitter_store_id
- target_type
- target_id
- content_type
- submitted_value
- source_type
- source_business_id（如有）
- evidence_count
- current_review_status
- last_updated_at

原始业务字段视为只读。

### 9.2 审核员填写列

至少可包含：

- reviewer_decision
- approved_value
- reviewer_reason_code
- reviewer_comment
- visibility_scope
- effective_until
- severity_level
- require_followup
- followup_note

### 9.3 上传安全

- 以 `review_item_id` 定位；
- 校验 `row_version`；
- 导出后原记录已变化则该行冲突，不覆盖；
- 已由其他审核员处理的行不得再次覆盖；
- 同一文件重复上传必须幂等；
- 上传先预检差异，再确认执行；
- 支持部分成功 / 部分失败并逐行返回结果；
- 原始提交内容、审核前后结果和上传批次永久可追溯。

多审核员默认采用乐观并发，不因某人下载文件就锁死全部待审核记录。

## 10. 双向风险信息

### 10.1 顾客风险：主观备注与跨店共享分层

已确认产品原则：

> **共享客观风险事件，不共享主观人格评价。**

单个 Merchant 可保留本店内部自由备注，例如沟通习惯、服务过程备注；这类主观备注默认不得跨商户共享。

跨门店层统一称为**顾客风险**，内部按风险对象明确区分“顾客相关”或“宠物相关”；宠物相关记录必须关联具体宠物。跨店层只能考虑标准化、可核验、可申诉的客观风险事件，例如：

- 多次预约未到且未取消；
- 服务完成后拒绝支付已确认费用；
- 有明确记录的辱骂 / 威胁事件；
- 已核验的恶意退款 / 毁损事件。
- 宠物在真实服务中发生的挣脱、咬人／抓伤、护食或明确服务安全事件。

不得跨店传播：

- 脾气差；
- 事多；
- 难搞；
- 爱投诉；
- 不讲理；

等主观人格标签。

已确认的门店授权与匹配规则：

- 来源门店先授权共享本店顾客风险提醒；未授权门店的本店风险提醒不进入跨店共享范围。
- 查看门店也必须已经授权参与共享。双方门店授权有效、顾客已单独同意共享服务履约记录时，按顾客手机号或微信号匹配；任意一种匹配即可查询对应可共享风险提醒，不要求两种同时匹配，也不要求顾客先在查看门店完成小程序绑定。
- 查询必须由新增顾客、确认预约等已确认的真实门店业务动作触发，并稳定关联当前Customer创建／预约处理对象。不得提供脱离业务对象、可任意输入手机号或微信号的独立查询页、批量查询、导出或试探接口；不得通过循环创建空业务对象绕过该限制。
- 服务端必须同时校验来源门店授权、查看门店授权、顾客对应分项同意、当前员工与门店关系及业务对象关联；前端显示或隐藏入口不能代替这些校验。查询额度按“查看Store + 同一顾客／标准化身份 + Asia/Shanghai自然月”计算，每个自然月最多3次，店内所有员工共享该额度。手机号与稳定微信身份能唯一指向同一Platform User时必须合并到同一主体额度，不能换标识重置。进入身份匹配服务的成功、无匹配和冲突查询均计数；相同 `related_request_id` 的网络重试不重复计数。达到3次后，本自然月拒绝新的匹配查询，不能换员工、重复建空Customer或改入口绕过。
- 每次查询都记录操作者、查看门店、业务对象、标准化身份指纹、自然月、请求时间、结果类别和请求标识；继续按员工和门店监测连续换号、批量命中／未命中等异常模式。每月3次是同店同顾客额度，不替代跨顾客批量枚举告警和临时风控阻断。
- 无授权、无同意、无匹配、标识冲突、达到限额或查询失败时，不向调用方返回可用于判断其他门店是否存在该顾客／风险记录的差异化原因；对外仅提供完成当前业务所需的最小结果。匹配仅开放可共享的顾客风险提醒，不开放来源门店的订单、会员余额、消费记录或内部主观备注；不据匹配结果合并客户账号或转移客户关系。03g的私有资料读取／身份绑定规则继续适用于那些资料。
- “微信号”不能解释为微信昵称；应使用平台可验证的稳定微信身份映射。手机号和微信身份分别归一并保留验证状态；具体采集技术可在账号设计阶段实现，但不得把昵称、模糊姓名或相似号码当作匹配标识。
- 门店参与共享授权与顾客同意共享相互独立，不能互相代替。顾客端名称和分项选择按§10.3执行；未取得服务履约记录共享同意时，不因门店已授权或标识匹配而开放该类跨店提醒。保存期限按§10.1.4执行；当前预约确认的阅读提醒、不自动拒单及共享提醒不可用可直接继续已按04§3.7／6.5.1确认，适用于新老顾客的已确认新增／预约流程，无门店资料真实性核验或人工核对门槛，不绕过共享鉴权；其他未决自动业务影响仍受 `DEC-RISK-01` 阻塞。已确认的授权撤回、冲突处理、无条件申诉、月度限额、业务关联、服务端校验、最小披露、审计和异常告警原则不得回退。
- 共享内容继续遵循客观风险事件、不共享主观人格评价的规则；本次不改变既有内容审核要求，也不扩展为全部顾客资料共享。

#### 10.1.1 已确认：授权撤回

- 来源门店、查看门店和顾客均可撤回自己作出的授权／分项同意，不要求说明理由，也不得以已有投诉、预约或会员关系阻止撤回。
- 撤回经服务端确认后立即生效：来源门店撤回时，其记录不再进入新的跨店结果；查看门店撤回时，该店停止新的跨店查询；顾客撤回服务履约记录同意时，所有查看门店停止获得该分项。
- 撤回后立即失效缓存和继续展示权限，但不能让已经看过的人“忘记”，也不删除查询审计、申诉材料和真实订单／服务／争议事实。已发生业务不因撤回自动取消、退款或改判。
- 再次开启必须重新明确授权／同意并记录新时间，不能静默恢复旧授权。撤回前已使用的月度次数不返还、不重置。

#### 10.1.2 已确认：手机号／微信身份冲突处理

- 手机号与稳定微信身份都唯一指向同一Platform User时正常匹配；只提供其中一种且能唯一、安全匹配时，继续遵循“任一匹配即可”的既有规则。
- 两种标识分别指向不同主体、任一标识对应多个候选、号码存在换号／回收疑点，或验证状态过期时，统一进入 `identity_conflict`，不得自动选择其中一个、拼接记录、合并Customer或展示任何跨店风险结果；该次查询仍计入月度额度。
- 冲突生成平台审核项，由持有平台审核权限的管理员处理，门店员工不能自行解除。解除冲突必须取得当前手机号所有权验证、当前微信登录身份或账号恢复流程等可核验证据；仅凭某门店口头确认、姓名相似或历史昵称不得通过。
- 核验成功后只更新标识到Platform User的安全映射，不能改写原风险事件、原Customer归属或历史查询日志；证据不足时保持冲突状态。处理期间店员端只显示统一的“共享提醒暂不可用，可继续”，不得暴露冲突来自哪个门店或哪类记录。平台冲突核验仍继续，当前新增／预约可依04§6.5.1直接继续、不要求门店核验资料；继续不解除冲突或开放共享取数。

#### 10.1.3 已确认：无条件申诉

- 被服务履约记录指向的当事顾客可随时申诉，不设费用、次数、距事件时间、先联系门店、先完成赔付或先取得门店同意等准入条件。
- 系统只校验申诉人与记录主体的关系以防冒名；身份核验不能被扩展为业务门槛。提交后必须受理并生成可追踪的申诉记录，重复内容可关联同一审核案，但不得以“重复”为由拒绝接收；已有结论后再次提交也必须保留新一轮申诉记录。
- 无条件申诉不等于自动申诉成立、自动隐藏记录或自动改判。审核期间标明“申诉中”，由平台审核员依据证据作出维持、更正或撤销共享结论，并记录理由、证据、审核人与时间；来源门店和查看门店均不能自行裁决。
- 顾客端不提供风险记录列表、详情、存在提示或申诉状态页；已审核和未审核记录的存在、状态、摘要、原文、证据和来源门店均不向顾客展示，也不因此发送消息。顾客通过其他途径得知或主动提出异议时，仍可直接联系客服无条件申诉；平台按身份关系定位记录，不以顾客先看见记录为受理条件。

#### 10.1.4 已确认：保存期限与到期动作

“保存期限”不是“顾客撤回授权后是否还能继续查询”的同义词；撤回仍按§10.1.1立即停止新共享，不等待以下期限届满。保存规则固定为：

- 客观风险事件首次形成可跨店共享的平台结论并生效后，跨店展示期为12个月；到期时立即从新的查询结果、店员弹窗和详情中的跨店区域移除。申诉提交、审核中、维持原结论或普通文字更正均不暂停、不重新计算也不延长原12个月；平台撤销共享结论、顾客撤回分项同意或来源门店撤回共享授权时更早停止该事件的全局跨店展示。查看门店撤回参与授权只停止该店查询，不改变其他合法门店的展示截止。新的独立客观事件必须新建记录，不能续期旧记录。
- 原始事实、证据、平台审核过程与结论在跨店展示结束或该记录最后一轮申诉办结后保留3年，取较晚时间；期间仅向履职所需的平台审核／合规人员开放，不继续作为门店跨店查询结果。
- 有效门店授权和顾客分项同意在有效期间保留；撤回、替换或失效后，其授权／同意记录及操作审计保留3年。查询日志从每次查询发生时间起保留3年；身份冲突材料与处理日志从冲突办结时间起保留3年，尚未办结时不得因达到3年自动删除。
- 每轮申诉的内容、证据和处理结果从该轮申诉办结时间起保留3年；后续再次申诉会形成新记录，并按新一轮办结时间单独计算。即使旧材料已按期处置，系统仍须接收无条件申诉并如实说明当前可用证据，不能以事件较早为由拒绝提交。
- 3年期满后，对不再依法或业务必需的原始媒体、个人信息及操作明细执行删除或不可逆匿名化，并保留最小化的到期处置审计；不得继续给门店查看。依法或独立业务规则必须保留的订单、支付、财务、正式服务和安全审计事实继续按其自身期限保存，但不能借此恢复跨店展示。

所有截止时间由服务端计算并保存。时间判断统一使用`Asia/Shanghai`；前端隐藏不等于完成到期处置，后台任务失败时须重试、告警并保留处置结果。

本节规定统一“顾客风险”的跨店展示与后台留存，不改变§6公开投诉长期保留规则，也不把12个月／3年期限自动套用到顾客主动共享的宠物护理注意事项；护理信息保留仍受`DEC-PETSAFETY-01`约束。

04§3.7已确认预约确认的有限衔接：有本店有权查看的已知提醒须明确阅读，不据提示自动拒单；共享提醒暂不可用统一提示“共享提醒暂不可用，可继续”，员工可直接继续当前合法本店新增／预约业务并保留记录，无门店资料真实性核验或人工核对门槛，不写成已查无风险或共享查询成功。这仅继续当前业务，不开放新的共享查询；授权／同意撤回、每自然月3次、身份冲突阻断及平台核验照常执行，不能合并身份、补假授权或通过重试重置次数。原本店顾客／宠物合法性及预约营业／截止／状态／版本检查不被绕过，对外差异原因最小披露仍按本节；新老顾客的保存后提醒、阅读／不可用继续及重复提醒频率已按04§6.5.1确认；其他未决业务干预继续待决。适用于全部顾客不授权批量查询或放开所有记录，去重也不保留已撤回／到期共享内容。

### 10.2 顾客风险中的宠物相关记录

产品不再设置独立的“宠物行为与服务安全”跨店分类、菜单或弹窗区块。原相关内容合并到统一**顾客风险**，风险对象标记为“宠物相关”并关联具体宠物；优先使用可操作的标准化行为信息，例如：

- 怕生；
- 对陌生人紧张；
- 抗拒吹风；
- 抗拒剪指甲；
- 护食；
- 对犬 / 猫敏感；
- 有挣脱倾向；
- 曾发生咬人 / 抓伤；
- 需要双人操作；
- 喜欢的安抚方式；
- 禁忌操作 / 触碰区域。

信息来源应能够区分：

- owner_reported：主人自报；
- staff_observed：员工观察；
- incident_recorded：关联真实服务事件；
- verified_by_multiple_services：多次独立服务重复观察。

自由文本门店备注不直接跨店传播；跨店共享优先使用标准化标签、来源、事件日期、最近更新时间和经客服审核的必要客观说明。现有`F-PET-043`～`050`只作为宠物相关风险的已有细节字段，不得据此恢复第二套跨店分类或独立授权；统一列表中的“顾客相关／宠物相关”为展示与业务对象区分，具体持久化映射须在数据库／API设计前登记，当前不新造同义风险账本。

顾客端共享提示文案已确认为“共享宠物护理注意事项给未来的门店”，其用途仅限宠物护理注意事项，详见03b§4.5。该提示不能作为§10.1顾客风险信息共享的替代告知或同意依据，两类信息不得在实现中共用一个含义不明的共享授权。

宠物相关顾客风险与顾客相关风险执行同一门店授权、顾客服务履约分项同意、业务触发查询、每月3次、12个月展示、3年受限留存、客服审核、顾客不可见和无条件申诉规则。平台审核通过前，不得把单个门店一次主观判断自动传播为全平台宠物事实。`DEC-PETSAFETY-01`只继续约束顾客主动共享的宠物护理注意事项字段、接收范围、纠错和保留，不再用于恢复独立宠物安全跨店分类。

本店老板和所有有效员工均可从“顾客／宠物详情 → 跨店共享记录”提交统一顾客风险。风险对象必选顾客或宠物；选择宠物时必须关联当前有权访问的具体宠物。事件类型、真实发生时间、关联顾客／宠物和客观经过必填，图片／视频选填；只能记录本店真实发生的服务事件，不得填写“难相处、爱投诉、人品差”等主观评价。

审核记录保留提交依据、审核结果、真实处理人和时间；客服审核不代替顾客服务履约分项同意、双方门店授权、有效期限或申诉规则。客服承担平台审核职责，具体映射现有平台角色／权限及技术接口继续按DEC-RISK-01与阶段05／08收口，不自行新增独立客服系统角色或给普通店员平台审核权限。

## 12. 隐私、内容安全与审计底线

- 公开投诉不得展示无关手机号、微信、家庭地址、会员资产等私密数据。
- 门店举证视频 / 图片涉及其他顾客或无关个人信息时必须进入隐私处理流程。
- 原投诉、商家回应、补证、第三方佐证、平台裁决、申诉和状态变化必须可审计。
- 商家回应不能直接删除原投诉；投诉人也不能通过普通编辑无痕重写已经进入争议流程的历史内容。
- 平台应防止竞争对手恶意投诉、批量账号刷投诉、复制模板化佐证、以删投诉为条件的勒索式行为。
- 排序不能简单按争议内容的刺激程度放大曝光。
- 本模块的内容治理、个人信息共享与自动化决策在进入正式开发 / 上线前需要结合适用法律与实际业务主体进一步完成合规审查。
