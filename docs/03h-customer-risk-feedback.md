## 1. 文档职责

本文件取代原“宠物交友”模块，负责当前客户端以下能力：

- 宠物食品争议 / 风险反馈；
- 附近宠物门店争议 / 风险反馈；
- 顾客对门店或宠物食品提交投诉；
- 门店回应、举证、邀请第三方顾客佐证；
- 平台内容审核、事实裁决、申诉和证据留痕；
- 同一食品同一批次的集中反馈风险提示；
- 平台批量人工审核工作流；
- 门店私有顾客风险备注与跨门店客观风险事件的边界；
- 宠物行为与服务安全档案的跨门店共享方向。

原 `docs/03h-customer-pet-social.md` 已归档至 `docs/history/`，不得继续作为当前产品或实现依据。

本模块不是“谁差评多谁有罪”的排行榜。投诉首先是用户事实主张；商家回应、第三方佐证、平台数据与其他证据共同进入核验，最终事实结论由平台审核员作出。

## 2. 客户端入口与对象

原首页“宠物交友”位置改为消费争议 / 风险反馈入口，至少提供两个一级分类：

1. **附近门店**
2. **宠物食品**

### 2.1 附近门店

用户可查看附近宠物门店的公开投诉 / 差评反馈和处理状态。

公开信息至少区分：

- 用户原始反馈；
- 商家回应状态；
- 平台核验结论；
- 是否已经解决。

不得在平台尚未核验时把用户主张写成平台事实结论。

### 2.2 宠物食品

用户可搜索 / 查看宠物食品风险反馈。

食品投诉的数据对象不能只有自由文本商品名。后续数据模型至少需要能够区分：

- 品牌；
- 商品主体；
- SKU / 规格；
- 批次 / 生产批次信息（用户可提供时）。

同一商品不同批次不得默认合并为同一质量事实。

### 2.3 宠物当前食品品牌与风险订阅

宠物档案可记录当前食用的宠物食品品牌，用于建立“正在食用 → 相关投诉提醒”的明确订阅关系。

- 标准品牌必须使用稳定 `brand_id` 关联，不以展示文本做唯一匹配；
- 品牌列表没有时允许选择“其他”并填写原始品牌名称；
- 自定义品牌可通过平台别名 / 品牌归一规则映射到标准品牌；
- 不能可靠归一时保持待识别状态，不得用模糊相似度强行推送风险；
- 一条新食品投诉通过基础内容审核并公开后，服务端按标准 `brand_id` 查找当前仍在食用该品牌的宠物主人；
- 同一用户即使有多只宠物匹配，同一 `complaint_id` 只提醒一次；
- 站内消息立即创建；微信渠道仅在已授权且可用时追加尝试；
- 通知只表达“出现新的投诉 / 风险反馈”，在平台事实裁决前不得写成已确认质量问题。

宠物品牌编辑细节见 `03b`，通知渠道见 `03f`。

### 2.4 已确认的跨端职责与入口

- 客户端投诉入口为“我的 → 投诉与建议”；首页“消费争议”用于浏览附近门店与宠物食品的公开争议信息。“建议”的分类、处理与关闭流程尚未确认，不得直接套用公开投诉流程。
- 门店正式回应在店员端处理，不放在客户端。争议门店所有在职且账号 / 门店关系有效的员工均可提交本店正式回应，老板同样可回应；不要求另行指定少数回应人员，不因此获得跨店操作或平台裁决权。修订已有回应、第三方邀请等尚未确认的动作仍按04收口。
- 食品投诉由后台发现问题后，客服发送邮件联系厂家；客服是工作职责描述，不据此新增系统角色。厂家回信由管理员在平台Web后台录入，不由店员录入；沿用现有Platform Super Admin角色，不新增角色。录入须关联原食品投诉并保留回信来源、原文 / 附件和录入审计，不得冒充厂家账号直接提交。录入后是否构成正式回应，以及销售门店、品牌、厂家之间的责任与期限映射，仍受 `DEC-FOOD-RESP-01` 阻塞；不能把邮件发送成功当作已正式回应。
- 店员不能维护宠物当前食用品牌，也不能维护食品品牌 / 厂家主资料；不因普通宠物资料或门店商品维护权限而获得这两类维护权。
- 给宠物主人的食品品牌风险提醒必须另行形成店员待办。该待办不是给主人的消息副本；待办归属争议门店，不按主人当前选择门店或所有关联门店分发。食品投诉尚未明确争议门店时，归属映射仍待确认，不得猜测门店。门店内部责任人、可见信息、去重及关闭条件待04确认。
- 投诉提醒与逾期处理增加发给争议门店的短信通知渠道，保留站内消息及已授权且可用的微信通知，详见 03f§13.2。短信不改变本文件的正式回应、补证、逾期与裁决规则。

## 3. 用户投诉提交

用户可以针对：

- 宠物门店；
- 宠物食品；

提交投诉 / 风险反馈。

### 3.1 最低提交要求

允许**仅提交文字**，不强制上传图片、视频、订单或其他证明。

无附件不等于投诉无效，但公开页面必须把它表达为“用户反馈 / 用户陈述”，不能因为已经公开就显示“事实成立”。

用户可在后续流程补充：

- 图片；
- 视频；
- 聊天记录；
- 订单 / 付款材料；
- 其他证据。

### 3.2 同一食品同一批次重复投诉

同一 `Platform User + product + batch` 已存在未终结投诉时，不允许创建第二条未处理投诉。

客户端固定提示：

> 已有投诉未处理

并引导进入原投诉补充文字或证据。

同一用户在同一统计窗口内默认只贡献 1 个独立投诉单位。

投诉已经最终裁决 / 解决后，同一用户何时可以再次针对同一批次创建新投诉，仍由 `DEC-COMPLAINT-08` 确认。

## 4. 投诉状态机与公开规则

投诉不能用一个模糊 `status` 同时表达内容审核、商家回应、事实结论和解决情况。至少分开保存：

- workflow_status：流程所处阶段；
- business_response_status：商家回应状态；
- decision_status：平台事实核验结论；
- resolution_status：是否已解决；
- appeal_status：申诉状态。

### 4.1 提交与基础内容审核

主流程：

`draft`
→ `submitted`
→ `pending_content_review`

基础内容审核至少检查：

- 是否泄露手机号、微信、家庭地址等无关隐私；
- 是否存在明显辱骂、威胁、人肉；
- 是否能够识别投诉对象；
- 是否明显属于广告、垃圾内容；
- 是否需要升级人工审核。

基础审核结果至少支持：

- `rejected_content`
- `needs_revision`
- `pending_business_response`

### 4.2 审核通过后立即公开

已确认：

**投诉通过基础内容审核后立即公开。**

公开时默认表达：

- 用户反馈；
- 商家回应：待回应；
- 平台核验：尚未核验。

不得在平台裁决前显示“投诉成立”“门店已确认有问题”“食品已确认存在质量问题”等结论。

### 4.3 7 天商家回应规则

7 天是**正式回应期限**，不是事实成立期限。

计时应在以下条件完成后开始：

- 基础内容审核通过；
- 投诉对象识别正确；
- 对已入驻可回应主体完成系统通知；
- 系统生成 `response_due_at`。

平台自身审核耗时不得占用商家的 7 天回应期。

正式回应至少包含：

- 回应立场：认可 / 部分认可 / 不认可 / 无法确认；
- 正式回应文字；
- 证据可选。

仅点击“已阅”、空内容、表情、私下电话或者只邀请第三方但门店自身不回应，不算正式回应。

7 天到期仍未正式回应：

- 标记 `business_response_overdue`；
- 记录逾期时间；
- 公开显示“商家逾期未回应”；
- 可进入平台裁决队列；
- **不得自动判定投诉成立。**

商家逾期后仍可补交回应；历史逾期事实继续保留。若平台已经作出最终裁决，后续异议应进入申诉流程，不无痕覆盖原结论。

### 4.4 商家回应后的 3 天补证

已确认：

**商家提交首个正式回应后，投诉双方统一获得 3 天补证期。**

补证期内允许：

- 投诉人补充材料；
- 商家补充材料；
- 商家邀请第三方顾客提供佐证；
- 平台关联自身订单 / 预约 / 退款 / 服务事实；
- 平台按需要要求进一步材料。

补证期结束后进入 `pending_platform_decision`。

平台主动要求补材料形成的额外期限必须单独记录；不能静默修改原 3 天规则。

## 5. 平台裁决

### 5.1 谁可以判定

投诉人只能提出主张。

被投诉门店 / 品牌只能回应和举证。

第三方顾客只能提供佐证。

AI 可以用于内容分类、摘要、重复检测和风险提示，但 V1.0 不单独作出“成立 / 不成立”裁决。

已确认：

**所有案件均允许由 1 名持有平台投诉裁决权限的审核员独立作出结论。**

建议权限键：

`complaint_review.decide`

审核员必须记录：

- 审核人；
- 审核时间；
- 裁决理由；
- 所依据的关键证据；
- 被拆分事实点的逐项结论。

允许审核员主动升级复核，但不设置“严重案件强制双人裁决”硬规则。

### 5.2 平台事实结论

至少支持：

- `established`：成立；
- `partially_established`：部分成立；
- `insufficient_evidence`：证据不足；
- `not_supported`：现有证据不支持。

“证据不足”不等于投诉人撒谎，也不等于商家已经证明无责。

### 5.3 事实点拆分

一个投诉可以拆为多个可判断事实点，不能强制整篇投诉只有“真 / 假”一个结果。

例如：

> 美容师把狗剪伤了、拒绝承认、还多收 100 元。

可拆为：

1. 是否发生剪伤；
2. 是否存在拒绝处理；
3. 是否实际多收 100 元。

各事实点可以分别得到成立、证据不足或不支持，最终形成“部分成立”。

## 6. 是否解决与公开排序

`resolution_status` 与 `decision_status` 独立。

因此允许：

- `established + resolved`
- `partially_established + resolved`
- `insufficient_evidence + resolved`

已确认：

**所有通过基础审核并进入公开流程的投诉长期保留公开记录。**

排序固定：

1. 未解决投诉整体优先；
2. 未解决投诉内部按时间倒序，越新越靠前；
3. 已解决投诉整体排在未解决投诉之后；
4. 已解决投诉内部按时间倒序，越新越靠前。

已解决记录必须明显显示“已解决”，避免被误认为仍处于未处理争议。

投诉人撤回、内容违规下架、平台裁决改变等场景保留审计历史；具体公开呈现可在后续 UI 细化，但不得通过普通修改无痕删除历史。

## 7. 第三方证据与商家辩护

门店可以：

- 正式回应；
- 上传图片 / 视频等材料；
- 邀请多名第三方顾客提供佐证。

第三方不是投票人，人数不能直接决定投诉成立或不成立。

当前证据处理原则：

- 与具体事件直接相关的客观证据优先于“平时这家店很好 / 很差”的一般评价；
- 独立、亲历、身份已验证的第三方证词优先于与事件无关的评价；
- 由被投诉门店主动邀请的第三方必须标明“由被投诉门店邀请提供佐证”；
- 高度模板化、相互复制的第三方内容应降低可信度；
- 多名第三方不能机械相加为票数；
- 平台自身不可变订单、付款、退款、预约、服务记录可作为客观事实来源。

证据等级 A～E、不同证据的精确权重和是否形成内部评分尚未冻结，由 `DEC-EVIDENCE-01` 继续确认。开发不得自行用简单票数或固定分数替代人工事实判断。

## 8. 食品同批次“出现集中反馈”

### 8.1 硬触发门槛

已确认：

同一食品 + 同一批次，在**最近 2 天滚动窗口**内，必须实际达到至少 **3 条独立投诉**，才显示：

> 出现集中反馈

3 条是硬门槛。

不得：

- 将 2 条跨门店投诉通过加权折算成 3 条；
- 将 1 条严重投诉折算成多条；
- 使用风险分绕过独立投诉数量门槛。

### 8.2 不同门店来源加权

达到 3 条硬门槛后，再计算来源分散度。

来自不同门店 / 销售来源的独立投诉应提高：

- 风险优先级；
- 风险列表排序；
- 平台审核队列优先级；
- 后续内部风险等级（如启用）。

具体权重系数尚未冻结；但加权与门槛判断必须是两个独立步骤。

### 8.3 not_supported 仍计入集中反馈

已确认：

即使单条投诉最终被判定为 `not_supported`，仍不从“近期反馈数量”中剔除。

因此“出现集中反馈”只表达：

> 近期出现多起独立投诉 / 反馈。

它不表达：

> 近期出现多起已成立投诉。

数据层应分别统计总反馈、成立、部分成立、证据不足、不支持等数量，避免公开文案混淆。

### 8.4 风险提示有效期

已确认：

“出现集中反馈”风险提示自生成后保留 **2 个月**，到期自动解除公开提示。

历史投诉、聚合记录和审计记录继续保留。

提示有效期内若再次出现新的 2 天 / 3 条集中反馈，是否重新计算 2 个月，受 `DEC-COMPLAINT-07` 阻塞，当前不得自行实现滚动续期。

### 8.5 对外措辞

自动提示只允许表达：

> 出现集中反馈

不得自动写成：

- 该批次存在质量问题；
- 该食品有毒；
- 已确认产品缺陷；
- 已确认厂家责任。

### 8.6 问题热度

宠物食品投诉列表与详情必须展示 **问题热度**。

问题热度是“该问题当前被关注 / 反馈的活跃程度”展示指标，不等于投诉成立概率、产品危险等级、事实严重程度或平台裁决结果。

前端不得自行根据投诉条数拼出热度值，必须使用服务端返回的热度展示结果。服务端计算可以考虑近期独立投诉数、时间衰减、来源分散度、未解决反馈等信号，但具体数值范围、计算公式、信号权重、更新频率以及最终显示纯数字 / 等级 / 组合，仍由 `DEC-FOOD-HEAT-01` 冻结。

在该决策关闭前，H5 / 视觉原型可以使用明确标注的 Mock 数值演示视觉，例如“问题热度 86”，但不得把该数值或公式写成生产业务规则。

## 9. 平台批量审核工作流

需要平台审核后才能公开 / 跨门店共享的记录，可以先采用批量审核方式：

> 待审核队列 → 下载 XLSX / CSV → 审核员在审核列批注 → 上传 → 系统预检查 → 审核员确认 → 批量落库

### 9.1 导出原则

每条必须存在稳定 `review_item_id`，不能以 Excel 行号定位。

导出至少包含：

- review_item_id
- review_batch_id
- row_version
- submitted_at
- submitter_merchant_id
- submitter_store_id
- target_type
- target_id
- content_type
- submitted_value
- source_type
- source_business_id（如有）
- evidence_count
- current_review_status
- last_updated_at

原始业务字段视为只读。

### 9.2 审核员填写列

至少可包含：

- reviewer_decision
- approved_value
- reviewer_reason_code
- reviewer_comment
- visibility_scope
- effective_until
- severity_level
- require_followup
- followup_note

### 9.3 上传安全

- 以 `review_item_id` 定位；
- 校验 `row_version`；
- 导出后原记录已变化则该行冲突，不覆盖；
- 已由其他审核员处理的行不得再次覆盖；
- 同一文件重复上传必须幂等；
- 上传先预检差异，再确认执行；
- 支持部分成功 / 部分失败并逐行返回结果；
- 原始提交内容、审核前后结果和上传批次永久可追溯。

多审核员默认采用乐观并发，不因某人下载文件就锁死全部待审核记录。

## 10. 双向风险信息

### 10.1 顾客风险：主观备注与跨店共享分层

已确认产品原则：

> **共享客观风险事件，不共享主观人格评价。**

单个 Merchant 可保留本店内部自由备注，例如沟通习惯、服务过程备注；这类主观备注默认不得跨商户共享。

跨门店层只能考虑标准化、可核验、可申诉的客观风险事件，例如：

- 多次预约未到且未取消；
- 服务完成后拒绝支付已确认费用；
- 有明确记录的辱骂 / 威胁事件；
- 已核验的恶意退款 / 毁损事件。

不得跨店传播：

- 脾气差；
- 事多；
- 难搞；
- 爱投诉；
- 不讲理；

等主观人格标签。

跨门店顾客风险事件的具体接收主体、告知 / 同意方式、保存期限、顾客查看与申诉、是否影响预约等受 `DEC-RISK-01` 阻塞。

### 10.2 宠物行为与服务安全档案

产品方向是把“宠物性格”转换为**宠物行为与服务安全档案**，优先使用可操作的标准化行为信息，例如：

- 怕生；
- 对陌生人紧张；
- 抗拒吹风；
- 抗拒剪指甲；
- 护食；
- 对犬 / 猫敏感；
- 有挣脱倾向；
- 曾发生咬人 / 抓伤；
- 需要双人操作；
- 喜欢的安抚方式；
- 禁忌操作 / 触碰区域。

信息来源应能够区分：

- owner_reported：主人自报；
- staff_observed：员工观察；
- incident_recorded：关联真实服务事件；
- verified_by_multiple_services：多次独立服务重复观察。

自由文本门店备注不直接跨店传播；跨店共享优先使用标准化标签、来源、最近更新时间和必要安全摘要。

谁可以查看、主人如何授权 / 关闭、严重安全事件保留多久、是否只向实际预约 / 服务门店开放，受 `DEC-PETSAFETY-01` 阻塞。

平台审核通过前，不得把单个门店一次主观判断自动传播为全平台宠物事实。

## 12. 隐私、内容安全与审计底线

- 公开投诉不得展示无关手机号、微信、家庭地址、会员资产等私密数据。
- 门店举证视频 / 图片涉及其他顾客或无关个人信息时必须进入隐私处理流程。
- 原投诉、商家回应、补证、第三方佐证、平台裁决、申诉和状态变化必须可审计。
- 商家回应不能直接删除原投诉；投诉人也不能通过普通编辑无痕重写已经进入争议流程的历史内容。
- 平台应防止竞争对手恶意投诉、批量账号刷投诉、复制模板化佐证、以删投诉为条件的勒索式行为。
- 排序不能简单按争议内容的刺激程度放大曝光。
- 本模块的内容治理、个人信息共享与自动化决策在进入正式开发 / 上线前需要结合适用法律与实际业务主体进一步完成合规审查。
