## 1. 文档职责

本文件取代原“宠物交友”模块，负责当前客户端以下能力：

- 宠物食品争议 / 风险反馈；
- 附近宠物门店争议 / 风险反馈；
- 顾客对门店或宠物食品提交投诉；
- 门店回应、举证、邀请第三方顾客佐证；
- 平台内容审核、事实裁决、异议联系客服和证据留痕；消费争议、食品问题及跨店顾客风险均不提供自助申诉。
- 同一食品同一批次的集中反馈风险提示；
- 平台批量人工审核工作流；
- 门店私有顾客风险备注与跨店“顾客风险”的边界；“顾客风险”统一承载顾客相关事件和宠物相关服务安全事件，不再设置第二个“宠物行为与服务安全”跨店分类。

原 `docs/03h-customer-pet-social.md` 已归档至 `docs/history/`，不得继续作为当前产品或实现依据。

本模块不是“谁差评多谁有罪”的排行榜。投诉首先是用户事实主张；商家回应、第三方佐证、平台数据与其他证据共同进入核验，最终事实结论由持有对应平台权限的 Platform Super Admin 作出。

## 2. 客户端入口与对象

原首页“宠物交友”位置改为消费争议 / 风险反馈入口，至少提供两个一级分类：

1. **附近门店**
2. **宠物食品**

### 2.1 附近门店

用户可查看附近宠物门店的公开投诉 / 差评反馈和处理状态。

公开信息至少区分：

- 用户原始反馈；
- 商家回应状态；
- 平台核验结论；
- 是否已经解决。

不得在平台尚未核验时把用户主张写成平台事实结论。

### 2.2 宠物食品

用户可搜索 / 查看宠物食品风险反馈。

食品投诉的数据对象不能只有自由文本商品名。后续数据模型至少需要能够区分：

- 品牌；
- 商品主体；
- SKU / 规格；
- 批次 / 生产批次信息（用户可提供时）。

同一商品不同批次不得默认合并为同一质量事实。

### 2.3 宠物当前食品品牌与风险订阅

宠物档案可记录当前食用的宠物食品品牌，用于建立“正在食用 → 相关投诉提醒”的明确订阅关系。

- 标准品牌必须使用稳定 `brand_id` 关联，不以展示文本做唯一匹配；
- 品牌列表没有时允许选择“其他”并填写原始品牌名称；
- 自定义品牌可通过平台别名 / 品牌归一规则映射到标准品牌；
- 不能可靠归一时保持待识别状态，不得用模糊相似度强行推送风险；
- 一条新食品投诉通过基础内容审核并公开后，服务端按标准 `brand_id` 查找当前仍在食用该品牌的宠物主人；
- 同一用户即使有多只宠物匹配，同一 `complaint_id` 只提醒一次；
- 站内消息立即创建；微信渠道仅在已授权且可用时追加尝试；
- 通知只表达“出现新的投诉 / 风险反馈”，在平台事实裁决前不得写成已确认质量问题。

宠物品牌编辑细节见 `03b`，通知渠道见 `03f`。

### 2.4 跨端职责、建议与食品问题

- 客户端入口仍为“我的 → 投诉与建议”。投诉进入消费争议流程；“建议”只提交给平台查看，门店不接收、不回应，也不在公开争议中展示。平台是否回复不作为V1门店待办。
- 门店正式回应仅用于门店消费争议，争议门店全部有效员工和老板均可回应，无审批。未入驻门店被投诉时公开标记“未入驻”，平台保存并处理投诉；该门店以后完成入驻和主体认领后，可以对仍可回应的原投诉补充正式回应，历史未入驻状态和原期限保留。
- 食品问题由平台直接联系厂家，不要求门店先核实、确认或正式回应。涉事门店只收到一条食品风险知悉通知，可查看公开风险摘要并点击“已知悉”；知悉不代表认责、核实完成或案件解决。
- 厂家真实回复由平台人员在Web后台录入，经过内容／身份审核通过即记为厂家回应；不设置厂家回应期限。录入前显示“平台核查中”，任何回应都不能自动结案，最终裁决仍由平台决定。
- 店员不能维护厂家回信、食品品牌主资料或宠物当前食用品牌；当前食用品牌只读，未填写时提示主人更新。
- 当前阶段不发送短信；站内普通／重要通知及已授权微信通知按现行规则执行。
## 3. 用户投诉提交

用户可以针对：

- 宠物门店；
- 宠物食品；

提交投诉 / 风险反馈。

### 3.1 最低提交要求

允许**仅提交文字**，不强制上传图片、视频、订单或其他证明。

无附件不等于投诉无效，但公开页面必须把它表达为“用户反馈 / 用户陈述”，不能因为已经公开就显示“事实成立”。

用户可在后续流程补充：

- 图片；
- 视频；
- 聊天记录；
- 订单 / 付款材料；
- 其他证据。

### 3.2 同一食品同一批次重复投诉

同一Platform User对同一食品同一批次已有未终结投诉时，不创建第二条，提示进入原投诉补充材料。原投诉已经最终裁决／解决后，允许再次投诉，但必须提交与上一案不同的新证据；只有重复文字、重复附件或没有新材料时，提示在原历史中查看，不创建新案。新案独立编号、重新审核，不覆盖旧案，也不把同一统计窗口内同一用户重复计算为多个独立投诉单位。

## 4. 投诉状态机与公开规则

投诉不能用一个模糊 `status` 同时表达内容审核、商家回应、事实结论和解决情况。至少分开保存：

- workflow_status：流程所处阶段；
- business_response_status：商家回应状态；
- decision_status：平台事实核验结论；
- resolution_status：是否已解决；
- 消费争议不设小程序申诉状态／提交入口，原complaint_appeal_status退役仅保留历史；异议提示联系客服。

### 4.1 提交与基础内容审核

主流程：

`draft`
→ `submitted`
→ `pending_content_review`

基础内容审核至少检查：

- 是否泄露手机号、微信、家庭地址等无关隐私；
- 是否存在明显辱骂、威胁、人肉；
- 是否能够识别投诉对象；
- 是否明显属于广告、垃圾内容；
- 是否需要升级人工审核。

基础审核结果至少支持：

- `rejected_content`
- `needs_revision`
- `pending_business_response`

### 4.2 审核通过后立即公开

已确认：

**投诉通过基础内容审核后立即公开。**

公开时默认表达：

- 用户反馈；
- 商家回应：待回应；
- 平台核验：尚未核验。

不得在平台裁决前显示“投诉成立”“门店已确认有问题”“食品已确认存在质量问题”等结论。

### 4.3 7 天商家回应规则

7 天是**正式回应期限**，不是事实成立期限。

计时应在以下条件完成后开始：

- 基础内容审核通过；
- 投诉对象识别正确；
- 对已入驻可回应主体完成系统通知；
- 系统生成 `response_due_at`。

平台自身审核耗时不得占用商家的 7 天回应期。

正式回应至少包含：

- 回应立场：认可 / 部分认可 / 不认可 / 无法确认；
- 正式回应文字；
- 证据可选。

门店选择立场并填写文字后直接提交，不设回应草稿；图片／视频等证据选填。服务端成功受理的原回应（立场、正文、附件及首次回应时间）保留，不提供覆盖编辑／删除；后续说明或材料在本节有效补证期内逐条追加，权限与提交一致性见04§6.1.2。

仅点击“已阅”、空内容、表情、私下电话或者只邀请第三方但门店自身不回应，不算正式回应。

7 天到期仍未正式回应：

- 标记 `business_response_overdue`；
- 记录逾期时间；
- 公开显示“商家逾期未回应”；
- 可进入平台裁决队列；
- **不得自动判定投诉成立。**

商家逾期后仍可补交回应；历史逾期事实继续保留。若平台已经作出最终裁决，后续异议提示“如有异议，请联系客服处理”，不提供小程序申诉／复议提交、申诉状态或申诉消息，也不无痕覆盖原结论。

店员端应将“请在7天内正式回应”作为重点信息，在工作台争议待办卡片、业务消费争议列表及详情顶部展示，并紧邻显示同一response_due_at具体截止与按服务端时间计算的真实剩余时间；不是每次打开重新给7天。逾期突出“已逾期，仍需正式回应”，不推导投诉成立；已正式回应后展示实际补证阶段，不继续假报待回应。期限重点展示按04§6.1.1，工作台归组／去重／移出按04§3.2.1，列表四组／筛选／历史按04§6.1.8。食品投诉仅明确涉及门店销售／处理行为的门店部分使用本期限，品牌／厂家后台部分不生成门店逾期。

### 4.4 商家回应后的 3 天补证

已确认：

**商家提交首个正式回应后，投诉双方统一获得 3 天补证期。**

首次正式回应由服务端成功受理后，同次记录首次回应时间、已回应状态及补证阶段／截止；原待回应事项自动转为补证信息。店员端相关卡片、业务列表及详情顶部突出evidence_window_ends_at具体截止与真实剩余时间，历史逾期保留，不再显示尚未正式回应。工作台同一卡片按04§3.2.1改为补证中并回到待处理；补证结束且无需门店办理时移出，仅有平台明确补材料要求等真实需办事项时再按原争议显示，不因仅等待平台长期占卡。重复请求或多人并发不得覆盖原回应或再开一轮；后来的首次提交提示已有回应，不能静默当作补充。

本店老板／所有账号及任职关系有效的员工均可在有效窗口内追加说明或材料，无老板审批、不限原经办人；逐条关联原投诉并保留提交人和时间，复用F-EVD及审计。补充不覆盖原立场／正文／附件，不重置首次回应时间或原3天截止；媒体选填不等于跳过原有内容审核／隐私边界。

补证期内允许：

- 投诉人补充材料；
- 商家补充材料；
- 商家邀请第三方顾客提供佐证；
- 平台关联自身订单 / 预约 / 退款 / 服务事实；
- 平台按需要要求进一步材料。

补证期结束后进入 `pending_platform_decision`。

平台主动要求补材料形成的额外期限必须单独记录；不能静默修改原 3 天规则。

§6.2的“提交处理情况”是实际处理进展：平台尚未确认解决时可在原补证期后追加，但不重开原补证窗口、不把裁决异议当普通补证重新受理。门店正式回应、原争议证据及第三方佐证仍分别执行原门槛与截止，不因处理进展入口放宽。

## 5. 平台裁决

### 5.1 谁可以判定

投诉人只能提出主张。

被投诉门店 / 品牌只能回应和举证。

第三方顾客只能提供佐证。

AI 可以用于内容分类、摘要、重复检测和风险提示，但 V1.0 不单独作出“成立 / 不成立”裁决。

已确认：

**所有案件均允许由 1 名持有 `complaint_review.decide` 权限的 Platform Super Admin 独立作出事实结论。**

权限键：

`complaint_review.decide`

本文件中的“审核员”仅是审核操作的职能称呼，不是独立系统角色；实际执行者为持有对应权限的 Platform Super Admin。平台角色与权限归属以02§2为准，不新增客服、审核员或仲裁员系统角色。

审核员必须记录：

- 审核人；
- 审核时间；
- 裁决理由；
- 所依据的关键证据；
- 被拆分事实点的逐项结论。

允许持有相应平台审核权限的 Platform Super Admin 主动升级复核，但不设置“严重案件强制双人裁决”硬规则。

### 5.2 平台事实结论

至少支持：

- `established`：成立；
- `partially_established`：部分成立；
- `insufficient_evidence`：证据不足；
- `not_supported`：现有证据不支持。

“证据不足”不等于投诉人撒谎，也不等于商家已经证明无责。

### 5.3 事实点拆分

一个投诉可以拆为多个可判断事实点，不能强制整篇投诉只有“真 / 假”一个结果。

例如：

> 美容师把狗剪伤了、拒绝承认、还多收 100 元。

可拆为：

1. 是否发生剪伤；
2. 是否存在拒绝处理；
3. 是否实际多收 100 元。

各事实点可以分别得到成立、证据不足或不支持，最终形成“部分成立”。

消费争议／门店及食品投诉的客户端、店员端均不提供申诉按钮、提交接口、申诉状态或申诉消息；有异议只展示“如有异议，请联系客服处理”。不把联系动作当已提交申诉、自动重审／改判／结案，也不恢复已结束的3天补证；客服的实际处理仍由平台按现有职责留痕，具体联系方式／配置和后台处置契约后续明确，不新建在线聊天或申诉中心。

原投诉、证据、裁决及已存在的历史申诉记录按各自适用的保存期限保留，只读追溯不意味着永久保存原件或继续开放新申诉。公开副本、原始媒体及投诉关联身份信息分别按§12.1处理；统一顾客风险的证据与审核数据仍按§10.1的独立期限规则处理。统一顾客风险同样不提供小程序申诉入口；所有新异议只提示联系客服处理。

## 6. 是否解决与公开排序

`complaint_resolution_status`（F-CMP-021，是否已解决）与 `complaint_decision_status`（F-CMP-020，事实结论）独立。文中的resolution_status／decision_status仅为业务简称，对外字段仍按FIELD-REGISTRY。

因此允许：

- `established + resolved`
- `partially_established + resolved`
- `insufficient_evidence + resolved`

已确认：

**所有通过基础审核并进入公开流程的投诉，其公开脱敏内容自首次公开之日起保留 1 年；到期处置按§12.1执行。**

排序固定：

1. 未解决投诉整体优先；
2. 未解决投诉内部按时间倒序，越新越靠前；
3. 已解决投诉整体排在未解决投诉之后；
4. 已解决投诉内部按时间倒序，越新越靠前。

已解决记录必须明显显示“已解决”，避免被误认为仍处于未处理争议。平台确认已解决后按04§3.2.1移出工作台；业务记录及历史按各数据类型的适用期限保留，公开副本、原始媒体及投诉关联身份信息分别按§12.1到期下架、删除或匿名化，审计元数据按独立审计规则处理。仅等待平台而移出工作台不等于已解决，也不改写回应／逾期／裁决事实。

投诉人撤回、内容违规下架、平台裁决改变等场景保留审计历史；具体公开呈现可在后续 UI 细化，但不得通过普通修改无痕删除历史。

当前证据处理原则：

- 与具体事件直接相关的客观证据优先于“平时这家店很好 / 很差”的一般评价；
- 独立、亲历、身份已验证的第三方证词优先于与事件无关的评价；
- 由被投诉门店主动邀请的第三方必须标明“由被投诉门店邀请提供佐证”；
- 高度模板化、相互复制的第三方内容应降低可信度；
- 多名第三方不能机械相加为票数；
- 平台自身不可变订单、付款、退款、预约、服务记录可作为客观事实来源。

## 8. 食品同批次“出现集中反馈”

### 8.1 硬触发门槛

已确认：

同一食品 + 同一批次，在**最近 2 天滚动窗口**内，必须实际达到至少 **3 条独立投诉**，才显示：

> 出现集中反馈

3 条是硬门槛。

不得：

- 将 2 条跨门店投诉通过加权折算成 3 条；
- 将 1 条严重投诉折算成多条；
- 使用风险分绕过独立投诉数量门槛。

### 8.2 不同门店来源加权

达到 3 条硬门槛后，再计算来源分散度。

来自不同门店 / 销售来源的独立投诉应提高：

- 风险优先级；
- 风险列表排序；
- 平台审核队列优先级；
- 后续内部风险等级（如启用）。

具体权重系数尚未冻结；但加权与门槛判断必须是两个独立步骤。

### 8.3 not_supported 仍计入集中反馈

已确认：

即使单条投诉最终被判定为 `not_supported`，仍不从“近期反馈数量”中剔除。

因此“出现集中反馈”只表达：

> 近期出现多起独立投诉 / 反馈。

它不表达：

> 近期出现多起已成立投诉。

数据层应分别统计总反馈、成立、部分成立、证据不足、不支持等数量，避免公开文案混淆。

### 8.4 风险提示有效期

集中反馈提示从本次触发时间起保留2个月。有效期内再次满足“最近2天至少3条独立投诉”的触发条件时，立即从最新一次触发时间重新计算2个月；系统保留每次触发时间和前后截止，不删除旧投诉或把续期解释为责任成立。


### 8.5 对外措辞

自动提示只允许表达：

> 出现集中反馈

不得自动写成：

- 该批次存在质量问题；
- 该食品有毒；
- 已确认产品缺陷；
- 已确认厂家责任。

### 8.6 问题热度

食品问题热度只对外显示“低／中／高”三档，由服务端根据当前有效投诉、时间和处理状态计算并返回；前端不得自行按条数拼档。具体内部信号可由平台调整，但同一版本须稳定、可审计，热度不是事实成立概率、危险等级或裁决结果。列表和详情显示当前档位及更新时间。

## 9. 平台批量审核工作流

需要平台审核后才能公开 / 跨门店共享的记录，可以先采用批量审核方式：

> 待审核队列 → 下载 XLSX / CSV → 审核员在审核列批注 → 上传 → 系统预检查 → 审核员确认 → 批量落库

### 9.1 导出原则

每条必须存在稳定 `review_item_id`，不能以 Excel 行号定位。

导出至少包含：

- review_item_id
- review_batch_id
- row_version
- submitted_at
- submitter_merchant_id
- submitter_store_id
- target_type
- target_id
- content_type
- submitted_value
- source_type
- source_business_id（如有）
- evidence_count
- current_review_status
- last_updated_at

原始业务字段视为只读。

### 9.2 审核员填写列

至少可包含：

- reviewer_decision
- approved_value
- reviewer_reason_code
- reviewer_comment
- visibility_scope
- effective_until
- severity_level
- require_followup
- followup_note

### 9.3 上传安全

- 以 `review_item_id` 定位；
- 校验 `row_version`；
- 导出后原记录已变化则该行冲突，不覆盖；
- 已由其他审核员处理的行不得再次覆盖；
- 同一文件重复上传必须幂等；
- 上传先预检差异，再确认执行；
- 支持部分成功 / 部分失败并逐行返回结果；
- 原始提交内容、审核前后结果和上传批次按各数据类型的适用保存期限可追溯；原始媒体及身份信息不得因批量审核而永久保存，分别按§12.1处理，最小审计元数据按独立审计规则保留。

多审核员默认采用乐观并发，不因某人下载文件就锁死全部待审核记录。

## 10. 双向风险信息

### 10.1 顾客风险的跨店共享

统一名称为“顾客风险”，内部区分顾客相关与宠物相关。来源门店和查看门店必须已参与共享，顾客已同意服务履约记录分项，且只能在新增顾客、确认预约等真实业务动作中查询；禁止独立输入号码批量查人。

跨店风险只按已认证手机号唯一匹配Platform User，不使用微信号、微信昵称、OpenID或其他标识作为替代匹配。无法唯一匹配、号码冲突或每自然月同店同顾客超过3次时，不展示内容并记录审计；相同请求重试不重复计次。

来源门店或查看门店可以撤回本店的共享参与授权，成功后立即停止对应的新查询和展示；再次参与必须由该店重新明确授权。顾客端不提供自助撤回按钮，顾客需要变更已同意的共享授权时必须联系客服，由平台核验身份并处理；处理成功前不得假报已撤回。顾客端不显示风险记录存在、摘要、状态或内容，也不提供申诉入口；有异议统一提示“请联系客服处理”。联系客服不等于自动改判或重新开放门店查看。

审核通过的客观风险跨店展示12个月，到期或授权提前失效即停止门店展示；原始证据、审核和查询日志按原受限期限留存。系统自动记录每次查询、授权变更和风险修改的实际主体、服务端时间及前后值。
### 10.2 顾客风险中的宠物相关记录

产品不再设置独立的“宠物行为与服务安全”跨店分类、菜单或弹窗区块。原相关内容合并到统一**顾客风险**，风险对象标记为“宠物相关”并关联具体宠物；优先使用可操作的标准化行为信息，例如：

- 怕生；
- 对陌生人紧张；
- 抗拒吹风；
- 抗拒剪指甲；
- 护食；
- 对犬 / 猫敏感；
- 有挣脱倾向；
- 曾发生咬人 / 抓伤；
- 需要双人操作；
- 喜欢的安抚方式；
- 禁忌操作 / 触碰区域。

信息来源应能够区分：

- owner_reported：主人自报；
- staff_observed：员工观察；
- incident_recorded：关联真实服务事件；
- verified_by_multiple_services：多次独立服务重复观察。

自由文本门店备注不直接跨店传播；跨店共享优先使用标准化标签、来源、事件日期、最近更新时间和经持有 `customer_risk.review` 权限的 Platform Super Admin 审核的必要客观说明。现有`F-PET-043`～`050`只作为宠物相关风险的已有细节字段，不得据此恢复第二套跨店分类或独立授权；统一列表中的“顾客相关／宠物相关”为展示与业务对象区分，具体持久化映射须在数据库／API设计前登记，当前不新造同义风险账本。

顾客端共享提示文案已确认为“共享宠物护理注意事项给未来的门店”，其用途仅限宠物护理注意事项，详见03b§4.5。该提示不能作为§10.1顾客风险信息共享的替代告知或同意依据，两类信息不得在实现中共用一个含义不明的共享授权。

宠物相关顾客风险与顾客相关风险执行同一门店授权、顾客服务履约分项同意、业务触发查询、每月3次、12个月展示、3年受限留存、平台审核、顾客不可见和联系客服异议规则。平台审核通过前，不得把单个门店一次主观判断自动传播为全平台宠物事实。宠物护理注意事项仍按03b的独立护理分项授权和字段规则处理，不得据此恢复第二套宠物安全跨店分类。

## 12. 隐私、内容安全与审计底线

- 公开投诉不得展示无关手机号、微信、家庭地址、会员资产等私密数据。
- 门店举证视频 / 图片涉及其他顾客或无关个人信息时必须进入隐私处理流程。
- 原投诉、商家回应、补证、第三方佐证、平台裁决和状态变化必须可审计；旧申诉记录只读保留，不再产生新申诉。
- 商家回应不能直接删除原投诉；投诉人也不能通过普通编辑无痕重写已经进入争议流程的历史内容。
- 平台应防止竞争对手恶意投诉、批量账号刷投诉、复制模板化佐证、以删投诉为条件的勒索式行为。
- 排序不能简单按争议内容的刺激程度放大曝光。
- 本模块的内容治理、个人信息共享与自动化决策在进入正式开发 / 上线前需要结合适用法律与实际业务主体进一步完成合规审查。

### 12.1 投诉公开内容、原始材料与关联身份信息保存期限

本节适用于门店／宠物食品投诉及其公开副本、原始媒体和投诉处理所必需的身份关联信息。跨店顾客风险记录不适用本节，继续按§10.1执行其12个月展示期及3年受限留存规则。

| 数据类型 | 保存期限 | 起算时间 | 到期处置 |
|---|---:|---|---|
| 公开脱敏投诉内容 | 1年 | 投诉首次公开时间（F-CMP-011） | 到期停止公开展示，并删除或不可逆匿名化公开副本 |
| 原始投诉视频 | 3个月 | 每个原始视频资源成功上传／接收时间 | 删除原始视频及其可访问副本；已制作并发布的脱敏公开副本仍按公开内容的一年期限独立处理 |
| 原始投诉图片 | 1年 | 每个原始图片资源成功上传／接收时间 | 删除原始图片及其可访问副本；已制作并发布的脱敏公开副本仍按公开内容的一年期限独立处理 |
| 投诉关联身份信息 | 1年 | 每项必要身份信息首次收集时间 | 删除或不可逆匿名化该项身份信息及不再必要的关联映射 |

公开脱敏投诉内容包括公开投诉正文、门店回应、已审核发布的第三方佐证文字、脱敏媒体副本以及对外展示的处理状态／裁决摘要。原始媒体与脱敏公开副本必须作为不同资源管理；不得将原始图片／视频直接作为公开副本返回。

投诉关联身份信息仅限受理、核验和争议追溯所必需的最小身份关联数据，不得把用户完整账号资料、无关联系方式或认证凭证整体复制进投诉档案。身份信息保存期届满后，不得仅因公开投诉仍在一年展示期内而继续保留身份映射。

用户账号注销不会触发本节所列投诉资料提前删除；在各自保存期限内，仅为处理投诉、争议追溯及履行适用法律义务而受限保留，不得转用于营销、画像或无关跨店查询。注销不延长、不重置任何保存期限；期限届满仍须按表删除或不可逆匿名化。

确有具体法律义务、监管要求或正在进行的争议程序需要保全的，只能对必要数据作例外保全，并记录保全依据、数据范围、责任人、开始时间及复核／解除条件；保全结束后立即恢复到期处置，不得以笼统的“可能需要”无限期延长。

最小审计元数据（操作者、时间、动作、对象标识及处理结果）与原始媒体／身份内容分开管理，按独立审计规则保存；不得把原始媒体、完整身份信息或未脱敏正文复制进审计日志以规避本节期限。媒体级、身份关联级到期字段及自动清理任务在阶段09／11按实际数据对象登记，不得把F-CMP-011或F-EVD-010直接复用为其他含义的保留截止字段。上线前仍须完成适用法律、隐私告知、备份清理和数据处理责任的合规复核。
